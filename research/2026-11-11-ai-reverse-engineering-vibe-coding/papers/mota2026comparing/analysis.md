# Comparing the Quality of Code Generated by Vibe Coding Tools

- Authors: Mota, Gustavo da; Gama, Kiev
- Year / venue: 2026, arXiv (preprint)
- DOI: 10.48550/arxiv.2608.16302 · URL: https://arxiv.org/abs/2608.16302
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.

Note on the source: arXiv v1 (arXiv:2608.16302, 17 Aug 2026), 7 pages. **Not peer-reviewed as far as we can tell**: the page header names the 40th Brazilian Symposium on Software Engineering (SBES 2026), Innovative Ideas and Emerging Results track (p. 2), but the artifact link is "anonymized for review" (p. 6), so this appears to be a submitted version; acceptance is not stated. ## 1. Research objective
- [A] To obtain "initial evidence about the structural quality of code generated by vibe coding tools from the same requirements specification", explicitly "rather than declaring one tool superior" (p. 2).
- [A] Motivation: evaluating "entire AI-generated applications" rather than isolated functions or algorithmic solutions (p. 1).

## 2. Research questions / hypotheses
- [V] RQ1: "How do vibe coding tools differ in the number and severity of code smells detected in web applications generated from the same set of requirements?" (p. 2)
- No hypotheses (exploratory) (p. 2).

## 3. Methodology
- Research design: [V] Exploratory comparative design; unit of analysis is one project generated by a platform from an identical prompt (p. 2).
- Approach / model / intervention: [V] One zero-shot prompt (no example code) derived from the "Nature Park Wildlife App" exercise (wildlife sighting registration, safety reports, notification subscriptions, geolocated map) (p. 2). Each tool received the same prompt "with no additional instructions or manual corrections"; repeated three times per tool (p. 2). Each project analysed independently with SonarQube (p. 2).
- Baselines or comparison conditions: [V] The three tools are compared with each other (Lovable, v0, Replit) (p. 2). No human-written reference implementation; no non-AI baseline.

## 4. Dataset and sample
- Data source(s): [V] Nine generated web applications: Lovable (tanstack_start_ts template, gpt-engineer-app agent), v0 (Next.js 16.2.4), Replit (Replit Agent, Node.js 24); generated 6-21 May 2026 on free tiers (p. 2).
- Sample size (N) and unit: [V] 9 projects, 3 per tool (p. 2). NCLOC totals: Lovable 17,081; v0 27,583; Replit 48,411 (p. 5). Issues: 390, 254, 463 (total 1,107) (p. 5).
- Sampling / selection method: [V] Tools chosen as widely used, fully web-based app generators with free tiers sufficient for the experiments (p. 2). Three runs per tool limited by free-tier token credits and time (p. 6). No power or sample-size rationale beyond this.
- Data availability (public? link?): [V] Full prompt, source code of all nine projects and full SonarQube reports at an anonymised 4open.science link (p. 6). We did not open it.

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] SonarQube (version and quality profile/rule set: not reported) on each project (p. 2). Tool versions not public; generation window and build identifiers reported instead (p. 2). Tags (39 distinct) grouped by the authors into five clusters: Semantic, Technical Quality, Security, Technological Context, Language/Ecosystem (Table 1, p. 3). How the grouping was decided: not reported. Whether template, scaffolding or vendored UI-component code was excluded from analysis: not reported.
- Code availability: [V] Generated code and SonarQube reports in the artefact package (p. 6). No analysis scripts mentioned.

## 6. Evaluation metrics
- Metric — what it measures — why chosen: [V] SonarQube issues by type (code smell, bug, vulnerability; hotspots in Table 6), severity (MINOR/MAJOR/CRITICAL), rules and tags, remediation effort in minutes (as a technical-debt estimate), duplicated-line density, cyclomatic and cognitive complexity, NCLOC (p. 2, p. 3, p. 5). Raw and per-KLOC values reported because code volume differs while required functionality is the same (p. 2). SonarQube chosen as widely adopted in industry and research (p. 2).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): not reported (descriptive only). Standard deviation reported only for code smells per project (Lovable 62.1, v0 7.0, Replit 20.3) (p. 6). Cyclomatic complexity is listed as collected (p. 1, p. 2) but its values are not reported.

## 7. Key findings
1. [V] Per KLOC, Lovable had 22.83 issues vs 9.21 (v0) and 9.56 (Replit); remediation effort 220.77 min/KLOC vs 34.12 and 34.87 (Table 6, p. 5).
2. [V] Raw totals: Lovable 390 issues / 3,771 min effort; v0 254 / 941; Replit 463 / 1,688 (Table 6, p. 5). Lovable effort is about 4.0x v0's (p. 6).
3. [V] Lovable's issues are almost all code smells (389 of 390) and mostly MINOR (85.6%) (p. 3, p. 5); rule S1874 (deprecated APIs) accounts for 204 occurrences (p. 3, p. 5) and, per the authors, more than half of Lovable's effort (p. 6).
4. [V] Replit produced the most code (48,411 NCLOC), about 60% duplicated lines vs <=7% (v0) and 0% (Lovable), and the highest MAJOR share (213 issues, 46%); Replit had no CRITICAL issues, Lovable and v0 1.0% and 1.2% (p. 4, p. 5, p. 6).
5. [V] Bugs per tool are few: 1 (Lovable), 5 (v0), 8 (Replit); security hotspots 6, 10, 30 (Table 6, p. 5).
6. [V] Within-tool variation is large: Lovable's wildlife-whisperer-app had 59 issues and 215 min effort vs 167/1,782 and 164/1,774 for the other two Lovable projects (Table 3, p. 3).
7. [A] v0 "emerged as the most balanced alternative" (p. 6); Lovable "may produce code that looks clean but relies on APIs whose reliability ... has already been questioned" (p. 6); Replit's productivity gain "may come with a more significant structural debt over the medium term" (p. 6).
8. [A] The deprecated-API pattern is explained by LLMs over-representing API patterns prevalent at training time (p. 5, p. 6). This is a plausible literature-based explanation, not tested here.

## 8. Limitations stated by the authors
- [A] Static analysis (SonarQube) cannot definitively quantify code quality; only a subset of its checkers may reveal real flaws, which may inflate technical-debt indices (p. 6).
- [A] Only three projects per tool because of free-tier token limits and time; results are susceptible to anomalous outputs, as shown by Lovable's SD of 62.1 driven by one project (p. 6).
- [A] Platform opacity: no transparency on resource allocation in free tiers; lower-capacity models might be used at peak times ("speculation, not a claim") (p. 6).

## 9. Limitations we identified
- [I] Sample size: n = 3 per tool and n = 9 overall, one prompt, one application domain (p. 2). With this N, tool differences cannot be separated from run-to-run variance; a single outlier project (Lovable's wildlife-whisperer-app, p. 3) changes the tool ranking on issues and effort. All tool-level conclusions are hypotheses, not findings.
- [I] Functional fidelity is not checked: the paper never verifies that the nine apps run or implement the prompted requirements, while per-KLOC comparisons assume "the expected functionality of the projects is the same" (p. 2). Code volume and smell counts are hard to compare if the apps deliver different features.
- [I] Template and boilerplate confound: Lovable starts from a dated template (p. 2) and Replit's ~60% duplication (p. 4) may come from scaffolding or copied UI components. The paper does not say whether such code was excluded, so part of the measured "generated" quality may belong to templates. S1874 (deprecated APIs) is a likely candidate for template- or library-driven issues.
- [I] Lovable's remediation effort (3,771 min) is concentrated in two projects (1,782 and 1,774 min) and one rule (p. 3, p. 6); the "highest remediation effort" conclusion rests on a narrow base.
- [I] The text calls Replit's severity profile the "highest absolute and relative share of severe issues" (p. 4), yet Replit is the only tool with no CRITICAL issues (p. 5); "severe" here means MAJOR.
- [I] Tag-to-cluster mapping is author-defined without a stated procedure (p. 3); the "Security" cluster is only the `cwe` tag.
- [I] SonarQube version and rule profile not reported; free tiers only; no repeated analysis with a second tool.
- [I] The acknowledgements state that Claude generated "all the figures and tables" from the authors' specifications (p. 6). We re-computed the Table 6 per-KLOC values from the raw totals and they are consistent, but transcription errors elsewhere cannot be ruled out without the artefacts.

## 10. Threats to validity
- Internal (confounds, leakage, selection): [I] Templates/boilerplate not separated; platform model tier not controlled ([A] p. 6); different stacks per tool (TanStack Start, Next.js, Node) mean SonarQube rules apply differently.
- External (generalisability of sample/context): [I] One prompt, one small CRUD-plus-map web app, free tiers, May 2026 platform versions; premium tiers may differ ([A] p. 6).
- Construct (do metrics measure the concept?): [A] SonarQube issues are an auxiliary indicator, not a definitive quality measure (p. 6). [I] Remediation minutes are SonarQube defaults per rule, not observed effort; no maintainability task (e.g. change requests) measured.
- Statistical conclusion (power, multiple comparisons, variance): [I] No inferential statistics; n = 3 per group; high within-tool variance (p. 6).
- Reproducibility (data/code/setup reported?): [V] Prompt, generated code and SonarQube reports shared (p. 6); generation window and build identifiers reported (p. 2). [I] SaaS platforms change continuously and are non-deterministic, so regeneration will not reproduce the same code; the shared code allows re-analysis only.

## 11. Future research directions
- Stated by authors [A]: substantially more iterations per tool; premium versions of the platforms; additional static analysis tools besides SonarQube (p. 6). Broader replications across varied contexts before definitive conclusions (p. 6).
- Suggested by us [I]: add functional verification (requirement-based acceptance tests) alongside static analysis; separate template/vendored code from generated code; use several prompts and app types; add maintainability tasks (implementing change requests) rather than only static indicators. For our project: this is the closest design to a vibe-coded application study and could be extended with a reference application (to measure fidelity) and a human-written baseline.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1 (whole-app generation with commercial vibe-coding platforms: Lovable, v0, Replit), RQ3 (SonarQube smells, duplication, remediation effort of vibe-coded apps), RQ4 (very small N, no functional check, single static tool), RQ5 (joint fidelity + quality evaluation missing).
- How it informs our work [I]: it evaluates complete web applications produced end-to-end by vibe-coding platforms from one NL specification, which is the closest setting in our set to rebuilding an app by vibe coding. It shows that quality profiles differ by platform and by run, but it does not measure functional fidelity, so it illustrates exactly the gap our RQ5 targets. Evidence weight is low (preprint, n = 9), relevance high.
