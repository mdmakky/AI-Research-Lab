## 1. Research objective
Audit the code smells (technical debt) in code produced by single LLMs and by a multi-agent system, and analyse how moving from single-file algorithmic tasks to multi-file applications changes the density and kinds of smells [A] (p. 1).

## 2. Research questions / hypotheses
- RQ1: To what extent do code-generating agents introduce code smells in standard coding tasks? RQ2: What taxonomy of code smells do code-generating agents most often show? RQ3: How does the complexity of the target architecture affect smell prevalence, and can prompt strategies mitigate it? [V] (p. 1). These are the paper's own RQs, not our project RQs.
- No formal hypotheses. Note: the results section maps RQ2 and RQ3 differently from the introduction (RQ2 = complex-system smells, RQ3 = drivers of decay) (p. 6, p. 8, p. 9).

## 3. Methodology
- Research design: exploratory, two-experiment static-analysis study [V] (p. 3). Experiment I: five LLMs generate Python solutions for algorithmic problems under zero-shot and few-shot prompts; smells compared with human solutions [V] (p. 3, p. 4). Experiment II: MetaGPT multi-agent framework (Qwen-Coder 480B backend) generates full Python applications for 5 scenarios, each at 4 increasingly detailed requirement stages; smells related to size, scenario and stage [V] (p. 5, p. 8).
- Approach / model / intervention: Exp I models: Gemini 2.5 Pro, Llama 3.3 70B, deepseek-coder-v2 16B, qwen3-coder 30B and 480B [V] (p. 3). Zero-shot prompt replicates Santa et al.; few-shot prompt adds role, output rules and a boilerplate `solution` method [V] (p. 4). Exp II prompts require OOP and modular files because preliminary trials produced monolithic "God Class" scripts [V] (p. 5). Scenarios: Crossy Road game, Flashcard app, Pacman, Personal Finance (CLI + web dashboard), Online Bookstore backend [V] (p. 5).
- Baselines or comparison conditions: Exp I — one randomly sampled verified human Python submission per problem; zero-shot as prompt baseline [V] (p. 4). Exp II — no human or alternative-agent baseline; comparison only across scenarios and stages [V] (p. 5, p. 9).

## 4. Dataset and sample
- Data source(s): CodeContests dataset (AlphaCode) for Exp I; author-written product requirements for Exp II [V] (p. 1, p. 3, p. 5).
- Sample size (N) and unit: Exp I — 90 problems, 5 LLMs × 2 prompt conditions, plus 90 human solutions; unit = one generated .py file per problem [V] (p. 4). Exp II — 5 scenarios × 4 stages [V] (p. 5); the resulting number of repositories (20 implied) and the number of generation runs per prompt are not reported explicitly. [I] n ≈ 20 is supported by the reported Spearman p-values. Under the usual t-approximation, ρ = 0.53 → p = 0.017 and ρ = 0.59 → p = 0.007 (Table 3, p. 9) correspond to n ≈ 19–20 (our calculation). [I] Each stage is probably an independent generation, not an evolution of the previous codebase, because the four stage prompts are self-contained (p. 5).
- Sampling / selection method: 90 problems "randomly sampled" (p. 4), later described as a "stratified sample" balanced across Easy/Medium/Hard (p. 9) [V]. Model selection to span dense vs MoE, proprietary vs open, and parameter scale [V] (p. 3).
- Data availability (public? link?): replication package at https://doi.org/10.5281/zenodo.19245562 with sampling scripts, Exp I scripts, Exp II prompts and analysis scripts [V] (p. 10). Generated repositories announced as a benchmark dataset "released alongside this paper" [A] (p. 5).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: each solution saved as a .py file and analysed with PyExamine; counts per smell type aggregated [V] (p. 4). Exp II repositories also measured with cloc (TLoC), total number of files (ToF) and Agent Action Count (AAC) [V] (p. 5). No iterative "validate and correct" loop in Exp I (budget) [V] (p. 9). Temperature, sampling settings, model quantisation/hosting, PyExamine version and thresholds: not reported. Results for AAC: not reported. The factor "ALpF" in Table 3 is not defined in the text (p. 9).
- Code availability: scripts in the Zenodo package (p. 10).

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - PyExamine smell counts at three levels: code-level (e.g. Long Method, Long File, High Cyclomatic Complexity), structural (class/object level, e.g. Too Many Branches, High Response for a Class, Temporal Field) and architectural (e.g. Unstable Dependency, Scattered Functionality, Potential Improper API Usage) [V] (p. 3, p. 7, p. 8). Chosen as a comprehensive, "un-opinionated", static and repeatable Python smell detector, and to separate structural smells from superficial linting issues counted by SonarQube [A] (p. 2, p. 4).
  - TLoC and ToF as project size/complexity [V] (p. 5).
  - Feature Envy and Potential Shotgun Surgery were excluded from Exp I interpretation after a manual audit found systematic false positives; Long Method and Long File were judged high precision [V] (p. 6). The size of this audit and precision values are not reported.
- Statistical testing (tests used, significance, effect sizes, confidence intervals): Exp I — raw counts only, no statistical test, no normalisation by code size [V] (p. 7). Exp II — Spearman's ρ (continuous factors) and Kruskal-Wallis H (Scenario, Stage), p < 0.05; no multiple-comparison correction, no confidence intervals [V] (p. 8, p. 9). Functional correctness of generated code: not measured or reported.

## 7. Key findings
1. Exp I: Long Method counts were higher for larger LLMs than for humans — zero-shot Qwen Coder 480B 11, Qwen Coder 30B 7, Gemini 2.5 Pro 5, deepseek 2, Llama 3 70B 0, human 1 (across 90 problems) — [V] (p. 7, Table 1).
2. Exp I: Temporal Field appeared only in human solutions (4 instances), never in LLM output — [V] (p. 6, p. 7).
3. Exp I: few-shot prompting did not reduce Long Method (Qwen 480B 11 → 13; Gemini 5 → 8) — [V] (p. 6, p. 7, Table 2).
4. Exp I interpretation: a "Reasoning-Complexity Trade-off" — more capable models produce more procedural bloat; larger models' failed solutions had more Long Methods — [A] (p. 6, p. 7). The failed/passing split is not shown in any table.
5. Exp II: ranked by mean count over all Exp II repositories (pooled), the most prevalent smells were Too Many Branches, High Response for a Class, Potential Improper API Usage, Scattered Functionality and Unstable Dependency — [V] (p. 8, Figure 1 caption; p. 7). The authors add that these smells appear consistently "across all stages and scenarios" — [A] (p. 7); Figure 1 pools repositories and no per-stage or per-scenario breakdown is shown.
6. Exp II: TLoC correlated with code-level (ρ = 0.53, p = 0.017), structural (ρ = 0.59, p = 0.007) and architectural smell counts (ρ = 0.94, p < 0.001); ToF with architectural smells ρ = 0.72 (p < 0.001) — [V] (p. 8, p. 9, Table 3).
7. Exp II: scenario affected architectural smells (H = 9.86, p = 0.043); requirement stage had no significant effect on any smell level (p > 0.8) — [V] (p. 8, p. 9, Table 3).
8. Authors' framing: a "Volume-Quality Inverse Law" and a "Modular Mirage" (files are separated but behaviour is fragmented); agents act like "junior developers" lacking architectural foresight — [A] (p. 8, p. 9).
9. Abstract/introduction claim that functional correctness is decoupled from quality ("running code is just as likely to be structurally flawed as failed code") — [A] (p. 1, p. 2). No supporting data is reported in the results.

## 8. Limitations stated by the authors
- [A] No iterative debug/repair loop in Exp I; first-pass code only (p. 9, p. 10).
- [A] Exp I uses 90 problems, not the full dataset; may miss long-tail problem types; authors plan to scale up "to verify the statistical significance of these findings" (p. 9).
- [A] Exp II uses only MetaGPT; findings may be specific to its SOP-based paradigm; other tools (SpecKit, Cursor Composer) may differ (p. 9, p. 10).
- [A] Small sample, so non-parametric tests were used (p. 8).

## 9. Limitations we identified
- [I] Central claims rest on very small counts. Exp I differences are a handful of smell instances over 90 files (e.g. 11 vs 1 Long Method), with no test, no per-LoC normalisation and no variance across runs (p. 7). Treat as descriptive.
- [I] The "Volume-Quality Inverse Law" correlates smell *counts* with code size (p. 8, p. 9). More code mechanically yields more smell instances, so ρ = 0.94 does not show that larger code is worse per line. The paper says size metrics allow density normalisation (p. 5) but reports no density analysis.
- [I] The claims that functional correctness does not mitigate decay (p. 1, p. 2) are not backed by any reported correctness measure; Exp II apps were not executed or tested at all as far as the paper reports.
- [I] The "longitudinal"/"architectural rot" framing (p. 2, p. 5) is questionable: the four stage prompts are self-contained (p. 5), and the paper does not say that each stage evolves the previous codebase. It may be four independent generations.
- [I] Exp II has n ≈ 20, one LLM backend, one framework, no human or single-agent baseline, and 15 significance tests without correction (p. 9); the "near-perfect predictor" wording overstates a single small sample.
- [I] Internal inconsistencies: RQ numbering differs between introduction and results; "random" vs "stratified" sampling; "ALpF" undefined; smell abbreviations in Exp I (EC, HFI) are not expanded (p. 1, p. 4, p. 6, p. 7, p. 9).
- [I] PyExamine validity: two smell types were dropped as false positives after an unquantified audit (p. 6); no precision figures for the architectural smells that drive the main conclusion.
- [I] Model inference settings (temperature, quantisation; model names suggest local deployment) are not reported, which limits reproducibility.

## 10. Threats to validity
- Internal (confounds, leakage, selection): size confounds smell counts (Exp II); CodeContests problems may be in model training data (not discussed); prompts for Exp II were engineered to force modularity after preliminary trials (p. 5).
- External (generalisability of sample/context): Python only; competitive programming tasks (Exp I); five small app scenarios with a single agent framework and one LLM (Exp II) (p. 5, p. 9, p. 10).
- Construct (do metrics measure the concept?): maintainability is equated with PyExamine smell counts; no human assessment of maintainability; FE and PSS judged unreliable (p. 6).
- Statistical conclusion (power, multiple comparisons, variance): no tests in Exp I; small n and no correction in Exp II; no repeated generations, so model randomness is not estimated (p. 7, p. 8, p. 9).
- Reproducibility (data/code/setup reported?): Zenodo package with scripts and prompts (p. 10); generation hyper-parameters not reported. Authors note Gemini 3.1 was used for editorial purposes (p. 10).

## 11. Future research directions
- Stated by authors [A]: architecturally-aware agents (explicit "Architect" role, constitutional design principles); refactoring agents that detect and fix AI-specific smells such as the "Modular Mirage"; longitudinal benchmarks of continuous software evolution; metrics for semantic cohesion (p. 10); extend the benchmark to other agent platforms (p. 9); scale Exp I to the full dataset (p. 9).
- Suggested by us [I]: repeat Exp II with smell density per KLoC, multiple runs per prompt, a human-written reference implementation of the same apps, and functional tests, so that "correctness vs quality" is actually measured.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ3 (main), RQ1, RQ4.
- How it informs our work [I]: Exp II is close to our setting: complete small applications (games, GUI tools, web backend) generated by an agent from natural-language requirements. It gives a smell taxonomy for agent-built apps (God-class branching, unstable dependencies, scattered functionality) that a reconstruction study could measure. Its evidence is weak (preprint version, tiny n, count-based statistics, no correctness data), so it should support hypotheses rather than conclusions, and it illustrates RQ4 weaknesses (no size normalisation, no baselines).
