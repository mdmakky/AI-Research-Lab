# Vibe Code Bench: Evaluating AI Models on End-to-End Web Application Development

- Authors: Tran, Hung; Nashold, Langston; Krishnan, Rayan; Bigeard, Antoine; Gu, Alex
- Year / venue: 2026, Proceedings of the ACM Conference on AI and Agentic Systems (published)
- DOI: 10.1145/3786335.3813180 · URL: https://doi.org/10.1145/3786335.3813180
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
[A] To measure whether LLMs can carry out the complete "zero-to-one" process of building a working, deployable web application from a natural-language specification alone, judged by user-visible behaviour, and to check how reliable automated browser-agent evaluation is (p. 1, p. 3).

## 2. Research questions / hypotheses
No formal RQs or hypotheses. Stated contributions (p. 1–2):
- [A] A benchmark and browser-based evaluation pipeline for end-to-end web-app development (p. 1).
- [A] A comparison of 16 frontier models including cost, latency and error analysis (p. 1–2).
- [A] An evaluator-alignment protocol with cross-model and human annotation (p. 2).

## 3. Methodology
- Research design: benchmark construction plus a comparative evaluation of 16 models in one fixed agent harness; secondary analyses (tool use, error taxonomy, reasoning-effort and vision ablations, variance decomposition, human-alignment study) (p. 4–9). [V]
- Approach / model / intervention: each model receives only a non-technical text specification and builds the app from scratch inside a modified OpenHands container with terminal, browser, Supabase/MailHog/Stripe services and MCP tools, up to 5 hours wall-clock per app (p. 3–4). [V] The system prompt mandates React + Vite, Tailwind, Supabase and Docker Compose (p. 4, p. 16). [V] The authors say a fixed stack was needed because otherwise apps "were too heterogeneous to evaluate consistently at scale" (p. 4). [A]
- How functional correctness is tested: pre-authored natural-language UI workflows (6–23 per task, each with substeps) are executed by an autonomous Browser Use agent (canonical evaluator model Claude Sonnet 4.5, vision on, headless 1920×1200, max 100 steps per workflow) against the deployed app; the agent produces pass/fail per substep ("LLM-as-judge substep judgments"); a workflow passes when ≥ 90% of substeps succeed; app accuracy = share of passing workflows (p. 4–5, p. 15). [V] If deployment fails, all workflows fail (p. 5). [V] The evaluator follows fixed workflow definitions rather than generating tests on the fly (p. 4). [V] Fresh browser session and unique account data per workflow to stop state leaking between tests (p. 5). [V]
- Baselines or comparison conditions: 16 models from 9 providers compared with each other; no human-developer or commercial-tool baseline (p. 5). [V]

## 4. Dataset and sample
- Data source(s): task ideas inspired by consumer apps, YC startup ideas, consulting case studies and internal enterprise needs; specifications and 6–23 draft workflows generated by a structured-output GPT-5 pipeline; two-pass review by two PM reviewers (Accept/Modify/Reject per test); PM line review plus an LLM-based audit for spec/test misalignment before freeze (p. 3). [V]
- Sample size (N) and unit: 100 specifications (24 Individual, 45 Solo Founder, 31 Enterprise Tool), 964 workflows, 10,131 substeps; test split 50 apps / 473 workflows / 5,136 substeps (p. 3–4, Table 3). [V] 28/100 apps need Stripe and/or email (p. 3). [V] Test-split difficulty tiers: Easy 23, Medium 19, Hard 8 (p. 6, Table 5). [V]
- Sampling / selection method: expert-designed, not sampled from a population of real apps; selection criteria beyond the idea sources are not reported (p. 3). [V] Difficulty tiers are assigned after the fact from mean pass rate across the 16 models (p. 6). [V]
- Data availability (public? link?): harness fork and all trajectories/generated apps released on GitHub (p. 11). [A] Whether the test-split specifications and workflows are public is not stated; the text calls validation "private" (p. 1, p. 3) while Table 3 labels it "Validation (public)" (p. 4). [V]

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: per-model temperature, top-p, reasoning level and vision flag listed (p. 15, Table 15); highest reasoning level and provider default temperature (p. 5); GLM-5, MiniMax M2.5 and DeepSeek V3.2 ran without usable browser vision (p. 5, p. 15). [V] Same retry policy for all runs (p. 15). [V] Evaluator hyper-parameters (timeouts, step caps, 90% threshold) in Table 16 (p. 15). [V] Main results use one generation per model per app (the variance study is the only multi-run experiment, p. 8). [V]
- Code availability: harness and artifacts on GitHub (p. 11). [A] Full generation system prompt, an example spec and an example UI-test file are printed (p. 16–23). [V]
- Evaluator-reliability design: (a) variance panel — 6 specs x 3 source models x 5 independent generations (90 generations), and the same frozen apps re-evaluated 5 times (90 evaluations) (p. 8); (b) human alignment — 6 tasks x 3 source models = 18 apps, 1,401 substeps; each app evaluated by two of three human evaluators who used only the browser, were calibrated on a practice question and were blind to model and to other evaluators' scores; four evaluator models each ran once per app; no adjudication (p. 8–9). [V]

## 6. Evaluation metrics
- Accuracy — percentage of workflows passing (≥ 90% substeps) — chosen to tolerate minor non-critical errors and avoid credit from unrelated workflows ("cross-workflow masking") (p. 5). [V]/[A]
- Cost (API cost of generation, caching included) and latency (wall-clock generation time) (p. 5). [V]
- Pairwise step-level agreement — share of substeps where two evaluators give the same pass/fail (p. 9). [V] No chance-corrected statistic (e.g. Cohen's kappa) is reported. [V] (p. 9)
- Statistical testing (tests used, significance, effect sizes, confidence intervals): mean ± standard error across the 50 test apps (p. 5); Pearson correlations between tool use and accuracy across 16 models (p. 7); variance decomposition into generation vs evaluator share (p. 8). No significance tests for model differences. [V]

## 7. Key findings
1. Top test-split accuracy: GPT-5.3-Codex 61.77 ± 4.71%, Claude Opus 4.6 57.57 ± 4.37%, GPT-5.2 53.50 ± 5.07%; lowest Grok 4.1 Fast Reasoning 1.20 ± 1.20% (p. 6, Table 4). [V] Open-weight models range ~5–23% (p. 6, Table 4). [V]
2. Accuracy falls with difficulty (all-model average 44.29% easy, 21.36% medium, 6.03% hard) and with external integrations (34.18% none vs 13.49% email + Stripe) (p. 6, Tables 5–6). [V] Average by domain: Individual 43.01%, Solo Founder 29.94%, Enterprise Tool 18.64% (p. 7, Table 7). [V]
3. Browser tool calls per app correlate with accuracy across the 16 models (Pearson r = 0.72; partial r = 0.72 controlling for latency); edit calls barely correlate (r = 0.09) (p. 7). [V] The authors interpret this as self-testing being associated with better outcomes (p. 7). [A]
4. Failures are mostly zero-score apps: 12.8% of apps score zero for the top five models vs 73.2% for the bottom five; 14.0% of apps from the worst five fail to start; only 8.8% of top-five apps score 100% (p. 7). [V]
5. Behavioural failure taxonomy (apps that started): missing feature 46.7%, authorization 20.4%, validation/policy block 14.8%, UI rendering/navigation 6.0%, data consistency/backend 1.9%, other 10.2% (p. 8). [V] How failures were classified (human or LLM) is not reported.
6. Variance: generation-side variance dominates (92.5%, 92.1%, 73.5% of observed variance for Gemini 3.1 Pro, GPT-5.2, Claude Sonnet 4.6); evaluator rerun SE 0.99–3.00 pp vs generation SE 3.47–5.00 pp (p. 8, Table 9). [V] The authors conclude rankings are robust except for near-ties (p. 8). [A]
7. Human–human step agreement 88.6–93.6%; Claude Sonnet 4.5 (canonical evaluator) 86.4% mean agreement with humans, Claude Sonnet 4.6 86.3%, Gemini 3.1 Pro 84.7%, GPT-5.2 only 36.1% (p. 9, Table 10). [V] Model–model agreement ranges 33.1–87.8% (p. 9). [V]
8. Vibe Code Bench separates models more than SWE-Bench: MiniMax M2.5 vs Claude Opus 4.6 gap 2.8% on SWE-Bench vs 42.7% on VCB (p. 2). [V] (57.57 − 14.85 = 42.72, consistent with Table 4.)

## 8. Limitations stated by the authors
- [A] Design and code quality not measured: no evaluation of code readability, visual design quality or security vulnerabilities; passing functional tests does not imply maintainable, secure or documented code (p. 9).
- [A] Single OpenHands-based harness; other harnesses might score higher (p. 9).
- [A] Single technology stack (React/Vite + Supabase); results may not generalise to other stacks (p. 9).
- [A] Web applications only; CLI, desktop and mobile apps unexplored (p. 9).
- [A] Three models ran without browser vision because of provider configuration (p. 5).

## 9. Limitations we identified
- [I] Functional fidelity is judged by an LLM browser agent, and the canonical evaluator (Claude Sonnet 4.5) belongs to the same family as several evaluated models (Claude Opus/Sonnet/Haiku). Self-preference or style-familiarity bias is not tested: alignment was measured only on apps from Gemini 3.1 Pro, GPT-5.2 and Claude Sonnet 4.6 (p. 8–9), and per-source-model agreement is not reported.
- [I] Agreement is raw percent agreement with no chance correction (p. 9). If most substeps pass or most fail, high percent agreement can coexist with low kappa. The very low GPT-5.2 agreement (31.8–48.0% with every other evaluator) is unexplained; agreement this far below the 84–94% of the other pairs implies GPT-5.2 labels largely the opposite way (e.g. mostly "fail" where others say "pass"), which points to a systematic problem (such as runs without structured output counted as fails) rather than ordinary judgment disagreement. Based on Table 10 (p. 9) and failure semantics (p. 5).
- [I] The alignment panel is small (18 apps from 6 tasks) relative to 50 test apps x 16 models; agreement is reported at substep level, while the leaderboard uses workflow-level pass with a 90% threshold. Workflow-level human–model agreement is not reported (p. 5, p. 9).
- [I] Main leaderboard numbers come from a single generation per model per app; ± SE reflects variation across apps, not across runs (p. 5, p. 8). Generation variance is large (SE up to 5 pp on the 6-app panel, p. 8), so adjacent ranks (e.g. GPT-5.2 vs Opus 4.6 Thinking, both 53.50) are not separable.
- [I] Specifications and workflows were drafted by GPT-5 (p. 3); a possible advantage for OpenAI models (top rank) is not examined.
- [I] The self-testing correlation is across only 16 models and is observational; the system prompt itself demands browser testing (p. 16, p. 19), so browser-call counts may reflect instruction following as much as testing skill. Identical r and partial r (both 0.72, p. 7) are reported without explanation.
- [I] Difficulty tiers are defined from the evaluated models' own pass rates (p. 6), so tier results are partly circular.
- [I] The error taxonomy procedure (who labelled, how many failures) is not described (p. 8).
- [I] Authors are mostly from Vals AI, a company (p. 1); funding and conflicts are not reported. Not a model vendor, so no direct ranking conflict is visible.
- [I] The validation split is called "private" in the text (p. 1, p. 3) but "public" in Table 3 (p. 4); public availability of test tasks (and thus future contamination risk) is unclear.

## 10. Threats to validity
- Internal (confounds, leakage, selection): mandated tech stack and prompt reduce heterogeneity but make results harness- and prompt-specific (p. 4, p. 9) [V]. Evaluator same-family bias not tested [I]. Test-isolation measures reported (p. 5) [V].
- External (generalisability of sample/context): 100 expert-written greenfield specs, one stack, web only (p. 3, p. 9) [V]. Tasks start from a text spec, not from an existing app's UI or behaviour, so results transfer to reconstruction only indirectly [I].
- Construct (do metrics measure the concept?): browser workflows measure user-visible functional behaviour and are implementation-agnostic (p. 3–4) [V]; they do not capture code quality, security, visual fidelity or maintainability (p. 9) [V]. The 90% substep threshold is a design choice without sensitivity analysis [I] (p. 5).
- Statistical conclusion (power, multiple comparisons, variance): SE across 50 apps reported; variance decomposition on 6 apps x 3 models (p. 5, p. 8) [V]; no significance tests; correlations with n = 16 [I].
- Reproducibility (data/code/setup reported?): unusually complete — prompts, hyper-parameters, evaluator settings, harness and trajectories released (p. 11, p. 15–23) [V]; evaluator uses LLM sampling without fixed seed ("none set in evaluator code", p. 15) [V].

## 11. Future research directions
- Stated by authors [A]: extending "zero-to-one" evaluation to CLI, desktop and mobile apps; testing other harnesses and stacks; measuring readability, visual design and security (implied by the limitations list, p. 9). Treat evaluator choice as "a first-class reporting concern" (p. 9).
- Suggested by us [I]: reuse the browser-workflow oracle for reconstruction tasks — run the same workflows on the original app and the rebuilt app to score behavioural fidelity; add static-analysis and maintainability metrics on the generated repositories (which the authors release); report chance-corrected agreement and workflow-level human–judge agreement.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1 (agentic vibe-coding generation of full web apps from text specs), RQ2 (functional fidelity via browser workflows; headline accuracy), RQ3 (explicitly not measured — useful as negative evidence), RQ4 (LLM-judge reliability, human alignment, variance decomposition), RQ5 (authors' own call for code-quality measurement).
- How it informs our work [I]: This is the closest benchmark to a vibe-coding rebuild: a non-technical spec in, a deployed multi-page app out, judged only through the browser like a user. Its evaluation design (pre-authored natural-language workflows run by a browser agent, with a human-alignment check) is a ready template for measuring functional fidelity of a reconstructed app against the original. It also shows that the judge itself is a major source of measurement error (36% vs 86% human agreement depending on judge model), and that code quality and maintainability remain unmeasured.
