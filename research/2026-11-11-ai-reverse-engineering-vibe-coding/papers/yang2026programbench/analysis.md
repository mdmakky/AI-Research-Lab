# ProgramBench: Can Language Models Rebuild Programs From Scratch?

- Authors: Yang, John; Lieret, Kilian; Ma, Jeffrey; Thakkar, Parth; Pedchenko, Dmitrii; Sootla, Sten; McMilin, Emily; Yin, Pengcheng; Hou, Rui; Synnaeve, Gabriel; Yang, Diyi; Press, Ofir

- DOI: 10.48550/arxiv.2605.03546 · URL: https://arxiv.org/abs/2605.03546

## 1. Research objective
- [A] Measure whether software-engineering (SWE) agents can develop whole programs "holistically", including the high-level architecture decisions that existing bug-fix or single-feature benchmarks do not test (p. 1; p. 2).
- [A] Task: "given only a program and its documentation, agents must architect and implement a codebase that matches the reference executable's behavior" (p. 1).

## 2. Research questions / hypotheses
- Not stated as formal RQs. [I] Implicit questions: (1) can LMs rebuild real programs from an executable plus docs; (2) do generated behavioural tests capture the programs well enough to judge this; (3) how do model-written codebases and development trajectories differ from human ones; (4) how often do models cheat when allowed internet access.

## 3. Methodology
- Research design: [V] A benchmark built semi-automatically from open-source repositories, plus an evaluation of 9 LMs, two ablations (forced different language; internet access with cheating detection), test-suite validation (coverage, assertion strength) and descriptive analyses of codebases and trajectories (p. 3; p. 5; p. 7; p. 9).
- Approach / model / intervention: [V] The agent receives the compiled gold executable (execute-only permissions, so it cannot be decompiled) and its usage documentation, inside a Docker container without internet. It must write source code in any language plus a build script that produces an executable with the same behaviour (p. 2; p. 4; p. 18). [V] The system prompt forbids obtaining source code, wrapping the binary, and decompiling or tracing it (strace/ltrace); only running the executable and reading the bundled docs is allowed (p. 19; p. 20).
- Fidelity oracle: [V] Behavioural tests are generated by a SWE-agent (mini-SWE-agent with Claude Sonnet 4.5) that explores the program, its source code, existing tests and documentation. It harvests existing behavioural tests and iteratively adds tests that cover missing code paths, guided by line coverage (p. 3). Assertions target observable effects only: stdout/stderr content, exit codes and files produced (p. 2; p. 3). Weak tests are flagged by an assertion-quality linter and revised. Tests that do not pass the gold binary deterministically, or that pass a dummy binary, are discarded (p. 3; p. 27). The tests are never shown to the solving agent (p. 3).
- Baselines or comparison conditions: [V] 9 LMs compared with each other; no human baseline ("we do not carry out any formal human studies") (p. 5; p. 20). For test quality, the generated suites are compared with the projects' native test suites (p. 7; p. 8).
- [I] Relation to our topic: this is the closest design to black-box reverse engineering of an application. The agent observes the running program and its docs but not the source, and fidelity is judged by behavioural equivalence. The targets are CLI/TUI programs, not GUI or web apps.

## 4. Dataset and sample
- Data source(s): [V] 200 GitHub repositories in compiled languages that build a standalone executable: Rust 107, Go 46, C/C++ 45, other 2 (one Java, one Haskell). They range from small CLI tools to FFmpeg, SQLite, DuckDB, PHP and Lua (p. 2; p. 4).
- Sample size (N) and unit: [V] 200 tasks; 248,853 test functions (median 770 per task, min 224, max 14,645) (p. 4). [V] 9 models x 200 tasks = 1,800 runs (p. 10); some analyses use 1,788 runs (p. 32). [V] Median codebase size 8,635 code lines (min 212, max 2,701,283) and 50 code files (p. 4). [V] Difficulty bins: Easy 28, Medium 143, Hard 29 (p. 31).
- Sampling / selection method: [V] Filter for repositories that can produce a standalone executable, with compiled language as the heuristic. Repositories whose executable needs the internet are excluded; 18 networking tools are kept and tested over localhost (p. 3; p. 21). [I] How the 200 were chosen from the eligible pool (random, by stars, by build success) is not reported.
- Data availability (public? link?): [A] Code at github.com/facebookresearch/ProgramBench, open-sourced (p. 1; p. 2).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] mini-SWE-agent (bash-only minimal scaffold), vendor-default hyperparameters, 20 CPUs and 60 GB RAM per container, 1,000-step and 6-hour limits (p. 5), 3-minute per-action timeout, no cost limit, outputs truncated at 10,000 characters (p. 32). [V] Base image: Ubuntu 22.04 with Rust 1.92.0, Python 3.12, Go 1.21.0, a C/C++ toolchain and tmux for TUIs (p. 16). [V] Binary test assets that models cannot easily generate (images, audio, custom formats) are provided; standard text formats are not (p. 21; p. 22). [V] Before evaluation, all files matching the hash of the original executable are removed, and git history is wiped (p. 18; p. 19).
- Number of runs: [V] One run per model-task (1,800 runs, p. 10). Repeats or seeds: not reported.
- Code availability: [A] public (p. 1).

## 6. Evaluation metrics
- % Resolved: share of tasks where all tests pass and no cheating is flagged; the primary metric (p. 5).
- % Almost: share of tasks with ≥95% of tests passing (p. 6).
- % Tests Passed: per-task pass fraction. The authors say it is "only meaningful for relative comparisons" and "does not reliably correlate with percentage of working functionality" (p. 5).
- Test-suite quality: line coverage of the original binary versus native suites; dummy pass rate (share of tests that a trivially wrong program passes) (p. 7; p. 8).
- Code structure (descriptive): lines of code, number of files, maximum directory depth, function count and average function length, compared with the reference, for runs passing ≥75% of tests (p. 8; p. 9).
- Trajectory metrics: action types (read/write/probe/execute/git) classified by keyword matching; edit counts; share of code written in the single largest edit (p. 9; p. 10).
- Cheating rate: majority vote of 9 LM judges (p. 6; p. 17).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): [V] No significance tests or confidence intervals. The paper reports Pearson correlations of pass rate with API calls (r = 0.27) and cost (r = 0.21) (p. 33) and Fleiss' κ for judge agreement (p. 17). [I] The statement that "test pass rates are significantly different between models" (p. 2) is not backed by any reported test.

## 7. Key findings
1. [V] No model resolves any task (0% resolved for all 9). Claude Opus 4.7 reaches ≥95% of tests on 3.0% of tasks, Opus 4.6 on 2.5%, Sonnet 4.6 on 1.6%, and all others on 0% (p. 6).
2. [V] Macro-averaged test pass rates: Opus 4.6 52.0%, Opus 4.7 51.2%, Sonnet 4.6 48.5%, GPT 5.4 38.3%, Gemini 3.1 Pro 36.6%, down to GPT 5 mini 15.9%. Rates fall from Easy to Hard for every model, e.g. Opus 4.6 from 73.9% to 24.7% (p. 31).
3. [V] Across all runs, the median pass rate is 32%; about 18% of runs fall in the 0–5% bin, and fewer than 5% exceed 90% (p. 32). C/C++ tasks average 27.7%, against 38.5% for Rust and 38.4% for Go (p. 33).
4. [V] Generated test suites average 79.7% line coverage (median 86.2%), against 56.8% (median 64.3%) for native suites, over 100 sampled repositories. Against 12 dedicated behavioural/integration suites, coverage is 62.16% versus 66.11% (p. 7; p. 8).
5. [V] The assertion linter cut the mean dummy pass rate from 18.5% to 3.7%, and the stricter tests were 20–30 percentage points harder to pass without changing the model ranking (p. 8; p. 23).
6. [V] Models chose the reference language in exactly 50% of runs. Python was the most common choice overall (36% of 1,800 runs) (p. 8).
7. [V] Among 207 runs passing ≥75% of tests (88 tasks), model code had a median of 1,173 lines against 3,068 for the reference, 3 files against 15, and maximum directory depth 1 against 2. 60% of solutions had 1–3 code files, and 67% were shallower than the reference (p. 9).
8. [V] Models write 10–29% as many functions as the reference, and their functions are longer (e.g. Gemini 3.1 Pro 1.62x, Sonnet 4.6 1.46x, GPT 5.4 1.08x average length) (p. 8; p. 9).
9. [V] Development styles differ widely. Sonnet 4.6 issues a median of 868 commands per task, GPT 5.4 17 (p. 9). GPT 5.4 writes nearly all its code in one turn and makes 1.2 file modifications per trajectory on average, with 39.5% of trajectories making none (p. 10; p. 11). For the four models in the trajectory analysis (Opus 4.7, Sonnet 4.6, Gemini 3.1 Pro, GPT 5.4), probing the executable is the second-largest action category, at 22.6–34.1% of turns (p. 10).
10. [V] More turns or money do not reliably help: per-run correlation with pass rate is r = 0.27 for API calls and r = 0.21 for cost, driven mostly by between-model differences (p. 33).
11. [V] Forcing a different implementation language lowered Opus 4.7 (−8.0%) and Opus 4.6 (−3.5%) but raised each GPT model by 4.2%; the share of Python rose to 51% (p. 6; p. 7).
12. [V] With internet access, 20–36% of tasks were flagged as cheating for the three stronger models tested (1% for GPT 5 mini), mostly source-code lookup (79–95% of flags). Judges disagreed on many tasks, with pooled Fleiss' κ = 0.57 over 786 tasks (p. 6; p. 7; p. 17).

## 8. Limitations stated by the authors
- [A] A finite test suite under-approximates the executable's full specification, so evaluation is a "lower bound" on correctness: passing solutions may still differ on untested inputs (p. 12; p. 3).
- [A] Only input-output equivalence is tested. Non-functional properties (speed, memory, disk footprint) are not, so a passing solution could be far slower or more resource-hungry (p. 12).
- [A] Only a single-agent baseline is evaluated; multi-agent and human-in-the-loop settings are left for future work (p. 12).
- [A] Distinguishing meaningful behaviour from implementation artefacts is subjective. The gold executable is treated as the complete specification, and 5 tasks are at risk of implementation-dependent output (p. 26).
- [A] No formal human study of feasibility; solvability is argued theoretically (Church–Turing) and from the observable, deterministic tests (p. 20).
- [A] Cheating detection with LM judges is unreliable, so internet access is blocked by default (p. 6; p. 19).

## 9. Limitations we identified
- [I] Possible test-oracle bias. The test-writing agent had full access to the source code (p. 21) and used Claude Sonnet 4.5 (p. 3). The behaviours it chose to test may favour what a source reader finds salient, and same-family models (Claude) top the leaderboard (p. 31). The paper does not test for this.
- [I] "Agent-driven fuzzing" (p. 1) overstates the method. The tests are LLM-written, coverage-guided pytest cases (p. 3; p. 23), not randomised input fuzzing. Coverage is high, but semantic coverage of edge cases is unknown.
- [I] Contamination is only partly controlled. No-internet stops lookup, not memory. Many targets (FFmpeg, SQLite, jq, ripgrep) are famous and widely present in training data, and models can identify the program from `--help` output (p. 17). The different-language ablation (p. 5; p. 6) is the only memorisation probe, and its mixed results do not settle the question.
- [I] Code-quality evidence is thin. Only size and structure statistics are reported (LoC, files, depth, function count and length) (p. 9), with no maintainability index, smells, duplication, tests, documentation or readability. These are computed only on runs passing ≥75% of tests, a selected subset, and are confounded by language changes: Python rewrites of C code are naturally shorter (p. 35). "Monolithic" is shown, but whether it is worse for maintenance is not measured.
- [I] Single run per model-task (p. 10) with vendor-default sampling (p. 5), so run-to-run variance is unknown. Differences between closely ranked models (e.g. Opus 4.6 52.0% vs Opus 4.7 51.2%, p. 31) cannot be separated from noise.
- [I] Small internal inconsistencies:
  - 1,800 runs (p. 10) vs 1,788 runs (p. 32);
  - median tests per task 770 (p. 4) vs 750 (p. 23);
  - the Fig. 12 boxplot shows Sonnet 42% and Gemini 51%, the text says 44% and 53%, and the caption says GPT 5.4 writes "a median of 96%" while the text says 100% (p. 10);
  - "best model" is Opus 4.7 by % almost (p. 6), but Opus 4.6 has the higher mean pass rate (p. 31).
  
  None changes the conclusions, but they lower confidence in exact figures.
- [I] The main metric (% resolved) is all-or-nothing and saturates at 0% for every model (p. 6), so it cannot rank models; the paper relies on the softer metric that it itself says is only relative (p. 5).
- [I] Tasks are CLI/TUI programs; GUI, web or mobile apps are not covered, so UI and visual fidelity are untested.

## 10. Threats to validity
- Internal (confounds, leakage, selection): [V] Leakage controls: separate build and inference containers, execute-only binary, wiped git history, no internet, hash-based removal of the original binary (p. 18; p. 19). [I] Remaining threats: pretraining memory of famous programs; test generation by a same-family model with source access; the provided test assets may hint at tested behaviours (p. 21).
- External (generalisability of sample/context): [I] Compiled-language CLI/TUI programs; a minimal single-agent scaffold, unlike practitioners' vibe-coding tools with rich IDE context and human steering (p. 5; p. 12).
- Construct (do metrics measure the concept?): [I] Behavioural equivalence on observable stdout/stderr/exit codes/files is a strong operational definition of functional fidelity for CLIs. The authors admit, however, that % tests passed does not track the share of working functionality (p. 5), and that untested inputs remain (p. 12). Code-structure metrics are size measures, not quality measures.
- Statistical conclusion (power, multiple comparisons, variance): [I] One run per cell; no CIs or tests; large N (200 tasks) partly offsets this for model-level means, but not for per-task claims.
- Reproducibility (data/code/setup reported?): [V] Harness configuration, prompts, linter rules and the full repository list are reported (p. 19; p. 27; p. 32; p. 36). [A] Benchmark open-sourced (p. 2).

## 11. Future research directions
- Stated by authors [A] (p. 12):
  - richer test generation that improves coverage and adds system constraints (speed, memory);
  - multi-agent approaches to long-horizon coding;
  - human-centred agents, where a developer guides design decisions while the agent works from the executable;
  - using the pipeline to generate training data (p. 5).
- Suggested by us [I]:
  1. Add maintainability measures (complexity, smells, duplication, modularity, ease of change) to the rebuilt codebases, and compare across languages.
  2. Repeat runs to estimate variance.
  3. Generate tests with several model families to check oracle bias.
  4. Extend the same black-box protocol to GUI/web applications, where observable behaviour includes visuals and interaction.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1, RQ2, RQ3, RQ4, RQ5.
- How it informs our work [I]: This is the most direct evidence on our core scenario: an agent rebuilding software only from the running artefact and its documentation, judged by behavioural equivalence. It gives (a) a concrete protocol for black-box reconstruction with leakage controls, (b) an oracle-construction method with measured coverage and assertion strength, and (c) evidence that rebuilds diverge structurally from human code (monolithic, few files, long functions). It does not measure maintainability as such, does not cover GUIs, and has no human-in-the-loop condition. These three gaps sit directly on RQ3 and RQ5.
