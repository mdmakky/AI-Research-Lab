One row per piece of evidence that bears on a research question. Source is a pandoc citation with the paper key and PDF page (checked by `rlab cite-check`).
Label: **[V]** VERIFIED (checked in the paper's own data/results), **[A]** AUTHOR-CLAIM (stated by authors, not independently checkable), **[I]** INTERPRETATION (our reasoning).
Strength: strong / moderate / weak (see docs/research-standards.md §5).

How this matrix was built (compare-methods, 2026-11-12):

- **Preprint downgrade**: the 7 preprints (bai2026recreationworld, chen2025iwr, kim2026programdistill, mota2026comparing, pan2026functional, yang2026programbench, zhao2025vibe; `venue_kind: preprint`) are downgraded one level (strong → moderate, moderate → weak; weak stays weak). The analyst's original strength is kept in Notes. No paper is abstract-only, so no abstract-only downgrade applies.
- The ehsani2026faster row restating he2026speed's +30% warnings / +41.6% complexity is kept for traceability but **not counted**; the effect is counted once, from he2026speed.

## Contradictions
<!-- Findings that disagree: which papers, what differs (data, method, population, metric), likely explanation (INTERPRETATION). -->

Each entry records both sides with page refs, then compares data, population, method, metric and time. Explanations are labelled [I]. We do not pick a side.

### C1. Does AI assistance harm maintainability? he2026speed vs borg2026echoes
- **Side A** [V]: Cursor adoption in 806 OSS repositories raised total SonarQube static-analysis warnings by +30.26% and total cognitive complexity by +41.64% relative to matched controls (Borusyak DiD) [@he2026speed, p. 7]. The complexity effect stays significant after controlling for codebase size in the GMM (0.086, p<0.01) [@he2026speed, p. 8].
- **Side B** [V]: When a second developer evolved AI-co-developed code without AI, there was no significant difference in completion time [@borg2026echoes, p. 33], CodeHealth (8.49 vs 8.44) [@borg2026echoes, p. 38] or test coverage [@borg2026echoes, p. 35]. The only "significant" maintainability effect, a Bayesian +0.10 CodeHealth for code from habitual AI users, favours AI [@borg2026echoes, p. 39].
- **Differences**:
  - Data and population: real-world OSS repositories with ≥10 stars [@he2026speed, p. 4] vs one 2 KLoC Java/Spring Boot task done by 151 volunteer professionals [@borg2026echoes, p. 19; @borg2026echoes, p. 64].
  - Tool generation: an agentic IDE (Cursor Composer/agent) [@he2026speed, p. 2] vs late-2024 assistants (Copilot, ChatGPT, Cursor) [@borg2026echoes, p. 3; @borg2026echoes, p. 60].
  - Metric: repository-total warnings and cognitive complexity, which scale with code size [@he2026speed, p. 5] vs a LoC-weighted file-level CodeHealth average plus a second developer's evolution time [@borg2026echoes, p. 13].
  - Time: monthly panel of up to about 20 months [@he2026speed, p. 5] vs a single hand-off task.
  - Robustness: he2026speed's quality effects turn negative and non-significant under the Callaway–Sant'Anna estimator (warnings −10.49%, complexity −3.80%) [@he2026speed, p. 16]. borg2026echoes is underpowered (75 of 128 planned participants; 80% power only for d≈0.66) [@borg2026echoes, p. 19].
- **Partial agreement** [V]: borg2026echoes' observational Phase 1 also found more duplication (23% vs 11%), more complex conditionals and very large code-volume outliers in AI-assisted code [@borg2026echoes, p. 30; @borg2026echoes, p. 46]. With size controlled, he2026speed finds no direct Cursor effect on warnings [@he2026speed, p. 8].
- **Possible explanation** [I]: the two results need not conflict. Both fit "AI adds more code, and project-level totals rise with it, while per-file health and the short-term effort of the next developer are not clearly worse". The he2026speed effect depends on the estimator, and borg2026echoes can rule out only large effects. Neither study settles the question.

### C2. Fewer or more static-analysis issues in LLM code? molison2025llm vs he2026speed
- **Side A** [V]: GPT-4o solutions had far lower odds of SonarQube-flagged "bugs" than APPS human solutions (OR 0.00–0.019) [@molison2025llm, p. 8], and lower SonarQube fix effort on introductory and interview tasks [@molison2025llm, p. 7].
- **Side B** [V]: Cursor adoption raised repository SonarQube warnings by +30.26% [@he2026speed, p. 7].
- **Differences**:
  - Unit: per-solution odds of an issue in single-file stdin/stdout programs [@molison2025llm, p. 5] vs monthly repository totals [@he2026speed, p. 5].
  - Baseline: competitive-programming submissions written for correctness, not maintainability [@molison2025llm, p. 9] vs matched non-adopting repositories, which may themselves use other AI tools [@he2026speed, p. 7].
  - Metric: the SonarQube "bug" category vs all reliability, maintainability and security warnings.
  - Leakage: molison2025llm's few-shot prompt contains the human reference solutions [@molison2025llm, p. 4].
  - Time: GPT-4o in 2024 vs Cursor agents in 2024–2025.
- **Possible explanation** [I]: the results are not comparable. Both use SonarQube, but the units, baselines and code types differ, so neither one refutes the other. molison2025llm's smell results are themselves mixed: zero-shot code had 3.57x the odds of a smell on introductory tasks [@molison2025llm, p. 8].

### C3. Which instrument measures the quality of AI code? zhu2026understanding vs SonarQube-based studies
- **Side A** [A]: zhu2026understanding chose PyExamine to separate structural and architectural smells from the "superficial linting issues" counted by SonarQube [@zhu2026understanding, p. 2; @zhu2026understanding, p. 4]. It found more Long Method smells in larger LLMs' code than in human code [@zhu2026understanding, p. 7].
- **Side B** [V]: SonarQube-based studies report fewer issues in LLM code [@molison2025llm, p. 8], a platform-dependent issue density (22.83 vs about 9 issues/KLOC) [@mota2026comparing, p. 5], or more warnings with adoption [@he2026speed, p. 7].
- **Context** [A]: technical-debt tools disagree on what counts as real debt [@ehsani2026faster, p. 5], and SonarQube and general linters were not designed for LLM-specific debt [@ehsani2026faster, p. 22]. mota2026comparing calls SonarQube an auxiliary indicator only [@mota2026comparing, p. 6]. borg2026echoes argues that CodeHealth outperforms the SonarQube Maintainability Rating; note that its first author works for CodeScene, the vendor of CodeHealth [@borg2026echoes, p. 4; @borg2026echoes, p. 75].
- **Differences**: the tools differ (PyExamine, SonarQube, CodeHealth, MI), and so do the task types (algorithmic snippets, generated web apps, OSS repositories). zhu2026understanding's Exp I counts are small, unnormalised and untested [@zhu2026understanding, p. 7].
- **Possible explanation** [I]: the direction of "LLM vs human code quality" may depend on the measuring instrument. The field has no validated, size-normalised maintainability measure for AI-generated code.

### C4. Does iterative feedback or self-repair help? pan2026functional vs tran2026vibe / zhou2025declarui / wu2026looks
- **Side A** [V]: On GPT-5.2, three one-shot strategies all lowered the aggregate non-functional score without raising functional correctness: self-repair, environment repair and planning (NF 46.1–49.9% vs 57.1% at baseline) [@pan2026functional, p. 8].
- **Side B**:
  - [V] Browser self-testing during generation correlates with accuracy across 16 models (r = 0.72) [@tran2026vibe, p. 7].
  - [V] Removing DeclarUI's page-transition graph plus refinement loop cuts navigation coverage to 23.1% [@zhou2025declarui, p. 10]. Its compile success is 98% vs 74–76% for raw MLLMs [@zhou2025declarui, p. 9].
  - [V]/[A] A tsc + vite verify-repair loop gives 100% build success for all six models [@wu2026looks, p. 6]. The authors attribute this to the loop [@wu2026looks, p. 12].
- **Further evidence** [A]: agents' own validation missed behavioural mismatches with the reference [@kim2026programdistill, p. 12].
- **Differences**:
  - Feedback type: generic one-shot repair of a whole Python repository [@pan2026functional, p. 8], targeted compile and navigation checks [@zhou2025declarui, p. 5], and build checks [@wu2026looks, p. 6].
  - Design: a single-model intervention (pan2026functional) vs an observational correlation across models, where the system prompt itself demands browser testing [@tran2026vibe, p. 16].
  - Outcome: non-functional quality (pan2026functional) vs compilation, navigation or build (zhou2025declarui, wu2026looks).
  - Circularity: zhou2025declarui scores navigation against the same graph that guides its refinement [@zhou2025declarui, p. 7].
- **Possible explanation** [I]: feedback improves the property it checks (compilation, build, navigation edges). Self-testing goes along with stronger models. No study shows that generic repair improves both behavioural fidelity and code quality, and the only study that measures quality after repair finds harm (single model, single run).

### C5. Do rebuilds "look right but behave wrong"? chen2025iwr / lu2025webgen / xiao2025benchmarking vs bai2026recreationworld / wu2026looks
- **Side A** [V]:
  - Interactive functionality is below visual fidelity for all 28 models (GPT-5 IFS 24.39 vs VFS 64.25) [@chen2025iwr, p. 8].
  - Design-validation tests are passed more often than functional tests (e.g. 44.3% vs 21.1%) [@lu2025webgen, p. 9].
  - Interactive regions score lower than full pages for all six models [@xiao2025benchmarking, p. 6].
- **Side B** [V]:
  - In bai2026recreationworld the visual (VLM) channel is below the programmatic channel for 9 of 10 models [@bai2026recreationworld, p. 11], although static structure beats actions within the programmatic tests [@bai2026recreationworld, p. 16].
  - In wu2026looks navigation passes 58–92% [@wu2026looks, p. 7], while visual fidelity stays at or below 2.99/5 [@wu2026looks, p. 6].
- **Differences**:
  - chen2025iwr's VFS is averaged only over reached checkpoints, so part of its IFS<VFS gap comes from how the metrics are built [@chen2025iwr, p. 7].
  - Visual scores come from different instruments: OCR+DINO+MLLM rubric, VLM assertions, Borda ranks and CLIP.
  - Functional scores also differ: action replay, accessibility tests and navigation tests.
- **Possible explanation** [I]: bai2026recreationworld and chen2025iwr are only *directionally consistent* on one point: static structure is reproduced more easily than interaction logic. The broader claim "visual fidelity systematically exceeds functional fidelity" is not supported, because the visual and functional scales are not commensurable across or within papers.

### C6. Multi-agent / agentic frameworks: MetaGPT fails in liu2026benchmarking but leads in mock2026vibe
- **Side A** [V]: MetaGPT nearly always fails on E2EDev (0–5.4% Req.Acc) [@liu2026benchmarking, p. 6]. Multi-agent frameworks "do not consistently improve" over a plain LLM (by our count, 9 of 24 cells higher [I]) [@liu2026benchmarking, p. 6].
- **Side B** [V]: Agentic MetaGPT X runs had the highest test pass rate (mean 94.58%) [@mock2026vibe, p. 25; @mock2026vibe, p. 41]. zhu2026understanding generated complete multi-file apps with MetaGPT, but only after adding explicit modularity prompts [@zhu2026understanding, p. 5].
- **Differences**:
  - Task size: a two-function string task [@mock2026vibe, p. 12] vs 46 multi-requirement web apps.
  - Backbone: GPT-5 and Claude Sonnet 4 [@mock2026vibe, p. 17] vs older or smaller backbones such as GPT-4o and Qwen2.5 [@liu2026benchmarking, p. 5].
  - Product: MetaGPT X web interface vs the open-source framework.
  - Evaluation: 12 runs pooled vs 46 projects x 3 runs.
- **Possible explanation** [I]: framework value depends on the backbone and the task scale. mock2026vibe's agentic advantage is confounded with the newer model generation.

### C7. Security of generated code: pan2026functional vs zhao2025vibe
- **Side A** [V]: Reference-normalised security averages 87.40% and is the strongest non-functional dimension [@pan2026functional, p. 6].
- **Side B** [V]: 79.3% of the functionally correct solutions of the best agent fail targeted security tests, and SecPass is only 3.8–12.9% [@zhao2025vibe, p. 6].
- **Differences**: pan2026functional counts high-risk static findings relative to the reference, and the score can reward incomplete code. zhao2025vibe runs 3.5 targeted security tests per task for a known historical CWE [@zhao2025vibe, p. 5]. The tasks also differ: whole-repository generation vs security-sensitive feature patches.
- **Possible explanation** [I]: the two instruments measure different things, a static absence of flagged patterns vs exploit-relevant behaviour. "Secure" cannot be compared across them.

### C8. More code or less code? Rebuilds are smaller, but assisted development adds code
- **Side A** [V]: Reconstructions are much smaller than their references. In bai2026recreationworld they are 89.4% smaller with 92.3% fewer files (4 of 10 models; desktop and Android only) [@bai2026recreationworld, p. 15]. In yang2026programbench they are shorter (median 1,173 vs 3,068 lines) and use fewer files [@yang2026programbench, p. 9].
- **Side B** [V]:
  - Cursor adoption raises lines added by +281.3% in month 1 [@he2026speed, p. 8].
  - AI-assisted Task 1 code produced outliers of up to 10,788 lines [@borg2026echoes, p. 30].
  - In MetaGPT apps, architectural smell counts track code size (ρ = 0.94) [@zhu2026understanding, p. 8].
  - The visual-fidelity leader writes 1,441 LoC vs 668 for GPT-5 [@wu2026looks, p. 7].
- **Differences**: rebuilds from scratch scored against a behavioural oracle of a mature original, vs incremental additions to existing projects or apps generated from a spec.
- **Possible explanation** [I]: reconstructions under-implement the original, which is consistent with low full-pass rates. Assisted development adds volume. Size therefore carries opposite signals in the two settings, and size-driven quality metrics (smell counts, totals) must be normalised before comparison.

### C9. Apparent disagreements that come from different constructs (do not pool)
- **"Vibe coding" means different things** [V]:
  - fawzy2026vibe: natural-language prompting plus re-prompting with minimal review [@fawzy2026vibe, p. 1].
  - asdaque2026novice: a supervised agent workflow, operationalised as opening agentic PRs [@asdaque2026novice, p. 1]. Its authors warn that the findings may not hold under a broader definition [@asdaque2026novice, p. 4].
  - mock2026vibe: human-written TDD tests plus scripted prompts that participants could not modify [@mock2026vibe, p. 15].
  - he2026speed: Cursor configuration files committed to a repository (intent-to-treat) [@he2026speed, p. 4].
  - ehsani2026faster: a driver of fast-integration debt in mostly grey sources [@ehsani2026faster, p. 17].
  - [I] These are different interventions. Their results should not be pooled as "effects of vibe coding".
- **Fidelity scores are not comparable** [V]:
  - 58.06% average of programmatic and VLM channels [@bai2026recreationworld, p. 11].
  - 36.35 Final Score (0.7 IFS + 0.3 VFS) [@chen2025iwr, p. 8].
  - 49.15% cumulative workflows [@kim2026programdistill, p. 11].
  - 53.75% Req.Acc with `data-testid` anchors [@liu2026benchmarking, p. 6].
  - 27.8% UI-agent accuracy with half credit for PARTIAL [@lu2025webgen, p. 8].
  - 61.77% workflows passing at ≥90% of substeps [@tran2026vibe, p. 6].
  - 0% resolved / 3% almost [@yang2026programbench, p. 6].
  - [I] Each figure uses a different oracle, input, application type and model generation. Do not rank across them.

### C10. Same model family builds or judges the benchmark and is evaluated (possible bias; untested)
- **Overlap and the same family wins** [V]:
  - yang2026programbench: Claude Sonnet 4.5 wrote the tests [@yang2026programbench, p. 3], and Claude models top the leaderboard [@yang2026programbench, p. 31].
  - tran2026vibe: GPT-5 drafted the specs [@tran2026vibe, p. 3], and GPT-5.3-Codex ranks first [@tran2026vibe, p. 6]. The canonical judge is Claude Sonnet 4.5 [@tran2026vibe, p. 4].
  - kim2026programdistill: GPT-5.6 Sol builds the tasks [@kim2026programdistill, p. 2], GPT-6 Astra ranks first [@kim2026programdistill, p. 8], and GPT-6 Astra also classifies the failures [@kim2026programdistill, p. 12].
  - zhao2025vibe: Claude 4 Sonnet runs the environment-building agent [@zhao2025vibe, p. 17], and SWE-agent constructs the tasks [@zhao2025vibe, p. 4]. The best setting is SWE-agent + Claude 4 Sonnet [@zhao2025vibe, p. 7].
- **Overlap without a visible advantage** [V]:
  - liu2026benchmarking: GPT-4o built the annotations and is evaluated [@liu2026benchmarking, p. 13]; the best backbone is Claude-Haiku.
  - lu2025webgen: GPT-4o wrote the test cases and scored low [@lu2025webgen, p. 8].
  - bai2026recreationworld: the Qwen3.7-Plus judge is the lowest-scoring model (average 9.15) [@bai2026recreationworld, p. 11].
  - chen2025iwr: the Gemini-2.5-Pro judge ranks mid-table [@chen2025iwr, p. 7].
  - wu2026looks: the judge is Gemini 2.5 Pro, Opus leads [@wu2026looks, p. 13], and the authors report no self-preference [A].
- [I] No paper tests construction-model or judge-model self-preference directly. The pattern is a validity threat, not a demonstrated bias.

## Agreements / converging evidence

- **G-A1. Whole-application functional fidelity is far from complete** [V]. Every benchmark agrees:
  - Full behavioural equivalence: 2.8% of apps [@bai2026recreationworld, p. 11] and 0 of 200 programs [@yang2026programbench, p. 6].
  - Best workflow-level or requirement-level pass rates: 49–62% [@kim2026programdistill, p. 11; @liu2026benchmarking, p. 6; @tran2026vibe, p. 6].
  - Lower still in some benchmarks: IFS <25 [@chen2025iwr, p. 8], <45% [@pan2026functional, p. 5], 27.8% [@lu2025webgen, p. 8].
  - Strength [I]: **moderate**. The direction is consistent across 8 independent benchmarks, but 5 of them are preprints and most use single runs.
- **G-A2. Behaviour and interaction are harder than static structure** [V]:
  - Structure beats actions [@bai2026recreationworld, p. 16].
  - Static tasks score higher than interactive ones [@chen2025iwr, p. 16].
  - Interactive parts score lower than full pages [@xiao2025benchmarking, p. 6].
  - UI plus logic is harder than logic alone [@kim2026programdistill, p. 38].
  - "Click has no effect" is the largest navigation failure category (48.4%) [@wu2026looks, p. 8].
  - Strength [I]: **moderate**, with the measurement caveat in C5.
- **G-A3. Fidelity falls as dependency depth, size or complexity rise** [V]: [@kim2026programdistill, p. 8; @yang2026programbench, p. 31; @tran2026vibe, p. 6; @zhao2025vibe, p. 14]. Strength [I]: **moderate**.
- **G-A4. Functional correctness and other quality dimensions diverge** [V]:
  - Best static quality but lowest Pass@1 [@molison2025llm, p. 8].
  - Correct but insecure [@zhao2025vibe, p. 6].
  - Equal functional scores but very different non-functional scores [@pan2026functional, p. 5].
  - The visual leader is not the maintainability leader [@wu2026looks, p. 7].
  - Authors state that passing functional tests does not imply maintainable code [A] [@tran2026vibe, p. 9].
  - Strength [I]: **moderate**. The pattern is consistent, but each study measures a different second dimension.
- **G-A5. Rebuilt code is structurally simpler and more monolithic than the original** [V]: [@bai2026recreationworld, p. 15; @yang2026programbench, p. 9]. Strength [I]: **weak**. It rests on 2 preprints, selected subsets and size proxies only.
