# Novelty check: security fidelity of AI-reconstructed applications

- Project: 2026-11-11-ai-reverse-engineering-vibe-coding
- Date of check: 2026-11-12
- Proposed topic (from the user): when an LLM agent rebuilds an application from its observable artefacts (UI, screenshots, interaction behaviour, a running reference), are the original's security controls (authentication, authorization / access control, input validation, session handling, CSRF/XSS protection, secrets handling) preserved, dropped, or are new vulnerabilities introduced?
- Type of document: novelty check for a *proposed new topic*, not a full gap report. Papers outside the project are cited as plain references with identifiers retrieved on the check date. They have **not** been analysed in full; statements about them come from their abstracts or from the specific sections we fetched, and are labelled [A] (author claim) unless stated otherwise. Papers inside the project are cited in pandoc style with their project key and page.

Labels: [V] verified in the paper's own text/data, [A] author claim, [I] our interpretation.

## 1. Verdict

**Partially novel, with a clearly defensible novel core.** [I]

- *Already done (not novel):* measuring the **absolute** security of code or whole apps generated by LLMs/agents from a natural-language specification (many benchmarks with exploits or security tests; real-world audits of vibe-coded apps). Also done: SAST scans of programs that agents **rebuilt from behaviour**, but only for command-line tools, only with static scanners, and **without comparing against the original program** (Rajput et al. 2026, see §3).
- *Done in a neighbouring setting:* measuring whether security is **preserved or degraded relative to an original** when an LLM **translates source code** to another language (Chang et al. 2026). There the model sees the original source code.
- *Novel core (we found no study that does this; searches on 2026-11-12):* a **differential, reference-anchored** security evaluation of applications that agents rebuild from **observable behaviour only** (UI, screenshots, interaction traces, live black-box access). The evaluation asks which of the original's security controls survive, which are dropped, and which new weaknesses appear. It uses dynamic security-property tests and exploits that run against **both** the original and the rebuild, not only static scanners. It targets multi-user web applications with real authentication and authorization logic.
- Confidence in the novelty claim: **moderate**. The field moves monthly (several close papers appeared between June and November 2026). Semantic Scholar was rate-limited (HTTP 429) and Google Scholar was not queried directly. Re-run the check before submission.

## 2. Why the topic matters (evidence from the analysed papers)

- [V] Reconstruction from a running reference is an active research setting. In RecreationWorld, agents receive only a running reference application and must build a faithful reimplementation; the reference serves as the oracle for hidden tests [@bai2026recreationworld, p. 1; @bai2026recreationworld, p. 3]. Evaluation there is purely functional (programmatic assertions) and visual (VLM judge) [@bai2026recreationworld, p. 11]. No security dimension is scored. [I] The ProgramBench and IWR-Bench reconstruction settings likewise score behaviour and appearance only [@yang2026programbench, p. 1; @chen2025iwr, p. 7].
- [V] Rebuilds are much smaller than their references: 89.4% have less production source code, with a median LOC ratio of 16.9% [@bai2026recreationworld, p. 15-16]. [I] Code that is not reproduced can include security checks. Whether the missing code is disproportionately security logic is exactly what has not been measured.
- [V] Functional correctness and security diverge for agent-written code. In SusVibes, 79.3% of the functionally correct solutions of the best setting were insecure [@zhao2025vibe, p. 6]. Each task is checked by only about 3.5 security tests on average, aimed at one historical vulnerability [@zhao2025vibe, p. 5]. SusVibes' task design masks an existing implementation and asks an agent to re-implement it from a description [@zhao2025vibe, p. 4]. [I] This is reconstruction from a *specification*, not from observed behaviour.
- [V] The one in-project study that scores security *relative to a reference implementation* is RAL-Bench. It uses only counts of high-risk static-analysis findings in the generated vs the reference code [@pan2026functional, p. 3]. [V] GPT-3.5-Turbo gets a 97.37 security score with only 29.76 functional score [@pan2026functional, p. 6]. [I] Static, count-based scores can therefore reward incomplete code: less code means fewer findings. A new study must control for this.
- [A] Grey literature reports vibe-coded apps that "lacked authentication, authorization, or contained hardcoded secrets" [@fawzy2026vibe, p. 9]. [V] Vibe Code Bench explicitly does not measure security vulnerabilities [@tran2026vibe, p. 9]. [V] In Vibe Code Bench, 14.8% of failures were "Validation or Policy Block" errors, in which the agent blocks actions that should be allowed. The most common variant is misconfigured Row-Level Security policies [@tran2026vibe, p. 8]. [I] So rebuilt access control can also fail in the over-restrictive direction. A preservation metric must capture both directions.
- [V] Behavioural properties can be recovered from a running app by an LLM. An LLM given only an app description produced 0 valid properties, while runtime-grounded generation produced 92.6% valid ones [@xiong2026propgen, p. 8-9]. [I] This suggests a feasible way to derive security-property tests from the original's observed behaviour.

## 5. Sharpened topic (maximise novelty and publishability)

**Working title [I]:** *"Rebuilding What You Cannot See: Security-Control Preservation in Black-Box AI Reconstruction of Web Applications."*

Core idea [I]: many security controls are **not observable** from the UI. Examples are server-side object-level authorization, CSRF-token checks, password hashing, rate limiting and cookie flags. Others are visible, such as login forms and "permission denied" pages. Hypothesis: agents preserve visible controls and drop invisible ones, so a rebuild can be functionally faithful but less secure than the original. We call this the *security-observability gap*. This framing:
1. differs from absolute-security benchmarks (BaxBench, DualGauge, SusVibes, Last Secure Code Benchmark) because the **original is the oracle**;
2. differs from code-translation security (Chang 2026) because the agent has **no source access**;
3. differs from Rajput 2026 because it uses **dynamic, exploit-validated, reference-differential** tests on **multi-user web apps**;
4. connects to the A.S.E 2.0 mechanism (unseen safeguards are not reproduced) and to RecreationWorld's finding that rebuilds are far smaller [@bai2026recreationworld, p. 15-16].

Suggested research questions:

- **RQ1 (preservation):** What share of an original web application's security controls (authentication, authorization including object-level, session management, CSRF, output encoding / input validation, secrets and credential storage) are preserved by agent rebuilds made from observable artefacts? Preservation is measured by a security-property test suite that passes on the original and is run unchanged on the rebuild, scoring both missing and over-restrictive controls.
- **RQ2 (observability and input modality):** Does preservation depend on how observable a control is (UI-visible vs server-side-only) and on what the agent is given? Conditions: (a) screenshots plus a flow description, (b) recorded interaction traces, (c) live black-box access with two test accounts, (d) control: source-visible rewrite. Is preservation predicted by functional fidelity?
- **RQ3 (regression):** Which vulnerabilities does the rebuild contain that the original does not, after size normalisation and manual/exploit confirmation? Does a cheap mitigation reduce the gap? Candidates: a security-aware instruction, or a "security probing" step in which the agent explores the original as an unauthenticated user and as a second user.

## 6. Feasible study design for a beginner [I]

- **Apps (6-10).** Small-to-medium, open-source, permissively licensed web apps with multi-user roles and clear ownership rules, deployable with Docker. Candidate families to verify: apps implementing the RealWorld "Conduit" specification (articles owned by users; only the author may edit or delete), and small Django/Flask/Express multi-user apps such as bookmark, notes or todo managers. Prefer some apps released after the models' training cutoff, or less-known apps, to limit memorisation. Check licences first. Exclude deliberately vulnerable apps (e.g. OWASP Juice Shop) from the main set; one may serve as a sanity check that the test suite detects missing controls.
- **Security-property suite per app (about 20-40 tests).** Written once against the original with Playwright/pytest + HTTP requests. Examples: protected routes reject unauthenticated access; user B cannot read, edit or delete user A's objects (IDOR/BOLA); admin-only actions are refused for normal users; state-changing requests without a CSRF token fail; session cookie has HttpOnly/SameSite (and Secure if served over TLS); logout invalidates the session; passwords are not stored in plaintext (inspect the DB); an XSS payload in a text field is rendered escaped; an SQL-injection payload does not change query results. **Every test must pass on the original** (oracle validation, as in RecreationWorld's reference-validated tests [@bai2026recreationworld, p. 3]). Tag each test *UI-visible* or *server-side-only* before running agents (pre-registered).
- **Functional suite.** End-to-end user flows (Playwright) validated on the original, so security can be read conditional on functional fidelity.
- **Agents and runs.** 2-3 agent harnesses (e.g. Claude Code, Codex CLI, OpenHands) × 1-2 models, conditions (a)-(c) plus (d) as a control, **3 runs** per cell for variance. Record the harness, because harness and model are entangled otherwise [@bai2026recreationworld, p. 28]. Run in isolated containers without internet, so the agent cannot download the original source (RecreationWorld observed shortcut attempts [@bai2026recreationworld, p. 13]). Also measure exact-line overlap with the original as a contamination check, as in [@bai2026recreationworld, p. 18].
- **Metrics.** (1) Security Control Preservation Rate = passed security tests / tests applicable to features the rebuild actually implements. Also report the unconditional rate, so that missing features are not counted as "secure". (2) Over-restriction rate: functional actions wrongly blocked. (3) New-vulnerability count from Semgrep + CodeQL diffs (rebuild minus original), per KLOC, manually triaged. (4) OWASP ZAP authenticated scan alerts on both versions. (5) Exploit-confirmed vulnerabilities. (6) Functional pass rate.
- **Analysis.** Per-category preservation with Wilson 95% CIs. Mixed-effects logistic regression: `preserved ~ observability + condition + harness + (1|app) + (1|test)`. McNemar / paired tests between conditions on the same tests. Spearman correlation between functional fidelity and preservation. Size-normalised comparison (do not use raw finding counts; see the RAL-Bench issue [@pan2026functional, p. 6]).
- **Main validity threats.** (i) Oracle validity: tests written by the researcher may favour some implementations, so phrase them through the external HTTP/UI surface, not internal code. (ii) SAST noise: SonarQube found no vulnerabilities at all in one in-project study [@molison2025llm, p. 5], and Rajput et al. report low cross-tool agreement, so rely on dynamic tests and treat SAST as secondary. (iii) Contamination of popular apps. (iv) Small N of apps, so report per-app results. (v) Rebuild incompleteness confounds security, which is handled by the conditional metric. (vi) Model and harness drift over time, so record versions and dates.
- **Feasibility: moderate.** It needs Docker, Playwright, basic web security knowledge (OWASP Top 10 / ASVS) and an API budget. Per-task cost for small web apps is unknown. RecreationWorld reports $41-$91 per task, but for long desktop runs [@bai2026recreationworld, p. 11], so pilot with 2 apps first. Expected workload: about 1-2 days per app to build and validate the security suite.

## 7. Ethics and dual use [I]

- **Risk.** Better app cloning can help attackers build look-alike phishing apps. LLMs already produce working credential-harvesting pages in a share of cases (PhishGen, arXiv 2610.30226, [A] 38.7%). Clones can also infringe copyright or terms of service.
- **Defensive framing.** Present the study as *assurance for legitimate reconstruction*: legacy modernisation, migration of one's own apps, re-platforming, and benchmark design. The message is "AI rebuilds silently drop invisible security controls; here is how to test for it". The contribution is a differential security test method and a mitigation, not a better cloner.
- **Safeguards.** Only open-source apps with licences that permit modification. Run everything locally in isolated containers; never target live third-party sites or commercial apps. Use no real user data or credentials. Do not release prompts or tooling optimised for cloning proprietary apps. If tests reveal vulnerabilities in the *original* projects, disclose them responsibly to the maintainers before publication. Add an ethics section (many security venues require one). No human subjects are involved unless a user study is added.
