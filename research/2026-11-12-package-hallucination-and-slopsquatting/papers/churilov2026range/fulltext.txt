  The Range Shrinks, the Threat Remains: Re-evaluating LLM
   Package Hallucinations on the 2026 Frontier-Model Cohort
                 Aleksandr Churilov · Independent Researcher · churik0509@gmail.com

                                                   Abstract
      Package hallucinations, LLM-generated references to packages that do not exist, enable slopsquatting:
      an attacker registers the hallucinated name. We replicate Spracklen et al. (USENIX Security ’25) on
      five 2026 frontier models over 199,840 Python and JavaScript generations. This version reports a
      preregistered live revalidation that replaces the static package lists of earlier versions with two
      independent checks against the live PyPI and npm registries. Hallucination rates are 3.6–5.0% of
      package mentions (2.2–3.4% of generations): the 2026 frontier sits at the level of 2024’s commercial
      models, and the open-weight gap seen in 2024 has disappeared. Python exceeds JavaScript for every
      model. The set of names hallucinated by all five models shrinks from the 127 reported earlier to 104;
      26 earlier entries were correct import statements whose module name differs from the package name.
      Using the accidental six-month public exposure of our own list as a natural experiment, we find no
      detectable effect of publication: about 1% of hallucinated names were registered within six months, at
      the same rate for published and unpublished names, and the 95% interval excludes increases above
      2.5 percentage points. Still, at least 23 package names that the models suggest had previously hosted
      malware later removed by the registries, and one hallucinated name was registered with malware after
      our runs.

Version 4 (November 2026). This version replaces the validation of earlier versions (static package lists) with
a preregistered live revalidation, and it supersedes all numbers in versions 1–3 and in the SCORED ’26

1 Introduction
Modern software development depends on centralized package registries: PyPI for Python and npm for
JavaScript host millions of packages installable with a single command. Code-generating large language
models have added a new actor to this supply chain. When a developer asks an LLM for code, the model often
emits pip install or npm install directives, or import statements that name particular packages. If
the developer trusts the suggestion and installs the named package, an attacker who has registered a malicious
package under that name succeeds without ever interacting with the developer or the LLM provider.
Spracklen et al. [1] characterized this risk on the 2024 model cohort, generating 576,000 code samples across
16 models. Hallucinated package references averaged 5.2% for commercial models and 21.7% for open-source
models, and the authors identified 205,474 unique hallucinated package names. The resulting attack is now
called slopsquatting [18]: registering malicious packages under names that LLMs have, by their hallucination
behavior, primed developers to install.
Two model generations later, Anthropic, OpenAI, Google and DeepSeek have released code-capable models
with larger training sets, broader safety post-training and, in several cases, reasoning-effort controls. We
measure whether package hallucination has changed with them.
We report five findings. First, the 2026 frontier sits at the level of 2024’s best commercial models: per-model
rates range from 3.63% to 5.02% of package mentions, between the lowest rate Spracklen et al. report for any
model (3.59%, GPT-4 Turbo) and their commercial average (5.2%), and the open-weight model in our cohort
is no longer an outlier. Second, 104 package names (88 PyPI, 16 npm) are hallucinated by all five models.
Third, Python rates exceed JavaScript rates for every model, the reverse of the 2024 pattern. Fourth, within the

2 Background and Related Work
2.1 Package Confusion Attacks
Package confusion attacks predate LLM-generated code by more than a decade. Typosquatting registers
packages under names one or two edits away from a legitimate package, exploiting developer typos at install
time; Neupane et al. [14] catalog thousands of such attacks on PyPI and npm. Birsan’s 2021 dependency-
confusion disclosure [15] showed that internal package names, shadowed on a public registry, can be silently
substituted by the package manager. Slopsquatting [18] is the LLM-induced variant: instead of waiting for a
typo or a name leak, the adversary registers names that the LLM itself has primed developers to type. This
paper continues the measurement line of [1] on the size of the attack surface that current LLMs create.

2.2 Hallucinations in Code-Generating LLMs
LLM hallucination has been studied extensively for natural-language output [16, 17]. Code-generation
hallucination is a security-relevant special case: the model emits syntactically plausible but wrong tokens, and
when those tokens are package names they become an installation request rather than a textual claim. Pearce et
al. [13] established the underlying pattern for vulnerable code generated by GitHub Copilot. Related work [20]
extends the package-hallucination measurement to more models. The present paper is a temporal replication: it
runs the same prompts on newer models in order to compare them with the 2024 baseline.

2.3 The Spracklen Baseline
Spracklen et al. [1] is the baseline for this work. They evaluated 16 LLMs released between mid-2023 and
mid-2024 on two prompt datasets, 576,000 generations in total. Hallucination rates averaged 5.2% for
commercial and 21.7% for open-source models; the lowest per-model rate was 3.59% (GPT-4 Turbo). They
identified 205,474 unique hallucinated names and characterized them by repeatability, similarity to real
packages, persistence across temperatures and recurrence across models. Their public artifact [19] contains the
two prompt datasets, package-name lists for PyPI and npm, and the extraction and validation code. Earlier
versions of this paper validated names against those lists; this version validates against the live registries
(§4.5).

2.4 Concurrent and Subsequent Work
Importing Phantoms [20] reports comparable rates on a partially overlapping model set. Industry monitoring
services have published rate measurements in 2025–2026 [18]. Spracklen, Aghazadeh, Koushanfar and
Jadliwala [21] suppress package hallucinations with adaptive unlearning; their method uses the registry as an
oracle that labels names as valid or hallucinated, and they note that an attacker who pre-registers hallucinated
names inverts that signal (“oracle poisoning”). Section 8 estimates how often that precondition occurs in
practice. Spracklen et al. [1] already measured how often the same hallucinated name recurs across models in
their cohort and found that 81% of distinct hallucinated names came from a single model; we report the
intersection across all five 2026 frontier models and its registrability as assessed by PyPI Security and Socket.

3 Threat Model
We adopt the threat model of Spracklen et al. [1]. The adversary is an unprivileged actor whose only required
capability is registering packages on PyPI and npm. Anyone with an email address can do this, and neither
registry reviews first-time uploads. The adversary’s goal is to publish a malicious package under a name that
one or more frontier LLMs are likely enough to hallucinate that developers, prompted with similar queries,
will install it. The attack chain (Figure 1) has six stages:
  1.    the adversary samples one or more LLMs and identifies hallucinated package names;
  2.    the adversary registers a malicious package on PyPI or npm under each such name;
  3.    later, a victim developer issues a code-generation query to the same or a related LLM;
  4.    the LLM generates code that references the hallucinated name;
  5.    the developer’s package manager, trusting the registry, installs the adversary’s package;
  6.    the malicious code executes in the developer’s environment.
We assume no compromise of the LLM provider, no fine-tuning by the adversary, no privileged access to user
systems, and no involvement of the registries beyond their public interfaces. Uploads are free, so the
adversary’s only cost is the LLM API spend needed to enumerate hallucinations; our pipeline’s own cost
estimate (Appendix A) puts it at about $1,160 for a sweep of comparable scope.
The universal-hallucination set of §6 strengthens the adversary’s position: one registered name can target users
of several providers at once, since 104 names in our data are hallucinated by all five models. Whether a name
can actually be registered depends on each registry’s own rules (§6).

4.2 Prompt Datasets
We re-use the two prompt datasets released by Spracklen et al. [1] without modification: 20,163 programming
questions drawn from Stack Overflow (subsets SO_AT and SO_LY) and 19,806 LLM-synthesized questions
(subsets LLM_AT and LLM_LY), each split evenly between Python and JavaScript. We generate one sample
per prompt per model. The stored corpus has 199,840 generations: 39,969 for each model except Claude
Sonnet 4.6, for which five generations are missing (Appendix A). We add no new 2026 prompts, so that the
corpus matches Spracklen’s exactly and the comparison is direct. We discuss the resulting training-data
leakage concern in §10.

4.3 Generation Configuration
For each model we record the API endpoint, the snapshot identifier returned in the response metadata, the
temperature, the top-p value and, where available, the reasoning-effort setting. Defaults were used unless
noted. GPT-5.4-mini was run with reasoning_effort set to minimal, a choice made for cost reasons and

=== [PDF page 5] ===

discussed as a confounder in §10. Neither Anthropic model was queried with extended thinking: our client
code passes no thinking parameter on either the synchronous or the batch path. Snapshot identifiers are listed
in Table 1.

4.4 Package Extraction
We extract package references in two ways. Install commands are matched by regular expressions: pip
install anywhere in a response (first argument only) and npm install inside code blocks. Import
statements are parsed from the code (Python’s ast module; tree-sitter for JavaScript), and Python sub-imports
are resolved to the top-level module. Scoped npm names ( @scope/name) are kept whole. Other install
forms (requirements files, uv, poetry, yarn, pnpm) are not extracted (§10). We follow Spracklen’s
extraction approach and inherit its known false-positive behavior; §4.6 removes the classes of false positives
we could identify.

4.5 Validation Against the Live Registries
Earlier versions judged a name hallucinated if it was absent from the package-name lists shipped with the
Spracklen artifact. Those lists predate our runs, so names registered in between were miscounted (§7). This
version checks every candidate name against the live registries, with two methods per registry: for PyPI, the
JSON API and the Simple API (PEP 691); for npm, the registry document and the deps.dev package API [24].
Every response is stored in an append-only log with its status code, a hash of its body and a UTC timestamp. A
response of 200 counts as EXISTS and 404 as ABSENT; anything else (rate limiting, server errors, timeouts)
counts as UNKNOWN. A name is finally ABSENT only if both methods return ABSENT in two rounds at
least 12 hours apart (round 1: November 7, 2026, 11:53–13:14 UTC; round 2: November 8, 10:16–11:22
UTC); if the methods disagree, the name is UNKNOWN. Requests were limited to one per second per host.
The two rounds made 14,821 requests without a single rate-limit or server error.
Hallucination is judged as of the moment of generation, not as of today. For each existing package we record
its creation time (npm: time.created; PyPI: the earliest file upload) and compare it with the generation
time of the name: the generation’s own timestamp or, for batch requests, the window between batch
submission and completion. A name whose package existed before generation is a false positive; a name
whose package was created after generation is a hallucination that was registered later (§8); a creation time
inside a batch window makes the name UNKNOWN. We also query OSV [23] for malicious-package records
and keep npm security-holding placeholders, unpublished npm packages and PyPI projects without files as
separate categories.

4.6 Exclusions
Before the live checks we remove four classes of names that are not package hallucinations; Table 7 counts
each class.
  1.    Extraction noise. One noise filter, published with the code, removes syntactic prefixes ( package:,
        dart:, node:), path aliases, template placeholders and path fragments.
  2.    Standard-library and built-in modules: the union of sys.stdlib_module_names for Python
        3.10–3.13 and the built-in module lists of Node.js 18, 20 and 22. No hallucination candidate of earlier
        versions matched this rule, so standard-library names do not inflate our rates.
  3.    Names that the registry would reject, under PEP 508 for PyPI and npm’s naming rules for new
        packages (for example, names containing whitespace or line breaks).
  4.    Import names of real packages. A Python name extracted only from import statements is not a
        hallucination if the pipreqs import-to-package mapping [22] maps it to a distribution that exists: the

=== [PDF page 6] ===

        code is correct, and only the module name differs from the package name. A name that appears at
        least once as an install target stays a candidate, because installing it fetches whatever is registered
        under that exact name.

4.7 Rates and Statistical Analysis
We report two rates. The mention-level rate is the share of extracted package references that are hallucinated; it
matches the unit of Spracklen et al. and of earlier versions. The generation-level rate is the share of all
generations of a model that contain at least one hallucinated reference; this is the rate named in our
preregistration. Both come with 95% Wilson confidence intervals [8, 11]. We compare models pairwise with a
Pearson χ² test on each 2×2 table [9], with Holm–Bonferroni correction [10] across the 10 pairs at α = 0.05,
and confirm each pair with a permutation test (10,000 resamples, seed 42). Overlap of the unique hallucinated
names of two models is measured by Jaccard similarity.

4.8 Refusals
A generation is a refusal if the model declined or returned no usable code (an empty or “none” response).
Refusal rates range from 1.27% (Claude Haiku 4.5) to 31.51% (GPT-5.4-mini at minimal reasoning effort).
Refusals contain no package references: they do not enter the mention-level rate but lower the generation-level
rate. We discuss the consequences in §10.

4.9 Preregistration
The revalidation and the registration analysis of §8 follow a plan committed to the project repository on
November 7, 2026, before any live registry check (commit 686f648 in our private repository; the plan file’s
SHA-256, 18067fe7…c608, can be checked against the copy in the public artifact). The plan fixes the
definitions above, the groups and the primary test of §8, and it was not edited afterwards. Every later change is
recorded with its date and reason in a deviation log of 20 entries. Thirteen were written before the first live
check (T0 = November 7, 2026, 11:44 UTC); among them are the import-name rule of §4.6 and the batch-
window rule of §4.5. Six were written after T0 but before any group-level result was seen: the handling of npm
placeholders and unpublished packages, a category for PyPI projects without files, the registry naming rules,
the handling of removed malicious packages, and the use of arXiv submission times as exposure dates. One
entry records a safety check made after the analysis (§8.5). The repository was local, so the commit times are
self-attested; the plan, the log and the commit history are published with the artifact (§11.3).

5 Results
5.1 Headline Rates
Per-model mention-level rates range from 3.63% (Claude Haiku 4.5) to 5.02% (GPT-5.4-mini) (Figure 2a). All
five lie between the lowest rate Spracklen et al. report for any model (3.59%, GPT-4 Turbo) and their
commercial-model average (5.2%); the best 2026 model is practically level with the best 2024 model. Seven of
the ten pairwise differences are significant after Holm–Bonferroni correction (Table 4), and the models fall
into three tiers: Claude Haiku 4.5; Claude Sonnet 4.6; and a cluster of Gemini 2.5 Pro (4.77%), DeepSeek V3.2
(4.80%) and GPT-5.4-mini (5.02%) whose mutual differences are not significant. At the generation level
(Figure 2b) rates range from 2.15% (GPT-5.4-mini) to 3.39% (Gemini 2.5 Pro), and 8 of 10 pairs differ
significantly. The order changes mainly because GPT-5.4-mini refuses 31.51% of prompts, and refusals lower
the generation-level rate.

5.5 The Haiku-below-Sonnet Inversion
Claude Haiku 4.5 hallucinates less than Claude Sonnet 4.6 at both levels (3.63% vs 4.09% of mentions, Holm-
corrected p = 0.012; 2.34% vs 2.75% of generations), contrary to Spracklen’s observation that smaller models
within a family tend to hallucinate more. Earlier versions explained the inversion in part by Haiku 4.5 having
been queried with extended thinking. We withdraw that explanation: our client code passes no thinking
parameter to either model (§4.3). Differences in post-training between the two models remain a possible cause
that we cannot test. The low overlap between the two models (J = 0.176) suggests that they make different
errors rather than one making a subset of the other’s; we have no mechanism for the inversion.

names and says little. This version prints no other universal name. Earlier versions printed 18 names from their
universal list, 13 of which remain in the current set; those names are therefore public, and we do not repeat or
extend the list.

6 Universal Hallucinations as a Model-Agnostic Attack Vector
The universal-hallucination set contains the names that all five models invent. We define it as the intersection
of the per-model sets of names that were hallucinations at generation time, after the exclusions of §4.6. It
contains 104 names (88 PyPI, 16 npm), which account for 2,699 hallucinated mentions across the five models.
In April 2026 we disclosed the earlier, larger list to PyPI Security and to Socket.dev and asked which names an
outsider could actually register (§11.1). Socket’s review of the 18 npm names found six non-exploitable: the
four @ember/* names, which are Ember.js virtual modules in a scope owned by the Ember organization; one
already-published package; and one npm security-holding placeholder. Our revalidation independently
classifies the last two as false positives, so the 16 npm names of the current set are Socket’s 12 registrable
candidates plus the four @ember/* names. On the PyPI side, PyPI Security reported that its prohibited-name
list and normalization rules left 41 of the disclosed names registrable, without listing which. Because the PyPI
part of the set has changed (§7), we do not re-estimate PyPI registrability; we have asked PyPI Security for the
list.
Universal names carry a risk that no single-model rate shows. By studying all five models, an attacker finds
names that reach users of several providers: a single registration of a registrable universal name would be
installed regardless of which of the five models the victim uses.

=== [PDF page 10] ===

We suggest two non-exclusive mechanisms by which a name becomes universal. First, shared training data:
tutorials, posts and documentation that refer to a package by a module or informal name instead of its
distribution name become a stable signal across providers, which scrape similar public corpora. Second,
overgeneralized naming conventions: scoped npm names such as @ember/service follow a convention
that models extend to install targets, although Ember ships those modules only inside its main package. Both
mechanisms lead different providers to the same wrong name, so post-training at any one provider does not
remove it.
The DeepSeek V3.2–GPT-5.4-mini Jaccard peak (J = 0.342, §5.4) fits this picture: the shared errors are a small
fraction of any one model’s set overall, but between certain pairs they reach one third. We make no inference
about the direction of any data-sharing relationship.
A single-model measurement therefore understates the slopsquatting attack surface: it cannot tell a name that
one model hallucinates from a name that every comparable model hallucinates. We recommend reporting
cross-cohort intersections as a standard quantity.

8 Do Hallucinated Names Get Registered?
8.1 A Natural Experiment
Our list of universal names became public by mistake on April 30, 2026, one day after we disclosed it to PyPI
Security and Socket (§11.2). It stayed public in our repository and in an open archive until November 7, 2026,
and a third-party fork still holds a copy. Ten names printed in version 1 of this paper were public from May 16,
2026, and further names printed in version 2 from June 11, 2026. All other hallucinated names were never
published. This gives a natural experiment. If publishing hallucinated names attracts registrations, published
names should be registered more often than comparable unpublished ones.
We fixed the design in the preregistration (§4.9) before checking any registry. Group A is the universal set
(104 names), split into A1 (13 names printed in the paper) and A2 (91 names that were only in the list). Group
B contains all other hallucinated names (2,178); its subset B4, the main comparison group, contains the names
in B that exactly four of the five models hallucinate (128). The outcome is registration between the start of
exposure and T0 (November 7, 2026). Exposure starts at the arXiv submission of the first version that printed

=== [PDF page 12] ===

the name (A1) or on April 30, 2026 (A2 and B). The primary test compares A with B4 within common strata
of name frequency and name length, with Fisher’s exact test (two-sided).

8.2 Results
No effect of publication is visible at this precision (Table 8). In the primary comparison, 0 of 87 names in A
and 2 of 101 names in B4 were registered: a difference of −2.0 percentage points (95% CI −6.9 to +2.5; p =
0.50). The interval excludes an increase above 2.5 points. Stratified tests (Cochran–Mantel–Haenszel, p = 0.59
by ecosystem and p = 0.72 by stratum) and all preregistered sensitivity analyses lead to the same conclusion.
With these group sizes, the study could detect only a rise from a 1% baseline to about 10.5%.
Overall, 25 of the 2,282 names that were hallucinations at generation were registered within about six months:
1 of 104 published names (1.0%) and 24 of 2,178 unpublished names (1.1%). The median time from the start
of exposure to registration was 89 days in B (range 13–153); the one registered name in A was registered after
47 days.

8.3 What Was Registered
We classify registered packages from registry metadata only. Of the 24 registrations in B, 22 are published
packages with files whose content we did not inspect; one is an npm security-holding placeholder whose
package carries a malicious-package record published after our runs, so it was registered with malware and
removed by npm; and one is an empty placeholder whose publisher describes it as a name reservation. The
single registration in A, a name printed in version 2 of this paper, is a package with one version; a static check
(§8.5) found it empty. We do not infer intent from registrations: researchers and defenders also reserve names.
For methods that use the registry as an oracle [21], these results mean that the precondition for oracle
poisoning does occur, but rarely: about 1% of hallucinated names were registered within six months, and at
least one registration carried malware.

8.4 Names with a Malware History
Packages registered before our runs matter as well. Thirteen npm names that the models suggest were, at
generation time, npm security-holding placeholders: packages that existed before our runs, carry malicious-
package records in OSV, and were replaced by npm. On PyPI, ten names that the models suggest have OSV
malicious-package records whose identifiers date from before 2026; the packages are gone. In total, at least 23
package names that the models suggest had hosted malware that the registries later removed. Fifteen further
npm names belong to packages that were unpublished, 14 of them before our runs; two of these also have
malicious-package records. Such names are natural slopsquatting targets, because the models still suggest them
after the registries have removed the malware.

8.5 Safety Check
Because the one registered name in group A was printed in this paper, we checked it statically after the
analysis (deviation D19): we downloaded and listed its archive without installing or running it. The archive
contains only a package manifest, with no scripts, no dependencies and no code.

9 Discussion
9.1 Why Has the Range Compressed?
Our five models span 1.39 percentage points (3.63–5.02% of mentions). In 2024 the class averages alone were
5.2% for commercial and 21.7% for open-source models. We propose three contributing causes. First, the gap
between open and closed models that drove the upper end of the 2024 range has closed at the frontier:
DeepSeek V3.2 (4.80%) sits inside the commercial cluster. Second, training-data curation for package
references may be near saturation: the lower end of our range (3.63%) matches Spracklen’s best 2024 model
(3.59%) almost exactly. Third, post-training recipes have converged across providers, reducing behavioral
variance.

9.2 Why Does the Threat Persist?
A rate of 3.6–5.0% keeps slopsquatting economically viable. Even the lowest-rate model produced 1,098
hallucinated mentions over 39,969 prompts, covering 605 unique names. A single popular hallucinated name,
reproduced under similar prompts, yields a steady stream of install attempts once a malicious package is
registered, and registration is free. Section 8 shows that hallucinated names are in fact registered, at least one
with malware, and that names which once hosted malware are still suggested.

9.3 Python Worse Than JavaScript: An Inversion
Spracklen reported JavaScript as the noisier ecosystem, attributing the effect to npm’s larger and more
fragmented namespace. We find the opposite for every 2026 model, with Python exceeding JavaScript by
2.34–3.47 percentage points of mentions. The asymmetry survives the removal of import names of real
packages (§4.6), so it is not an artifact of module-name confusion. One plausible mechanism is that 2026
models have absorbed npm’s flat naming convention more thoroughly than Python’s mix of single-token,
snake_case, dotted and dash-separated names, and of distribution names that differ from module names. With
more ways to combine name parts, a model more often produces a plausible but wrong name.

9.4 Synthesized Prompts Surface More Hallucinations
LLM-synthesized prompts produce higher rates than curated Stack Overflow prompts for every model (Table
3). A cautious reading is that synthetic prompts drift away from the training distribution and reveal failure
modes that organic developer questions do not. Rates measured on curated questions alone are therefore lower
bounds on what deployment will see, and an attacker gets more hallucinated names from synthesized prompts
than from Stack Overflow questions.

9.5 Dependence on Model Selection
We sampled five frontier models, and the compression is conditional on that selection. Models from the next
tier down, such as smaller Qwen, Mistral or older Llama checkpoints still in production, may still show 2024-
like rates. The finding applies to the frontier; we do not claim that the attack surface has narrowed at every
capability tier.

10 Limitations and Threats to Validity
Scope. We evaluate five frontier models; smaller open models, fine-tuned variants and quantized local
checkpoints are out of scope, as are agentic configurations in which retrieval could eliminate hallucinations.
Timing. Generations were collected on April 22–28, 2026, and registries were checked on November 7–8,
2026. Models change opaquely, and our rates describe one point in time.
Leakage. The Spracklen prompt corpus, released in January 2025, may be part of 2026 pretraining data, which
would bias rates downward. We did not run a held-out set of new prompts.
GPT-5.4-mini. It was run at minimal reasoning effort and refused 31.51% of prompts. Refusals do not enter the
mention-level rate but lower the generation-level rate, which is why the two levels rank this model differently.
The compliant responses may not be a random subset of prompts, and we did not sweep reasoning effort.
DeepSeek. DeepSeek does not pin model versions in its public API. The deepseek-chat alias was nominally
V3.2 during our run, but same-window response metadata returned the identifier deepseek-v4-flash; the
underlying model may have changed during or shortly after the run [7].
Run configuration. The generation code in the repository is unchanged since April 28, 2026, but the repository
alone cannot prove that this exact code produced every generation.
Extraction. Install commands are extracted only from pip install (first argument) and from npm
install inside code blocks; other forms are missed, so rates may be underestimated.
Import names. The pipreqs mapping covers about 1,157 common import names. Rarer mismatches between
module and package names are still counted as hallucinations, mostly among names that few models produce.
Creation dates. The PyPI creation date is the earliest visible upload and can be late if files were deleted (no
such case was flagged). Removed malicious packages have no creation date and are UNKNOWN; for them we
use the year in the malicious-package record identifier as an approximate date.
Registrability. It is known only from the review of the earlier list by PyPI Security and Socket in April–May
2026 and was not re-estimated.
Natural experiment. It is small and can detect only large effects; exposure intensity is only partly known (20
downloads of the open archive, one public fork); and registrations by researchers or defenders cannot be told
apart from attacks without inspecting content.
Preregistration. The plan and the deviation log were committed to a local repository, so their timestamps are
self-attested.

11 Ethics and Open Science
11.1 Ethical Considerations
This study produces lists of hallucinated package names that, if registered, could be weaponized into a supply-
chain attack. We followed a stakeholder-based analysis [12] covering developers who receive hallucinated
suggestions, the LLM providers, the PyPI and npm maintainers, and downstream users of compromised
software. To minimize harm we (a) registered no names on any registry; (b) disclosed the enumerated
universal list to PyPI Security (security@pypi.org) and to Socket.dev (ticket #2893) on April 29, 2026,
intending a private window before any publication (npm’s security mailbox no longer accepted external
reports, and its support portal redirects registry-level reports to a bug-bounty program unsuited to academic
disclosure); (c) plan to share model-specific results with each provider; (d) in this version print no hallucinated
name that an outsider could register, whereas earlier versions printed a top-10 table and a few examples, which

=== [PDF page 15] ===

are therefore already public; and (e) installed and ran no third-party package, reading registry metadata only,
apart from the static check of §8.5. PyPI Security and Socket reviewed the list (§6). The study used no human
subjects, so IRB review did not apply. The author has no conflicts of interest with the studied providers.

11.2 Accidental Exposure of the List
Our coordinated disclosure did not go as planned. On April 30, 2026, one day after the disclosure, the full
universal list was committed by mistake to a disclosure/ directory of our public artifact repository and
archived in an open Zenodo version, which was downloaded 20 times. We found the mistake on July 23 and
informed Socket; the directory was removed from the current tree in August but remained in the repository
history and in the archive. On November 7, 2026, we removed it from the full history, restricted the archived
files, informed PyPI Security of the exposure and Socket that it had lasted longer than we had reported, and
asked GitHub to remove cached copies. A third-party public fork created on July 26 still contains the list. We
therefore treat the list as public since April 30, 2026. Section 8 uses this exposure as a natural experiment, but
the list was not kept public for that purpose.

11.3 Open Science
The replication code is at https://github.com/churik5/slopsquatting-replication-2026 (MIT license); its history
was rewritten on November 7, 2026, so commit references from earlier versions no longer resolve. The Zenodo
concept DOI 10.5281/zenodo.19859120 resolves to the latest archived version; the files of version v0.2 are
restricted because they contain the list. The revalidation code, the preregistration with its deviation log and
commit       history,  and      all    aggregate    results   of     this    version     are    published     at
https://github.com/churik5/slopsquatting-revalidation-2026. No file in the artifact contains a registrable
hallucinated name. The SQLite database of raw model responses is available to verified researchers on request
via churik0509@gmail.com, mirroring the policy of [1]; earlier versions stated that it had been deposited in an
access-controlled Zenodo record, which was not the case.

12 Conclusion
We replicated Spracklen et al. on five frontier code-generating LLMs released between October 2025 and
March 2026 and revalidated every name against the live registries. The range has shrunk: the five models
hallucinate 3.6–5.0% of package references, at the level of 2024’s best commercial models. Still, 104 names
are hallucinated by all five models, one registration of a registrable name can reach users of all four providers,
and about 1% of hallucinated names were registered within six months (at least one with malware), whether or
not anyone had published them. At least 23 names the models suggest had already hosted malware. Single-
model rate measurements understate the attack surface; cross-cohort intersections and registration monitoring
should be standard parts of future measurements.
