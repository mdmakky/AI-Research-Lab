# Secure or Suspect? Investigating Package Hallucinations of Shell Command in Original and Quantized LLMs

- Authors: Haque, Md Nazmul; Lin, Elizabeth; Arkoh, Lawrence; Tadesse, Biruk; Xu, Bowen
- Year / venue: 2025, arXiv (preprint, not peer-reviewed)
- DOI: 10.48550/arxiv.2512.08213 · URL: https://arxiv.org/abs/2512.08213
- Source text: `fulltext.txt` (page refs = PDF page index); arXiv 2512.08213v1, 9 Dec 2025.

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
[A] First systematic empirical study of how weight quantization affects package hallucination and known-vulnerability risk when LLMs generate shell commands that install Go packages (p. 1, p. 3). Central question: "How does quantization impact package hallucination while generating shell commands?" (p. 2).

## 2. Research questions / hypotheses
- [A] RQ1: To what extent do original and quantized LLMs generate hallucinated packages in shell commands? (p. 3)
- [A] RQ2: What proportion of the valid packages generated by LLMs have known security vulnerabilities? (p. 3)
- [A] RQ3: What are the properties of the hallucinated packages of original and quantized models? (p. 3)
- [A] No formal hypotheses; the authors speculate that quantized models could even hallucinate less (p. 2).

## 3. Methodology
- Research design: [V] Factorial measurement: 5 Qwen model sizes x 3 precisions (full, 8-bit, 4-bit) x 3 prompt datasets (p. 1, p. 4, p. 5). [I] One generation pass per prompt is implied, since no repetitions are reported.
- Approach / model / intervention: [V] Intervention = post-training weight quantization with bitsandbytes (8-bit and 4-bit), models loaded with Hugging Face transformers (p. 5). Hallucination oracle: the module URL in a `go get`/`go install` command is requested over the network; unreachable means hallucinated (p. 4). Vulnerability oracle: OSV API (p. 4). Threat model: the user blindly runs the LLM's command; the attacker watches for frequently hallucinated names and publishes a malicious Go package under that string (p. 2).
- Baselines or comparison conditions: [V] The full-precision version of each model (labelled "Org(32-bit)" in figures) (p. 5, p. 6). No other mitigation or model-family baseline.

## 4. Dataset and sample
- Data source(s): [V] (a) Stack Overflow questions tagged "golang" via Stack Exchange Data Explorer: 10,157 questions -> GPT-4o rewrites to generic tasks -> GPT-4o "as judge" generates shell commands -> keep those with install commands = 5,435; (b) MBPP text-to-code prompts adapted to language-generic prompts = 974; (c) awesome-go package names/metadata turned into paraphrased prompts by GPT-4o = 1,746 (p. 4).
- Sample size (N) and unit: [V] 8,155 prompts in total (our sum of the three sets) (p. 4); unit of analysis is the generated package string. Per-condition counts of generated Go package strings range from 0 (3B full/8-bit on MBPP) to 21,439 (1.5B full on SO), Table 1 (p. 6).
- Sampling / selection method: [V] Convenience/LLM-filtered: SO questions kept only if GPT-4o produced install commands (p. 4).
- Data availability (public? link?): [A] Datasets, results and replication package at https://anonymous.4open.science/r/phrGo-39EB (p. 2).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Qwen "LLMs4Code" family from the EvalPlus leaderboard, sizes 0.5B, 1.5B, 3B, 7B, 14B (p. 4); exact checkpoint names (e.g. Coder vs base, instruct vs base, version) not reported. bitsandbytes 8/4-bit; one NVIDIA A100 80GB (p. 5). Prompt wording, decoding parameters (temperature, max tokens), how package strings are extracted from responses, and the date of the reachability checks are not reported.
- Code availability: [A] Anonymous replication link (p. 2).

## 6. Evaluation metrics
- [V] PHR = |H| / |G|, hallucinated package strings over all generated package strings; answers RQ1 (p. 4, p. 5).
- [V] VPR = |V| / |E|, OSV-flagged packages over existing (reachable) packages; answers RQ2 (p. 5).
- Statistical testing: [V] none reported in the results — no confidence intervals, repeated runs or significance tests (p. 5, p. 6).

## 7. Key findings
1. [A] 8-bit quantization causes "a moderate and consistent increase" in PHR, e.g. 0.5B on SO 40.60% -> 43.04% (p. 5). [V] Table 1 does not show a consistent increase: PHR falls at 8-bit for 0.5B MBPP (53.58% -> 49.21%), 1.5B SO (46.17% -> 44.16%), 14B SO (30.52% -> 29.24%) and 3B Paraphrase (85.71% -> 78.89%), and rises sharply for 7B MBPP (48.39% -> 69.59%) (p. 6).
2. [V] 4-bit quantization raises PHR drastically for small models: 0.5B reaches 96.11% (SO), 98.78% (MBPP), 96.66% (Paraphrase); 3B 4-bit 92.09% / 97.60% / 87.74% (p. 6).
3. [V] Exception: 7B on SO falls from 34.00% to 10.21% at 4-bit, while its number of generated package strings drops from 4,185 to 1,655 (p. 5, p. 6).
4. [V] The discussion's summary numbers (8-bit "<2.5% PHR change"; 4-bit "0.5B: +55.5%, 3B: +58.8%", 7B "-23.8%", 14B "+6.6%") (p. 7) match percentage-point differences on the Stack Overflow dataset only (e.g. 96.11 - 40.60 = 55.51; 92.09 - 33.33 = 58.76; 34.00 - 10.21 = 23.79; 37.10 - 30.52 = 6.58), Table 1 (p. 6). The 3B full-precision SO baseline rests on only 3 generated package strings (p. 6).
5. [V] VPR among existing packages: 7B SO rises 12.89% -> 19.58% at 4-bit (p. 5); small models fluctuate (0.5B SO 12.49% -> 10.98%; 1.5B SO 13.70% -> 15.83%) (p. 5); some 4-bit VPRs fall (0.5B Paraphrase 15.57% -> 8.22%; 14B Paraphrase 12.30% -> 9.57%) (p. 6). [A] "Quantization correlates with an increased vulnerability presence rate" (p. 5) is therefore only partly supported.
6. [A] Generated package strings are mostly URLs, mainly github.com and golang.org; more than half of generated github.com URLs are hallucinated (p. 6). [V] In the only distribution table shown (1.5B 4-bit, SO; Table 2), 2,418 of 4,751 (51%) hallucinated strings are URLs (github.com 1,868; golang.org 42; other URLs 508) and 2,333 (49%) are file paths (1,372) or free-form strings (961) (p. 8). Existing strings in the same cell: github.com 1,794, golang.org 721 (p. 8).
7. [V] A placeholder string, `your.package.name`, resolved as an existing URL (p. 7).
8. [A] GitHub is "the largest attack vector" because anyone can create any username and repository; attackers may also compromise frequently recommended existing repositories or poison training data (p. 7).
9. [A] 8-bit quantization is recommended for resource-constrained deployment; 4-bit "requires extreme caution and robust validation layers" (p. 7).

## 8. Limitations stated by the authors
- [A] Package existence was checked by HTTP reachability "for simplicity" due to time constraints; an unreachable URL could still be downloadable as a Go package; future work should run `go get` instead (p. 7).
- [A] Prompts were not varied; future work should test different prompts (p. 7).

## 9. Limitations we identified
- [I] Tiny denominators are reported as rates without warning: 3B full/8-bit produced 3 and 1 package strings on SO and 0 on MBPP; 14B on MBPP produced 13/8/7, Table 1 (p. 6). The near-zero output of 3B at full precision is unexplained (possibly a generation or parsing failure).
- [I] The headline claim of a "consistent" increase (p. 5) contradicts the paper's own table (finding 1); the summary percentages in the discussion use only the SO dataset (finding 4). Conclusions overreach the data.
- [I] Oracle validity: HTTP reachability is neither necessary nor sufficient for a valid Go module (the authors acknowledge one direction, p. 7). File paths (1,372 on SO for 1.5B 4-bit) (p. 8) and "other" strings are counted as hallucinated packages, inflating PHR with strings that are not installable or squattable names.
- [I] About half of the "hallucinated packages" in the only distribution table (2,333 of 4,751 for 1.5B 4-bit on SO, Table 2 (p. 8)) are file paths or free-form strings, not installable module paths, so PHR overstates the number of squattable names.
- [I] Exploitability differs from PyPI/npm: Go modules are URL paths, so "squatting" means registering a free GitHub user/repo; whether hallucinated owners/repos were registrable was not checked. No persistence (repeat) analysis, so RQ2-style predictability is not measured.
- [I] Single model family (Qwen) and a single quantization library (bitsandbytes); laptop runtimes usually use other formats (e.g. GGUF k-quants), so effects may not transfer.
- [I] Prompts were created and filtered by GPT-4o (p. 4), which selects tasks GPT-4o itself answers with install commands — a selection bias toward install-heavy tasks.
- [I] The PDF still carries ACM template residue ("Do Not Use This Code", "Woodstock, NY", 2018 dates) (p. 1, p. 2), suggesting an early draft; preprint, not peer-reviewed.

## 10. Threats to validity
- Internal: no repeats or decoding settings reported; possible extraction failures (3B); GPT-4o-based prompt filtering — [I].
- External: Go only; one model family; one quantization method; open models up to 14B (p. 4, p. 5) — [I].
- Construct: "hallucinated" = unreachable URL string, including file paths and free-form strings (p. 4, p. 8) — [I].
- Statistical conclusion: no tests, no CIs, rates on n<=13 in several cells (p. 6) — [I].
- Reproducibility: anonymous link (may not persist), no prompts or decoding parameters in the paper — [I].

## 11. Future research directions
- Stated by authors [A]: verify packages by executing `go get`; vary prompts (p. 7); RQ3 insights could feed automated detection of suspicious recommendations and prompt strategies (p. 3).
- Suggested by us [I]: repeat the quantization comparison on PyPI/npm with GGUF quantization levels (as used by local runtimes), proper registry lookups, several samples per prompt and CIs; measure name repetition across runs and precisions.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1, RQ2, RQ4, RQ5.
- How it informs our work [I]:
  - RQ1: Only paper among this batch to vary quantization directly; suggests 4-bit small models hallucinate far more, but evidence is weak (single run, oracle problems, contradictory cells).
  - RQ2: Go-specific attack surface (GitHub user/repo paths) differs from registry-name squatting.
  - RQ4: Example of a weak existence oracle (HTTP reachability) and of counting non-package strings — pitfalls a new study should avoid.
  - Laptop-scale implication: quantized 0.5B–14B models are exactly what a laptop runs. A laptop study could cleanly re-test "does 4-bit raise PHR?" for PyPI/npm using a local runtime, several samples per prompt, and a registry API check. A lightweight defence suggested by this setting: resolve every `go get`/`pip install`/`npm install` target against the registry/module proxy before execution.
  - Replication checklist: Qwen 0.5B/1.5B/3B/7B/14B; full vs bitsandbytes 8-bit vs 4-bit; prompt sets SO (5,435), MBPP (974), awesome-go paraphrase (1,746); metric PHR over package strings, VPR via OSV; existence via URL reachability (replace with `go list -m`/module proxy) (p. 4, p. 5).
