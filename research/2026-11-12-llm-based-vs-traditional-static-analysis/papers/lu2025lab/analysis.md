# From Lab to Reality: A Practical Evaluation of Deep Learning Models and LLMs for Vulnerability Detection

- Authors: Lu, Chaomeng; Lagaisse, Bert
- Year / venue: 2025, arXiv (record in metadata.json). **Published version:** Journal of Systems and Software, Nov 2026, doi 10.1016/j.jss.2026.113185 (Elsevier, not OA). The orchestrator verified this via Crossref on 2026-11-12; it is not in metadata.json. Status: **peer-reviewed**.
- DOI: 10.48550/arxiv.2512.10485 · URL: https://arxiv.org/abs/2512.10485
- Source text: `fulltext.txt` = arXiv v4, the accepted manuscript ("accepted for publication in the Journal of Systems and Software", footnote p. 1). Page refs = PDF page index of arXiv v4, not JSS pagination.

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
- [A] Test whether DL vulnerability detectors and LLMs that score well on curated benchmarks still work under deployment-like conditions. The study looks at three things: separability of code representations, within- vs cross-dataset generalisation, and detection of recent, temporally separated vulnerabilities (p. 1, p. 2).
- [A] Contribution claimed: VentiVul, a temporally separated out-of-distribution (OOD) benchmark of 200 CVEs / 263 vulnerable–patched pairs, plus a "Whole-File" + "Function-Pair" evaluation protocol (p. 2). "Out-of-distribution" means test data drawn from a different source or period than the training data.

## 2. Research questions / hypotheses
- [A] RQ1: do graph-based and CodeBERT representations separate vulnerable from non-vulnerable code before task-specific training? (p. 6)
- [A] RQ2: how do benchmark characteristics affect within-dataset and cross-dataset performance of DL detectors? (p. 7)
- [A] RQ3: how well do trained DL models and off-the-shelf LLMs detect recent vulnerabilities on a temporally separated benchmark? (p. 7)
- No formal hypotheses.

## 3. Methodology
- Research design: [V] Controlled empirical evaluation in three stages: representation diagnostics (t-SNE + centroid distance), 4×4 train/test matrix of DL models across datasets, inference-only evaluation on VentiVul (pp. 6–8).
- Approach / models: [V] DL: Devign (gated GNN on code property graphs), ReVeal (Joern graphs + token embeddings, SMOTE), LineVul (fine-tuned CodeBERT), VulBERTa (RoBERTa pretrained on C/C++) (p. 5). LLMs, open-weight, no fine-tuning: Qwen2.5-Coder-32B-Instruct, DeepSeek-Coder-V2-Lite-Instruct (16B MoE, 2.4B active), Qwen3-30B-A3B (thinking mode disabled), Mistral-Small-24B-Instruct-2501, all released before May 2025 (p. 5, p. 8).
- Baselines or comparison conditions: [V] DL vs LLM only on VentiVul. Only ReVeal and LineVul (each trained on the four datasets) were taken to VentiVul; Devign and VulBERTa were not (p. 7). LLM prompting: zero-shot, few-shot (demonstrations drawn from complete vulnerable–patched pairs, the same number from each project; k = 4 is given only "for example", and the k actually used is not stated), chain-of-thought (p. 8, Table 4 p. 9). [I] No SAST tool, no proprietary/frontier LLM, no fine-tuned LLM and no trivial baseline (e.g. all-positive or random) is included.

## 4. Dataset and sample
- Data source(s): [V] Juliet 253,002 functions, 37% vulnerable, synthetic; Devign 27,318, 46%, manual; BigVul 188,636, 6%, patches; ICVul 15,396, 41%, patches (p. 3, Table 1). All C/C++.
- VentiVul: [V] CVEs for Linux and Chromium disclosed from May 1, 2025, taken from NVD in disclosure order until 100 per project; manually verified; target size fixed before collection; "records were not selected based on model predictions" (p. 4). 13,326 functions, 200 CVEs, 39 CWEs, 263 pairs; Chromium 7,095 functions / 100 CVEs / 20 CWEs / 147 pairs; Linux 6,231 / 100 / 27 / 116 (p. 4, Table 2). Pre-fix function = vulnerable, post-fix = non-vulnerable, plus other functions from the same files labelled non-vulnerable to keep realistic imbalance (p. 4).
- Sample size (N) and unit: functions (Whole-File), CVEs (CDR) and vulnerable–patched pairs (PACC) (p. 7). [I] Each of the 263 pairs has exactly one vulnerable function (p. 4), so prevalence p = 263/13,326 = 1.97%. The Table 7 numbers confirm this: back-calculating prevalence from accuracy, precision and recall gives 1.97% for every LineVul row, which matches 263/13,326. The ReVeal rows give 1.79%, because ReVeal is scored only on the functions its preprocessing can handle (p. 7). An all-positive classifier would therefore score F1 = 2p/(1+p) ≈ 3.87% on the full set and ≈ 3.5% on ReVeal's subset (our calculation from p. 4 and Table 7 p. 13).
- Sampling / selection method: [V] Inclusion: valid references, explicit fix in non-test C/C++ files, CWE available; excluded: missing references, non-C/C++ or test-only fixes, fixes with "excessive unrelated files or functions" (p. 4). Train/test split ratios for the four benchmarks: not reported.
- Data availability: [V] "All of our datasets, code, and results are available" on GitHub (p. 2).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] DL models use the original authors' code and "recommended settings" (p. 8); H100 GPUs (p. 8). Leakage controls: strict train–test splits with duplicate functions filtered, a fixed test set per target benchmark (p. 7). LLMs run locally via vLLM on B200 GPUs, temperature 0, top-p 1, seed 42, max 384 output tokens, JSON-only binary label; unparseable outputs kept as failures (p. 8). Each model, DL or LLM, receives one function at a time (p. 7, p. 8). Few-shot demonstrations are removed from the test set by pair identifier and code hash (p. 8). ReVeal metrics are computed only over functions its preprocessing can handle (p. 7). Two policies for LLMs: valid-only and conservative (failures counted wrong) (p. 8).
- Code availability: [V] public GitHub repository (p. 2).

## 6. Evaluation metrics
- Metric — what it measures — why chosen: [V] Accuracy, Precision, Recall, F1 for Whole-File (p. 9). CVE Detection Rate (CDR): share of CVEs with at least one vulnerable function flagged, i.e. CVE-level coverage (p. 9). Patch Pair Accuracy (PACC): share of pairs where the vulnerable version is flagged and the patched version is not, i.e. sensitivity to the fix (p. 9). Centroid distance in min-max normalised t-SNE space, described as descriptive only (pp. 8–9).
- Statistical testing: not reported. There are no significance tests or confidence intervals. LLMs use one deterministic run (temperature 0, seed 42, p. 8). For DL training, the number of runs and the random seeds are not reported (p. 8 refers only to the original authors' "recommended settings").

## 7. Key findings
1. In-distribution DL (within-dataset) — [V] LineVul F1 94.52 and VulBERTa 94.14 on Juliet; LineVul F1 91.00 on BigVul (p. 11; Table 6 p. 12). On BigVul, ReVeal, Devign and VulBERTa reach accuracy 87.45, 94.09, 94.39 but F1 only 23.58, 16.90, 0.19 (p. 11). [A] Because BigVul has a much smaller vulnerable share (6%), "predictions biased toward the non-vulnerable majority class can produce high accuracy while detecting few vulnerable functions" (p. 11).
2. Cross-dataset DL — [V] LineVul (Juliet) F1 94.52 in-dataset falls to 53.95 (Devign), 10.73 (BigVul), 51.22 (ICVul) (p. 11). LineVul (BigVul) falls from 91.00 to 0 (Juliet), 1.90 (Devign), 13.05 (ICVul) (p. 12). ReVeal (BigVul) is below 1.00 F1 on all three external sets (p. 11). [A] "No evaluated model consistently preserves its within-dataset performance" (p. 11).
3. Temporally separated DL (VentiVul, Whole-File) — [V] F1 3.47–8.65 across the 8 ReVeal/LineVul configurations; best ReVeal (BigVul) F1 8.65 with precision 5.25%, recall 24.43% (p. 13, Table 7). Devign-trained models: recall 99.24–100% but precision about 2% (p. 13, Table 7). LineVul (BigVul) F1 6.87 on VentiVul vs 91.00 in-distribution (Table 7 p. 13; Table 6 p. 12).
4. Temporally separated LLMs (VentiVul) — [V] Conservative F1 0.79–5.36 across 4 models × 3 prompts; all conservative F1 < 5.5% and all PACC < 6% (p. 13; Table 8 p. 14). Best: Mistral-Small-24B few-shot F1 5.36%, CDR 46%, PACC 5.75% (p. 13). Highest valid-only F1: Qwen2.5-Coder-32B CoT 8.21% (conservative 3.04%) (p. 14, Table 8). Zero-shot conservative F1: Qwen2.5-Coder 3.72, DeepSeek-Coder-V2-Lite 4.29, Qwen3 3.09, Mistral 4.07 (p. 14, Table 8). LLM precision and recall are not reported, and the LLMs have no in-distribution numbers.
5. DL vs LLM on VentiVul (mostly but not exactly the same samples) [V/I] — [V] best DL Whole-File F1 8.65 (ReVeal-BigVul) vs best LLM conservative F1 5.36 (Mistral few-shot) (p. 13; p. 14). Zero-shot LLM CDR (34%, 20%, 9%, 5%) is lower than most DL configurations (p. 13). Best PACC: DL 5.34% vs LLM 5.75% (p. 13). [V] The evaluated samples differ: ReVeal is scored only on functions it can process (p. 7), the few-shot test set excludes pairs used as demonstrations, and valid-only metrics use only parseable outputs (p. 8). [I] F1 against chance (all-positive F1 ≈ 3.87% at p = 1.97%; ≈ 3.5% on ReVeal's subset; §4): the best DL F1 of 8.65 is about 2.5× its chance level, while the best LLM F1 of 5.36 is about 1.4× chance. LineVul (Devign), with recall 100%, precision 2% and F1 3.93, is in effect the all-positive predictor (p. 13, Table 7). [I] PACC against chance: a random labeller that flags a fraction q of functions independently of their content would get PACC = q(1−q), up to 25% at q = 0.5. All observed PACC values (≤ 5.75%, DL and LLM) are far below that, which means the models usually give the vulnerable and the patched version the same label (our reasoning from the PACC definition, p. 9). This matches ding2025vulnerability, where random pair-wise correctness is 22.70% and models fall far below it [@ding2025vulnerability, p. 9].
6. CDR vs PACC gap — [V] ReVeal (Devign), ReVeal (ICVul), LineVul (Devign) reach CDR 99.10%, 94.59%, 100% but PACC 0.76%, 0%, 0% (p. 13). [A] Detecting a vulnerable function "does not imply" telling it apart from its patch (p. 13).
7. Prompting — [V] Few-shot improves Mistral on all three metrics but degrades the other models; CoT raises Qwen2.5-Coder valid-only F1 but lowers its PACC (p. 13). [A] Prompting effects are "model- and metric-dependent" (p. 13).
8. Project/CWE variation — [V] All LLMs have higher CDR on Linux than Chromium. DeepSeek-Coder-V2-Lite zero-shot CDR is 26% on Chromium and 42% on Linux (p. 13). LineVul (BigVul) has CDR 76% on Chromium and 0 on Linux (p. 13). The LLM project-specific results are zero-shot, valid-only (p. 13). Best project-specific PACC is < 8% (LineVul-ICVul 7.48% on Chromium) (p. 14). Per-CWE PACC peaks at 18.18% (LineVul-ICVul, CWE-472) on small cells (p. 14).
9. Representations — [V] GNN centroid distances: Juliet 0.0242, ICVul 0.0057, BigVul 0.1612; CodeBERT: BigVul 0.166, Devign 0.0068 (pp. 9–10). [A] Neither representation consistently separates vulnerable from non-vulnerable code (p. 10).

## 8. Limitations stated by the authors
- [A] Only four DL models, two DL families on VentiVul, four open-weight LLMs; no proprietary LLMs; conclusions apply to the evaluated models (p. 17).
- [A] LLM pretraining corpora and cutoffs are unknown, so temporal separation "cannot fully exclude training-data contamination" (p. 17).
- [A] t-SNE is parameter-sensitive, and centroid distance cannot capture nonlinear structure. RQ1 does not establish a causal link to RQ2/RQ3 performance (p. 17, p. 15).
- [A] Dataset characteristics vary simultaneously, so individual causes cannot be isolated. Preprocessing drops some functions, which affects comparability (p. 17).
- [A] VentiVul is C/C++ only (Linux, Chromium) and may not generalise to other languages or proprietary code. "Unrelated" functions may hide other vulnerabilities (residual label noise), and regex function extraction can miss complex C/C++ syntax, which mainly affects Whole-File (p. 17).
- [A] VentiVul "does not contain every vulnerability reported for the selected project versions" (incomplete coverage) (p. 17).
- [A] Model coverage was constrained by reproducibility, experimental consistency and computational feasibility; conclusions apply "to the evaluated models and settings rather than to all existing vulnerability detection techniques" (p. 17).
- [A] The Function-Pair setting is "less exposed" to label-noise and extraction threats because it uses manually verified vulnerable functions and their patched versions (p. 17).
- [A] ICVul and VentiVul come from open-source projects and may not represent proprietary industrial software (p. 17).

## 9. Limitations we identified
- [I] No trivial baseline. At p = 263/13,326 = 1.97% (p. 4), an all-positive classifier scores F1 = 2p/(1+p) ≈ 3.87%. All eight DL F1 values (3.47–8.65, Table 7 p. 13) are at most 4.8 points above that. Seven of the 12 LLM conservative F1 values (Table 8 p. 14) fall below it: 3.72, 2.95, 3.04, 3.64, 3.09, 0.79 and 1.39. The paper calls these results "limited" or "weak" (p. 13) but never compares them with chance.
- [I] The DL and LLM comparison is asymmetric. DL models were trained on historical data; LLMs were used zero/few-shot without fine-tuning, with small open-weight models (MoE models with 2.4–3B active parameters) and Qwen3 thinking disabled (p. 5, p. 8). The study says nothing about frontier or fine-tuned LLMs, and nothing about LLMs in-distribution, because LLMs were not run on the four benchmarks.
- [I] LLM precision/recall are not reported (Table 8 gives F1, CDR, PACC only, p. 14), so we cannot tell whether LLMs fail through false positives or false negatives.
- [I] No confidence intervals. LLMs get a single deterministic run (temperature 0, seed 42, p. 8); DL run counts and seeds are not reported. With 263 pairs, PACC differences of a few points (e.g. 5.34% vs 5.75%) are within noise.
- [I] One function at a time with no context (p. 7). This is fair between families but disadvantages LLMs, which may need inter-procedural context. With 263 pairs across 200 CVEs (p. 4), at most 63 CVEs have more than one affected function (e.g. CVE-2025-37777, two functions in two files, p. 4). The share of CVEs that need cross-function reasoning is not reported.
- [I] No static-analysis tool is evaluated, although the introduction positions learning-based detection as a complement to static analysis (p. 1).
- [I] Version: we analyse arXiv v4 (4 Nov 2026), the accepted manuscript (footnote p. 1). The published JSS version (doi 10.1016/j.jss.2026.113185, Crossref-verified 2026-11-12) is not open access and was not compared with it, so small differences between the two versions cannot be ruled out. Page refs follow arXiv v4.

## 10. Threats to validity
- Internal: [I] Deduplication within datasets and fixed test sets are reported (p. 7), but split ratios and cross-dataset overlap checks are not reported (Devign is from FFmpeg/QEMU and BigVul from open-source C/C++ repositories, p. 3, so project overlap is possible but unchecked). ReVeal is scored only on functions it can process (p. 7), which may inflate or deflate its numbers relative to LineVul. Overlap with training and pretraining data was not checked. Temporal separation covers the CVEs and their fixes (disclosed from May 2025, p. 4). The "unrelated" same-file functions that make up most of VentiVul can be much older code. The paper describes BigVul and ICVul only as drawn from open-source C/C++ repositories and GitHub fix commits (p. 3), and does not say whether they contain older Linux/Chromium code. It reports no check of whether VentiVul functions appear in the DL training sets or in LLM pretraining corpora (pp. 3–4).
- Conflict of interest: [I] ICVul, one of the four training benchmarks, is the authors' own dataset (Lu, Li, Dehaene, Lagaisse, MSR 2025; p. 3, reference list p. 18). The paper presents it as "high-quality" (p. 3). Its results are not singled out favourably, but the dependence should be noted. Funding: not reported (no funding or acknowledgement statement in the text).
- External: [I] C/C++, two very large projects, 200 CVEs, open-weight mid-size LLMs only (p. 4, p. 5).
- Construct: [I] Labelling unrelated same-file functions as non-vulnerable (p. 4) is a realistic construct for "scan the whole file", though label noise remains (p. 17). PACC is a strict and useful measure of patch sensitivity. CDR rewards indiscriminate positive prediction, as the paper itself shows (p. 13).
- Statistical conclusion: [I] No tests, single runs, small per-CWE cells (p. 14).
- Reproducibility: [I] Good overall: data, code and results are public (p. 2), and the decoding settings are fully given (p. 8). Prompt templates are given (Table 4, p. 9), but the system prompt is only paraphrased (p. 8) and the few-shot demonstrations are not listed in the paper. DL hyper-parameters are given only by reference to the original implementations (p. 8), and DL run counts and seeds are not reported.

## 11. Future research directions
- Stated by authors [A]: representations and training that emphasise security-relevant changes, e.g. vulnerable–patched pair supervision (p. 16); datasets prioritising reliable labels, diverse patterns and explicit vulnerability–fix links over size (p. 16); complementing within-dataset evaluation with cross-dataset and temporally separated testing, and reporting CDR and patch-pair metrics with function-level metrics (p. 16); studying individual dataset factors, broader ecosystems and "more advanced LLM adaptation strategies" (p. 16).
- Suggested by us [I]: run SAST tools and frontier/fine-tuned LLMs on VentiVul with file/repository context and a chance baseline. That would give exactly the same-benchmark LLM vs SAST vs DL comparison our RQ5 identifies as missing.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1 (DL vs LLM on largely shared OOD data), RQ2 (temporal separation, cross-dataset shift, class ratio, accuracy vs F1), RQ4 (per-project and per-CWE variation, C/C++), RQ5 (patch-pair sensitivity, chance baselines).
- How it informs our work [I]: This is direct, peer-reviewed (JSS 2026) evidence that in-distribution DL scores do not survive temporal shift. It is consistent with ding2025vulnerability, which shows BigVul-trained models collapse on PrimeVul [@ding2025vulnerability, p. 7]. LineVul's F1 falls from 91–94.5 in-distribution (p. 12) to 4.39–6.87 on VentiVul, and all 8 DL configurations score 3.47–8.65 (p. 13). On F1, the evaluated open-weight LLMs (≤ 32B) do no better than the shifted DL detectors (0.79–5.36), and both families sit within a few points of the all-positive F1 of ≈ 3.87%. On PACC, both families are far below the random q(1−q) level (up to 25%), i.e. they rarely tell a function apart from its patch. It supports the RQ2 claim that evaluation setup drives the reported ranking. It covers no SAST tool or cost, so it adds nothing for RQ3.
