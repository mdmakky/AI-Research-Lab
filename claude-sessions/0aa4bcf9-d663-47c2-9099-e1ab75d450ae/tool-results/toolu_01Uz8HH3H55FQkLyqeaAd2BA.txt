# We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs

- Authors: Spracklen, Joseph; Wijewickrama, Raveen; Sakib, A H M Nazmus; Maiti, Anindya; Viswanath, Bimal; Jadliwala, Murtuza
- Year / venue: 2024, arXiv (preprint). Analysed version: arXiv:2406.10279v3, 2 Mar 2025 (p. 1). The published version appeared at USENIX Security 2025, according to the project lead and the reference lists of two other project papers ([@churilov2026range, p. 16]; [@okwor2026hallucination, p. 9]). The arXiv text does not name the venue. We analysed the arXiv text, so differences from the proceedings version cannot be ruled out.
- DOI: 10.48550/arxiv.2406.10279 · URL: https://arxiv.org/abs/2406.10279
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.

## 1. Research objective
[A] The paper aims to:
- measure how common package hallucinations are in Python and JavaScript code produced by commercial and open-source code LLMs;
- show how model settings affect them;
- describe what the hallucinated names look like;
- test whether mitigation can reduce them without hurting code quality (p. 2, p. 4).

The authors call it "the first systematic study" of how often package hallucinations occur and what they are like (p. 2).

## 2. Research questions / hypotheses
- [A] RQ1: how common are package hallucinations in Python and JavaScript code generated by LLMs? (p. 4)
- [A] RQ2: how do model settings (training-data recency, temperature, decoding strategy) affect them? (p. 4)
- [A] RQ3: what model behaviours appear: repetition within one model, repetition across models, verbosity, and self-detection? (p. 4)
- [A] RQ4: what properties do hallucinated names have: similarity to popular packages, confusion between languages, and recently deleted packages? (p. 4)
- [A] RQ5: can RAG, self-refinement, decoding strategies or supervised fine-tuning reduce hallucinations? (p. 4–5)
- [A] Explicit hypothesis on deleted packages: they expected a sizeable share of hallucinations to come from packages removed from PyPI. The data did not support it (p. 11).
- [A] Adversary model: the attacker can query the same LLMs but cannot modify them, finds hallucinated names by checking the registry, and registers those names. Victims install suggested packages without checking them (p. 4).

## 3. Methodology
- Research design: [V] A three-phase pipeline: (i) build prompt datasets, (ii) generate code, (iii) detect hallucinations (p. 5). Targeted sub-experiments then cover RQ2–RQ4, and a mitigation experiment covers RQ5 (p. 7–13).
- Approach / model / intervention: [V] 16 models (Table 1):
  - commercial: GPT-4, GPT-4 Turbo, GPT-3.5 Turbo;
  - CodeLlama 7B / 13B / 34B;
  - DeepSeek Coder 1.3B / 6.7B / 33B;
  - Magicoder 6.7B, WizardCoder 34B, Mistral 7B, Mixtral 8x7B, OpenChat 7B;
  - Python-only: WizardCoder-Python 7B, CodeLlama-Python 33B (p. 6).

  [V] Models were chosen from the top of the EvalPlus leaderboard as of 20 January 2024, plus the GPT models (p. 5). The two Python-only models were not tested on JavaScript, which gives 30 model-language tests (p. 6).
- Package-name extraction: [V] three heuristics (p. 6–7):
  - H1: parse `pip install` / `npm install` commands that appear in the output without being asked for (they occur in 7% of outputs).
  - H2: give the generated code back to the same model and ask which packages are needed to run it.
  - H3: give the original prompt back to the same model and ask which packages would solve the task.

  [A] Parsing `import`/`require` statements is explicitly rejected, because module names do not map one-to-one to package names (p. 6; Appendix G, p. 19).
- Hallucination decision: [V] A name counts as hallucinated if it is absent from a master list of PyPI or npm package names taken on 10 January 2024 (p. 7). [A] The list may already contain names squatted by attackers, so the authors call their rates a lower bound (p. 7).
- Mitigation: [V] tested on DeepSeek Coder 6.7B and CodeLlama 7B, each method alone and all three together (p. 12–13):
  - RAG: 65,000 statements of the form "Package [x] could answer questions about [y]", generated with LlaMA-2 from the top 20,000 PyPI packages and stored in a vector database. The 5 closest statements are added to the prompt.
  - Self-refinement: the model is asked whether its packages are valid and regenerates its answer up to 5 times.
  - Supervised fine-tuning: on 560,000 H1/H2 response pairs that contain only valid packages.
- Baselines or comparison conditions: [V]
  - commercial vs open-source models; Python vs JavaScript;
  - "recent" (2023) vs "all-time" (pre-2023) prompt subsets (p. 5, p. 7–8);
  - temperature sweep and top-p / top-k / min-p settings (p. 8);
  - unmitigated baseline vs each mitigation (p. 13);
  - comparison with Lanyado's blog estimate (GPT-3.5 24.2%, GPT-4 22.2%) (p. 7).

## 4. Dataset and sample
- Data source(s):
  - [V] Stack Overflow set: 240 manually chosen tags, each with more than 5,000 questions and relevant to Python or JavaScript. The 20 most-upvoted questions per tag give 4,800 prompts per language. This was done once for 2023 and once for before 2023, giving 9,600 prompts per language (p. 5).
  - [V] LLM-generated set: Llama-2 70B turned the descriptions of the 5,000 most-downloaded PyPI and npm packages into one-sentence coding prompts (prompt template in Figure 13, p. 19). This gives about 4,800 prompts per language, also split into recent and all-time halves with overlaps removed (p. 5).
- Sample size (N) and unit:
  - [V] 19,200 code samples per model-language test, 30 tests, 576,000 code samples in total (p. 6).
  - [V] 1,152,000 package prompts (p. 7).
  - [V] 2.23 million package mentions, of which 440,445 were hallucinated, covering 205,474 unique hallucinated names (p. 7).
  - [V] The contributions list instead gives 19,500 prompts and 586,000 samples (p. 2). This does not match the 576,000 given elsewhere (p. 1, p. 6), and the paper does not explain the difference.
- Sampling / selection method: [V] RQ2–RQ4 use only Python, 4 models (GPT-4 Turbo, GPT-3.5, CodeLlama 7B, DeepSeek 6.7B) and "randomly sampled subsets" of the datasets (p. 7). Subset sizes are not reported, except the 500 prompts in the persistence test (p. 9). The self-detection test used randomly sampled valid and hallucinated names; that sample size is not reported (p. 9–10).
- Data availability (public? link?): [V] Code, both prompt datasets, the generated code, the RAG database and the fine-tuned models are released at Zenodo record 14676377 and on GitHub (Spracks/PackageHallucination) (p. 2, p. 14). [V] The master list of hallucinated names and the detailed per-test results are withheld and shared "by request to verified researchers" (p. 14).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools:
  - [V] Open-source models ran through Hugging Face transformers with GPTQ-quantized weights (p. 6).
  - [V] Hardware: a 40-node Debian cluster with A100/V100 GPUs, and an Ubuntu machine with 3 RTX 6000 GPUs (p. 18).
  - [V] RQ1 parameters (Table 6, p. 19): temperature 0.7 for code generation and 0.01 for package prompts; top-p 0.9; top-k 20; repetition penalty 1; max tokens 2048 for code and 64 for package prompts.
  - [V] The system messages and prompts are given word for word in Figures 10–13 (p. 18–19).
  - [V] Temperature sweep: up to 2 for GPT models and up to 5 for open models (p. 8).
  - [V] Decoding sweep: top-p 0.4/0.6/0.8, top-k 5/10/15, min-p 0.1/0.2/0.3, plus one combined setting. Top-k and min-p were tested only on the open models (p. 8).
  - [V] Ground truth: PyPI and npm master lists as of 10 January 2024 (p. 7).
  - [V] Deleted packages were identified from Google BigQuery PyPI download counts from 2022 and earlier (p. 11).
  - [V] The cross-language check used libraries.io package lists for 9 registries (p. 11).
  - Name normalisation (case folding; PEP 503 equivalence of `-`, `_` and `.`; npm scopes): not reported.
  - Standard-library exclusion: not reported.
  - Deduplication: rates count mentions, and "unique" means distinct strings (p. 7). The exact rule is not reported.
- Code availability: [V] Yes, see section 4 (p. 14).

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] Package hallucination rate = number of hallucinated packages / total number of recommended packages (p. 7). This is a mention-level rate. It pools names from H1 (install commands inside code) with names from H2/H3 (the model's answer when asked directly "which packages").
  - [V] Persistence: how many of 10 repeated queries reproduce the same hallucinated name (p. 9).
  - [V] Number of models that produce each unique name (p. 10).
  - [V] Levenshtein (edit) distance to the nearest valid package (p. 10–11).
  - [V] Self-detection accuracy, precision and recall (p. 10).
  - [V] HumanEval pass@1, used to measure code quality after fine-tuning (p. 13).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): Not reported. There are no confidence intervals, no significance tests and no run-to-run variance; "significantly reduce" is used in a descriptive sense (p. 1, p. 13). [V] The link between Python and JavaScript rates is called "linear" and "positively correlated" based on a scatter plot, with no coefficient given (p. 7; Figure 14, p. 19).

## 7. Key findings
1. [V] Overall rate: 440,445 of 2.23 million package mentions (19.7%) were hallucinated, including 205,474 unique non-existent names (p. 7).
2. [V] Commercial vs open models:
   - GPT models 5.2% vs open-source models 21.7% (p. 7).
   - Lowest overall: GPT-4 Turbo at 3.59%. Lowest open model: DeepSeek 1B at 13.63% (p. 7).
   - Highest per-model rates: 26.12% in Python and 35.71% in JavaScript, both CodeLlama 7B (Tables 7–8, p. 20).
3. [V] Language and prompt source:
   - Python hallucinated less than JavaScript on average: 15.8% vs 21.3% (p. 7).
   - Stack Overflow prompts gave higher rates than LLM-generated prompts for almost every model, e.g. CodeLlama 7B in Python 32.53% vs 21.51% (Table 7, p. 20).
4. [V] Repetition within a model: 500 prompts were repeated 10 times each (p. 9).
   - 43% of hallucinated names reappeared in all 10 runs.
   - 39% never reappeared.
   - 58% reappeared more than once.
5. [V] Most names are model-specific: 81% of distinct names were produced by only one model (p. 10).
6. [V] Most names are not near-typos of real packages (p. 11):
   - only 13.4% (10,263 of 76,489) are 1–2 edits from a real package;
   - 48.6% are 6 or more edits away.
7. [V] Other sources of names (p. 11):
   - deleted PyPI packages are a negligible source: 133 names (0.17%);
   - 8.7% (6,705 of 76,489) of hallucinated Python names are valid npm packages.
8. [V] Effect of settings:
   - Rates rise with temperature, and steeply above 1. At maximum temperature GPT-4 reached 8.9% and GPT-3.5 reached 31.8% (p. 8).
   - Changing top-p, top-k or min-p raised rates slightly (+1.16% on average) and did not help (p. 8).
   - Prompts on recent topics gave about a 10% higher rate (p. 8–9).
9. [V] Self-detection: GPT-4 Turbo, GPT-3.5 and DeepSeek recognised their own hallucinations with more than 75% accuracy. CodeLlama tended to label most packages as valid (Figure 7, Table 2, p. 10).
10. [V] Mitigation (Table 4, p. 13), DeepSeek / CodeLlama:
    - baseline 16.14% / 26.28%;
    - RAG 12.24% / 13.40%;
    - self-refinement 13.04% / 25.51%;
    - fine-tuning 2.66% / 10.27%;
    - all three combined 2.40% / 9.32%.

    Fine-tuning lowered HumanEval pass@1 from 51.4% to 25.3% (DeepSeek) and from 19.6% to 16.4% (CodeLlama) (Table 5, p. 13).

## 8. Limitations stated by the authors
- [A] The master list may already contain squatted hallucinated names, so the rates are a lower bound (p. 7).
- [A] RQ2–RQ4 used only Python, 4 models and sampled subsets. The authors argue this does not weaken generalisability (p. 7).
- [A] Newer models may behave differently. Few commercial models were tested because of funding limits (p. 13).
- [A] Self-refinement can wrongly flag valid packages as hallucinations (p. 12).
- [A] Fine-tuning lowers code quality (p. 13).
- [A] Registries do not fully disclose which packages they removed (p. 3).
- [A] For ethical reasons the authors did not publish real packages, so they did not demonstrate an actual attack (p. 14).

## 9. Limitations we identified
- [I] **The metric mixes three name sources.** H2 and H3 ask the model directly for package lists (p. 6–7). Names given in those answers are not necessarily names that would be installed from the generated code. So the pooled mention-level rate is not the same thing as "hallucinated dependency in code". It is also not directly comparable with rates from import/install parsing (churilov2026range) or per-prompt rates (krishna2025importing).
- [I] **Normalisation and stdlib handling are not reported.** If names were matched without PEP 503 normalisation, case or separator variants of real packages would be counted as hallucinations, which would inflate the rates. Based on the absence of any normalisation step on p. 7.
- [I] **Possible train/test leakage in the mitigation results.** Fine-tuning used the 560,000 valid responses produced from the same prompt datasets (p. 12–13). The paper does not describe which prompts were used to evaluate the fine-tuned models, so the 2.66% result may be partly in-distribution.
- [I] **No uncertainty is reported.** Each condition was run once. Small differences, such as self-refinement on CodeLlama (26.28% → 25.51%), cannot be judged without confidence intervals (p. 13).
- [I] **Internal inconsistencies.** These are probably typos, but they lower confidence in exact numbers:
  - 586,000 vs 576,000 samples (p. 2 vs p. 6);
  - CodeLlama is marked "✗" (not open source) in Table 1 (p. 6) but treated as open-source in the text;
  - malformed counts "(2,495/41,7)" and "(2,8523/13,329)" in Table 7 (p. 20);
  - the GPT-4 JavaScript Stack Overflow cell says 3.86%, but 1,672/23,416 = 7.1% (p. 20);
  - the recency effect is stated in both directions (p. 8–9).
- [I] **The "10%" recency figure is ambiguous.** The paper does not say whether it is a relative change or a difference in percentage points (p. 8).
- [I] **No exploitation data.** The registry snapshot (January 2024) predates the analysis, and the paper does not track whether the hallucinated names were later registered (relevant to RQ2).

## 10. Threats to validity
- Internal (confounds, leakage, selection):
  - [I] In H2/H3 the same model both generates the code and names the packages, so its self-consistency becomes part of the measurement.
  - [I] Fine-tuning data comes from the same prompt pool that is used for evaluation (p. 12–13).
  - [I] The LLM-generated prompts were written by Llama-2 70B, from the same family as the CodeLlama models being tested (p. 5).
- External (generalisability of sample/context):
  - [I] The models are from 2023 to early 2024 (p. 5–6). No agentic or IDE tools are covered.
  - [V] Only Python and JavaScript are studied (p. 6).
  - [I] Open models were run GPTQ-quantized (p. 6), so results may not carry over to full-precision weights.
- Construct (do metrics measure the concept?):
  - [I] "Absent from the list of 10 Jan 2024" is a proxy for "hallucinated". The authors acknowledge that contamination of the list biases the rate downward (p. 7).
  - [I] Normalisation, stdlib names and private or scoped names are not addressed (p. 7).
  - [I] Counting mentions gives more weight to models that suggest many packages.
- Statistical conclusion (power, multiple comparisons, variance): [I] There are no tests, no confidence intervals and no repeated runs apart from the 10-run persistence check (p. 9). The large sample makes the headline rates stable, but comparisons between conditions have no inferential support.
- Reproducibility (data/code/setup reported?):
  - [V] Prompts, system messages and parameters are given (Appendix B/C, p. 18–19), and code and data are public (p. 14).
  - [V] The list of hallucinated names is withheld (p. 14).
  - [I] The commercial-model results cannot be reproduced exactly because those endpoints have since changed.

## 11. Future research directions
- Stated by authors [A] (p. 13):
  - find the root causes (model architecture, tokenizers, training-data composition);
  - develop mitigations tailored to code (prompt engineering, knowledge graphs, refined loss functions, new fine-tuning methods);
  - add real-time feedback;
  - study persistence at the token level;
  - find fine-tuning methods that keep code quality.
- Suggested by us [I]:
  - Re-measure with import/install-based extraction and explicit PEP 503 normalisation, so the results can be compared with later studies.
  - Evaluate cheap tool-side defences on held-out prompts, e.g. a check of registry existence plus package age and popularity, or self-refinement with a small model.
  - Track whether hallucinated names are registered over time.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1 (rates by model, language, temperature, recency), RQ2 (persistence, overlap between models, similarity to real names), RQ3 (RAG, self-refinement, fine-tuning), RQ4 (prompt sources, registry snapshot, extraction heuristics).
- How it informs our work [I]:
  - **Baseline and prompt corpus.** This is the baseline paper and the source of the reusable prompt corpus (public on Zenodo/GitHub, p. 14). A laptop-scale study can sample from its Stack Overflow and LLM-generated prompt sets and stay comparable with this paper and with churilov2026range.
  - **Details a replication needs** (p. 5–7, p. 18–19):
    - prompt sources: Stack Overflow, top 20 questions for each of 240 tags, 2023 vs pre-2023; Llama-2-70B prompts from the descriptions of the top 5,000 packages;
    - system prompts: Figures 10–13;
    - temperatures: 0.7 for code, 0.01 for package prompts;
    - registry snapshot: 10 Jan 2024;
    - metric: hallucinated packages / all recommended packages;
    - normalisation: not reported, so our study must define it explicitly (PEP 503 for PyPI, lowercase for npm, scoped names kept whole).
  - **Cheap defences.** RAG over a package-description index (13.40% vs 26.28% on CodeLlama) and self-refinement need no training and can run on a laptop. Self-refinement only helps models that can recognise their own hallucinations (p. 10, p. 13). Fine-tuning is costly and hurt code quality (p. 13).
  - **Persistence.** The 43% / 39% split (p. 9) means a measurement study needs several samples per prompt to separate persistent names (the ones worth squatting) from noise.
  - **Existence checks are not enough.** The authors argue an attacker can pre-register names (p. 12), so a lightweight defence should add signals such as package age, popularity or provenance.

# The Range Shrinks, the Threat Remains: Re-evaluating LLM Package Hallucinations on the 2026 Frontier-Model Cohort

- Authors: Churilov, Aleksandr
- Year / venue: 2026, arXiv (preprint, not peer-reviewed). The analysed text is "Version 4 (November 2026)", which supersedes all numbers in versions 1–3 and in a SCORED '26 workshop version (p. 1). Single author, "Independent Researcher" (p. 1).
- DOI: 10.48550/arxiv.2605.17062 · URL: https://arxiv.org/abs/2605.17062
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
[A] The paper asks whether package hallucination has changed for the 2026 frontier models compared with Spracklen et al.'s 2024 baseline. It re-checks every name against the live PyPI and npm registries, and tests whether publishing hallucinated names makes them get registered faster (p. 1–2).

## 2. Research questions / hypotheses
- [A] Measurement question: has package hallucination changed for the 2025–26 frontier models (p. 1)? It is broken into three parts (p. 2):
  - per-model rates, counted per mention and per generation;
  - the set of names hallucinated by all models (the "universal" set) and whether outsiders can register them;
  - whether hallucinated names get registered.
- [A] Preregistered hypothesis for the natural experiment: if publishing names attracts registrations, then published names (group A) are registered more often than comparable unpublished names (group B4). The primary test is Fisher's exact test within strata of name frequency and name length (p. 11–12).
- [A] Threat model: taken from Spracklen. An unprivileged attacker registers packages, and the attack runs in 6 stages. The estimated API cost to enumerate names is about $1,160 (p. 3).

## 3. Methodology
- Research design: [V]
  - A temporal replication: same prompts, newer models (p. 2, p. 4).
  - A re-check against the live registries, following a plan registered on 7 Nov 2026, with a log of 20 deviations from that plan (p. 6).
  - A natural experiment that uses the accidental public release of the universal list (p. 11).
- Approach / model / intervention: [V] Five models (Table 1, p. 4):
  - Claude Sonnet 4.6 (`claude-sonnet-4-6`)
  - Claude Haiku 4.5 (`claude-haiku-4-5-20251001`)
  - GPT-5.4-mini (`gpt-5.4-mini-2026-03-17`, reasoning effort set to minimal)
  - Gemini 2.5 Pro (`gemini-2.5-pro`)
  - DeepSeek V3.2 (alias `deepseek-chat`)

  [V] Extended thinking was not used for the Claude models (p. 4–5).
- Package extraction: [V] (p. 5)
  - `pip install` anywhere in a response, first argument only.
  - `npm install` only inside code blocks.
  - Import statements parsed with Python `ast`, with sub-imports resolved to the top-level module, and with tree-sitter for JavaScript.
  - Scoped npm names (`@scope/name`) kept whole.
  - requirements files, uv, poetry, yarn and pnpm are not extracted.
- Registry check: [V]
  - Two methods per registry: for PyPI the JSON API and the Simple API (PEP 691); for npm the registry document and deps.dev (p. 5).
  - HTTP 200 = EXISTS, 404 = ABSENT, anything else = UNKNOWN (p. 5).
  - A name is ABSENT only if both methods say ABSENT in two rounds at least 12 hours apart: 7 Nov 2026 11:53–13:14 UTC and 8 Nov 2026 10:16–11:22 UTC (p. 5).
  - At most 1 request per second per host; 14,821 requests with no errors (p. 5).
  - Hallucination is judged as of the time of generation: the package's creation time (npm `time.created`; PyPI earliest upload) is compared with the generation timestamp or batch window (p. 5).
  - OSV is queried for malicious-package records (p. 5).
- Exclusions: [V] four kinds of names are removed (p. 5–6):
  1. extraction noise;
  2. standard-library modules: the union of `sys.stdlib_module_names` for Python 3.10–3.13 and the Node 18/20/22 built-ins;
  3. names that break PEP 508 or npm naming rules;
  4. Python import names that the pipreqs mapping links to an existing package. Names that appear as install targets stay candidates.
- Baselines or comparison conditions: [V]
  - Spracklen's 2024 figures: 3.59% best model, 5.2% commercial average, 21.7% open-source average (p. 3, p. 6).
  - Pairwise comparisons between the five models (p. 8).
  - Earlier versions of this paper (p. 10–11).

- Data source(s): [V] Spracklen's released prompt datasets, unchanged: 20,163 Stack Overflow prompts (SO_AT, SO_LY) and 19,806 LLM-written prompts (LLM_AT, LLM_LY), split evenly between Python and JavaScript (p. 4). No new 2026 prompts were added (p. 4).
- Sample size (N) and unit: [V]
  - One sample per prompt per model: 39,969 generations per model (39,964 for Sonnet 4.6), 199,840 in total (p. 4).
  - Unique hallucinated names: 1,746 on PyPI and 536 on npm (Table 7, p. 11).
  - Registration groups: A = 104 names and B = 2,178 names (p. 11–12).
- Sampling / selection method: [V] The models were chosen to cover the main commercial and open-weight providers at the frontier tier (p. 4). [A] The author notes the results depend on this choice of models (p. 13).
- Data availability (public? link?): [V] (p. 15)
  - Code: GitHub `churik5/slopsquatting-replication-2026` (MIT licence).
  - Re-check code, preregistration, deviation log and aggregate results: GitHub `churik5/slopsquatting-revalidation-2026`.
  - Raw responses (SQLite database): available to verified researchers on request.

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools:
  - [V] Generations were collected on 22–28 April 2026 (p. 4, p. 14).
  - [V] Provider defaults were used "unless noted". Temperature and top-p were recorded, but their values are not printed (p. 4).
  - [V] Refusal rates range from 1.27% (Haiku 4.5) to 31.51% (GPT-5.4-mini) (Table 1, p. 4; p. 6).
  - [V] Estimated cost: $1,160.29 in total (Table A.1, p. 17).

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] Mention-level rate: the share of extracted package references that are hallucinated. It is chosen to match Spracklen's unit (p. 6).
  - [V] Generation-level rate: the share of generations with at least one hallucinated reference. This is the rate named in the preregistration (p. 6).
  - [V] Jaccard similarity: how much two models' sets of hallucinated names overlap (p. 6).
  - [V] Registration share: the fraction of names registered between the start of exposure and the reference date T0 (p. 11).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): [V]
  - 95% Wilson confidence intervals for rates (p. 6).
  - Pearson χ² tests with Holm–Bonferroni correction over the 10 model pairs (α = 0.05) (p. 6).
  - Permutation tests (10,000 resamples, seed 42) (p. 6).
  - Newcombe intervals for differences (p. 7, p. 12).
  - Fisher's exact test and Cochran–Mantel–Haenszel tests (p. 12).
  - A stated minimum detectable effect: 10.5% at a 1% baseline with power 0.8 (p. 12).

## 7. Key findings
1. [V] Rates per model range from 3.63% (Haiku 4.5) to 5.02% (GPT-5.4-mini) of mentions, and from 2.15% (GPT-5.4-mini) to 3.39% (Gemini 2.5 Pro) of generations (p. 6; Table 2, p. 7).
2. [V] 7 of 10 model pairs differ significantly at the mention level and 8 of 10 at the generation level. Gemini, DeepSeek and GPT-5.4-mini do not differ significantly from each other (p. 6; Table 4, p. 8).
3. [V] Python rates exceed JavaScript rates for every model, by 2.34 to 3.47 percentage points per mention (Table 2, p. 7). [A] The author reads this as the reverse of Spracklen's 2024 finding (p. 7, p. 13).
4. [V] LLM-written prompts give higher rates than Stack Overflow prompts for every model. Pooled over models: 4.79% (LLM_AT) and 5.44% (LLM_LY) vs 2.28% (SO_AT) and 3.10% (SO_LY) (Table 3, p. 7).
5. [V] Overlap between models' hallucinated names: mean Jaccard 0.219 (range 0.173–0.342). DeepSeek and GPT-5.4-mini overlap most (J = 0.342) (p. 8).
6. [V] The universal set (Table 5, p. 9):
   - 104 names (88 PyPI, 16 npm) are hallucinated by all five models, accounting for 2,699 mentions;
   - 54 are one edit away from a registered package;
   - 4 lie in npm scopes owned by an organisation, so outsiders cannot register them.
7. [V] Haiku 4.5 hallucinates less than Sonnet 4.6 (3.63% vs 4.09%, Holm-corrected p = 0.012). [A] The author withdraws an earlier explanation and has no mechanism for this (p. 9).
8. [V] Checking against the live registries lowered every model's rate by about a fifth. The largest correction was import names of real packages (144–207 mentions per model). The universal set shrank from 127 to 104 names (p. 10–11; Tables 6–7).
9. [V] Registration within about six months (p. 12):
   - 25 of 2,282 hallucinated names (1.1%) were registered;
   - publishing had no detectable effect: 0 of 87 published vs 2 of 101 comparable unpublished names, a difference of −2.0 points (95% CI −6.9 to +2.5), p = 0.50.
10. [V] What the 24 registrations in group B were (p. 12):
    - 22 are packages whose content was not inspected;
    - one is an npm security placeholder that carries a malicious-package record published after the runs;
    - one is a name-reservation placeholder.
11. [V] At least 23 names the models suggest had previously hosted malware that the registries removed: 13 npm security placeholders and 10 PyPI names with OSV malicious records (p. 12).

## 8. Limitations stated by the authors
- [A] Scope: smaller open models, fine-tuned variants, quantized local models and agentic setups are not studied (p. 14).
- [A] Timing: generations from April 2026 and registry checks from November 2026 describe one point in time, and models change without notice (p. 14).
- [A] Leakage: the Spracklen prompts were released in January 2025 and may be in 2026 training data, which would push rates down. No new held-out prompts were used (p. 14).
- [A] GPT-5.4-mini ran at minimal reasoning effort and refused 31.51% of prompts. The prompts it answered may not be a random subset (p. 14).
- [A] The DeepSeek alias returned `deepseek-v4-flash` in its response metadata during the run window, so the underlying model may have changed (p. 14).
- [A] Other install forms are missed, so rates may be underestimated (p. 14).
- [A] The pipreqs mapping covers only about 1,157 import names (p. 14).
- [A] PyPI creation dates can be too late if files were deleted, and removed malicious packages have no creation date (p. 14).
- [A] Whether names can be registered by outsiders was not re-estimated (p. 14).
- [A] The natural experiment is small, can detect only large effects, and cannot tell defensive from malicious registrations without inspecting content (p. 14).
- [A] The preregistration timestamps are self-attested, because the repository was local (p. 6, p. 14).

## 9. Limitations we identified
- [I] **The comparison with Spracklen uses a different measurement.** The paper says "We follow Spracklen's extraction approach" (p. 5), but it parses import statements. Spracklen explicitly rejects import parsing and asks the model for package lists instead ([@spracklen2024we, p. 6–7]). So the headline "2026 frontier at 2024's commercial level" (p. 1, p. 6) and the Python>JavaScript "inversion" (p. 13) compare different measurements. Based on comparing the two papers' method sections.
- [I] **Two claims attributed to Spracklen were not found in Spracklen.** Churilov says Spracklen blamed npm's "larger and more fragmented namespace" for the higher JavaScript rates (p. 13), and observed that "smaller models within a family tend to hallucinate more" (p. 9). A text search of spracklen2024we found neither statement.
- [I] **Python rates may still be inflated.** pipreqs maps only about 1,157 import names (p. 14). Other cases where the module name differs from the package name still count as hallucinations, and these mostly affect Python. This could partly explain why Python exceeds JavaScript; the author argues against this on p. 13.
- [I] **Long gap between generation and checking.** About six months separate generation (April 2026) and the registry checks (November 2026). The creation-time rule handles names registered in between (p. 5), but packages deleted in between could be wrongly counted as hallucinations.
- [I] **Generation settings are not printed.** Temperatures are not given (p. 4), so rates cannot be matched to Spracklen's setting of 0.7.
- [I] **Reliability record.** This is the fourth version of a fast-revised single-author paper, and several numbers in earlier versions could not be reproduced (p. 10–11, p. 17). The author used AI assistance to draft the text (p. 15). The transparency is good, but exact values should be independently replicated before relying on them.
- [I] **Model rankings depend on refusals.** GPT-5.4-mini ranks differently at the mention and generation levels (p. 6), so "which model is safest" depends on how refusals are treated.

## 10. Threats to validity
- Internal (confounds, leakage, selection):
  - [A] The prompts may be in the models' training data (p. 14).
  - [I] Models refuse at different rates, which distorts generation-level comparisons (p. 6).
  - [I] Reasoning-effort settings and the DeepSeek alias may have shifted (p. 14).
- External (generalisability of sample/context):
  - [A] Results apply to frontier API models only. Smaller or local models may still show 2024-like rates (p. 13–14).
  - [I] No agentic or IDE setting is tested.
- Construct (do metrics measure the concept?):
  - [I] Import-based extraction counts names in code that may never actually be installed. Install targets are treated more strictly than imports (p. 5–6).
  - [V] The dated check, with two methods per registry, is stronger than the static lists used earlier (p. 5).
- Statistical conclusion (power, multiple comparisons, variance):
  - [V] Holm correction is applied and confirmed with permutation tests (p. 6, p. 8).
  - [V] The natural experiment is explicitly underpowered: it could only detect an effect of about 10.5% (p. 12).
  - [I] Only one sample per prompt was drawn, so repetition within a prompt is not measured.
- Reproducibility (data/code/setup reported?):
  - [V] Code, preregistration and aggregates are public; raw responses are available on request (p. 15).
  - [A] The repository history was rewritten, and an earlier claim that data had been deposited on Zenodo was wrong (p. 15).

## 11. Future research directions
- Stated by authors [A]:
  - report overlaps across models as a standard quantity (p. 10);
  - make registration monitoring a standard part of measurement studies (p. 15);
  - test smaller, quantized and next-tier models (p. 13–14);
  - use new held-out prompts (p. 14);
  - vary reasoning effort (p. 14);
  - study agentic setups with retrieval (p. 14).
- Suggested by us [I]:
  - Re-run on laptop-scale open-weight models with the same live-check protocol, since this tier is explicitly out of scope (p. 14).
  - Compare import-based and model-queried extraction on the same generations, to make the 2024 and 2026 numbers comparable.
  - Measure repetition with more than one sample per prompt.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1 (frontier rates, language, prompt source, refusals), RQ2 (universal set, registrations, malware history), RQ4 (two-method live check, time-of-generation rule, exclusions, statistics), RQ5 (untested settings: local/quantized models, agents).
- How it informs our work [I]:
  - **Validation protocol.** This paper gives the most complete replicable protocol in the set, and all of it runs on a laptop (p. 5–6):
    - two methods per registry: PyPI JSON plus Simple API, npm registry plus deps.dev;
    - two rounds at least 12 h apart, at 1 request per second per host;
    - an append-only log of every response;
    - comparing package creation time with generation time;
    - an OSV lookup for malicious records;
    - excluding the standard library via `sys.stdlib_module_names` and the Node built-ins;
    - filtering names with PEP 508 / npm naming rules;
    - mapping import names to packages with pipreqs;
    - Wilson intervals and Holm-corrected χ² tests.
  - **The gap a laptop study can fill.** The paper explicitly leaves out quantized local models and agentic setups (p. 14).
  - **Prompt source matters.** LLM-written prompts give about double the rate of Stack Overflow prompts (p. 7), so a small study should stratify by prompt source.
  - **Existence checks are not enough.** About 1% of hallucinated names are registered within six months, and at least 23 suggested names have a malware history (p. 12). A defence that only checks whether a package exists would let some dangerous names through. This supports adding checks on package age, OSV records and placeholder status.

# From Hallucination to Registration: Do the Package Names That LLMs Invent Actually Get Claimed?

- Authors: Okwor, Daniel
- Year / venue: 2026, Zenodo preprint ("Preprint, July 2026"), single author, affiliation Orygn LLC (p. 1). **Source tier 4: grey literature, not peer-reviewed, usable as background evidence only.** The metadata was verified from one source only (OpenAlex).
- DOI: 10.5281/zenodo.21199426 (metadata). The PDF prints 10.5281/zenodo.21199427 (p. 1). This may be the difference between the Zenodo concept DOI and a version DOI; not resolved.
- Source text: `fulltext.txt` (page refs = PDF page index); user-supplied PDF.

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
[A] Earlier studies measure exposure (how often models hallucinate). This paper measures the next step, harm: how many invented names are actually registered on the package index, by whom, and with what intent (p. 1–2). [A] The author claims no prior work retrieves true registration dates and judges the intent behind registrations (p. 2).

## 2. Research questions / hypotheses
- [A] Of the names models invent, how many are registered today? When a hallucinated name is registered, what is the person who registered it doing with it (p. 2)? No formal hypotheses are stated.

## 3. Methodology
- Research design: [V] Two registration measurements plus a lab demonstration (p. 2):
  - (a) a corpus of self-generated names, re-checked live;
  - (b) an "anchor set" of previously published hallucinated names, judged by registration date and by static inspection of package content;
  - (c) an offline demonstration of code running at install time.
- Approach / model / intervention: [V] Five open-weight models run locally through Ollama: qwen2.5-coder:7b, deepseek-coder:6.7b, codellama:13b, codestral:22b and gpt-oss:20b (p. 3). The prompts ask for Python and JavaScript solutions from a "fixed task set" at temperatures 0.7 and 1.0, with fixed seeds. gpt-oss gets a larger output budget (p. 3).
- Hallucination gate (two checks): [V] (p. 3)
  - Check A: the name is absent from a frozen snapshot taken at t0 = 2026-06-30. The snapshot holds 839,365 normalised PyPI names (from the simple index) and 4,194,421 lowercased npm names (from a public name mirror), each list hashed with SHA-256.
  - Check B: the live registry returns 404 for the name.
  - When the checks disagree: absent at t0 but live now = a candidate registration after t0; present at t0 but 404 now = a yanked package; a network error = unknown.
- Extraction: [V] (p. 3)
  - Python parsed with `ast`; JavaScript with acorn, with a lenient fallback for malformed code.
  - Import names mapped to package names where they differ (e.g. sklearn → scikit-learn); the source of the mapping is not reported.
  - PEP 503 normalisation.
  - Standard-library and built-in modules excluded.
  - Scoped and subpath specifiers resolved.
  - Names that fail the registries' naming rules dropped.
- Anchor-set judgement: [V] (p. 4)
  - True first-registration time: npm `time.created`; on PyPI, the earliest release upload time.
  - Static inspection only: `setup.py`, `PKG-INFO` and manifests are read as text and scanned for install-time hooks and red-flag tokens.
  - A fixed rubric classifies each name as malicious, defensive placeholder, organic (a real unrelated package) or individual reservation.
- Baselines or comparison conditions: None. [V] There is a negative control: names absent from the snapshot but live in the extra run (p. 7).

## 4. Dataset and sample
- Data source(s): [V] The self-generated corpus (p. 3–4). [V] The anchor set: 149 previously published hallucinated names from the Trend Micro slopsquatting dataset and the DepScope corpus (p. 2–4). The selection is described only as names "that have circulated long enough to attract registration" (p. 1, p. 5); the actual selection rule is not reported.
- Sample size (N) and unit: [V] 4,800 generations, then 2,000 more with fresh seeds, 6,800 in total. These gave 1,186 + 455 = 1,641 distinct confirmed hallucinated names (p. 4). [V] Anchor set: 149 names, 22 of them registered (p. 5).
- Sampling / selection method: [V] Generations were spread evenly across the five models in round-robin order (p. 5, Figure 1). Not reported: the size of the task set, the prompt texts, the split between languages.
- Data availability (public? link?): [A] Code, configuration and snapshot hashes "will be deposited" with a DOI. The raw name list is withheld, and the registry metadata behind the attribution is available to reviewers under embargo (p. 8–9). Not available at the time of writing.

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools:
  - [V] Temperatures 0.7 and 1.0, fixed seeds, Ollama runtime (p. 3).
  - Not reported: seed values, maximum tokens, quantization level of the Ollama models, hardware.
  - [V] All 1,641 names were re-checked live on 2026-07-04 (p. 5). The date of the anchor-set registration check is not reported.
  - [V] The gate was tested on 17 known-real and 8 made-up names, with precision and recall of 1.000 (p. 4).
  - [A] "Every headline count" was re-derived by an independent recomputation (p. 4); how is not described.
- Code availability: Not yet available (p. 8).

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] Number of distinct confirmed hallucinated names, and new names per generation, used to judge whether the name space runs out (p. 4).
  - [V] Share of names registered, with a rule-of-three 95% upper bound (the "rule of three": if 0 of n cases are seen, the 95% upper bound is about 3/n) (p. 5–6).
  - [V] Classification of registered names by intent (p. 5–6).
  - Not reported: any hallucination rate, per mention or per generation.
- Statistical testing (tests used, significance, effect sizes, confidence intervals): [V] Rule-of-three upper bounds only: below 0.2% for 0 of 1,641, about 14% for 0 of 22, about 2% for 0 of 149 (p. 5–6). No other tests.

## 7. Key findings
1. [V] New names keep appearing: 0.228 new names per generation in the extra run vs 0.247 in the original. 450 of the 455 new names came from a single model (p. 4). 82 of the first 1,186 names came from two or more models (p. 4).
2. [V] All 1,641 self-generated hallucinated names were still unregistered on 2026-07-04; the 95% upper bound is below 0.2% (p. 5).
3. [V] Of the 149 public anchor names, 22 are registered: 19 defensive research placeholders, 1 organic name collision, 1 individual reservation, 1 typosquat from 2019, and 0 malicious. The 95% upper bound on the malicious share is about 14% (p. 5–6).
4. [V] The 19 placeholders all have the same summary ("Benign slopsquatting research package") and blank identity fields. They were uploaded by numbered accounts of one operator, consistent with working around a per-account rate limit (p. 6).
5. [V] Negative control: 11 names were absent from the snapshot but live at check time. All were registered before t0 (2014–2023), so they are names the npm mirror missed, not new squats (p. 7).
6. [V] In an offline lab, a harmless package ran code at install time under both pip (`setup.py` during the build) and npm (`postinstall`), before any import (p. 7).
7. [V] The npm name mirror is unreliable: it lists more names than npm's own total, yet misses real packages registered years ago (p. 3).

## 8. Limitations stated by the authors
- [A] Zero malicious does not mean zero risk. A benign placeholder can be turned malicious in a later release (p. 8).
- [A] The registered sample is small (22 of 149) and biased towards names claimed by defenders, because defenders scrape the same public lists. One person assigned all intent labels (p. 6, p. 8).
- [A] The corpus is a lower bound, because false entries in the npm mirror reject some real hallucinations before the live check (p. 3, p. 8).
- [A] The corpus comes from the author's own prompts, not from production or agent traffic (p. 8).
- [A] The time window is short (p. 7–8).

## 9. Limitations we identified
- [I] **The "cleanest result" is almost guaranteed by design.** The 1,641 names were generated privately and re-checked only 4 days after the snapshot (p. 3, p. 5). An attacker could only have registered them by generating the same names independently within those days. The 0 of 1,641 result therefore says little about attacker behaviour.
- [I] **No hallucination rate is reported.** Neither mentions per generation nor share of generations is given, so this paper cannot contribute rates to RQ1. The setup is also under-specified: the task set, prompts and quantization are unknown.
- [I] **Cited numbers are misreported.**
  - It describes Spracklen's 21.7% as "of generations" (p. 1). Spracklen defines the rate per recommended package ([@spracklen2024we, p. 7]).
  - It quotes Churilov's "4.62% to 6.10% per generation", "127 names" and "53 registrable" (p. 1–2). These are figures from Churilov's versions 1–3. Version 4 supersedes them (3.63–5.02% of mentions, 104 names, registrability not re-estimated), and the earlier rates were per mention, not per generation ([@churilov2026range, p. 10–11]).
- [I] **The anchor-set selection is unclear.** How the 149 names were drawn from the datasets is not specified (p. 4–5), and the date of the registration check is not given.
- [I] **Static inspection may miss payloads.** Reading `setup.py`, `PKG-INFO` and manifests can miss malicious code placed in package modules or run at import time. Wheel-only packages are not discussed (p. 4).
- [I] **Possible conflict of interest not addressed.** The author is affiliated with a company (Orygn LLC, p. 1), and there is no funding or conflict-of-interest statement.
- [I] **Not reproducible yet.** The promised code deposit has not appeared (p. 8).

## 10. Threats to validity
- Internal (confounds, leakage, selection):
  - [A] The anchor set over-represents names claimed by defenders (p. 6).
  - [I] One person assigned all labels (p. 8), with no check of agreement with a second rater.
- External (generalisability of sample/context):
  - [A] Only small local open-weight models are studied, not agent traffic (p. 8).
  - [I] Only PyPI and npm.
  - [I] A single snapshot from mid-2026.
- Construct (do metrics measure the concept?):
  - [I] "Unregistered after 4 days" does not measure whether a name can be exploited.
  - [V] The two-check gate (absent at t0 and live 404) is a sound definition of hallucination as of t0 (p. 3).
  - [I] The gate ignores whether the package was registered after the model's training cutoff (compare krishna2025importing).
- Statistical conclusion (power, multiple comparisons, variance): [V] Only rule-of-three bounds are reported (p. 5–6). [I] With only 22 registered names, the bound on the malicious share (about 14%) is wide. The author acknowledges it rules out only a high malicious rate (p. 6).
- Reproducibility (data/code/setup reported?):
  - [V] Snapshot hashes are promised (p. 3).
  - [I] Prompts, seeds and the task set are not given.
  - [A] The code has not been deposited yet (p. 8).

## 11. Future research directions
- Stated by authors [A] (p. 8):
  - keep watching the 1,641 names and re-check them periodically;
  - move from self-generated output to live coding-agent traffic;
  - get access to larger gated corpora that are not pre-filtered by public visibility.
- Suggested by us [I]:
  - report hallucination rates with their denominators;
  - publish the prompt set;
  - re-check registrations at 3, 6 and 12 months;
  - inspect wheel contents as well as setup files;
  - combine with Churilov's six-month registration data for a longer baseline.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ2 (registration and intent of hallucinated names; defensive squatting), RQ4 (frozen hashed snapshot plus live check; mapping import names to packages), RQ5 (local Ollama setting; agent traffic proposed as future work).
- How it informs our work [I]:
  - **Closest template for a laptop-scale measurement.** Five open-weight models run locally through Ollama (p. 3). The pipeline components can be reused directly (p. 3):
    - a frozen registry snapshot hashed with SHA-256 (PyPI simple index with PEP 503 normalisation; npm names lowercased) used as an offline first filter;
    - a live 404 check to confirm absence;
    - parsing with `ast` and acorn;
    - mapping import names to package names;
    - excluding the standard library.
  - **Known pitfall.** The npm name mirror is unreliable (p. 3). Treat the live registry as ground truth, or use npm's replication feed.
  - **Gaps in reported detail.** The task set, prompts, seeds and hardware are not given, so the setup cannot be copied exactly.
  - **How much weight to give it.** Its registration findings agree with churilov2026range, which found about 1% of names registered within six months, one of them with malware. Together they suggest that weaponised slopsquatting on PyPI and npm is still rare. As tier-4 evidence, this paper should only support RQ2 claims, not anchor them.

# Importing Phantoms: Measuring LLM Package Hallucination Vulnerabilities

- Authors: Krishna, Arjun; Galinkin, Erick; Derczynski, Leon; Martin, Jeffrey (University of Waterloo; NVIDIA) (p. 1)
- Year / venue: 2025, arXiv (preprint, not peer-reviewed), arXiv:2501.19012v1, 31 Jan 2025 (p. 1). Page 1 carries the footer "Proceedings of the 41st International Conference on Machine Learning, Vienna, Austria. PMLR 235, 2024" (p. 1). [I] This is most likely left over from the ICML paper template: v1 was posted in January 2025, after ICML 2024 had taken place. We treat the venue as unverified.
- DOI: 10.48550/arxiv.2501.19012 · URL: https://arxiv.org/abs/2501.19012
- Source text: `fulltext.txt` (page refs = PDF page index). PDF pages 13–23 are only figure-placeholder stubs.

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
[A] The paper aims to measure package hallucination across programming languages (Python, JavaScript, Rust) and types of LLM, to find patterns linking model characteristics to hallucination, and to develop defences (p. 1–2).

## 2. Research questions / hypotheses
- [A] RQ1: how often does package hallucination happen? (p. 2)
- [A] RQ2: what impact does the programming language have? (p. 2)
- [A] RQ3: how does model size affect package hallucination? (p. 2)
- [A] RQ4: does it differ between coding-specialised and general-purpose LLMs? (p. 2)
- [A] Also studied: "induced" hallucination, where the prompt asks for a package or API that does not exist, vs "natural" hallucination (p. 3, p. 5).

## 3. Methodology
- Research design: [V] Black-box probing with the garak framework (an open-source tool for probing LLMs). Prompts are sent to the model, imported packages are extracted from the output, and the names are compared with registry lists (p. 3).
- Definition: [V] A package counts as hallucinated if it meets any of these conditions (p. 3):
  - it is not registered on npm, PyPI or crates.io; or
  - it was first registered after the model's knowledge cutoff; or
  - if the cutoff is unknown, it was first registered less than 90 days before the model was first published.

  How the knowledge cutoffs were obtained is not reported.
- Approach / model / intervention: [V] 11 models (Table 1, p. 3):
  - CodeGemma 7B
  - Dracarys-Llama-3.1-70B
  - GPT-4o (gpt-4o-2024-08-06)
  - Granite-3.0 8B
  - Llama-3.1 8B and Llama-3.1 70B
  - Mamba-Codestral 7B
  - Mistral-NeMo-Minitron-8B
  - Llama-3.1-Nemotron-70B
  - Qwen2.5-Coder 7B
  - StarCoder2-15B

  [V] Six are classed as code-specialised and five as general-purpose (p. 6). Open-weight models were preferred (p. 3–4).
- Prompts: [V] Every combination of 7 request templates and 13 coding-task descriptions, filled in for each language (p. 4; Tables 6–7, p. 12). Each request is repeated five times (p. 4).
  - [V] Some templates use personas, e.g. "As a woman, I need example...", "What <language> module would a Black person use..." (p. 12). Their purpose is not explained.
  - Which prompts count as "induced" is not stated explicitly.
- Extraction: [V] Regular expressions per language (p. 12):
  - Python: `import x`, `from x import`, `import x as`.
  - JavaScript: ES6 `import ... from`, CommonJS `require()`.
  - Rust: `use x`, `extern crate x`, and `x::` path references.

  Not reported: mapping import names to package names, name normalisation, exclusion of the standard library.
- Baselines or comparison conditions: [V] Comparisons across languages, code-specialised vs general models, model size, and HumanEval/MBPP scores (p. 4–7). There is no mitigation baseline.

## 4. Dataset and sample
- Data source(s): [V] Package names and release dates scraped from the registries, as of 30 January 2025: npm 3,391,235; PyPI 604,814; crates.io 169,823 (Table 2, p. 4). How the scraping was done is not reported.
- Sample size (N) and unit: The number of generations, per model or in total, is not reported. [I] From the design we estimate 7 templates × 13 tasks × 3 languages × 5 repeats = 1,365 prompts per model, about 15,000 in total (p. 4, p. 12). This is our estimate, not a reported figure. Number of models: 11 (p. 6).
- Sampling / selection method: [V] Models were chosen to vary in size, provider and purpose (p. 3). The tasks are a hand-picked mix that includes obscure or possibly fictional targets such as "StrombergDB", "Tektronics 4051" and "Query/400" (p. 12).
- Data availability (public? link?): [V] The paper only states generally that it used open-source software and openly available models (p. 10). No link to data or code is given.

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Experiments were run through garak (p. 3), with each request repeated five times (p. 4). Not reported: temperature, decoding settings, maximum tokens, hardware, inference provider, model quantization.
- Code availability: No repository is linked in the paper (p. 10). [I] garak itself is open source; the paper does not say whether the exact probe used is included in it.

## 6. Evaluation metrics
- Metric — what it measures — why chosen: [V] Package Hallucination Rate (PHR) = the share of prompts that produced at least one hallucinated package (p. 4). This is counted per generation, unlike Spracklen's per-package rate. Repeats and varied prompts are used to make the measure less fragile (p. 4).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): [V]
  - Pearson correlation between model size and PHR: r = −0.542, p = 0.00114; with log(size): r = −0.593, p = 0.00028 (p. 6–7).
  - HumanEval vs PHR: r = −0.7887. MBPP vs PHR: r = −0.2919. No p-values are given for these (p. 7).
  - A t-test of code-specialised vs general models: significant only for JavaScript, and not significant once GPT-4o is removed (p. 6).
  - No confidence intervals for PHR and no correction for multiple comparisons.

## 7. Key findings
1. [V] All models hallucinated packages in every language. PHR ranged from 0.22% (Nemotron-Llama-3.1-70B, JavaScript and Rust) to 46.15% (Granite-3.0, Python) (Table 3, p. 4; p. 8).
2. [V] Average PHR by language: JavaScript 14.73%, Python 23.14%, Rust 24.74% (p. 8; Figure 1, p. 5). Spread across models (standard deviation): Python 16.03, Rust 14.37, JavaScript 8.43 (p. 4).
3. [V] Best models (Table 3, p. 4), JavaScript / Rust / Python:
   - GPT-4o: 1.76% / 10.99% / 3.52%.
   - Nemotron-70B: 0.22% / 0.22% / 4.84%.
4. [V] Larger models hallucinate less: r = −0.542, p = 0.00114 (p. 6).
   - [I] These p-values are reproduced exactly with n = 33, i.e. 11 models × 3 languages treated as independent data points. With n = 11 models, the same correlations give p ≈ 0.085 (raw size) and p ≈ 0.055 (log size), which are not significant. So the size effect is not significant at the level of models. Based on our recomputation of the standard t-test for a correlation coefficient.
5. [V] Models with higher HumanEval scores have lower average PHR: r = −0.7887 over 10 models (Dracarys has no HumanEval score) (Table 5, p. 7). [A] The authors say coding benchmarks "can serve as efficient proxies for assessing hallucination risks" (p. 7).
6. [V] Code-specialised models have higher average PHR than general models: Python 30.22% vs 14.64%, Rust 31.58% vs 16.53%, JavaScript 18.90% vs 9.71% (Table 4, p. 6). The difference is significant only for JavaScript and disappears without GPT-4o. [A] The authors conclude there is likely no meaningful difference (p. 6).
7. [A] Induced hallucinations occur at "nearly double" the rate of natural ones. No figures are given, and the authors note there were far fewer induced attempts (p. 5).
8. [A] Proposed defence: a date-aware verification list of packages published before each model's training cutoff, used to flag suggestions. The authors also advise developers to prefer familiar packages and to name packages explicitly (p. 8). The defence is not evaluated.

## 8. Limitations stated by the authors
- [A] 11 models may be too few to detect a difference between code-specialised and general models (p. 6).
- [A] There were far fewer induced attempts than natural ones (p. 5).
- [A] The models' training-data composition is unknown, so explanations based on ecosystem size or language popularity are speculative (p. 5).
- [A] The verification list does not catch malicious packages that are already in the historical index (p. 8).

## 9. Limitations we identified
- [I] **Likely false positives from module/package name mismatches.** Python imports are extracted by regex, with no reported mapping from import names to package names and no standard-library filter (p. 12). Common modules whose names differ from their PyPI package (e.g. `sklearn`, `cv2`, `yaml`) and standard-library modules may be counted as hallucinations. In Rust, the `name::` pattern can match `std::`, `crate::` or local modules. This would push Python and Rust rates up. Compare churilov2026range, which found import names of real packages to be the largest single source of false positives ([@churilov2026range, p. 10]).
- [I] **The size correlation counts the same model three times.** See finding 4. The headline "statistically significant" size effect depends on treating each model's three language results as independent.
- [I] **Text contradicts the paper's own tables.**
  - The text says Mamba-Codestral achieves "lower PHRs than all other models in its size class" (p. 6). Table 5 gives Mamba-Codestral 21.03% vs Llama-3.1-8B 15.24% (p. 7).
  - Coding models are said to span "14.95% to 24.40% PHR ... µ = 26.90%" (p. 6); the mean lies outside that range.
  - The text describes Granite-3.0 at the "15 billion parameter scale" (p. 6), but Table 1 lists it as 8B (p. 3).
- [I] **Key numbers are missing.** Not reported: the number of generations, the temperature, where the cutoff dates came from, which prompts count as induced. The induced vs natural comparison has no figures.
- [I] **The defence is not evaluated.** The abstract and introduction say the paper develops and evaluates defences (p. 1–2), but the mitigation section only proposes one (p. 8).
- [I] **The task set is small and unusual.** 13 hand-picked tasks, several naming obscure or fictional systems (p. 12), make PHR depend heavily on task choice. The rates are not comparable in size with Spracklen's or Churilov's.
- [I] **Possible conflict of interest not disclosed.** Three of the four authors work at NVIDIA (p. 1), two NVIDIA-derived models are evaluated, and Nemotron performs best. There is no conflict-of-interest statement.
- [I] **Unexplained persona prompts.** The demographic persona templates (p. 12) add variation that is not controlled or analysed.

## 10. Threats to validity
- Internal (confounds, leakage, selection): [I] The choice of tasks drives the rates. Induced and natural prompts are pooled into one PHR, which mixes two different things (p. 4–5, p. 12).
- External (generalisability of sample/context):
  - [I] 11 models from 2024 and a small prompt grid.
  - [V] This is the only study in our set that covers Rust and crates.io (p. 4).
- Construct (do metrics measure the concept?):
  - [V] A distinctive strength: the date-aware definition counts packages registered after a model's cutoff, including possible squats, as hallucinations (p. 3).
  - [I] Regex import extraction without name mapping weakens the measure.
  - [I] PHR is per generation, so it differs from Spracklen's per-mention rate.
- Statistical conclusion (power, multiple comparisons, variance): [I] Correlations count the same models several times, PHR has no confidence intervals, and the HumanEval correlation (10 points) has no p-value (p. 6–7).
- Reproducibility (data/code/setup reported?):
  - [V] The prompt templates and tasks are listed in full (p. 12).
  - [I] Decoding settings, generation counts and code are not reported, so exact replication is not possible.

## 11. Future research directions
- Stated by authors [A] (p. 6–9):
  - reduce package hallucination in smaller models;
  - study the link between code optimisation and security;
  - build defences that work across languages and model architectures;
  - test whether non-transformer models (e.g. Mamba) are more robust;
  - use more models to test the code-specialised vs general difference (p. 6);
  - optimise coding quality and PHR together, i.e. multi-objective optimisation (p. 7).
- Suggested by us [I]:
  - Implement and evaluate the proposed date-aware verification list, which is cheap and feasible on a laptop.
  - Re-run with import-to-package mapping and a standard-library filter.
  - Report generation counts and do statistics at the level of models.
