# Names Can Hurt: Spotting Slopsquatting Risks Caused by Package Name Hallucinations in Local Coding LLMs

- Authors: Raj, Akash; Sahu, Sargam
- Year / venue: 2026, arXiv (Cornell University) (preprint)
- DOI: 10.5281/zenodo.22087562 · URL: https://arxiv.org/abs/2608.23897

## 1. Research objective
- [A] Build and evaluate a client-side guard that stops a coding LLM's hallucinated Python package names from turning into slopsquatting installs. The guard targets "small, open-weight, locally runnable LLMs in the 7B to 70B range" (p. 2).
- [A] The authors say local models matter for three reasons (p. 2):
  - developers outside large companies run them;
  - they "tend to hallucinate more often than frontier systems";
  - local deployment rules out asking a hosted model to verify the output.

  No evidence is given for the second point.

## 2. Research questions / hypotheses
- No formal RQs or hypotheses. The paper lists five contributions instead (p. 2):
  1. a two-layer detector (PyPI existence check plus a per-LLM Random Forest);
  2. an import-name reconciler;
  3. a LangGraph retry/fallback agent;
  4. an evaluation on 300 prompts;
  5. a user acceptance study.
- §6 implicitly answers six questions (pp. 6–12):
  - how often the pipeline gives up;
  - how much retries and fallback recover;
  - how give-up varies by prompt tier;
  - how many flagged names already exist on PyPI;
  - whether per-LLM classifiers transfer across models;
  - whether a hand-written rule matches the Random Forest.

## 3. Methodology
- Research design: [V] A system-building paper with a single-configuration evaluation (one primary/fallback model pair), an offline classifier analysis and a convenience-sample survey (pp. 6–12). There is no control condition without the detector, apart from earlier buggy system versions (p. 7).
- Approach / model / intervention:
  - [V] **Extractor.**
    - Parses the syntax tree (AST) of Python code blocks and keeps only the top-level module name.
    - A regex fallback runs only inside code fences and ignores keywords and shell tokens.
    - `pip install` lines are read only inside code fences (pp. 3, 5).
  - [V] **Layer 1, deterministic check.** One PyPI JSON API lookup per name. A 404 means the name is fake; a 200 sends the package metadata to the classifier (p. 5).
  - [V] **Layer 2, Random Forest.** 400 trees, 10 features (p. 5):
    - 8 name features: length, number of parts, digits, a letter repeated three times, hype words (`super`, `pro`, `ai`, `magic`), generic words (`helper`, `tools`), a `py-`/`python-` prefix, and Levenshtein distance to a list of the top 15,000 PyPI names;
    - 2 metadata features: maintainer count and whether a GitHub URL is present.
  - [V] **Import-name reconciler.**
    - A 24-entry YAML table (e.g. `cv2` → `opencv-python`, `PIL` → `Pillow`).
    - It is consulted only after a PyPI 404, and a mapped name is accepted only if the install name passes both layers.
    - The authors' security argument: an attacker-registered `cv2` returns 200, so the reconciler never runs and the classifier must catch it (pp. 5–6).
  - [V] **Agent.**
    - A LangGraph state machine with six nodes.
    - Retry budget is 1 per model ("up to 2 attempts"), with rising temperature (0.7 → 1.0 → 1.2).
    - After the budget is spent, the task goes to a fallback model with its own matched classifier.
    - Every attempt is logged to JSONL (pp. 3, 6).
- Baselines or comparison conditions:
  - [V] Earlier system versions v0/v1 (broken regex, no reconciler) are used as an ablation (p. 7).
  - [V] Three hand-written rules are compared with the Random Forest on the same package-disjoint split (p. 12).
  - [V] LLM self-verification is described as a "baseline" in related work but is **not run** (p. 3).
  - [V] There is no comparison with any published detector or with Spracklen et al.'s method; the reference list has only three entries (p. 15).

## 4. Dataset and sample
- Data source(s):
  - [V] 300 single-line Python coding prompts, written by hand (p. 6).
  - [V] Classifier data: "Sargam's dataset" (`raw_master_dataset.csv`) of package names generated by seven LLMs (pp. 9, 14). How it was generated (prompts, hosting, dates) is not reported.
- Sample size (N) and unit:
  - [V] Prompts: 300 in 18 tiers of 5–30 prompts each (pp. 6–8):
    - about 140 routine tasks (data engineering, security/DevOps, standard workflows);
    - about 55 obscure-dependency tasks;
    - about 105 adversarial prompts.
  - [V] Runs and verdicts: 385 runs (300 primary + 85 fallback) gave 823 package verdicts (p. 8).
  - [V] Classifier data (pp. 9–10):
    - 464 unique package names across 7 LLMs; 210 occur in at least two models and 42 in all seven;
    - each model has 68–108 hallucinated rows, which leaves 2–12 positive examples per test slice.
  - [V] Survey: n = 24 CS undergraduates (p. 11).
- Sampling / selection method:
  - [V] The researchers wrote the prompts themselves. Adversarial prompts name packages or use "tricky wording" such as asking for "the newest and most capable library for X" (p. 6).
  - [V] Survey participants were "Sargam's CS undergraduate peers" / "the intern's friends" (pp. 2, 11).
  - Not reported: the tier construction criteria, and the classifier labelling procedure (who or what decided "hallucinated" in the training data).
- Data availability: [A] Code, mapping table, the 300 prompts, seven classifiers, the 385-record run log and the leakage-safe matrix are released at a GitHub repository (p. 15). We did not check the repository.

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools:
  - [V] **Models.**
    - Classifiers were trained for `gpt-5`, `gpt-oss-120b`, `llama-3.1-8b`, `llama-3.3-70b`, `llama-4-scout`, `qwen3-27b` and `qwen3-32b` (p. 2).
    - The agent evaluation uses two **Groq-hosted** models chosen to fit "our free-tier budget": primary `llama-3.1-8b`, fallback `llama-3.3-70b` (p. 2).
    - Not reported: exact model versions/checkpoints and quantization.
  - [V] **Classifier.** Random Forest with 400 trees; scikit-learn 1.8 in v2 (pp. 5, 7). Other hyper-parameters and the decision threshold on P(fake) are not reported.
  - [V] **Split.** The original split was a per-model 75/25 row split with `random_state=42`. It was replaced by a package-disjoint 75/25 split over the 464 unique names (p. 9).
  - [V] **Uncertainty.** Bootstrap 95% CIs with 1,000 resamples, for F1 only (p. 10).
  - **Standard-library handling: not reported.** The extractor keeps every top-level import name (p. 5), and every 404 counts as "fake" (p. 5). [I] Whether stdlib modules are filtered before the PyPI lookup is never stated. Any unfiltered stdlib name that returns 404 would be flagged and trigger a retry, which directly affects the give-up rates.
  - **Hardware: not reported.** All generation ran through Groq's hosted API, and the classifier analysis was "computed offline" (pp. 2, 6). [I] Despite the title, no model was run on local hardware. "Local" describes the model class (open-weight, 7–70B), not the deployment. The classifier training set also includes `gpt-5`, which is not a local model.
  - [V] **Run budget.**
    - One fallback run was lost to a mid-batch Groq rate-limit event (p. 7).
    - A cross-family fallback was not run because it "would have required 5 times the Groq token budget beyond the free tier" (p. 11).
  - [V] **Survey.** Standalone Streamlit tool; seven dimensions on a 1–5 Likert scale (p. 11).
- Code availability: [A] A GitHub repository is stated, and twelve extractor regression tests are said to pass (p. 15).

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] **Primary give-up rate:** share of prompts where the primary model exhausts its retry budget (p. 6).
  - [V] **Fallback rescue rate:** share of give-ups that the fallback recovers (p. 6).
  - [V] **End-to-end clean rate:** share of prompts that finish with no hallucinated recommendation (p. 6).
  - [V] **Per-tier and per-name breakdowns** (p. 6).
  - [V] **Classifier F1** in a 7×7 train-LLM × test-LLM matrix (p. 9).
  - [V] **Random Forest split importance** per feature (p. 10).
  - [V] **Likert means/medians** from the survey (p. 11).
  - [I] Why these metrics were chosen is not justified.
  - [I] Retries are triggered both by non-code answers and by flagged names (p. 4). The give-up rate is therefore a pipeline outcome, not a pure hallucination rate, and it also absorbs detector false positives (see §9).
  - Not reported: detector precision/recall against a manually checked ground truth on the 300-prompt run.
- Statistical testing:
  - [V] Bootstrap CIs are reported for the F1 matrix only (p. 10).
  - There are no CIs or tests for give-up, rescue or tier rates, and no significance testing.

## 7. Key findings
1. **Pipeline outcome on `llama-3.1-8b`.** [V]
   - 186/300 prompts (62%) produced code on the first try (p. 7).
   - 114 triggered a retry, and 28 of those were fixed by the retry, a 24.6% intra-model rescue (p. 7).
   - 86/300 (28.7%) exhausted the budget (p. 7).
   - The fallback ran on 85 of those 86 and recovered 14 (16.5%) (p. 7).
   - End to end, 228/300 (76%) finished clean; the remaining 72 would get a "do not pip install" warning (p. 7).
2. **Most of the give-up reduction came from preprocessing fixes, not the classifier.** [V] Primary give-up rates by version (p. 7):
   - v0: 79% (55/70), broken regex on the full text;
   - v1: 57% (33/58), AST plus code-only regex;
   - v2: 30% (18/60) on 60 prompts and 28.7% (86/300) on 300 prompts, after the reconciler was added.

   These are different, overlapping prompt sets, not one fixed set (p. 7). The reconciler fired 29 times over 4 distinct alias pairs in the 300-prompt run (p. 7). [A] The extractor and reconciler fixes together "caused a 49-point drop"; "Changing the classifier itself did not help much" (p. 12).
3. **Give-up rate rises with prompt tier.** [V]
   - Low tiers: Data Engineering 0% (n=20); Security & DevOps 5% (n=20); Level 1 and Level 2 10% each (n=10 each) (pp. 7–8).
   - High tiers: Hallucination Bait 55% (n=20); Adversarial (Realistic Hallucination Bait) 73.3% (n=30) (p. 8).
   - Direct Slopsquatting Stress Tests: 30% (n=30) (p. 8). This is below the abstract's "40 to 73% on slopsquat baits" (p. 1).

   [I] Table 2 is sorted by rate, not by any independent measure of how adversarial a prompt is. The "Level N" tiers are not in order of rate (Level 8 = 0%, Level 4 = 60%; pp. 7–8). The abstract's claim that the rate "scales almost linearly with prompt adversariality" (p. 1) is therefore an author claim with no defined adversariality scale.
4. **"Already-registered lookalike" finding (the paper's headline).**
   - [V] 385 runs produced 823 verdicts: 644 `real` (78.3%) and 179 `hallucinated` (21.7%) (p. 8).
   - [V] Of the 179 flags, "Half were true 404s". The other half returned PyPI status 200 and were flagged by the classifier because of suspicious metadata. The paper later gives 90 `status=200` flags (pp. 8–9).
   - [V] Table 3, "Wild caught PyPI registered squats and lookalikes" (pp. 8–9):

     | Name | Canonical project (per Table 3) | P(fake) | Flags |
     |---|---|---|---|
     | `pil` | Pillow | 0.89 | 36 |
     | `faiss` | faiss-cpu/-gpu | 0.57 | 10 |
     | `tabula` | tabula-py | 0.57 | 4 |
     | `haystack` | now haystack-ai | 0.56 | 2 |
     | `camelot` | camelot-py | 0.95 | 1 |
     | `skimage` | scikit-image | 0.58 | 1 |
     | `fastyaml` | none identified | 0.99 | 1 |
     | `fastvector` | none identified | 0.82 | 1 |
     | `graphbrain` | ambiguous | 0.92 | 2 |

     Further rows include `aiworkflow`, `taskgraph`, `promptstudio`, `flowgraph-ai`, `embeddinghub`, and "22 more" names with one or more flags each.
   - [A] "Approximately half of the hallucinated recommendations produced by the LLM were already present on PyPI as squats or low-quality lookalikes", so a deterministic-only check "would have caught only the other half" (p. 9).
   - [V] Security invariant: for all 90 `status=200` flags, the reconciler was never called (p. 9).
   - [A] The reconciler "correctly refused to help every single time" against an attacker suite; the attacker suite is not described (p. 6).
   - [V] **The paper's own evidence that import names are being flagged:**
     - The reconciler table maps `pil` → `Pillow` (p. 7). It can only fire after a 404, and `pil` returns 200 (p. 5), so it never fires for `pil`. As a result `pil` was flagged 36 times as a registered squat (Table 3, p. 8).
     - `pkg-resources` is listed among the true-404 "inventions" (p. 8).
     - In the bait test, the model's plain `faiss` is counted as a hallucinatory variant because the name is "metadata suspicious" (p. 11).
   - [I] **This finding needs caution.**
     - In Table 3, 36 + 10 = 46 of the 90 status-200 flags (≈51%) come from `pil` and `faiss`. Both are the normal *import* names of real projects (`import PIL` for Pillow, `import faiss` for faiss-cpu), as the paper's own "Canonical project" column shows (p. 8).
     - `skimage`, `camelot`, `tabula` and `haystack` are also import or legacy names of legitimate projects. `pkg_resources` is a module shipped with setuptools (general Python knowledge).
     - So a large share of the "already registered" half is probably correct `import` statements whose import name happens to be a separate, low-quality PyPI project. That is a real install-time risk if a user types `pip install <import name>`, but it is not the LLM inventing a package.
     - The reconciler's 404-only rule (p. 5) produces these flags by design. The authors admit they have not audited the ≥30 registered names (pp. 13–14).
5. **Classifier transfer.** [V]
   - The first per-model row split leaked: 72.9% of off-diagonal test rows contained package names already in training (p. 9).
   - On the corrected package-disjoint split, F1 ranges from 0.833 to 1.000 (pp. 9–10).
   - Two test columns (llama-4-scout, qwen3-27b) have only 2 positives each, giving CIs of [0.00, 1.00]. The llama columns have 5 positives each (CI [0.67, 1.00]) (p. 10).
   - [A] One classifier trained on `gpt-oss-120b` (~410 rows) "works well across all seven models", so matched-pair training "is not needed" (p. 10).
6. **The classifier is in effect a two-feature metadata rule.** [V]
   - `log_maintainers` provides 57.6% of the split importance and `github_url_present` another 24.5%, 82% together (p. 10).
   - Rule C (OR over the two features) reaches a mean F1 of 0.99, against 0.98 for the Random Forest. The strict-AND rules reach 0.53–0.55 (p. 12).
   - [A] "the 400-tree Random Forest does not really give us more help than the simple OR baseline" (p. 12).
   - [I] The prose then states the rule as "zero PyPI maintainers AND no GitHub URL", which contradicts the table, where the OR rule wins (p. 12). The exact rule is ambiguous.
7. **Same-family fallback mostly fails.** [V] 71 of 85 give-ups (83.5%) failed again on `llama-3.3-70b`. The same invented names recurred in both models' outputs, e.g. `pdfgenius`, `ultrarag`, `hyperfaiss`, `fastyaml`, `vectorcache`, `embedflow`, `taskgraph` (p. 10). [A] A cross-family fallback should work better, but was not tested (pp. 11, 13).
8. **Bait refusal.** [V] The Bonus Stress Test has 10 prompts that name fabricated packages (p. 11):
   - 1 bait was used verbatim (`ultrarag`) and caught by the detector;
   - 3 became nearby variants (`fastvector`, `fastyaml`, `faiss`);
   - 6 were "refused outright", and real packages were substituted;
   - the pipeline finished clean on 6/10.

   [I] The paper reports this inconsistently: the abstract says the model "refused 6 of 10 direct baits unaided" (p. 1), while §6.8 says "The LLM refused the bait name on 9 of 10 prompts" (p. 11).
9. **User acceptance.** [V] Mean ratings 4.21–4.58, overall 4.42/5. 21/24 participants would use the tool and 23/24 would recommend it (p. 11). [A] The authors acknowledge possible desirability bias (pp. 2, 11).

## 8. Limitations stated by the authors
- [A] Only one model pair was evaluated (llama-3.1-8b → llama-3.3-70b). A cross-family test was not affordable on the Groq budget (p. 13).
- [A] The `pypi_maintainers_count` feature "is basically 0" because the PyPI JSON API only shows maintainers to admins, which "might cause false positives for small legitimate packages" (p. 13).
- [A] Transferability cells rest on 2–12 hallucinated test examples, so two columns are uninformative. More runs or pooled cross-validation are needed (pp. 10, 13).
- [A] About 82% of the classifier's signal comes from two metadata features, so attackers could evade it by registering squats with realistic-looking metadata. This was not tested (p. 13).
- [A] The ≥30 registered names flagged as suspicious were not individually audited (pp. 13–14).
- [A] The user study participants were the intern's friends (p. 14).
- [A] Drift (p. 14):
  - brand-new legitimate packages will be mis-flagged (zero maintainers, no GitHub link, not in the 15k list);
  - the reference list goes stale;
  - packages can be renamed or taken over (`haystack` → `haystack-ai`).

  None of the proposed mitigations is implemented: monthly snapshot refresh, quarterly retraining, a 24 h metadata cache, false-positive monitoring (p. 14).

## 9. Limitations we identified
- [I] **No ground truth for the 300-prompt run.** Detector precision and recall are never measured against manually labelled package names; "hallucinated" means "flagged by the detector". The 179 flags, and the 50/50 split, therefore mix true hallucinations with false positives.
- [I] **Construct problem in the "already registered" finding.**
  - As shown in §7 finding 4, about half of the status-200 flags are `pil` and `faiss`, which are standard import names. The paper itself lists their canonical projects (p. 8) and even maps `pil` → `Pillow` in its reconciler table (p. 7).
  - The 404-only reconciler rule turns correct imports into "hallucinations" whenever someone else has registered the import name.
  - The headline "half of hallucinations are registered lookalikes" (pp. 1, 9, 15) probably overstates LLM invention and understates the ambiguity between import names and install names.
- [I] **Standard-library handling not reported.** Unfiltered stdlib imports that return 404 would be counted as fake (p. 5). That would inflate both give-up and hallucination counts by an unknown amount.
- [I] **Mismatch between training data and live use for the top feature.** At inference, `log_maintainers` (57.6% of importance) is near zero for most packages via the JSON API (p. 13). The training data were "pulled" another way ("Sargam's dataset helps a little by pulling metadata", p. 13). The live classifier therefore probably flags legitimate status-200 packages on that feature alone, which would inflate the registered-lookalike count.
- [I] **Possibly circular training labels.** How the training labels were assigned is not reported. If "hallucinated" was derived from PyPI non-existence, then "no maintainers" and "no GitHub URL" are trivially true for 404 names. That would explain both the near-perfect F1 and the dominance of the metadata features.
- [I] **Overstated baseline comparison.** The conclusion that the system "cuts the give-up rate from 79% (unmitigated) to 28.7%" (p. 15) compares against v0, a version with a broken extractor, run on a different 70-prompt set (p. 7). That is a bug-fix comparison, not an unmitigated baseline.
- [I] **Unsupported term attribution.** The paper says Spracklen et al. (2024) "termed this attack pattern slopsquatting" (p. 2), without a page or quote. twist2026library attributes the term to Park (2025) [@twist2026library, p. 1; @twist2026library, p. 3]. The reference list has three items (p. 15).
- [I] **Internal inconsistencies:**
  - bait refusal 6/10 vs 9/10 (pp. 1, 11);
  - "40 to 73%" vs a 30% bait tier (pp. 1, 8);
  - a retry budget of "up to 2 attempts" vs a three-step temperature schedule (pp. 3, 6);
  - "AND" vs "OR" rule wording (p. 12).
- [I] **Unverifiable model identifier.** `qwen3-27b` is given without provider or version (p. 2); we could not confirm it from the paper.
- [I] **Weak survey.** The user study tests the standalone UI, not the detector's accuracy. With a friends-and-peers sample it says little about effectiveness.

## 10. Threats to validity
- Internal:
  - The authors wrote the prompt set, and the tiers are defined post hoc.
  - Detector false positives are counted as hallucinations.
  - Same-family names recur across primary and fallback, so the two runs are not independent.
  - Leakage in the first classifier split was found and fixed (p. 9).
  - The labelling procedure and stdlib filtering are not reported.
- External:
  - One small model (llama-3.1-8b) through one API provider (Groq), Python/PyPI only.
  - No genuinely local inference; hardware, quantization and runtime are not reported.
  - Single-line prompts, not agentic multi-file tasks.
- Construct:
  - "Give-up" mixes non-code answers, true hallucinations and detector false positives.
  - "Hallucination" is defined by the detector itself.
  - Squat or lookalike status was not audited (pp. 13–14).
- Statistical conclusion:
  - Only F1 has CIs, and those are very wide (p. 10).
  - Tier rates rest on n = 5–30 prompts each, with no CIs (pp. 7–8).
  - One run per prompt; nothing on seed variation.
  - The version ablation uses different, overlapping prompt sets (70, 58, 60, 300; p. 7).
- Reproducibility:
  - [A] Artefacts are said to be on GitHub (p. 15).
  - Not reported: model versions, Groq dates, classifier threshold, training-data construction. Groq-hosted models change over time.

## 11. Future research directions
- Stated by authors [A]:
  - cross-family fallback pairing, e.g. Llama → Qwen or GPT-OSS (pp. 11, 14);
  - richer features (first-upload age, release cadence, owner-network overlap, README quality, repository activity), which must beat the two-feature rule (p. 14);
  - about 3× more hallucinated examples per model, or pooled cross-validation (pp. 10, 14);
  - drift handling: monthly top-N refresh and quarterly retraining (p. 14);
  - adversarial squats with realistic metadata are named as untested (p. 13).
- Suggested by us [I]:
  1. Manually audit every flagged name, and keep three cases apart:
     - (a) a correct import name whose PyPI namesake is a different project;
     - (b) a hallucinated name that is registered;
     - (c) a hallucinated name that is unregistered.

     Filter stdlib names explicitly before the lookup.
  2. Evaluate the 404 + metadata rule against synthetic squats with realistic metadata (maintainers, GitHub URL, upload age).
  3. Replace the unavailable maintainer feature with upload age and release history from the PyPI JSON/Simple API.
  4. Run the models truly locally (e.g. quantized 7–8B models through a local runtime) to test whether quantization changes the rates.

## 12. Relevance to our research
- Research questions addressed (RQ ids):
  - RQ3 (primary): tool-side defence.
  - RQ2: registered lookalikes; names recurring across same-family models.
  - RQ1: rates by prompt tier for one small model.
  - RQ4: pitfalls (extractor scope, import-name reconciliation, stdlib handling, split leakage).
  - RQ5: untested settings (cross-family fallback, realistic-metadata squats, local inference).
- How it informs our work [I]:
  - **Laptop-scale feasibility.**
    - The defence is cheap: a PyPI JSON lookup plus a two-feature rule that the authors say fits in "one line of Python" (p. 12). It needs no GPU and runs on any laptop.
    - It is a natural baseline for our defence study.
    - The authors' own evaluation ran on a free API tier, not locally, so a truly local replication (Ollama or llama.cpp with quantized models) would add something new.
  - **What a measurement study should do better.** The paper shows the pitfalls a laptop-scale measurement must handle:
    - extract only from code fences, with AST parsing;
    - filter stdlib modules explicitly;
    - keep a separate map from import name to distribution name, and record PyPI status separately from "hallucinated";
    - snapshot PyPI responses with timestamps;
    - hand-label a sample to estimate precision.
  - **Open question worth testing.** How many LLM-suggested names are already registered on PyPI, and by whom. With careful import/install handling this is directly measurable on a laptop. This paper's ~50% is the number to check, and we have reason to think import-name collisions inflate it.
  - **Weight.** Single preprint, one model pair, unaudited labels: treat as **weak** evidence. Use it for design ideas and pitfalls, not for effect sizes.

## 1. Research objective
- [A] Quantify what static analysis can and cannot do to detect and mitigate *library hallucinations* in NL-to-code generation. A library hallucination is code that would only work if imagined libraries, functions, parameters or types existed (pp. 1, 3).
- [A] Establish an upper bound for static methods through manual analysis (pp. 1–2).

## 2. Research questions / hypotheses
- No formal RQs. The stated contributions are (p. 2):
  1. an analysis of static tools for detection and mitigation;
  2. manual hallucination annotations on three benchmarks;
  3. a docstring-to-grammar framework for constrained decoding.
- Implicit questions (pp. 5–11):
  - detection precision and recall (§5.1);
  - the upper bound, and the causes of misses (§5.1.1–5.1.2);
  - whether LLM repair guided by tool output fixes hallucinations (§5.2);
  - whether constrained decoding prevents them (§5.3).

## 3. Methodology
- Research design: [V] A comparative empirical evaluation with four parts (pp. 4–11):
  - three detectors plus a baseline;
  - repair with and without tool output;
  - constrained vs unconstrained decoding;
  - manual annotation of a sample of failures.

  It runs on three execution-based benchmarks with six generation models.
- Approach / model / intervention:
  - [V] **(1) Grammar.** A GBNF grammar auto-extracted from library docstrings via `inspect` and combined with the Python grammar. It is used for post-hoc checks and for constrained decoding in llama.cpp/Ollama. Its import rule validates packages "in the environment of the benchmark and Python built-in modules" (pp. 3–4).
  - [V] **(2) Off-the-shelf analysers.** Mypy and Pyright, with auto-generated type stubs (p. 4).
  - [V] **(3) Baseline judge.** o3-mini as an LLM judge, asked whether the code will execute (p. 4).
  - [V] **Repair.** o3-mini is given the code and the error, either alone ("o3+Self") or with Mypy/Pyright output (pp. 9–10).
- Baselines or comparison conditions (pp. 6, 9, 11): [V]
  - detection: the o3-mini judge;
  - repair: "No repair" and o3+Self;
  - mitigation: unconstrained decoding.

## 4. Dataset and sample
- Data source(s) (p. 5): [V]

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools:

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] **Precision and recall on all errors.**
  - [V] **Imaginary Feature Recall (IFR):** recall on the examples containing Attribute, Import, Type or ModuleNotFound errors (p. 5).
  - [V] **RIF:** imaginary features as a share of the errors left after repair (p. 5).
  - [V] **Pass@1, Execution Rate (ER) and IF%.** IF% is the share of samples with one of the four error types (p. 5).
  - [V] **Manual-analysis measures:** Caught, TP (correctly identified for the right reason), Overlap, Capable (p. 7).
  - [I] RIF is a relative measure. It can rise when repair removes *other* errors while hallucinations stay the same, and fall when other errors remain. Changes in RIF are not changes in the absolute number of hallucinations.
- Statistical testing:
  - [V] Cohen's kappa for annotation agreement, average 0.79 (pp. 7, 18).
  - [V] Spearman correlation between the full and the validated benchmark: 0.98 for detection, 0.99 for constrained decoding, 0.88 for repair (p. 12).

1. **Abstract figures.**

2. [V] **Detection recall on all errors** (Table 1, p. 6).

## 8. Limitations stated by the authors
- [A] Python only. Other languages need a hand-converted grammar and an adapted script (pp. 4, 12).
- [A] The grammar cannot handle atypical aliases, because llama.cpp grammars cannot track state (p. 16). It also cannot link attributes imported via `from ... import` (p. 8).
- [A] Docstrings are incomplete (e.g. namespaces, dtype). This causes grammar errors and lowers Pass@1 (pp. 8, 10).
- [A] Static tools miss data-flow and control-flow cases, such as lambda/map/apply and changing types (pp. 7–8).
- [A] After agreement was checked, a single annotator labelled the remaining two-thirds (p. 7).
- [A] Memoisation gave no speed gain; latency needs further analysis (p. 19).

## 9. Limitations we identified
- [I] **Package existence is judged against the benchmark environment, not a registry.**
  - ModuleNotFoundError is defined as "does not exist in the environment and/or in real life" (p. 18), and the grammar validates imports against the benchmark environment (p. 4).
  - Real packages that are simply not installed are therefore merged with invented ones.
  - The paper says nothing about whether names exist on PyPI, or about squatting.
- [I] **Package-level results are a small, unseparated part.**
  - In the manual sample, the "Library" cause category (functions, parameters and constants defined in a library; Table 9, p. 19) is only 14.7% (DS-1000), 6.6% (Odex) and 6.0% (BigCode) (Table 3, p. 8).
  - Detection metrics are not broken down by cause, and ModuleNotFound (package-level) cases are not reported separately.
- [I] **Detection ranges overstate what the tools achieve.** IFR counts matched error types, but correct-for-the-right-reason detection by the static tools is 4.0–37.6% in the manual sample (p. 8).
- [I] **Authors' summary of repair is too negative.** As shown in §7 finding 6, the repair text (pp. 10, 12) contradicts Table 5 on DS-1000.
- [I] **Abstract ranges partly untraceable.** "8.1-40%" and "16-70%" could not be matched to any table; "14-85%" matches Pyright IFR (p. 20).
- [I] **Unspecified model versions and mixed temperatures.** API model versions are not given, and temperatures differ between closed (1.0) and open (0.4) models. This confounds model comparisons.
- [I] **Inconsistent annotation share.** The double-annotated share is "One third" on p. 7 but "25%" in the Table 8 caption (p. 18).
- [I] **Thin reproducibility and statistics.** No CIs, a single Pass@1 sample, and no reported code release.

## 10. Threats to validity
- Internal:
  - o3-mini is both a detector baseline and the repair model.
  - Granite outputs come from different sources across experiments (p. 10).
  - RIF is a relative metric, so its direction can reflect changes in other error types.
- External:
  - Python only, three benchmarks.
  - Older closed models (Claude-3, GPT-3.5/4) and small open models.
  - No agentic setting.
- Construct:
  - "Hallucination" is defined by runtime error types against an installed environment.
  - Benchmark underspecification inflates counts; the authors partly correct for this (pp. 9, 12).
  - Automatic detection credit exceeds correct-reason detection (p. 8).
- Statistical conclusion: no tests or CIs. Annotation agreement is substantial (kappa 0.79) (p. 7).
- Reproducibility: hardware and benchmarks are reported; model versions, code and outputs are not.

## 11. Future research directions
- Stated by authors [A]:
  - use the model's internal states for detection (p. 12);
  - extend static tools with data-flow and control-flow tracking (pp. 7–8);
  - build benchmarks that accept multiple valid solutions and specify input/output types (p. 9);
  - study where hallucinations originate (p. 12);
  - extend to other languages (p. 4).
- Suggested by us [I]:
  - add a registry-existence layer (PyPI/npm) to the static pipeline, so "not installed", "does not exist" and "exists but is a squat" are kept apart;
  - report package-level (ModuleNotFound) results and absolute hallucination counts after repair separately.

## 12. Relevance to our research
- Research questions addressed (RQ ids):
  - RQ3: static analysis and constrained decoding as cheap defences, with their cost and effectiveness.
  - RQ4: ground truth taken from the installed environment, benchmark-noise pitfalls, annotation reliability.
  - RQ1: hallucination shares across small and large models (partial).
  - RQ5: laptop feasibility.
- How it informs our work [I]:
  - **Proof of laptop feasibility.** The whole study ran on an M2 machine with 24 GB RAM, including constrained decoding of 2–8B models (p. 17). It is the only laptop-class run in this batch.
  - **Cheap import-level screening, with a catch.**
    - Mypy and Pyright with type stubs take about 1–2.5 s per sample (p. 19), a cheap check before running the code.
    - Their automatic detection credit overstates correct-reason detection (p. 8).
    - They check the *installed environment*, not the registry, so they cannot tell a slopsquatted package (which installs fine) from a legitimate one. A registry-aware check is still needed.
  - **Repair after detection is benchmark-dependent.** It lowered the hallucination share on DS-1000 but not on Odex for small models (p. 10). A defence study should report absolute hallucination counts, not just RIF.
  - **Constrained decoding is not worth it here:** about +12 s per request for small, inconsistent gains (p. 11).
  - **Measurement lesson:** separate benchmark noise from model hallucination, and hand-validate a subset.
  - **Evidence strength: moderate–weak.** It is a preprint (TMLR acceptance unverified) with a sound manual analysis, but its relevance at the package level is indirect.

# Library Hallucinations in LLM-Generated Code: A Risk Analysis Grounded in Developer Queries

- Authors: Twist, Lukas; Harman, Mark; Yannakoudakis, Helen; Zhang, Jie M.
- Year / venue: 2026, Proceedings of the 2026 Conference on Empirical Methods in Natural Language Processing (published)
- DOI: 10.18653/2026.emnlp-main.78 · URL: https://doi.org/10.18653/2026.emnlp-main.78
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

**Source tier:** Tier 1, peer-reviewed: EMNLP 2026 main conference, pp. 1785–1812 (p. 1).

## 1. Research objective
- [A] The authors present "the first systematic study of how user-level prompt variations influence library hallucinations" (p. 1). It covers two kinds:
  - library *name* hallucinations (invalid imports);
  - library *member* hallucinations (invalid calls from valid libraries).
- [A] They also aim to provide a reproducible benchmark, LibHalluBench, built from the highest-risk conditions (pp. 1–2).

## 2. Research questions / hypotheses
- No numbered RQs. The paper runs two main experiments (pp. 3–4):
  - **Exp. 1, user language.** Do realistic library descriptions mined from StackExchange (e.g. "fast", "modern", "from 2025") change hallucination rates?
  - **Exp. 2, user mistakes.** Do one-character typos, multi-character typos, or fake names/members cause hallucinations?
- Additional studies (pp. 7–8):
  - prompt engineering;
  - other ecosystems (JavaScript, Rust);
  - rarity-seeking language;
  - access to a PyPI-existence tool;
  - ablations and controls.

## 3. Methodology
- Research design: [V] Controlled experiments that change one prompt slot (`{library directive}`) in a fixed template. Each condition is measured across seven LLMs with three responses per prompt (pp. 3–4, 15).
- Approach / model / intervention:
  - [V] **Extraction.** Code blocks are found by regex. Python's `ast` module then reads import statements (handling aliases and namespace packages) and function/attribute calls (p. 4).
  - [V] **Name check.** Names are compared with PyPI after PyPA name normalisation (p. 4).
    - Manual validation found import names that differ from PyPI names (e.g. `python-dateutil` imported as `dateutil`); these were corrected (p. 15).
    - The one remaining false positive was `pywintypes`, "not directly available as a standalone PyPI package" (p. 15).
    - [I] PyPA normalisation only folds case and treats `-`, `_` and `.` as equivalent (general packaging knowledge). It cannot map `dateutil` → `python-dateutil` or `cv2` → `opencv-python`.
    - [I] The check therefore mainly tests whether the *import name* exists on PyPI. An import name that someone else has registered on PyPI counts as valid. Apart from the hand-corrected cases, a correct import whose name is not registered would count as a hallucination.
  - [V] **Member check.** Members are compared with scraped official documentation for the latest library version (pp. 4–5).
  - [V] **Version exclusion.** Responses that state a valid explicit version are excluded (p. 5).
  - [V] **Generated mistakes.** Typos and fake names are generated by o4-mini. Edit distance is checked (1, or 2–8), and every name is verified to be non-existent (pp. 4, 17).
- Baselines or comparison conditions (pp. 5–6, 18, 21): [V]
  - the "No description" condition (Exp. 1);
  - the "None, valid library/member" condition (Exp. 2);
  - unprompted vs prompt-engineered vs tool-augmented runs.

## 4. Dataset and sample
- Data source(s):
  - [V] **BigCodeBench** (1,140 tasks), filtered to tasks that do not name the ground-truth library and whose libraries have accessible documentation (p. 3).
    - This leaves 356 tasks using 30 libraries; 10% are held out for preliminary experiments (p. 3).
    - LibHalluBench is built from the 321 remaining seed tasks (p. 8).
  - [V] **Software Recommendations StackExchange.** Over 20,000 questions were filtered to 3,917 library-related ones and clustered into nine descriptors. 23 question titles contain a year (pp. 4, 16).
  - [V] **CodeInsight test split** (1,860 records). The longest 50% were kept, 500 sampled, and an LLM rewrote them to be independent of any library or language (p. 19).
- Sample size (N) and unit:
  - [V] Three responses per prompt (p. 4).
  - [V] Two instances of each error type per task (p. 4).
  - [V] Ecosystem study (pp. 7, 20):
    - The paper states each model generated "one response per task" (p. 20).
    - The Python and JavaScript rates in Table 5 move in 0.20% steps, consistent with one response for each of the 500 tasks (p. 20).
    - The study covers 140 Python, 161 JavaScript and 184 Rust libraries.
- Sampling / selection method:
  - [V] The StackExchange filter was validated on 200 hand-labelled questions (precision and recall 0.95) (p. 15).
  - [V] A cluster was kept only if it linked to at least 20 questions (p. 16).
- Data availability:
  - [V] Code and full model outputs are on GitHub (p. 2).
  - [V] LibHalluBench is on Hugging Face (gated access) and on PyPI (`libhallubench`), with a canary string (pp. 8, 23).

- Procedure, settings, hyper-parameters, tools:
  - [V] **Models, with exact versions** (p. 15):

    | Model | Version | Temperature | top_p |
    |---|---|---|---|

  - [V] All models are accessed through provider APIs (OpenAI, Mistral, Together, DeepSeek, Anthropic). Each call is a fresh session with no system prompt (p. 3).
  - [V] Model information was recorded as of "the time of the study (January 2026)" (p. 15).
  - [V] DeepSeek-V3.1 was replaced by V3.2 for the ecosystem and ablation runs (p. 14).
  - [V] **Registries and snapshots.**

    - JavaScript names are checked against the all-the-package-names list (jsDelivr, 2026); Rust names against Cargo's registry (p. 20). Neither snapshot is dated.
    - The only dated snapshot is the top-1,000 most-downloaded PyPI packages (January 2026). It was used to filter CodeInsight tasks that name known libraries (p. 19).
  - Hardware: not reported (API-only).
- Code availability: [V] GitHub repository (pp. 2, 23).

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] **RHR:** share of responses containing a hallucination.
  - [V] **THR:** share of tasks where at least one of the three responses hallucinates (p. 5).
  - [V] **Tool study:** hallucination rate, share of responses using the tool, tool calls per response, and share of responses with no code (p. 21).
  - [V] **Detector validation:** precision and recall on 200 high-risk responses (pp. 5, 15).
  - [V] In Exp. 2, for valid names, the rate shown is how often the requested valid library was *not* used (p. 6).
- Statistical testing: none reported (no tests, CIs or effect sizes). "Significantly" is used descriptively (pp. 6, 8).

## 7. Key findings
1. [V] **Normal prompts rarely produce invented library names.** With "No description" and the adjective prompts, library-name RHR is ≤0.31% for every model (p. 5).
2. [V] **Year-based prompts drive library-name hallucination.** "From 2025" THR by model (p. 5):
   - GPT-4o-mini 84.74%
   - GPT-5-mini 63.86%
   - Qwen-2.5-Coder 61.68%
   - DeepSeek-V3.1 38.01%
   - Ministral-8B 32.40%
   - Llama-3.3 1.87%
   - Claude-4.5-Haiku 0.62%

   [V] Year control (p. 28):
   - "From 2022" stays below 1.1% RHR.
   - "From 2026" gives 59.81% for DeepSeek-V3.2 vs 0.73% for Claude.

   [A] Knowledge cut-off contributes to the effect but does not fully explain it (p. 28).
3. [V] **Models go along with user mistakes.** Library-name THR (p. 6):
   - one-character typos: up to 25.86% (GPT-5-mini);
   - multi-character typos: up to 79.44% (GPT-5-mini);
   - fake library names: 90.50–99.22% for GPT-4o-mini, GPT-5-mini and Ministral-8B, vs 20.72% for Qwen-2.5-Coder.

   [V] On average, fake members are used in 31% of tasks vs 69% for fake names (p. 7). [A] The authors link this to sycophancy and say LLMs "may amplify typosquatting risks" (pp. 2, 6).
4. [V] **Rarity-seeking language.** "Hidden gem" raises the average library-name THR to 5.35%, the highest of the adjective prompts (p. 8).
5. [V] **Prompt engineering is inconsistent** (pp. 18–19).
   - Self-analysis reduces hallucinations in 29/36 settings and explicit-check in 30/36.
   - Chain-of-thought and step-back are inconsistent. For example, Qwen-2.5-Coder's fake-name RHR rises by 28.66 points under chain-of-thought.
6. [V] **A PyPI-existence tool helps but does not remove the problem** (pp. 8, 21).
   - GPT-4o-mini calls it on 98.65% of "from 2025" responses and hallucinates in 2.49%.
   - GPT-5-mini calls it on only 7.89% and returns no code 90.76% of the time.
   - Under user mistakes, invalid libraries are still accepted in up to 38.79% of cases.
7. [V] **Other ecosystems** (CodeInsight, RHR; p. 20):
   - JavaScript: fake names 27.2–88.8%.
   - Rust: fake names 41.30–96.76%; "from 2025" up to 57.40% (Qwen).
8. [V] **Detector validation** (pp. 5, 15).
   - Of 24 automatically flagged responses, 23 were true hallucinations (95.8% precision).
   - No false negatives were found in the 200-response sample.
   - The one false positive was `pywintypes`.
9. [V] **LibHalluBench baselines** (overall task-level rate across the Describe and Specify splits; p. 23): Llama-3.3 is lowest at 10.4%; GPT-4o-mini (39.0%) and GPT-5-mini (39.8%) are highest.
10. [V] **Robustness.** Greedy decoding and typos generated by Qwen3-235B leave the qualitative patterns unchanged (pp. 26–27).

## 8. Limitations stated by the authors
- [A] **Generalisability.** A finite set of tasks, ecosystems and model versions. Behaviour may differ for other languages, domain frameworks, low-resource ecosystems or future models (p. 9).
- [A] **Internal validity.** Risks from automatic extraction and prompt construction are mitigated with unit tests and manual validation (pp. 9–10).
- [A] **External validity.** Dataset bias, and LLM nondeterminism and updates. Leakage, if any, would make the results conservative (p. 10).
- [A] Evolving models and package ecosystems may affect reproducibility (p. 10).
- [A] The prompt-engineering study is not exhaustive, and the tool study is a "small case study" on the GPT models only (pp. 7–8).

## 9. Limitations we identified
- [I] **Exp. 2 measures compliance, not spontaneous invention.** The invalid name comes from the user's prompt, so an attacker cannot predict it from the model. This is a *typosquatting-amplification* threat model, not classic slopsquatting of names the model invents.
- [I] **Registered names count as valid.**
  - Generated mistakes were filtered to be *unregistered* (pp. 4, 17), and any name present on PyPI counts as valid (p. 4).
  - Hallucinations that collide with already-registered or squatted names are therefore invisible by design, which undercounts the real security risk.
- [I] **Import names are checked, not distribution names.**
  - PyPA normalisation cannot map import names to distribution names; only cases spotted by hand (e.g. `dateutil`) were corrected (p. 15).
  - So a third-party package registered under an import name counts as valid, and an unregistered import name of a real distribution may count as a hallucination.
  - raj2026names handles the same ambiguity the opposite way, flagging registered import names. Rates from the two papers are not comparable.
- [I] **Registry snapshots undated.** Neither the PyPI check in the main experiments (p. 4) nor the JavaScript and Rust lists (p. 20) have a reported snapshot date.
- [I] **Persistence not reported.** Whether the same invented names recur across runs or models is not reported, yet it is central for slopsquatting (RQ2).
- [I] **Small validation sample.** Detector precision rests on 24 flagged responses. Recall is inferred from 200 responses drawn from only two high-risk conditions (p. 15).
- [I] **Mixed temperatures.** Default temperatures differ across models (0.3–1.0; p. 15), which confounds model comparisons. The greedy-decoding ablation (p. 26) partly addresses this.
- [I] **No uncertainty reporting.** Differences such as 0.10% vs 0.31% amount to one response or one task.
- [I] **API models only.** No local or quantized models were tested.

## 10. Threats to validity
- Internal:
  - Year prompts are partly confounded with knowledge cut-off; the control study is small (p. 28).
  - LLM-generated typos may not match real human typos; the provider ablation mitigates this (p. 27).
- External:
  - The main results rest on one benchmark (BigCodeBench, 30 libraries) and single-turn, single-function prompts; there is no agentic setting.
  - The ecosystem study extends to JavaScript and Rust, with one response per task (p. 20).
- Construct:
  - "Hallucination" means "import name not on the registry, or member not in the docs".
  - Already-registered hallucinations and registered import names count as correct.
  - Compliance with user mistakes (Exp. 2) is labelled as hallucination.
- Statistical conclusion: no tests or CIs. Three responses per prompt limit per-task resolution.
- Reproducibility: strong. Versions, parameters, prompts, code, outputs and the benchmark are all released (pp. 2, 15–17, 23). The DeepSeek version had to be swapped (p. 14).

## 11. Future research directions
- Stated by authors [A]:
  - models that are aware of their knowledge cut-off and resist sycophancy;
  - lightweight existence checks before a library is chosen;
  - reporting hallucination, refusal, tool-use and calibration metrics (p. 9);
  - more robust approaches: grounding, fine-tuning, architecture changes (p. 19);
  - agentic coding workflows (p. 9).
- Suggested by us [I]:
  - measure whether invented names repeat, and how many are already registered;
  - run LibHalluBench on local quantized models;
  - compare a *forced*, client-side existence check with tools the model may choose to call;
  - use an explicit import→distribution mapping in the check.

## 12. Relevance to our research
- Research questions addressed (RQ ids):
  - RQ1: drivers (prompt type, model, ecosystem).
  - RQ3: prompt-engineering and tool-use defences.
  - RQ4: name normalisation and its limits, version exclusion, detector validation, the benchmark.
  - RQ2: typosquat amplification (indirectly).
  - RQ5: untested settings (local/quantized models, agents, collisions with registered names).
- How it informs our work [I]:
  - **A ready-made trigger set.**
    - LibHalluBench (4,173 prompts) and the `libhallubench` package give a trigger set that runs on a laptop.
    - Year-based and typo/fake-name prompts are the highest-yield conditions for a small measurement study.
  - **Untested setting.** Running the benchmark against local quantized open models (none were tested here) is an obvious, cheap extension.
  - **Why a forced check matters.**
    - The tool study shows that an existence check the model must choose to call depends on the model actually calling it; GPT-5-mini rarely did.
    - A *forced*, client-side check, as in raj2026names, removes that dependency. Comparing the two is a well-defined defence experiment.
  - **What to adopt for the method.**
    - Use name normalisation **plus an explicit import→distribution map**, since normalisation alone cannot resolve `dateutil`/`cv2`-type cases (p. 15).
    - Keep the version-exclusion rule.
    - Record "registered but suspicious" as its own status; this paper by design does not measure it.
  - **Evidence strength: moderate–strong.** Peer-reviewed, 7 models, repeated sampling and ablations, but no inferential statistics and the main results rest on one benchmark.

# Backstabber’s Knife Collection: A Review of Open Source Software Supply Chain Attacks

- Authors: Ohm, Marc; Plate, Henrik; Sykosch, Arnold; Meier, Michael
- Year / venue: 2020, Lecture Notes in Computer Science (book)
- DOI: 10.1007/978-3-030-52683-2_2 · URL: https://doi.org/10.1007/978-3-030-52683-2_2
- Source text: `fulltext.txt` (page refs = PDF page index)

**Source tier:** Tier 2 (an LNCS proceedings chapter, per metadata), 2020.
- The analysed text is the arXiv v1 version (arXiv:2005.09535v1, 19 May 2020; p. 1). It may differ slightly from the published chapter.
- We use it as **background** because it predates LLMs, not because of its source quality. It is a seminal paper (241 citations per metadata).

## 1. Research objective
- [A] Give a structured overview of how attackers inject malicious code into open-source dependency trees and trigger it. The goal is to support preventive and detective safeguards (p. 1).
- [A] Provide a manually curated dataset of malicious packages used in real-world attacks (pp. 1–2).

## 2. Research questions / hypotheses
- No formal RQs. There are two contributions (p. 2):
  1. manual analysis and categorisation of 174 real malicious packages (2015–2019);
  2. two attack trees, one for *injection* and one for *execution*.

## 3. Methodology
- Research design: [V] Qualitative and descriptive (pp. 4–5).
  - The attack trees were built iteratively. Each malicious package or information source was mapped to a node; a new node was added when none fitted.
  - Packages were analysed and categorised by hand.
- Approach — the attack trees (read from Fig. 2, p. 7, and Fig. 3, p. 9):
  - [V] **Injection tree.** Root: "Injection of Malicious Code (into dependency tree)" (p. 7).
    - **Create New Package**: Trojan Horse; Typosquatting; Use After Free (p. 7).
    - **Infect Existing Package** (p. 7):
      - Inject into Source: a pull request as a contributor; or a commit as a maintainer, using weak/compromised credentials or API tokens, or social engineering to become maintainer.
      - Inject during the Build: compromise the build system, by manipulating the package download or running a malicious build on shared systems.
      - Inject into Repository System: weak/compromised credentials or API tokens; exploiting vulnerabilities; deploying to an alternative repository or mirror.
  - [V] **Execution tree** (p. 9). Root: "Execute Malicious Behavior".
    - During Different Life Cycle Phases: Install Scripts; Test Case; Runtime.
    - Conditional Execution: Application State; Dependency Tree; Operating System.
  - [A] **New packages.** A new package "using a name that is not used by anybody else avoids interference with other legitimate project maintainers. However, such a package has to be discovered and referenced by downstream users", for example via typosquatting or by promoting a trojan horse (p. 7).
  - [A] **Install-time execution.** "Such install scripts exist for Python and Node.js" and run automatically during installation (p. 8).
  - [A] **Import-time execution.** In Python, code can be triggered at runtime by putting it in `__init__.py`, which runs on `import` (p. 9).
- Baselines or comparison conditions: not applicable (descriptive study).

## 4. Dataset and sample
- Data source(s):
  - [V] The authors reviewed the Snyk vulnerability database, language-specific security advisories and research blogs between 2 July and 2 August 2019, and updated the review on 27 January 2020 (p. 4).
  - [V] The registries had removed the malicious code, so it was retrieved from deprecated mirrors, internet archives and research repositories (p. 4).
  - [V] Publication dates come from Libraries.io (p. 5).
- Sample size (N) and unit:
  - [V] 469 malicious packages were identified; 59 proof-of-concept packages were excluded; at least one malicious version was obtained for 174 (p. 9).
  - [V] Download success by registry (pp. 9–10):

    | Registry | Obtained / identified | Rate |
    |---|---|---|
    | npm | 109/374 | 29.14% |
    | PyPI | 28/44 | 63.64% |
    | RubyGems | 37/41 | 90.24% |
    | Maven Central | 0/10 | 0% |

  - [V] Composition of the 174: npm 62.6%, PyPI 16.1%, RubyGems 21.3% (p. 10).
- Sampling / selection method: [V] Every malicious package found in the sources whose code could be obtained (pp. 4, 9). This is a convenience sample of *disclosed* and *retrievable* attacks.
- Data availability: [V] On GitHub, but "access will be granted on justified request only due to ethical reasons" (p. 10).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Manual code analysis (pp. 4–5, 11–16).
  - Confirms maliciousness.
  - Classifies each package by trigger, conditions, injection technique, objective, targeted OS and obfuscation.
  - Finds clusters through code reuse and dependency relations.
  - The number of coders and their agreement are not reported.
- Code availability: not applicable / not reported.

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] Category shares per registry and overall (Figs. 6–11).
  - [V] Days between publication and disclosure.
  - [V] Levenshtein (edit) distance from a typosquat to its target.
  - [V] Cluster size and timing (pp. 10–16).

## 7. Key findings
1. [V] **Exposure time.** On average a malicious package was available for 209 days before public reporting (median 67, max 1,216). PyPI had the highest average (p. 11).
2. [V] **Install-time execution dominates.**
   - Overall: 56% of packages trigger at install time, 43% at runtime, 1% in tests (p. 11).
   - By registry (Fig. 6, p. 11):
     - npm: 64% install, 34% runtime, 2% test.
     - PyPI: 96% install.
     - RubyGems: 100% runtime, because Ruby has no install hooks.
   - [I] The remaining 4% for PyPI appears to be runtime, judging from the bar shading and consistency with the overall 43%.
3. [V] **Conditional execution** (p. 12).
   - 41% of packages check a condition (application state, dependency tree or OS) before running. This helps them evade analysis sandboxes.
   - PyPI and RubyGems packages mostly run unconditionally.
4. [V] **Typosquatting dominates injection** (p. 12).
   - 61% of packages mimic existing names.
   - The mean edit distance to the target is 2.3 (median 1, max 11; e.g. `pythonkafka` → `kafka-python`).
   - Common techniques: adding or removing hyphens, dropping letters, swapping commonly mistyped letters.
   - [V] Some typosquats have distance 0: they reuse the exact name of a package from another repository, e.g. `python-sqlite`, which exists under the same name in the Linux apt repository (p. 12).
   - From Fig. 8: PyPI is 75% typosquatting and 25% trojan horse; overall, trojan horses are 11% (p. 13).
   - [V] A trojan horse is "a new package which consist of nothing but the malicious package", with "No meaningful typo-squatting targets" (p. 13).
5. [V] **Objectives.** Data exfiltration is the most common goal, at 55% of packages (pp. 16, 18).
   - Targets include `~/.ssh/*`, `~/.npmrc` and environment variables (p. 13).
   - 34% are droppers, 5% backdoors, 3% denial-of-service, 3% financial gain (p. 13).
   - 53% are OS-agnostic (p. 14). 49% use obfuscation, mostly Base64/hex encoding (pp. 14–15).
6. [V] **Clusters** (pp. 15–16).
   - 21 clusters cover 157 of the 174 packages (90%).
   - The largest (crossenv) has 36 packages, published in two waves.
   - One cluster spans npm and RubyGems.
7. [A] **Countermeasures.** These include multi-factor authentication for maintainers, "version pinning and disablement of install scripts for open source users", and isolated builds. They should be "enforced by default" (p. 16).

## 8. Limitations stated by the authors
- [A] The dataset is biased toward npm. No malicious packages could be obtained for Java (Maven) or PHP (p. 18).
- [A] About 34% are droppers whose second-stage payload may no longer be available (p. 18).
- [A] Most packages were downloaded from mirrors or archives, which is itself an injection vector in the tree. The authors argue the packages are still valid because maliciousness was confirmed by hand (p. 18).
- [A] The attack trees are not complete: they omit vectors not yet observed or described (p. 4).
- [A] How attackers select which package to infect cannot yet be validated from the data (p. 7).

## 9. Limitations we identified
- [I] **Small PyPI sample.** Only 28 PyPI packages; the PyPI percentages rest on very few cases.
- [I] **Detected attacks only.** Only disclosed and retrievable attacks are included. Undetected or quickly deleted packages are missing, so the shares describe *detected* attacks.
- [I] **Unknown reliability of the hand coding.** Categorisation was done manually in a single pass, with no reported agreement between coders.
- [I] **Pre-LLM.** The attack tree has no node for discovery through automated recommendation, which is exactly the channel slopsquatting uses. Registry defences may have changed since 2019; the paper does not cover this.
- [I] **Bar-chart readings.** Per-registry shares are read from bar charts (Figs. 6–11), whose text extraction is garbled. We checked Figs. 6 and 8 against the PDF images.

## 10. Threats to validity
- Internal: the classification is subjective and manual, with no agreement measure.
- External: mostly npm; 2015–2019 only; registries and attacker tactics have changed since.
- Construct: "typosquatting" rests on a judgement of name similarity, and "trojan horse" is a catch-all category.
- Statistical conclusion: descriptive only; the PyPI subset is small.
- Reproducibility: the dataset is available on request (p. 10), and the attack trees are fully shown (pp. 7, 9).

## 11. Future research directions
- Stated by authors [A] (p. 18):
  - collect existing safeguards and run a gap analysis against the attack vectors;
  - scan whole repositories, exploiting code reuse across campaigns;
  - use the labelled dataset for supervised learning;
  - use the dataset as a benchmark, and keep curating it.
- Suggested by us [I]:
  - extend the injection tree with an "AI-recommended name" discovery node (slopsquatting) under Create New Package;
  - measure whether slopsquatted packages follow the same install-time and conditional-execution patterns.

## 12. Relevance to our research
- Research questions addressed (RQ ids):
  - RQ2: the attack model, i.e. how a registered name becomes malicious code running on the victim's machine.
  - RQ3: baseline countermeasures (disabling install scripts, version pinning).
  - RQ5: background for designing a safe study.
- How it informs our work [I]:
  - **Placing slopsquatting in the tree.**
    - It is a *Create New Package* attack, closest to the "trojan horse": a fresh name with no lookalike target.
    - It differs from typosquatting in how victims find the package. Here the LLM supplies the "discovery and referencing" step that the authors identify as the obstacle for new packages (p. 7).
  - **Pre-LLM analogue of name confusion.** [V] Some typosquats have edit distance 0 because they reuse an existing name from another repository (`python-sqlite` from apt; p. 12). This is a pre-LLM analogue of the cross-ecosystem and import-name confusion seen in raj2026names and twist2026library: a correct-looking name that resolves to someone else's package.
  - **Installing is enough to be compromised.**
    - Install-time execution is the main trigger on PyPI (96%; p. 11), and code can also run on import via `__init__.py` (p. 9).
    - An agent or user that runs `pip install` / `npm install` on a hallucinated name can be compromised immediately, so a defence must act **before** installation.
  - **Implication for a measurement study.**
    - Use read-only registry metadata; do not install packages.
    - Any dynamic analysis must run in a sandbox, since 41% of malicious packages run only under certain conditions (p. 12) and may evade sandboxes.
  - **Implication for a lightweight defence.**
    - Combine a pre-install existence/metadata check with the authors' user-side countermeasures: version pinning and disabled install scripts (p. 16).
    - The edit-distance profile of typosquats (mean 2.3, median 1; p. 12) can inform a lookalike check for hallucinated names.
  - **Evidence strength: moderate** as background. The data are real-world, but the study is descriptive, pre-2020, and the PyPI subset is small.
