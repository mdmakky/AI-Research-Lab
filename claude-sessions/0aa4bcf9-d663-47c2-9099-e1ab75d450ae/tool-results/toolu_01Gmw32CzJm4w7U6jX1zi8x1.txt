## raj2026names
**Status:** ready (content below) · **Evidence basis:** full-text · **Tier:** arXiv preprint, not peer-reviewed

**Summary:** A client-side guard for Python package hallucinations: a PyPI existence check, a 10-feature Random Forest over package metadata, a 24-entry import-name mapping table, and a retry/fallback agent. On 300 hand-written prompts it finishes clean on 76% of runs with llama-3.1-8b falling back to llama-3.3-70b. The Random Forest turns out to be no better than a one-line two-feature rule.

**Key findings:**
1. **Setup.** Hardware is not reported, and no model actually ran locally. Generation went through Groq's hosted free tier, with primary `llama-3.1-8b` and fallback `llama-3.3-70b` (pp. 2, 6). The classifiers were trained on outputs from seven models, including `gpt-5` and a `qwen3-27b` identifier I could not confirm (p. 2).
2. **Pipeline numbers** (p. 7):
   - 186/300 prompts produced code on the first try.
   - 28 of the 114 retries succeeded (24.6%).
   - The primary model gave up on 86/300 (28.7%); the fallback recovered 14 of 85 (16.5%).
   - 228/300 (76%) finished clean.
3. **Detection metrics.**
   - On a split where no package name appears in both training and test, F1 ranges 0.833–1.000 (pp. 9–10).
   - Several test sets hold only 2–12 hallucinated examples; two columns have confidence intervals of [0.00, 1.00] (p. 10).
   - Two metadata features carry 82% of the signal: maintainer count 57.6%, GitHub URL 24.5% (p. 10).
   - A hand-written OR rule over those two features scores mean F1 0.99, against 0.98 for the Random Forest (p. 12).
4. **"Already-registered lookalike" finding.**
   - 179 of 823 verdicts were flagged as hallucinated. About half returned PyPI 404; 90 returned 200, meaning the name exists on PyPI (pp. 8–9).
   - My concern: in Table 3, `pil` (36 flags) and `faiss` (10) make up 46 of those 90 flags. Both are the normal import names of real projects (Pillow, faiss-cpu).
   - The tool only consults its import-name table after a 404, so correct `import PIL` lines get flagged whenever someone has registered `pil` on PyPI.
   - So the headline "half are registered squats" is probably inflated. The authors admit they did not audit the registered names (pp. 13–14).
5. **False-positive handling.** Restricting extraction to code blocks and using a syntax parser, plus adding the mapping table, cut the give-up rate from 79% to 28.7% (pp. 7, 12). Most of the improvement came from removing false positives, not from the classifier.
   - The maintainer feature is "basically 0", because PyPI's JSON API only shows maintainers to admins (p. 13).
   - Brand-new legitimate packages are mis-flagged because of drift (p. 14).
   - Detector precision is never measured against hand-labelled ground truth.

**Doubtful or could not verify:**
- Internal inconsistencies: bait refusal is "6 of 10" in the abstract but "9 of 10" on p. 11. The abstract says "40–73% on slopsquat baits", but one bait tier is 30% (p. 8). The retry budget allows two attempts, yet three temperatures are listed (pp. 3, 6). The rule is described as "AND" in prose, but the winning rule in the table is OR (p. 12).
- "79% unmitigated" baseline: the 79% is a buggy earlier version on a different 70-prompt set, not an unmitigated system.
- How the classifier's training labels were made is not reported. If "hallucinated" means "not on PyPI", the near-perfect F1 is circular.
- The DOI in metadata is a Zenodo DOI, and metadata verification is single-source.
- I did not check the GitHub artefacts.

## mirandapena2026empirical
**Status:** ready · **Evidence basis:** full-text · **Venue:** the PDF header says "Published in Transactions on Machine Learning Research (10/2026)" with an OpenReview link (p. 1). That is an author claim; `metadata.json` still lists it as a preprint (arXiv v3). Running `rlab validate` may be worth it.

**Summary:** Tests whether type checkers (Mypy, Pyright), a grammar built from library docstrings, and an o3-mini judge can detect and fix library hallucinations, across 6 LLMs and 3 Python benchmarks. Detection is partial; hand analysis puts the ceiling for static detection at 48.5–77%. LLM repair improves whether code runs but not hallucinations, and constrained decoding has small, mixed effects.

**Key findings:**
1. **Detection rates** (Table 10, p. 20):
   - Pyright is strongest, detecting up to 0.85 of library hallucinations (claude-3 on DS-1000).
   - The grammar detects 0.06–0.20 and Mypy 0.03–0.70.
   - Precision on hallucinations is about 1 (pp. 6–7).
2. **Hand-checked ceiling.** On 600 hand-annotated failures (Cohen's kappa 0.79), the share static tools could in principle catch is 77.0% (DS-1000), 70.5% (Odex) and 48.5% (BigCode) (pp. 7–8).
3. **Benchmark noise.** Over 30% of apparent hallucinations in Odex and BigCode come from under-specified benchmark tasks (p. 9). Removing noisy items preserves the model rankings (Spearman 0.98–0.99; repair 0.88) (p. 12).
4. **Repair and constrained decoding.**
   - Repair raises the execution rate, e.g. Gemma2 2B on DS-1000 from 47.2 to 77.9 (p. 9).
   - The share of remaining errors that are hallucinations does not fall, and rises on Odex (p. 10).
   - Constrained decoding changes the hallucination rate by small, mixed amounts and adds about 12 s per request (22.3 s to 34.76 s) (p. 11).
5. **Hardware (laptop-relevant).** An M2 machine with 8-core CPU, 10-core GPU and 24 GB RAM (p. 17), running llama.cpp/Ollama (p. 4). Detection takes about 1 s for Mypy, 2.5 s for Pyright or the grammar, and 4 s for o3-mini (p. 19).

**Doubtful or could not verify:**
- The abstract's "8.1–40% of responses", "16–70% of all errors" and "14–85%" can't be traced to one table. The body tables give 0.03–0.85 for the tools.
- "550 questions from RIG" is never defined; it is probably Odex (p. 5).
- The double-annotated share is "one third" on p. 7 but "25%" on p. 18.
- Closed-model versions are not reported. Temperatures differ between closed (1.0) and open (0.4) models.
- No code release is reported; only the annotation guideline is supplemental. No confidence intervals.
- Relevance limit: what counts as "does the package exist" is the benchmark's installed environment, not PyPI. ModuleNotFound errors include real packages that simply aren't installed (p. 18), and nothing about squatting is measured.

## twist2026library
**Status:** ready · **Evidence basis:** full-text · **Venue:** EMNLP 2026 main, pp. 1785–1812 (tier 1)

**Summary:** Seven API-hosted LLMs, 321 BigCodeBench tasks, three responses per prompt. Under ordinary prompts, invented library names are about 0%. Asking for a library "from 2025", typing a misspelt library name, or naming a fake library drives the rate sharply up. Prompting tricks and a PyPI-existence tool reduce but do not remove it. The paper releases LibHalluBench (4,173 prompts).

**Key findings:**
1. **Baseline vs year prompts.** With no description or adjective prompts, rates are about 0% (≤0.31% of responses). "From 2025" prompts produce hallucinated libraries in up to 84.74% of tasks for GPT-4o-mini, 63.86% for GPT-5-mini and 61.68% for Qwen-2.5-Coder, but only 0.62–1.87% for Claude-4.5-Haiku and Llama-3.3 (p. 5).
2. **User mistakes.** A one-character typo leads to use of the wrong library in up to 25.86% of tasks (GPT-5-mini); fake library names are used in up to 99.22%, against 20.72% for Qwen (p. 6). Fake members are used far less often than fake libraries: 31% vs 69% average (p. 7).
3. **Mitigations.**
   - Self-analysis and explicit-check prompts cut hallucinations in 29/36 and 30/36 settings; chain-of-thought and step-back are inconsistent and sometimes worse (p. 19).
   - With a PyPI-existence tool, GPT-4o-mini calls it on 98.65% of "from 2025" responses and drops to 2.49%. GPT-5-mini calls it on only 7.89% and produces no code 90.76% of the time. Typo and fake-name conditions still reach up to 38.79% (pp. 8, 21).
4. **Other ecosystems.** On 500 CodeInsight tasks, JavaScript and Rust show similar patterns (pp. 7, 20). A year-control study shows knowledge cut-off contributes but does not fully explain the year effect (p. 28). Greedy decoding and a different error generator leave the conclusions unchanged (pp. 26–27).
5. **Detection method.** Names are checked against PyPI after name normalisation. Responses that state a valid explicit version are excluded. On a 200-response hand check, 23 of 24 flags were true (95.8% precision) and no hallucinations were missed in that sample (pp. 4–5, 15).

**Doubtful or worth flagging:**
- Experiment 2 measures whether models *go along with* invalid names the user typed. The name comes from the user, so this is typo amplification, not spontaneous invention of a predictable name.
- The generated misspellings were checked to be *unregistered* (pp. 4, 17), and anything registered on PyPI counts as valid. So already-registered or already-squatted names are excluded by design, which undercounts the slopsquatting case.
- The PyPI snapshot date for the main check is not reported; only "January 2026" model info is given (p. 15).
- No statistical tests or confidence intervals. Default temperatures differ across models (0.3–1.0, p. 15).
- Whether hallucinated names repeat across runs or models is not reported.
- DeepSeek V3.1 was swapped for V3.2 in the later experiments (p. 14).

## ohm2020backstabbers
**Status:** ready · **Evidence basis:** full-text (arXiv v1 text of the LNCS chapter) · **Tier:** book chapter, used as 2020 background

**Summary:** A hand-collected dataset of 174 real malicious npm, PyPI and RubyGems packages (Nov 2015–Nov 2019) plus two attack trees: one for getting malicious code into dependency trees, one for running it. Typosquatting (61%) and running at install time (56%) dominate; for PyPI the figures are 75% and 96%.

**Key findings:**
1. **Injection attack tree** (p. 7). The "Create New Package" branch splits into {Trojan Horse, Typosquatting, Use After Free}. The "Infect Existing Package" branch splits into injection via source, build, or repository.
   - [A] A new package "has to be discovered and referenced by downstream users" (p. 7).
   - [I] Slopsquatting fits this branch, with the LLM recommendation acting as the discovery channel. The tree has no node for that.
2. **Execution attack tree** (p. 9). It covers install scripts, test cases and runtime, plus conditional execution on application state, dependency tree or operating system.
   - Install scripts exist for Python and Node.js (p. 8).
   - Python `__init__.py` runs on import (p. 9), so both `pip install` and `import` can execute attacker code.
3. **When malicious code fires** (Fig. 6, p. 11): 56% of packages overall run at install time; 96% on PyPI and 64% on npm.
   - 41% check a condition before running, which helps them evade sandboxes (p. 12).
4. **How packages get in** (p. 12): 61% use typosquatting overall, 75% on PyPI (Fig. 8, p. 13).
   - Average edit distance to the target name is 2.3, median 1 (p. 12).
   - "Trojan horse" packages with no lookalike target are 11% overall and 25% on PyPI (p. 13). This is the closest pre-LLM analogue to hallucinated names.
5. **Exposure and countermeasures.** Packages stayed available for an average of 209 days before disclosure (median 67) (p. 11). Suggested countermeasures include version pinning and disabling install scripts (p. 16).

**Caveats:**
- The PyPI sample is small: 28 of the 44 identified PyPI packages could be obtained (p. 10).
- Percentages per registry are read from bar charts. I confirmed the PyPI and overall bars from the PDF images; the PyPI 4% remainder in Fig. 6 being runtime is my inference from the shading and arithmetic.
- No inter-rater reliability is reported, and the paper predates LLMs.

# Names Can Hurt: Spotting Slopsquatting Risks Caused by Package Name Hallucinations in Local Coding LLMs

- Authors: Raj, Akash; Sahu, Sargam
- Year / venue: 2026, arXiv (Cornell University) (preprint)
- DOI: 10.5281/zenodo.22087562 · URL: https://arxiv.org/abs/2608.23897
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

**Source tier:** arXiv preprint, v1, August 2026 (p. 1); not peer-reviewed. Authors are an M.Tech student and a B.Tech intern; much of the work was done during an internship (p. 1, 15). The metadata DOI is a Zenodo DOI, and `metadata.json` verification is "single-source (openalex)".

## 1. Research objective
- [A] Build and evaluate a client-side guard that stops a coding LLM's hallucinated Python package names from turning into slopsquatting installs. The guard targets "small, open-weight, locally runnable LLMs in the 7B to 70B range" (p. 2).
- [A] The authors say local models matter because developers outside large companies run them, because they "tend to hallucinate more often than frontier systems", and because local deployment rules out asking a hosted model to verify the output (p. 2). No evidence is given for the second point.

## 2. Research questions / hypotheses
- No formal RQs or hypotheses. The paper lists five contributions instead (p. 2): (1) a two-layer detector (PyPI existence check plus a per-LLM Random Forest); (2) an import-name reconciler; (3) a LangGraph retry/fallback agent; (4) an evaluation on 300 prompts; (5) a user acceptance study.
- Implicit questions answered in §6: how often the pipeline gives up; how much retries and fallback recover; how give-up varies by prompt tier; how many flagged names already exist on PyPI; whether per-LLM classifiers transfer across models; whether a hand-written rule matches the Random Forest (pp. 6–12).

## 3. Methodology
- Research design: [V] System-building paper with a single-configuration evaluation (one primary/fallback model pair), offline classifier analysis and a convenience-sample survey (pp. 6–12). There is no control condition without the detector, apart from earlier buggy system versions (p. 7).
- Approach / model / intervention:
  - [V] **Extractor.** AST parsing of Python code blocks, keeping only the top-level module name. A regex fallback runs only inside code fences and ignores keywords and shell tokens. `pip install` lines are read only inside code fences (pp. 3, 5).
  - [V] **Layer 1, deterministic check.** A PyPI JSON API lookup per name. A 404 means the name is fake. A 200 sends the package metadata to the classifier (p. 5).
  - [V] **Layer 2, Random Forest.** 400 trees, 10 features (p. 5):
    - 8 name features: length, number of parts, digits, a letter repeated three times, hype words (`super`, `pro`, `ai`, `magic`), generic words (`helper`, `tools`), a `py-`/`python-` prefix, and Levenshtein distance to a list of the top 15,000 PyPI names.
    - 2 metadata features: maintainer count and whether a GitHub URL is present.
  - [V] **Import-name reconciler.** A 24-entry YAML table (e.g. `cv2` → `opencv-python`, `PIL` → `Pillow`). It is consulted only after a PyPI 404. A mapped name is accepted only if the install name passes both layers. The authors' security argument: an attacker-registered `cv2` returns 200, so the reconciler never runs and the classifier must catch it (pp. 5–6).
  - [V] **Agent.** A LangGraph state machine with six nodes. Retry budget is 1 per model ("up to 2 attempts"), with rising temperature (0.7 → 1.0 → 1.2). After the budget is spent, the task goes to a fallback model with its own matched classifier. Every attempt is logged to JSONL (pp. 3, 6).
- Baselines or comparison conditions:
  - [V] Earlier system versions v0/v1 (broken regex, no reconciler) are used as an ablation (p. 7).
  - [V] Three hand-written rules are compared with the Random Forest on the same package-disjoint split (p. 12).
  - [V] LLM self-verification is described as a "baseline" in related work but is **not run** (p. 3).
  - [V] There is no comparison with any published detector or with Spracklen et al.'s method; the reference list has only three entries (p. 15).

## 4. Dataset and sample
- Data source(s):
  - [V] 300 single-line Python coding prompts, written by hand (p. 6).
  - [V] Classifier data: "Sargam's dataset" (`raw_master_dataset.csv`) of package names generated by seven LLMs (pp. 9, 14). How it was generated (prompts, hosting, dates) is not reported.
- Sample size (N) and unit:
  - [V] Prompts: 300, roughly 140 routine tasks (data engineering, security/DevOps, standard workflows), 55 obscure-dependency tasks and 105 adversarial prompts, in 18 tiers of 5–30 prompts each (pp. 6–8).
  - [V] Runs and verdicts: 385 runs (300 primary + 85 fallback) gave 823 package verdicts (p. 8).
  - [V] Classifier data: 464 unique package names across 7 LLMs; 210 occur in at least two models and 42 in all seven. Each model has 68–108 hallucinated rows, which leaves 2–12 positive examples per test slice (pp. 9–10).
  - [V] Survey: n = 24 CS undergraduates (p. 11).
- Sampling / selection method:
  - [V] Prompts were authored by the researchers. Adversarial prompts name packages or use "tricky wording" such as asking for "the newest and most capable library for X" (p. 6).
  - [V] Survey participants were "Sargam's CS undergraduate peers" / "the intern's friends" (pp. 2, 11).
  - The tier construction criteria and the classifier labelling procedure (who or what decided "hallucinated" in the training data) are not reported.
- Data availability: [A] Code, mapping table, the 300 prompts, seven classifiers, the 385-record run log and the leakage-safe matrix are released at a GitHub repository (p. 15). We did not check the repository.

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools:
  - [V] **Models.** Classifiers were trained for `gpt-5`, `gpt-oss-120b`, `llama-3.1-8b`, `llama-3.3-70b`, `llama-4-scout`, `qwen3-27b` and `qwen3-32b`. The agent evaluation uses two **Groq-hosted** models chosen to fit "our free-tier budget": primary `llama-3.1-8b`, fallback `llama-3.3-70b` (p. 2). Exact model versions/checkpoints and quantization are not reported.
  - [V] **Classifier.** Random Forest, 400 trees; scikit-learn 1.8 in v2 (pp. 5, 7). Other hyper-parameters are not reported. The decision threshold on P(fake) is not reported.
  - [V] **Split.** The original split was a per-model 75/25 row split with `random_state=42`. It was replaced by a package-disjoint 75/25 split over the 464 unique names (p. 9).
  - [V] **Uncertainty.** Bootstrap 95% CIs with 1,000 resamples for F1 (p. 10).
  - **Hardware: not reported.** All generation ran through Groq's hosted API, and the classifier analysis was "computed offline" (pp. 2, 6). [I] So, despite the title, no model was run on local hardware. "Local" describes the model class (open-weight, 7–70B), not the deployment. The classifier training set also includes `gpt-5`, which is not a local model.
  - [V] **Run budget.** One fallback run was lost to a mid-batch Groq rate-limit event (p. 7). A cross-family fallback was not run because it "would have required 5 times the Groq token budget beyond the free tier" (p. 11).
  - [V] **Survey.** Standalone Streamlit tool, seven dimensions on a 1–5 Likert scale (p. 11).
- Code availability: [A] GitHub repository stated (p. 15); twelve extractor regression tests are said to pass (p. 15).

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] **Primary give-up rate:** share of prompts where the primary model exhausts its retry budget (p. 6).
  - [V] **Fallback rescue rate:** share of give-ups that the fallback recovers (p. 6).
  - [V] **End-to-end clean rate:** share of prompts that finish with no hallucinated recommendation (p. 6).
  - [V] **Per-tier and per-name breakdowns** (p. 6).
  - [V] **Classifier F1** in a 7×7 train-LLM × test-LLM matrix (p. 9).
  - [V] **Random Forest split importance** per feature (p. 10).
  - [V] **Likert means/medians** from the survey (p. 11).
  - [I] Why these metrics were chosen is not justified.
  - [I] Retries are triggered both by non-code answers and by flagged names (p. 4). The give-up rate is therefore a pipeline outcome, not a pure hallucination rate, and it also absorbs detector false positives (see §9).
  - Not reported: detector precision/recall against a manually checked ground truth on the 300-prompt run.
- Statistical testing:
  - [V] Bootstrap CIs are reported for the F1 matrix only (p. 10).
  - No CIs or tests for give-up, rescue or tier rates, and no significance testing.

## 7. Key findings
1. **Pipeline outcome.** [V] On `llama-3.1-8b`:
   - 186/300 prompts (62%) produced code on the first try (p. 7).
   - 114 triggered a retry, and 28 of those were fixed by the retry (24.6% intra-model rescue) (p. 7).
   - 86/300 (28.7%) exhausted the budget (p. 7).
   - The fallback ran on 85 of those 86 and recovered 14 (16.5%) (p. 7).
   - End-to-end, 228/300 (76%) prompts finished clean. The remaining 72 would get a "do not pip install" warning (p. 7).
2. **Most of the give-up reduction came from preprocessing fixes, not the classifier.** [V] Primary give-up was:
   - v0: 79% (55/70), broken regex on the full text (p. 7);
   - v1: 57% (33/58), AST + code-only regex (p. 7);
   - v2: 30% (18/60) on 60 prompts and 28.7% (86/300) on 300 prompts, after adding the reconciler (p. 7).

   The reconciler fired 29 times over 4 distinct alias pairs in the 300-prompt run (p. 7). [A] The extractor and reconciler fixes together "caused a 49-point drop"; "Changing the classifier itself did not help much" (p. 12).
3. **Give-up rate rises with prompt tier.** [V] Rates by tier:
   - Data Engineering 0% (n=20); Security & DevOps 5% (n=20); Level 1/Level 2 10% (n=10 each) (pp. 7–8).
   - Hallucination Bait 55% (n=20); Adversarial (Realistic Hallucination Bait) 73.3% (n=30) (p. 8).
   - Direct Slopsquatting Stress Tests 30% (n=30) (p. 8). This sits below the abstract's "40 to 73% on slopsquat baits" (p. 1).

   [I] Table 2 is sorted by rate, not by any independent measure of how adversarial a prompt is. The "Level N" tiers are not monotone (Level 8 = 0%, Level 4 = 60%; pp. 7–8). The abstract's "scales almost linearly with prompt adversariality" (p. 1) is therefore an author claim with no defined adversariality scale.
4. **"Already-registered lookalike" finding (the paper's headline).**
   - [V] 385 runs produced 823 verdicts: 644 `real` (78.3%) and 179 `hallucinated` (21.7%) (p. 8).
   - [V] Of the 179 flags, "Half were true 404s". The other half returned PyPI status 200 and were flagged by the classifier on suspicious metadata. The paper later gives 90 `status=200` flags (pp. 8–9).
   - [V] Table 3, "Wild caught PyPI registered squats and lookalikes" (pp. 8–9):

     | Name | Canonical project (per Table 3) | P(fake) | Flags |
     |---|---|---|---|
     | `pil` | Pillow | 0.89 | 36 |
     | `faiss` | faiss-cpu/-gpu | 0.57 | 10 |
     | `tabula` | tabula-py | 0.57 | 4 |
     | `haystack` | now haystack-ai | 0.56 | 2 |
     | `camelot` | camelot-py | 0.95 | 1 |
     | `skimage` | scikit-image | 0.58 | 1 |
     | `fastyaml` | none identified | 0.99 | 1 |
     | `fastvector` | none identified | 0.82 | 1 |
     | `graphbrain` | ambiguous | 0.92 | 2 |

     Further rows include `aiworkflow`, `taskgraph`, `promptstudio`, `flowgraph-ai`, `embeddinghub`, and "22 more" names with one or more flags each.
   - [A] "Approximately half of the hallucinated recommendations produced by the LLM were already present on PyPI as squats or low-quality lookalikes", so a deterministic-only check "would have caught only the other half" (p. 9).
   - [V] Security invariant: for all 90 `status=200` flags, the reconciler was never called (p. 9).
   - [A] The reconciler "correctly refused to help every single time" against an attacker suite. The attacker suite is not described (p. 6).
   - [I] **This finding needs caution.** In Table 3, 36 + 10 = 46 of the 90 status-200 flags (≈51%) come from `pil` and `faiss`. Both are the normal *import* names of real projects (`import PIL` for Pillow, `import faiss` for faiss-cpu). Several other rows (`skimage`, `camelot`, `tabula`, `haystack`) are also import or legacy names of legitimate projects. A large share of the "already registered" half is therefore probably correct `import` statements whose import name happens to be a separate, low-quality PyPI project. That is a real install-time risk if a user types `pip install <import name>`, but it is not the LLM inventing a package. Because the reconciler deliberately does not run on 200 responses (p. 5), the design itself produces these flags. The authors also admit they have not audited the ≥30 registered names (pp. 13–14).
5. **Classifier transfer.** [V]
   - The first per-model row split leaked: 72.9% of off-diagonal test rows contained package names already in training (p. 9).
   - On the corrected package-disjoint split, F1 ranges from 0.833 to 1.000 (pp. 9–10).
   - Two test columns (llama-4-scout, qwen3-27b) have only 2 positives each, giving CIs of [0.00, 1.00]. The llama columns have 5 positives each (CI [0.67, 1.00]) (p. 10).
   - [A] One classifier trained on `gpt-oss-120b` (~410 rows) "works well across all seven models", so matched-pair training "is not needed" (p. 10).
6. **The classifier is in effect a two-feature metadata rule.** [V]
   - `log_maintainers` provides 57.6% of the split importance and `github_url_present` another 24.5% (82% together) (p. 10).
   - Rule C (OR over the two features) reaches mean F1 0.99 versus 0.98 for the Random Forest. Strict-AND rules reach 0.53–0.55 (p. 12).
   - [A] "the 400-tree Random Forest does not really give us more help than the simple OR baseline" (p. 12).
   - [I] The prose then states the rule as "zero PyPI maintainers AND no GitHub URL", which contradicts the table's finding that the OR rule wins (p. 12). The exact rule is ambiguous.
7. **Same-family fallback mostly fails.** [V] 71 of 85 give-ups (83.5%) failed again on `llama-3.3-70b`. The same invented names recurred in both models' outputs (e.g. `pdfgenius`, `ultrarag`, `hyperfaiss`, `fastyaml`, `vectorcache`, `embedflow`, `taskgraph`) (p. 10). [A] A cross-family fallback should work better, but this was not tested (pp. 11, 13).
8. **Bait refusal.** [V] Bonus Stress Test, 10 prompts that name fabricated packages (p. 11):
   - 1 bait was used verbatim (`ultrarag`) and caught by the detector.
   - 3 became nearby variants (`fastvector`, `fastyaml`, `faiss`).
   - 6 were "refused outright", and real packages were substituted.
   - The pipeline finished clean on 6/10.

   [I] The paper reports this inconsistently. The abstract says the model "refused 6 of 10 direct baits unaided" (p. 1); §6.8 says "The LLM refused the bait name on 9 of 10 prompts" (p. 11).
9. **User acceptance.** [V] Mean ratings 4.21–4.58, overall 4.42/5. 21/24 participants would use the tool and 23/24 would recommend it (p. 11). [A] The authors acknowledge possible desirability bias (pp. 2, 11).

## 8. Limitations stated by the authors
- [A] Only one model pair was evaluated (llama-3.1-8b → llama-3.3-70b). A cross-family test was not affordable on the Groq budget (p. 13).
- [A] The `pypi_maintainers_count` feature "is basically 0" because the PyPI JSON API only shows maintainers to admins. This "might cause false positives for small legitimate packages" (p. 13).
- [A] Transferability cells rest on 2–12 hallucinated test examples, so two columns are uninformative. More runs or pooled cross-validation are needed (pp. 10, 13).
- [A] About 82% of the classifier's signal comes from two metadata features, so attackers could evade it by registering squats with realistic-looking metadata. This was not tested (p. 13).
- [A] The ≥30 registered names flagged as suspicious were not individually audited (pp. 13–14).
- [A] The user study participants were the intern's friends (p. 14).
- [A] Drift:
  - brand-new legitimate packages will be mis-flagged (zero maintainers, no GitHub link, not in the 15k list);
  - the reference list goes stale;
  - packages can be renamed or taken over (`haystack` → `haystack-ai`).

  None of the proposed mitigations (monthly snapshot refresh, quarterly retraining, 24 h metadata cache, false-positive monitoring) is implemented (p. 14).

## 9. Limitations we identified
- [I] **No ground truth for the 300-prompt run.** Detector precision and recall are never measured against manually labelled package names. "Hallucinated" means "flagged by the detector". The 179 flags, and the 50/50 split, therefore mix true hallucinations with false positives.
- [I] **Construct problem in the "already registered" finding.** As shown in §7 finding 4, about half of the status-200 flags are `pil` and `faiss`, which are standard import names. The paper's own security rule (the reconciler runs only after a 404) turns correct imports into "hallucinations" whenever someone else has registered the import name. The headline "half of hallucinations are registered lookalikes" (pp. 1, 9, 15) probably overstates LLM invention and understates the import-name/install-name ambiguity.
- [I] **Train/serve skew in the top feature.** If `log_maintainers` (57.6% of importance) is near zero for most packages at inference via the JSON API (p. 13), but training data were "pulled" by another route ("Sargam's dataset helps a little by pulling metadata", p. 13), the live classifier probably flags legitimate status-200 packages on that feature alone. This would inflate the registered-lookalike count.
- [I] **Possibly circular training labels.** How training labels were assigned is not reported. If "hallucinated" was derived from PyPI non-existence, then features such as "no maintainers" and "no GitHub URL" are trivially true for 404 names. That would explain the near-perfect F1 and the dominance of metadata features.
- [I] **Overstated baseline comparison.** The conclusion that the system "cuts the give-up rate from 79% (unmitigated) to 28.7%" (p. 15) compares against v0, a version with a broken extractor on a different 70-prompt set (p. 7). That is a bug-fix comparison, not an unmitigated baseline.
- [I] **Internal inconsistencies:**
  - bait refusal 6/10 vs 9/10 (pp. 1, 11);
  - "40 to 73%" vs the 30% tier (pp. 1, 8);
  - retry budget "up to 2 attempts" vs a three-step temperature schedule (pp. 3, 6);
  - "AND" vs "OR" rule wording (p. 12).
- [I] **Unverifiable model identifier.** `qwen3-27b` is given without provider or version (p. 2). We could not confirm the identifier from the paper.
- [I] **Weak survey.** The user study tests the standalone UI, not the detector's accuracy. With a friends-and-peers sample, it says little about effectiveness.

## 10. Threats to validity
- Internal:
  - The prompt set was written by the authors, and the tiers are defined post hoc.
  - Detector false positives are counted as hallucinations.
  - Same-family names recur across primary and fallback, so the two runs are not independent.
  - Leakage in the first classifier split was found and fixed (p. 9). The labelling procedure is not reported.
- External:
  - One small model (llama-3.1-8b) through one API provider (Groq), Python/PyPI only.
  - No genuinely local inference: hardware, quantization and runtime are not reported.
  - Single-line prompts are not agentic multi-file tasks.
- Construct:
  - "Give-up" mixes non-code answers, true hallucinations and detector false positives.
  - "Hallucination" is defined by the detector itself.
  - "Squat or lookalike" status was not audited (pp. 13–14).
- Statistical conclusion:
  - Only F1 has CIs, and those are very wide (p. 10).
  - Tier rates rest on n = 5–30 prompts each, with no CIs (pp. 7–8).
  - Single run per prompt; nothing on seed variation.
- Reproducibility:
  - [A] Artefacts are said to be on GitHub (p. 15).
  - Not reported: model versions, Groq dates, classifier threshold, training-data construction. Groq's hosted models change over time.

## 11. Future research directions
- Stated by authors [A]:
  - cross-family fallback pairing, e.g. Llama → Qwen or GPT-OSS (pp. 11, 14);
  - richer features (first-upload age, release cadence, owner-network overlap, README quality, repository activity), which must beat the two-feature rule (p. 14);
  - about 3× more hallucinated examples per model, or pooled cross-validation (pp. 10, 14);
  - drift handling: monthly top-N refresh and quarterly retraining (p. 14);
  - adversarial squats with realistic metadata are named as untested (p. 13).
- Suggested by us [I]:
  1. Manually audit every flagged name, and keep three cases apart: (a) a correct import name whose PyPI namesake is a different project; (b) a hallucinated name that is registered; (c) a hallucinated name that is unregistered.
  2. Evaluate the 404 + metadata rule against synthetic squats with realistic metadata (maintainers, GitHub URL, upload age).
  3. Replace the unavailable maintainer feature with upload age and release history from the PyPI JSON/Simple API.
  4. Run the models truly locally (e.g. quantized 7–8B models through a local runtime) to test whether quantization changes the rates.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ3 (primary: tool-side defence), RQ2 (registered lookalikes, name recurrence across same-family models), RQ1 (rates by prompt tier for one small model), RQ4 (pitfalls: extractor scope, import-name reconciliation, split leakage), RQ5 (untested: cross-family fallback, realistic-metadata squats, local inference).
- How it informs our work [I]:
  - **Laptop-scale feasibility.** The defence is cheap: a PyPI JSON lookup plus a two-feature rule, which the authors say fits in "one line of Python" (p. 12). It needs no GPU and runs on any laptop. It is a natural baseline for our defence study. The authors' own evaluation was done on a free API tier, not locally, so a truly local replication (Ollama or llama.cpp with quantized models) would add something new.
  - **What a measurement study should do better.** The paper lists the pitfalls a laptop-scale measurement must handle:
    - extract only from code fences, with AST parsing;
    - keep a separate import-name ↔ distribution-name map, and record PyPI status separately from "hallucinated";
    - snapshot PyPI responses with timestamps;
    - hand-label a sample to estimate precision.
  - **Open question worth testing.** How many LLM-suggested names are already registered on PyPI, and by whom. With careful import/install handling, this is directly measurable on a laptop. This paper's estimate (~50%) is the number to check, and we have reason to think it is inflated by import-name collisions.
  - **Weight.** Single preprint, one model pair, unaudited labels: treat as **weak** evidence. Use it for design ideas and pitfalls, not for effect sizes.

# An Empirical Analysis of Static Analysis Methods for Detection and Mitigation of Code Library Hallucinations

- Authors: Miranda-Pena, Clarissa; Reeson, Andrew; Paris, Cécile; Poon, Josiah; Kummerfeld, Jonathan K.
- Year / venue: 2026, arXiv (preprint)
- DOI: 10.48550/arxiv.2604.07755 · URL: https://arxiv.org/abs/2604.07755
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

**Source tier:**
- [A] Every page carries "Published in Transactions on Machine Learning Research (10/2026)", and p. 1 gives "Reviewed on OpenReview" with a forum link; the arXiv stamp is v3, 6 Nov 2026 (p. 1).
- `metadata.json` still records `venue_kind: preprint`.
- We treat it as a claimed TMLR (peer-reviewed journal) paper whose venue is not yet confirmed by metadata.

## 1. Research objective
- [A] Quantify what static analysis can and cannot do to detect and mitigate *library hallucinations* in NL-to-code generation. Library hallucinations are code that would work only if imagined libraries, functions, parameters or types existed (pp. 1, 3).
- [A] Establish an upper bound for static methods through manual analysis (pp. 1–2).

## 2. Research questions / hypotheses
- No formal RQs. The contributions are (p. 2):
  1. an analysis of static tools for detection and mitigation;
  2. manual hallucination annotations on three benchmarks;
  3. a docstring-to-grammar framework for constrained decoding.
- Implicit questions: detection precision and recall (§5.1); the upper bound and the causes of misses (§5.1.1–5.1.2); whether tool-guided LLM repair fixes hallucinations (§5.2); whether constrained decoding prevents them (§5.3) (pp. 5–11).

## 3. Methodology
- Research design: [V] Comparative empirical evaluation of three detectors plus a baseline, repair with and without tool output, and constrained vs unconstrained decoding. Run on three execution-based benchmarks and six generation models, with manual annotation of a failure sample (pp. 4–11).
- Approach / model / intervention:
  - [V] **(1) Grammar.** A GBNF grammar auto-extracted from library docstrings via `inspect`, combined with the Python grammar, used for post-hoc checks and for constrained decoding in llama.cpp/Ollama. Its import rule validates packages "in the environment of the benchmark and Python built-in modules" (pp. 3–4).
  - [V] **(2) Off-the-shelf analysers.** Mypy and Pyright with auto-generated type stubs (p. 4).
  - [V] **(3) Baseline judge.** An o3-mini LLM-as-judge asked whether the code will execute (p. 4).
  - [V] **Repair.** o3-mini is given the code and the error, alone ("o3+Self") or with Mypy/Pyright output (pp. 9–10).
- Baselines or comparison conditions: [V] o3-mini judge for detection; "No repair" and o3+Self for repair; unconstrained decoding for mitigation (pp. 6, 9, 11).

## 4. Dataset and sample
- Data source(s): [V] DS-1000 (1,000 problems, 7 libraries), ODEX (945 problems, 79 libraries, 4 natural languages), BigCodeBench-instruct (1,140 problems, 139 libraries) (p. 5).
- Sample size (N) and unit:
  - [V] All questions of DS-1000 and BigCodeBench, plus "550 questions from RIG" (questions not needing imports were skipped) (p. 5). [I] "RIG" is never defined and is probably ODEX.
  - [V] Six generation models (p. 5).
  - [V] Manual analysis: 200 failure cases per benchmark (600 in total), sampled equally across claude-3, gpt-3.5, gpt-4 and Granite 3B (p. 6).
  - [V] Repair: 2,210 erroneous samples (DS-1000), 2,001 (BigCode) and 1,291 (Odex) (p. 10).
- Sampling / selection method: [V] Benchmarks were chosen because they need an NL prompt that demands library use, plus test cases (p. 5). How the manual sample was drawn within the strata is not reported.
- Data availability:
  - [V] Benchmarks are used under Apache-2.0 / CC-BY-SA-4.0 (p. 17).
  - [A] The annotation guideline is supplemental material (pp. 7, 17).
  - A release of the generated outputs or annotations is not reported.

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools:
  - [V] **Models.** Claude-3, GPT-4 and GPT-3.5 (API); Gemma2 2B, IBM-Granite 3B and Qwen3 8B (open). Temperature 1 for API models and 0.4 for open models, "as reported in prior work" (p. 5). Exact API model versions are not reported.
  - [V] **Granite responses.** BigCodeBench responses came from the leaderboard and were re-run for the constrained comparison (p. 10).
  - [V] **Hardware.** "a local computer with an M2 processor, 8-core CPU, 10-core GPU, and 24GB RAM" (p. 17).
  - [V] **Decoding.** llama.cpp parser plus a pushdown-automata state cache. llama.cpp samples first and masks only when the grammar rejects (p. 4).
  - [V] **Grammar construction.** Converting the Python grammar to GBNF took about 4 h by hand; each library-grammar step takes under a second (pp. 4, 16).
  - [V] **Detection time.** Mypy about 1 s, Pyright and grammar about 2.5 s, o3-mini about 4 s (p. 19).
  - [V] **Constrained-decoding cost.** Unconstrained responses average 22.3 s, constrained 34.76 s (p. 11).
- Code availability: not reported (no repository link found).

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] **Precision/recall on all errors.**
  - [V] **Imaginary Feature Recall (IFR):** recall on examples with Attribute/Import/Type/ModuleNotFound errors (p. 5).
  - [V] **RIF:** imaginary features as a share of the errors remaining after repair (p. 5).
  - [V] **Pass@1, Execution Rate (ER), and IF%:** IF% is the share of samples with one of the four error types (p. 5).
  - [V] **Manual-analysis measures:** Caught, TP, Overlap, Capable (p. 7).
  - [I] RIF is relative: it can rise when repair removes *other* errors, even if the number of hallucinations is unchanged.
- Statistical testing:
  - [V] Cohen's kappa for annotation, average 0.79 (pp. 7, 18).
  - [V] Spearman correlation between the full and the validated benchmark: 0.98 (detection), 0.99 (constrained decoding), 0.88 (repair) (p. 12).
  - No CIs, significance tests or multiple-run variance.

## 7. Key findings
1. [A] LLMs use non-existent library features in "8.1-40% of responses" (p. 1). [I] This figure cannot be traced to a single body table. Table 6 gives IF% of 4.4–22.2 for the open models (p. 11), and the no-repair RIF ranges 8.1–44.9 (p. 10), but RIF is a share of errors, not of responses.
2. [V] **Detection on all errors.** Pyright has the highest recall overall (e.g. 0.70 claude-3/DS-1000, 0.82 gpt-4/Odex). Grammar recall is 0.04–0.22. o3-mini has high precision and low recall (p. 6).
3. [V] **Detection on hallucinations (IFR).** Pyright 0.14–0.85, Mypy 0.03–0.70, grammar 0.06–0.20, o3-mini 0.02–0.78 (o3-mini is better on the small models). Hallucination precision was 1 except one cell at 0.98 (pp. 7, 20).
   - [A] Mypy and the grammar do best on ImportError/ModuleNotFound, while Pyright is better on Type/AttributeError (p. 6).
4. [V] **Manual upper bound** (Table 2):
   - Static tools "Capable" on 77.0% (DS-1000), 70.5% (Odex) and 48.5% (BigCode); the grammar on 18.0/10.5/7.0% (p. 8).
   - Caught exceeds TP (e.g. static on DS-1000: 56.7 caught vs 37.6 TP), showing many detections are right for the wrong reason (pp. 7–8).
   - [A] "after manual inspection we found that false positives mean the true upper bound is 77%" (p. 12).
5. [V] **Benchmark noise.** "Ambiguous output" accounts for 30.3% (Odex) and 26.6% (BigCode) of sampled hallucinations (p. 8). [A] "over 30%" of apparent hallucinations come from benchmark underspecification (p. 9). Removing noisy items (3% / 7.7% / 6.1%) preserves model rankings (p. 12).
6. [V] **Repair raises ER and Pass@1** (e.g. Gemma2 2B on DS-1000: ER 47.2 → 77.9 with o3+Self) (p. 9).
   - The RIF does not fall and increases on Odex for the small models (e.g. Qwen3 8B 31.3 → 55.6 with Mypy) (p. 10).
   - [A] "While repair consistently improves executability, imaginary features prove resistant" (p. 10).
7. [V] **Constrained decoding** changes IF% by small, mixed amounts:
   - Odex: Gemma 5.4 → 4.8, Granite 8.9 → 8.2, Qwen 6 → 4.4.
   - DS-1000: Granite 10.4 → 6.7, but Gemma 10.4 → 12.6.
   - Pass@1 sometimes drops (p. 11).
   - It adds about 12 s per request (p. 11).

## 8. Limitations stated by the authors
- [A] Python only; other languages need a hand-converted grammar and an adapted script (pp. 4, 12).
- [A] The grammar cannot handle atypical aliases, because llama.cpp grammars cannot track state (p. 16). It cannot link attributes imported via `from ... import` (p. 8).
- [A] Docstrings are incomplete (e.g. namespaces, dtype), which causes grammar errors and lowers Pass@1 (pp. 8, 10).
- [A] Static tools miss data-flow and control-flow cases (lambda/map/apply, type mutation) (pp. 7–8).
- [A] One annotator labelled the remaining two-thirds after agreement was checked (p. 7).
- [A] Memoisation gave no speed gain; latency needs further analysis (p. 19).

## 9. Limitations we identified
- [I] **Package existence is judged against the benchmark environment, not a registry.** ModuleNotFoundError is defined as "does not exist in the environment and/or in real life" (p. 18), and the grammar validates imports against the benchmark environment (p. 4). Real-but-uninstalled packages and invented packages are therefore merged. The paper says nothing about whether names exist on PyPI or about squatting.
- [I] **Only part of the scope is package-level.** Most imaginary features are member-level (Attribute/Type errors). Package-level results are not separated out.
- [I] **Abstract ranges are not traceable.** The abstract's "8.1-40%", "16-70%" and "14-85%" do not match the table ranges directly.
- [I] **Unspecified model versions and mixed temperatures.** Model versions are not given, and temperatures differ between closed (1.0) and open (0.4) models, which confounds model comparisons.
- [I] **Inconsistent annotation share.** The double-annotated share is "One third" (p. 7) but "25%" in the Table 8 caption (p. 18).
- [I] **Thin reproducibility and statistics.** No CIs, a single Pass@1 sample, and no code release reported.

## 10. Threats to validity
- Internal: o3-mini is both a detector baseline and the repair model. Granite outputs come from different sources across experiments (p. 10). RIF is a relative metric.
- External: Python, three benchmarks, older closed models (Claude-3, GPT-3.5/4) and small open models; no agentic setting.
- Construct: "hallucination" is operationalised through runtime error types against an installed environment. Benchmark underspecification inflates counts, which the authors partly correct (pp. 9, 12).
- Statistical conclusion: no tests or CIs. Kappa is substantial (0.79) (p. 7).
- Reproducibility: hardware and benchmarks are reported; model versions, code and outputs are not.

## 11. Future research directions
- Stated by authors [A]:
  - use the model's internal states for detection (p. 12);
  - extend static tools with data-flow and control-flow tracking (pp. 7–8);
  - build benchmarks that accept multiple valid solutions and specify input/output types (p. 9);
  - study where hallucinations originate (p. 12);
  - extend to other languages (p. 4).
- Suggested by us [I]:
  - add a registry-existence layer (PyPI/npm) to the static pipeline, so that "not installed" is separated from "does not exist" and from "exists but is a squat";
  - report package-level results separately.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ3 (static analysis and constrained decoding as cheap defences; cost and effectiveness), RQ4 (environment-based ground truth, benchmark-noise pitfalls, annotation reliability), RQ1 (hallucination shares across small and large models, partially), RQ5 (laptop feasibility).
- How it informs our work [I]:
  - **Proof of laptop feasibility.** The whole study, including constrained decoding of 2–8B models, ran on an M2 machine with 24 GB RAM (p. 17).
  - **Cheap import-level screening.** Mypy/Pyright with stubs run in about 1–2.5 s per sample (p. 19), a cheap pre-execution layer for import-level hallucinations. However, they check the *installed environment*, not the registry, so they cannot tell a slopsquatted package (which installs fine) from a legitimate one. A registry-aware check is still needed.
  - **Constrained decoding is not worth it here.** It costs about +12 s per request for small, inconsistent gains (p. 11).
  - **Measurement lesson.** Separate benchmark noise from model hallucination, and validate a subset by hand.
  - Evidence strength: **moderate** (claimed peer-reviewed, sound manual analysis, but the package-level relevance is indirect).

# Library Hallucinations in LLM-Generated Code: A Risk Analysis Grounded in Developer Queries

- Authors: Twist, Lukas; Harman, Mark; Yannakoudakis, Helen; Zhang, Jie M.
- Year / venue: 2026, Proceedings of the 2026 Conference on Empirical Methods in Natural Language Processing (published)
- DOI: 10.18653/2026.emnlp-main.78 · URL: https://doi.org/10.18653/2026.emnlp-main.78
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

**Source tier:** EMNLP 2026 main conference, pp. 1785–1812 (p. 1). Tier 1, peer-reviewed.

## 1. Research objective
- [A] The authors present "the first systematic study of how user-level prompt variations influence library hallucinations". They cover library *name* hallucinations (invalid imports) and *member* hallucinations (invalid calls from valid libraries) (p. 1).
- [A] They also want to provide a reproducible benchmark (LibHalluBench) built from the highest-risk conditions (pp. 1–2).

## 2. Research questions / hypotheses
- No numbered RQs. The paper runs two main experiments (pp. 3–4):
  - **Exp. 1, user language.** Do realistic library descriptions mined from StackExchange (e.g. "fast", "modern", "from 2025") change hallucination rates?
  - **Exp. 2, user mistakes.** Do one-character typos, multi-character typos, or fake names/members cause hallucinations?
- Additional studies (pp. 7–8): prompt engineering, ecosystem generalisability, rarity-seeking language, PyPI-tool access, and ablations/controls.

## 3. Methodology
- Research design: [V] Controlled experiments that vary one prompt slot (`{library directive}`) in a fixed template, measured across seven LLMs with three responses per prompt (pp. 3–4, 15).
- Approach / model / intervention:
  - [V] **Extraction.** Code blocks are extracted by regex. Python `ast` reads Import/ImportFrom (handling aliases and namespace packages) and Call/Attribute nodes (p. 4).
  - [V] **Name check.** Names are compared with PyPI using PyPA name normalisation (p. 4).
  - [V] **Member check.** Members are compared with scraped official documentation (latest version) (pp. 4–5).
  - [V] **Version exclusion.** Responses that state a valid explicit version are excluded (p. 5).
  - [V] **Generated mistakes.** Typos and fake names are generated by o4-mini. Edit distance is checked (1, or 2–8), and every name is verified to be non-existent (pp. 4, 17).
- Baselines or comparison conditions: [V] "No description" (Exp. 1) and "None, valid library/member" (Exp. 2) conditions; un-prompted vs prompt-engineered vs tool-augmented runs (pp. 5–6, 18, 21).

## 4. Dataset and sample
- Data source(s):
  - [V] BigCodeBench (1,140 tasks), filtered to tasks that do not name the ground-truth library and whose libraries have accessible documentation. This gives 356 tasks using 30 libraries; 10% are held out for preliminary experiments (p. 3). LibHalluBench is built from 321 seed tasks (p. 8).
  - [V] Software Recommendations StackExchange: over 20,000 questions, filtered to 3,917 library-related questions and clustered into nine descriptors. 23 question titles contain a year (pp. 4, 16).
  - [V] CodeInsight test split (1,860 records). The longest 50% were kept, 500 were sampled, and an LLM rewrote them to be library- and language-agnostic (p. 19).
- Sample size (N) and unit:
  - [V] Three responses per prompt (p. 4).
  - [V] Two instances of each error type per task (p. 4).
  - [V] Ecosystem study: one response per task, with 140 Python, 161 JavaScript and 184 Rust libraries (pp. 7, 20).
- Sampling / selection method:
  - [V] The SRSE filter was validated on 200 hand-labelled questions (precision and recall 0.95) (p. 15).
  - [V] Clusters were retained if they linked to at least 20 questions (p. 16).
- Data availability:
  - [V] Code and full model outputs are on GitHub (p. 2).
  - [V] LibHalluBench is on Hugging Face (gated access) and on PyPI (`libhallubench`), with a canary string (pp. 8, 23).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools:
  - [V] **Models, with exact versions** (p. 15):

    | Model | Version | Temperature | top_p |

  - [V] All models are accessed via provider APIs (OpenAI, Mistral, Together, DeepSeek, Anthropic). Each call is a fresh session with no system prompt. Study date: January 2026 (pp. 3, 15).

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] **RHR:** share of responses containing a hallucination.
  - [V] **THR:** share of tasks with at least one hallucinating response out of three (p. 5).
  - [V] **Tool study:** hallucination rate, share of responses using the tool, tool calls per response, and share of no-code responses (p. 21).
  - [V] **Detector validation:** precision and recall on 200 high-risk responses (pp. 5, 15).
  - [V] In Exp. 2 with valid names, the rate shown is how often the requested valid library was *not* used (p. 6).
- Statistical testing: none reported (no tests, CIs or effect sizes). "Significantly" is used descriptively (pp. 6, 8).

## 7. Key findings
1. [V] **Normal prompts rarely produce invented library names.** With "No description" and adjective prompts, library-name RHR is ≤0.31% for all models (p. 5).
2. [V] **Year-based prompts drive library-name hallucination.** "From 2025" THR (p. 5):
   - GPT-4o-mini 84.74%
   - GPT-5-mini 63.86%
   - Qwen-2.5-Coder 61.68%
   - DeepSeek-V3.1 38.01%
   - Ministral-8B 32.40%
   - Llama-3.3 1.87%
   - Claude-4.5-Haiku 0.62%

   [V] A year control shows "from 2022" stays <1.1% RHR, while "from 2026" gives DeepSeek-V3.2 59.81% vs Claude 0.73% (p. 28). [A] Knowledge cut-off contributes but does not fully explain the effect (p. 28).
3. [V] **User mistakes are accepted** (library-name THR, p. 6):
   - one-character typos: up to 25.86% (GPT-5-mini);
   - multi-character typos: up to 79.44%;
   - fake library names: 90.50–99.22% for GPT-4o-mini, GPT-5-mini and Ministral-8B, vs 20.72% for Qwen-2.5-Coder.

   [V] Average usage of fake members is 31% vs 69% for fake names (p. 7). [A] The authors link this to sycophancy and say LLMs "may amplify typosquatting risks" (pp. 2, 6).
4. [V] **Rarity-seeking language.** "Hidden gem" raises the average library-name THR to 5.35%, the highest of the adjective prompts (p. 8).
5. [V] **Prompt engineering is inconsistent.** Self-analysis reduces hallucinations in 29/36 settings and explicit-check in 30/36. Chain-of-thought and step-back are inconsistent, e.g. Qwen-2.5-Coder fake-name RHR rises by 28.66 points under chain-of-thought (pp. 18–19).
6. [V] **A PyPI-existence tool helps but does not remove the problem** (pp. 8, 21):
   - GPT-4o-mini calls it on 98.65% of "from 2025" responses, with 2.49% hallucination.
   - GPT-5-mini calls it on only 7.89% and returns no code 90.76% of the time.
   - Under user mistakes, invalid libraries are still accepted in up to 38.79% of cases.
7. [V] **Other ecosystems** (CodeInsight, RHR; p. 20):
   - JavaScript fake names 27.2–88.8%;
   - Rust fake names 41.30–96.76%;
   - Rust "from 2025" up to 57.40% (Qwen).
8. [V] **Detector validation.** 24 responses were auto-flagged and 23 were true hallucinations (95.8% precision). No false negatives were found in the 200-response sample. The one false positive was `pywintypes` (pp. 5, 15).
9. [V] **LibHalluBench baselines** (overall task-level rate across the Describe and Specify splits): Llama-3.3 10.4% lowest; GPT-4o-mini 39.0% and GPT-5-mini 39.8% highest (p. 23).
10. [V] **Robustness.** Greedy decoding and Qwen3-235B-generated mistakes leave the qualitative patterns unchanged (pp. 26–27).

## 8. Limitations stated by the authors
- [A] Generalisability: a finite set of tasks, ecosystems and model versions. Behaviour may differ for other languages, domain frameworks, low-resource ecosystems or future models (p. 9).
- [A] Internal validity: automatic extraction and prompt construction are mitigated with unit tests and manual validation (pp. 9–10).
- [A] External validity: dataset bias and LLM nondeterminism and updates. Leakage would make the results conservative (p. 10).
- [A] Evolving models and package ecosystems may affect reproducibility (p. 10).
- [A] The prompt-engineering study is not exhaustive, and the tool study is a "small case study" on the GPT models only (pp. 7–8).

## 9. Limitations we identified
- [I] **Exp. 2 measures compliance, not spontaneous invention.** The invalid name comes from the user prompt, so the attacker cannot predict it from the model. This is a *typosquatting-amplification* threat model, not classic slopsquatting of model-invented names.
- [I] **Registered names count as valid.** Generated mistakes were filtered to be *unregistered* (pp. 4, 17), and any name present on PyPI counts as valid (p. 4). Hallucinations that collide with already-registered or squatted names are therefore invisible by design, which undercounts the real security risk.
- [I] **Registry snapshot undated.** The main check's PyPI snapshot date is not reported. The tool used a "cached PyPI package list" (p. 22) and the study ran in January 2026 (p. 15).
- [I] **Persistence not reported.** Whether the same invented names repeat across runs or models is not reported. This is a central question for slopsquatting (RQ2).
- [I] **Small validation sample.** Detector precision rests on 24 flagged responses. Recall is inferred from 200 responses drawn from only two high-risk conditions (p. 15).
- [I] **Mixed temperatures.** Default temperatures differ across models (0.3–1.0) (p. 15), which confounds model comparisons. The greedy ablation (p. 26) partly addresses this.
- [I] **No uncertainty reporting.** Differences such as 0.10% vs 0.31% equal one response or task.
- [I] **API models only.** No local or quantized models were tested.

## 10. Threats to validity
- Internal:
  - Year prompts are partly confounded with knowledge cut-off; the control is small (p. 28).
  - Typos generated by an LLM may not match real human typos; the provider ablation mitigates this (p. 27).
- External:
  - The main results rest on one benchmark (BigCodeBench, 30 libraries) and single-turn, single-function prompts; there is no agentic setting.
  - The ecosystem study extends to JS and Rust (p. 20).
- Construct:
  - "Hallucination" means "not on the registry or in the docs". Already-registered hallucinations are counted as correct.
  - Exp. 2 compliance is labelled as hallucination.
- Statistical conclusion: no tests or CIs. Three responses per prompt give limited per-task resolution.
- Reproducibility: strong. Versions, parameters, prompts, code, outputs and the benchmark are all released (pp. 2, 15–17, 23). The DeepSeek version had to be swapped (p. 14).

## 11. Future research directions
- Stated by authors [A]:
  - cut-off-aware behaviour and anti-sycophancy behaviour;
  - lightweight pre-decision existence checks;
  - reporting hallucination, refusal, tool-use and calibration metrics (p. 9);
  - more robust approaches (grounding, fine-tuning, architecture) (p. 19);
  - agentic coding workflows (p. 9).
- Suggested by us [I]:
  - measure name repetition and how many invented names are already registered;
  - run LibHalluBench on local quantized models;
  - test a *forced*, non-optional client-side existence check versus model-invoked tools.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1 (drivers: prompt type, model, ecosystem), RQ3 (prompt-engineering and tool-use defences), RQ4 (PyPI normalisation, version exclusion, detector validation, benchmark), RQ2 (typosquat amplification, indirectly), RQ5 (untested: local/quantized models, agents, registered-name collisions).
- How it informs our work [I]:
  - **A ready-made trigger set.** LibHalluBench (4,173 prompts) and the `libhallubench` package give a laptop-runnable trigger set. Year-based and typo/fake-name prompts are the highest-yield conditions for a small measurement study.
  - **Untested setting.** Running the benchmark against local quantized open models (none tested here) is an obvious, cheap extension.
  - **Why a forced check matters.** The tool study shows a model-invoked existence check depends on the model choosing to call it (GPT-5-mini rarely did). A *forced*, client-side check, as in raj2026names, avoids that dependency. The comparison is a well-defined defence experiment.
  - **Inherit the methods.** Adopt the PyPI name normalisation and the version-exclusion rule. Add a status for "registered but suspicious", which this paper by design does not measure.
  - Evidence strength: **moderate–strong** (peer-reviewed, 7 models, repeated sampling, ablations), but there is no inferential statistics and the main results rest on one benchmark.

# Backstabber’s Knife Collection: A Review of Open Source Software Supply Chain Attacks

- Authors: Ohm, Marc; Plate, Henrik; Sykosch, Arnold; Meier, Michael
- Year / venue: 2020, Lecture Notes in Computer Science (book)
- DOI: 10.1007/978-3-030-52683-2_2 · URL: https://doi.org/10.1007/978-3-030-52683-2_2
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

**Source tier:** LNCS book chapter (per metadata), 2020. The analysed text is the arXiv v1 version (arXiv:2005.09535v1, 19 May 2020; p. 1) and may differ slightly from the published chapter. It is used as **background only**: pre-LLM, seminal (241 citations per metadata).

## 1. Research objective
- [A] Give a structured overview of how attackers inject malicious code into open-source dependency trees and trigger it. The aim is to support preventive and detective safeguards (p. 1).
- [A] Provide a manually curated dataset of malicious packages used in real-world attacks (pp. 1–2).

## 2. Research questions / hypotheses
- No formal RQs. There are two contributions (p. 2):
  1. manual analysis and categorisation of 174 real malicious packages (2015–2019);
  2. two attack trees, one for *injection* and one for *execution*.

## 3. Methodology
- Research design: [V] Qualitative and descriptive (pp. 4–5).
  - Attack trees were built iteratively. Each malicious package or information source was mapped to a node, and a new node was added when none fitted.
  - Packages were analysed and categorised by hand.
- Approach — the attack trees (read from Fig. 2, p. 7, and Fig. 3, p. 9):
  - [V] **Injection tree.** Root: "Injection of Malicious Code (into dependency tree)" (p. 7).
    - **Create New Package**: {Trojan Horse; Typosquatting; Use After Free} (p. 7).
    - **Infect Existing Package** (p. 7):
      - Inject into Source: Pull Request as contributor; Commit as maintainer, via weak/compromised credentials or API tokens, or via social engineering to become maintainer.
      - Inject during the Build: Compromise Build System, by manipulating the package download or running a malicious build on shared systems.
      - Inject into Repository System: weak/compromised credentials or API tokens; exploit vulnerabilities; deploy in an alternative repository or mirror.
  - [V] **Execution tree** (p. 9). Root: "Execute Malicious Behavior".
    - During Different Life Cycle Phases: {Install Scripts; Test Case; Runtime}.
    - Conditional Execution: {Application State; Dependency Tree; Operating System}.
  - [A] **New packages.** Creating a new package "using a name that is not used by anybody else avoids interference with other legitimate project maintainers. However, such a package has to be discovered and referenced by downstream users", for example via typosquatting or by promoting a trojan horse (p. 7).
  - [A] **Install-time execution.** "Such install scripts exist for Python and Node.js" and run automatically during installation (p. 8).
  - [A] **Import-time execution.** In Python, runtime triggering can be achieved through code in `__init__.py`, which runs on `import` (p. 9).
- Baselines or comparison conditions: not applicable (descriptive study).

## 4. Dataset and sample
- Data source(s):
  - [V] The Snyk vulnerability database, language-specific security advisories and research blogs were reviewed between 2 July and 2 August 2019, with an update on 27 January 2020 (p. 4).
  - [V] Malicious code was retrieved from deprecated mirrors, internet archives and research repositories, because the registries had removed it (p. 4).
  - [V] Publication dates come from Libraries.io (p. 5).
- Sample size (N) and unit:
  - [V] 469 malicious packages identified; 59 proof-of-concept packages excluded; at least one malicious version obtained for 174 (p. 9).
  - [V] Download success by registry (pp. 9–10): npm 109/374 (29.14%), PyPI 28/44 (63.64%), RubyGems 37/41 (90.24%), Maven Central 0/10.
  - [V] Composition: npm 62.6%, PyPI 16.1%, RubyGems 21.3% (p. 10).
- Sampling / selection method: [V] Every malicious package found in the sources whose code could be obtained (pp. 4, 9). This is a convenience sample of *disclosed* and *retrievable* attacks.
- Data availability: [V] On GitHub, "access will be granted on justified request only due to ethical reasons" (p. 10).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Manual code analysis to confirm maliciousness and classify trigger, conditions, injection, objective, targeted OS and obfuscation. Clusters were found through code reuse and dependency relations (pp. 4–5, 11–16). The number of coders and their agreement are not reported.
- Code availability: not applicable / not reported.

## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] Category shares per registry and overall (Figs. 6–11).
  - [V] Days between publication and disclosure.
  - [V] Levenshtein distance from a typosquat to its target.
  - [V] Cluster size and timing (pp. 10–16).
- Statistical testing: descriptive statistics only (mean, min, max, standard deviation, median) (pp. 11–12, 15). No tests.

## 7. Key findings
1. [V] **Exposure time.** On average a malicious package was available for 209 days before public reporting (median 67, max 1,216). PyPI had the highest average (p. 11).
2. [V] **Install-time execution dominates.** 56% of packages trigger at install time, 43% at runtime and 1% in tests (p. 11).
   - By registry (Fig. 6): npm 64% install / 34% runtime / 2% test; PyPI 96% install; RubyGems 100% runtime, because Ruby has no install hooks (p. 11).
   - [I] The remaining 4% for PyPI appears to be runtime, based on the bar shading and arithmetic consistency with the overall 43%.
3. [V] **Conditional execution.** 41% of packages check a condition (application state, dependency tree or OS) before running. This is an evasion technique against sandboxes (p. 12). PyPI and RubyGems packages mostly run unconditionally (p. 12).
4. [V] **Typosquatting dominates injection.** 61% of packages mimic existing names. The mean Levenshtein distance to the target is 2.3 (median 1, max 11, e.g. `pythonkafka` → `kafka-python`). Common techniques: adding or removing hyphens, dropping letters, swapping commonly mistyped letters (p. 12).
   - From Fig. 8: PyPI is 75% typosquatting and 25% trojan horse; overall trojan horse is 11% (p. 13).
   - [V] Trojan horses are "a new package which consist of nothing but the malicious package", with "No meaningful typo-squatting targets" (p. 13).
5. [V] **Objectives.** Most packages aim at data exfiltration (e.g. `~/.ssh/*`, `~/.npmrc`, environment variables). 34% are droppers, 5% backdoors, 3% denial-of-service and 3% financial gain (p. 13).
   - 53% are OS-agnostic (p. 14) and 49% use obfuscation, mostly Base64/hex (pp. 14–15).
6. [V] **Clusters.** 21 clusters cover 157 of the 174 packages (90%). The largest (crossenv) has 36 packages published in two waves. One cluster spans npm and RubyGems (pp. 15–16).
7. [A] **Countermeasures.** These include multi-factor authentication for maintainers, "version pinning and disablement of install scripts for open source users", and build isolation. They should be "enforced by default" (p. 16).

## 8. Limitations stated by the authors
- [A] The dataset is biased toward npm. No malicious packages could be obtained for Java (Maven) or PHP (p. 18).
- [A] About 34% are droppers whose second-stage payload may be unavailable (p. 18).
- [A] Most packages were downloaded from mirrors or archives (an injection vector listed in the tree). The authors argue they are still valid, since maliciousness was confirmed by hand (p. 18).
- [A] The attack trees are not complete: they omit vectors not yet observed or described (p. 4).
- [A] Selection of infection targets cannot yet be validated from the data (p. 7).

## 9. Limitations we identified
- [I] **Small PyPI sample.** Only 28 PyPI packages; the PyPI percentages rest on very few cases.
- [I] **Sample biased toward detected attacks.** Only disclosed and retrievable attacks are included. Undetected or quickly deleted packages are missing, so the shares describe *detected* attacks.
- [I] **Unknown reliability of the hand coding.** Single-pass manual categorisation with no reported inter-rater agreement.
- [I] **Pre-LLM.** The attack tree has no node for discovery through automated recommendation, which is exactly the channel slopsquatting uses. Registry defences may have changed since 2019; the paper does not cover this.
- [I] **Bar-chart readings.** Per-registry shares are read from bar charts (Figs. 6–11), whose text extraction is garbled. We checked Figs. 6 and 8 against the PDF images.

## 10. Threats to validity
- Internal: the classification is subjective, done by hand, with no agreement measure.
- External: mostly npm; 2015–2019 only; registries and attacker tactics have evolved since.
- Construct: "typosquatting" is decided by judgement of name similarity. "Trojan horse" is a residual category.
- Statistical conclusion: descriptive only; the PyPI subset is small.
- Reproducibility: the dataset is available on request (p. 10). The attack trees are fully shown (pp. 7, 9).

## 11. Future research directions
- Stated by authors [A]:
  - collect existing safeguards and run a gap analysis against the attack vectors (p. 18);
  - repository-wide scanning that exploits code reuse across campaigns (p. 18);
  - supervised learning on the labelled dataset (p. 18);
  - use the dataset as a benchmark, and continue curating it (p. 18).
- Suggested by us [I]:
  - extend the injection tree with an "AI-recommended name" discovery node (slopsquatting) under Create New Package;
  - measure whether slopsquatted packages follow the same install-time and conditional-execution patterns.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ2 (attack model: how a registered name becomes malicious execution on the victim), RQ3 (baseline countermeasures: disabling install scripts, pinning), RQ5 (background for designing a safe study).
- How it informs our work [I]:
  - **Placing slopsquatting in the tree.** It is a *Create New Package* attack, close to "trojan horse": a fresh name with no lookalike target. It differs from typosquatting in how victims find the package. Here the LLM supplies the "discovery and referencing" step that the authors identify as the obstacle for new packages (p. 7).
  - **Installing is enough to be compromised.** Install-time execution is the main trigger on PyPI (96%) (p. 11), and import-time `__init__.py` execution is also possible (p. 9). An agent or user that runs `pip install` / `npm install` on a hallucinated name can be compromised immediately. A defence must act **before** installation.
  - **Implication for a measurement study.** Use read-only registry metadata (no installs). Any dynamic analysis must run in a sandbox, since 41% of malicious packages run only under certain conditions (p. 12) and may evade sandboxes.
  - **Implication for a lightweight defence.** Combine a pre-install existence/metadata check with the authors' user-side countermeasures: version pinning and disabled install scripts (p. 16). The edit-distance profile of typosquats (mean 2.3, median 1; p. 12) helps design a lookalike check for hallucinated names.
  - Evidence strength: **moderate** as background (real-world data, but descriptive, pre-2020, small PyPI subset).
