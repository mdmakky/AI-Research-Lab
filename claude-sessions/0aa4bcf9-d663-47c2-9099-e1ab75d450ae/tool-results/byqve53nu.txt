# HFuzzer: Testing Large Language Models for Package Hallucinations via Phrase-based Fuzzing

- Authors: Zhao, Yukai; Wu, Menghan; Hu, Xing; Xia, Xin
- Year / venue: 2025, 2025 40th IEEE/ACM International Conference on Automated Software Engineering (ASE) (published)
- DOI: 10.1109/ase63991.2025.00225 · URL: https://doi.org/10.1109/ase63991.2025.00225
- Source text: `fulltext.txt` (page refs = PDF page index). The text is the arXiv copy (2509.23835v2, 4 Oct 2025) of the ASE paper.

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
[A] Build a testing (not detection) framework that automatically generates enough diverse, code-relevant coding tasks to trigger package hallucinations in LLMs, so models can be tested for this supply-chain risk (p. 1, p. 2). Prior datasets (Spracklen et al., Krishna et al.) are described as limited in size and scenario coverage (p. 1).

## 2. Research questions / hypotheses
- [A] RQ1: How effective is HFuzzer in testing LLMs for package hallucinations, compared with GPTFuzzer-A? (p. 5)
- [A] RQ2: Are the tasks generated by HFuzzer more diverse? (p. 5)
- [A] RQ3: Does each module of HFuzzer contribute to its performance? (p. 5)
- [A] Plus a GPT-4o case study (p. 8) and discussion experiments on data contamination (post-cutoff packages) and parameter/temperature settings (p. 9, p. 10).

## 3. Methodology
- Research design: [V] Tool proposal evaluated by a controlled comparison against one adapted baseline, an ablation study, repeated runs on a subset, and a qualitative case study with manual classification (p. 5, p. 6, p. 8).
- Approach / model / intervention: [V] Two phases. (a) Phrase Extraction: a tester LLM turns each package's name and description into an ⟨Object, Predicate, Complement⟩ phrase composition; phrases fill three power-weighted pools (p. 3). (b) Fuzzing loop per round: weighted-random seed selection (one phrase per pool), task generation by the tester LLM, then two-stage "Hallucination Triggering" on the target LLM — Code Generation, then Package Recommendation, where the target is given its own code and asked for the installation commands (p. 3, p. 4). Recommended packages are classified as stdPackage / existPackage (registered in the repository before the model's knowledge cutoff) / otherLanguagePackage (not in the repository but in Libraries.io) / nonExistentPackage (p. 4). A Hallucination Score HS = α·N_non/N_package + β·N_other/N_package with α = 1, β = 0.5 drives power adjustment (k1 = 0.15, k2 = 0.8, k3 = 0.6) and seed-pool expansion from tasks that triggered hallucination (k = 0.6) (p. 4, p. 5). Standard-library names that the model asks to install are excluded from hallucinations (p. 4). Recommended packages are verified by querying package indices such as PyPI (p. 3).
- Baselines or comparison conditions: [V] GPTFuzzer-A, adapted from the GPTFuzzer jailbreak fuzzer: mutation operators changed to produce coding tasks, initial seeds replaced by coding tasks derived from package descriptions, random seed selection (p. 5). [A] No prior tool tests LLMs for package hallucination, so no direct baseline exists (p. 5). Ablation variants: w/o Expansion, w/o Power, w/o Phrase, w/o All (p. 8).

## 4. Dataset and sample
- Data source(s): [V] Descriptions of the top 100 Python packages on Libraries.io ranked by "SourceRank" (p. 6); top 1,000 packages for the GPT-4o case study (p. 8); the first 100 packages released after the models' training cutoffs for the contamination analysis (p. 9). Package information obtained via package-repository APIs and the Libraries.io API (p. 5).
- Sample size (N) and unit: [V] 9 models used both as tester and target = 81 combinations; each run limited to 1,000 rounds (p. 6). Repeated runs: three runs for three targets (GPT-4o mini, Meta-Llama-3.1, Mistral-v0.3) with all testers (p. 7). Case study: 10,000 rounds, GPT-4o mini as tester, GPT-4o as target (p. 8). Total numbers of responses/packages per model (PHR denominators) are not reported.
- Sampling / selection method: [V] Popularity-ranked packages (SourceRank); models chosen to cover different training data and architectures, open and closed (Table I (p. 5)).
- Data availability (public? link?): [A] Replication package at https://github.com/YukZhao/HFuzzer (p. 2, p. 12). Each round's task, model output and evaluation result is recorded so that found hallucinations can be reproduced (p. 5).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Models (Table I (p. 5)): Meta-Llama-3-8B-Instruct, Qwen2.5-Coder-7B-Instruct, DeepSeek-Coder-Instruct 6.7B, Meta-Llama-3.1-8B-Instruct, Mistral-7B-Instruct-v0.3, Meta-Llama-3.3-70B-Instruct, DeepSeek-V3 (671B), GPT-4o mini, GPT-4o. Tester temperature 0, target temperature 0.7, max tokens 3,000 (p. 6). Models accessed through the OpenAI library API; open models served with vLLM v0.6.1 on a server with four NVIDIA A800 GPUs, a 32-core Xeon and 2 TB RAM (p. 5, p. 6). Python only (p. 5). Prompts use a system prompt plus a one-shot formatting example and tags; invalid-format outputs are discarded; the tester may answer "None" and the target may refuse unrelated tasks (p. 3, p. 4, p. 10). [A] All score/power parameters were set from initial/preliminary experiments (p. 4, p. 5). Full prompt texts are not printed in the paper (fragments only in Fig. 2 (p. 3)). The registry query date is not stated; the PyPI entry in the reference list, "last accessed Mar. 2025" (p. 12), is the best available proxy.
- Code availability: [A] Yes, GitHub replication package (p. 2, p. 12).

## 6. Evaluation metrics
- [V] Package Hallucination Rate (PHR) — proportion of model responses containing hallucinated packages over all responses (definition from Krishna et al.) — measures how well generated tasks trigger hallucination (p. 5).
- [V] Number of unique hallucinated packages (P_uniq) — analogue of "unique bugs" in fuzzing — measures testing effectiveness (p. 5, p. 6); R_inc = HFuzzer / GPTFuzzer-A ratio (p. 6).
- [V] Diversity Index — number of DBSCAN clusters plus noise points over text-embedding-3-small embeddings of generated tasks, ε ∈ {0.1, 0.2, 0.3}, minS ∈ {1, 3, 5} (p. 5, p. 7).
- Statistical testing: [V] Welch's t-test over three runs and coefficient of variation (CV) (p. 7; Table III (p. 6)). No effect sizes, confidence intervals or multiple-comparison correction reported.

## 7. Key findings
1. [V] HFuzzer triggers package hallucinations in all nine target models and finds on average 2.60x more unique hallucinated packages than GPTFuzzer-A; largest per-target gain on DeepSeek-V3 (4.89x), largest per-tester gain with DeepSeek-Coder as tester (5.13x) (Table II (p. 6); p. 7).
2. [V] Average PHR per target (averaged over testers): GPT-4o, GPT-4o mini, DeepSeek-V3 and Qwen2.5-Coder 0.26–0.66%; DeepSeek-Coder 5.68%, Meta-Llama-3 7.10%, Meta-Llama-3.1 9.82%; Mistral-v0.3 16.47% (highest) (p. 6). Fig. 3/4 values are garbled in the text layer; numbers taken from the results text.
3. [V] Over three repeated runs HFuzzer averages a 3.02x improvement, significant (Welch's t-test, p < 0.05) for most combinations and with lower CV; non-significant cases arise where the target hallucinates little (p. 7; Table III (p. 6)).
4. [V] 190 non-existent and 176 other-language hallucinated packages are recommended by multiple models; `pkg_resources` is recommended by all models and 17 packages by more than half (p. 7). [A] Shared names likely originate from training data (p. 7). Models tend to build names from technical terms in the task, e.g. `jsonwebtoken`, `apache-arrow` (p. 7).
5. [A] Qwen2.5-Coder's low PHR is partly due to frequent refusals (over-refusal), inconsistent with other studies (p. 7).
6. [A] Meta-Llama-3.1 produced more unique hallucinated packages than Meta-Llama-3 (many starting with `google-cloud`, triggered by `from google.protobuf import ...`), so a newer, stronger model did not hallucinate less (p. 7).
7. [V] HFuzzer tasks have a 2.36x higher average Diversity Index than GPTFuzzer-A; 2.46x across repeated runs (p < 0.05) (p. 7, p. 8).
8. [V] Ablation: removing Phrase / Power / Expansion lowers unique hallucinated packages by 2.06x / 1.39x / 1.27x and Diversity Index by 4.40x / 1.25x / 1.26x (Table IV (p. 8)).
9. [V] GPT-4o case study (1,000 packages, 10,000 rounds): 46 unique hallucinated packages, 11 other-language; 34 are "package errors" (correct import, wrong install name, e.g. `import pywt` then `pip install pywt`) and 12 "code errors" (wrong import, e.g. `flask_livereload`); five placeholder names (e.g. `some_ml_library`); 12 hallucinated packages sit next to comments marking them as placeholders or assumptions, yet the model still returns install commands for them (p. 8, p. 9).
10. [A] Hypothesis: LLMs are more prone to package hallucination when assisting with environment configuration; regex-based extraction from imports used by earlier studies overlooks these (p. 9).
11. [V] Post-cutoff packages as seeds yield more hallucinated packages and slightly higher diversity than pre-cutoff packages (p. 9).
12. [V] Parameter variants find fewer hallucinated packages than the default; tester-model temperature (two model combinations) shows no clear trend in the number found (p. 10).
13. [A] A GPT-4o hallucinated name, "data-analysis-toolkit", appears in several open-source GitHub repositories (manual check, no counts) (p. 10).

## 8. Limitations stated by the authors
- [A] Evaluated on Python only, although the framework is language-agnostic (p. 10).
- [A] Regular-expression extraction from model output may misalign; mitigated with one-shot prompting and validation checks (p. 10).
- [A] Sampling-strategy (temperature) effects studied on only two model combinations for cost reasons (p. 10).
- [A] Whether the Llama-3.1 vs Llama-3 observation and the environment-configuration hypothesis hold for more models needs broader experiments (p. 7, p. 9).
- [A] Over-refusal of Qwen2.5-Coder limits both fuzzers on that model (p. 7).

## 9. Limitations we identified
- [I] Ground truth counts a name as hallucinated if it was registered after the model's knowledge cutoff (p. 4). How release dates were obtained is not reported, and the registry query date is not stated (best proxy: PyPI reference "last accessed Mar. 2025", p. 12); for slopsquatting, names that now exist (possibly squatted) are the interesting ones, but they are not reported separately.
- [I] Counting `pkg_resources` (recommended by all models, p. 7) as a hallucination is debatable: it is an import name shipped with setuptools, not an invented name. This shows the import-name vs distribution-name ambiguity that can inflate counts; the Libraries.io/PyPI lookup does not resolve it.
- [I] PHR for strong models is very low (0.26–0.66%, p. 6) because the fuzzer optimises for unique names, not for a representative prompt distribution; these PHRs are not comparable with base rates from prompt-sampling studies.
- [I] The baseline is the authors' own adaptation (p. 5); its fairness cannot be checked externally.
- [I] Case-study classification: preliminary examination by one author, then two authors classify; no agreement statistic reported (p. 8, p. 9).
- [I] Stability analysis uses three runs and three targets (p. 7); low statistical power.
- [I] Real-world exploitation evidence ("data-analysis-toolkit" in GitHub repos, p. 10) is anecdotal; registration status or maliciousness on PyPI is not reported.

## 10. Threats to validity
- Internal: tester and target are sometimes the same model (diagonal of the 9x9 grid, Table II (p. 6)); parameters tuned on preliminary runs without a held-out split (p. 4, p. 5) — [I].
- External: Python/PyPI only (p. 10); 2024-era models (p. 5); fuzzer-generated tasks are not natural developer prompts — [I].
- Construct: "hallucinated" includes other-language names and post-cutoff registrations (p. 4); unique-name counts reward breadth, not frequency or exploitability — [I].
- Statistical conclusion: Welch's t-test on n = 3 runs, no correction, no CIs (p. 7) — [I].
- Reproducibility: code released (p. 2); models, temperatures, token limit, vLLM version and hardware reported (p. 5, p. 6); prompt texts not in the paper; registry query date only approximable from the PyPI reference access date, Mar. 2025 (p. 12) — [I].

## 11. Future research directions
- Stated by authors [A]: test more LLMs and more languages; open-source results to promote mitigation research; extend to code hallucination generally (p. 11); study over-refusal (p. 7); study how code comments influence package recommendations (p. 9); use HFuzzer output as fine-tuning data for mitigation (p. 10).
- Suggested by us [I]: run the two-stage (code, then install command) protocol with agentic tools that actually execute installs; add npm and other ecosystems; separately report names registered after cutoff and check them for squatting; use HFuzzer-found names as a test set for a client-side install-time checker; test comment-aware filtering (block install commands for names that the generated code itself marks as placeholders or assumptions), motivated by the 12 such cases (p. 9).

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1, RQ2, RQ4, RQ5 (RQ3 only via discussion).
- How it informs our work [I]:
  - RQ1: Per-model PHR under one protocol shows 7–8B open models (Mistral-7B, Llama-3/3.1-8B, DeepSeek-Coder-6.7B) hallucinate far more than GPT-4o/DeepSeek-V3 (p. 6).
  - RQ2: Cross-model repeated names (190 + 176 shared; `pkg_resources` by all) support name predictability (p. 7); the install-command stage is a separate hallucination source (p. 8, p. 9).
  - RQ4: Contributes the four-way classification (std / exists-before-cutoff / other-language via Libraries.io / non-existent) and the argument that import-regex extraction misses install-command hallucinations (p. 4, p. 9).
  - Laptop-scale implication: the authors report the fuzzer "remains effective even with smaller-scale LLMs" as testers (p. 7), so a local 7B tester + target pair (e.g. a quantized model) running ~1,000 rounds is plausible on a laptop, although the original used four A800 GPUs (p. 6). The released code is a reusable task generator, and HFuzzer-found names could serve as a test set for a lightweight defence.
  - Replication checklist: Python; Libraries.io top-100 by SourceRank as seeds; tester temperature 0, target temperature 0.7, max tokens 3,000; 1,000 rounds; two-stage prompt (code, then "how to install these packages"); classification std / exists-before-cutoff (PyPI) / other-language (Libraries.io) / non-existent; metrics PHR per response, unique hallucinated names, Diversity Index (text-embedding-3-small + DBSCAN) (p. 4, p. 5, p. 6, p. 7).

# Secure or Suspect? Investigating Package Hallucinations of Shell Command in Original and Quantized LLMs

- Authors: Haque, Md Nazmul; Lin, Elizabeth; Arkoh, Lawrence; Tadesse, Biruk; Xu, Bowen
- Year / venue: 2025, arXiv (preprint, not peer-reviewed)
- DOI: 10.48550/arxiv.2512.08213 · URL: https://arxiv.org/abs/2512.08213
- Source text: `fulltext.txt` (page refs = PDF page index); arXiv 2512.08213v1, 9 Dec 2025.

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
[A] First systematic empirical study of how weight quantization affects package hallucination and known-vulnerability risk when LLMs generate shell commands that install Go packages (p. 1, p. 3). Central question: "How does quantization impact package hallucination while generating shell commands?" (p. 2).

## 2. Research questions / hypotheses
- [A] RQ1: To what extent do original and quantized LLMs generate hallucinated packages in shell commands? (p. 3)
- [A] RQ2: What proportion of the valid packages generated by LLMs have known security vulnerabilities? (p. 3)
- [A] RQ3: What are the properties of the hallucinated packages of original and quantized models? (p. 3)
- [A] No formal hypotheses; the authors speculate that quantized models could even hallucinate less (p. 2).

## 3. Methodology
- Research design: [V] Factorial measurement: 5 Qwen model sizes x 3 precisions (full, 8-bit, 4-bit) x 3 prompt datasets (p. 1, p. 4, p. 5). [I] One generation pass per prompt is implied, since no repetitions are reported.
- Approach / model / intervention: [V] Intervention = post-training weight quantization with bitsandbytes (8-bit and 4-bit), models loaded with Hugging Face transformers (p. 5). Hallucination oracle: the module URL in a `go get`/`go install` command is requested over the network; unreachable means hallucinated (p. 4). Vulnerability oracle: OSV API (p. 4). Threat model: the user blindly runs the LLM's command; the attacker watches for frequently hallucinated names and publishes a malicious Go package under that string (p. 2).
- Baselines or comparison conditions: [V] The full-precision version of each model (labelled "Org(32-bit)" in figures) (p. 5, p. 6). No other mitigation or model-family baseline.

## 4. Dataset and sample
- Data source(s): [V] (a) Stack Overflow questions tagged "golang" via Stack Exchange Data Explorer: 10,157 questions -> GPT-4o rewrites to generic tasks -> GPT-4o "as judge" generates shell commands -> keep those with install commands = 5,435; (b) MBPP text-to-code prompts adapted to language-generic prompts = 974; (c) awesome-go package names/metadata turned into paraphrased prompts by GPT-4o = 1,746 (p. 4).
- Sample size (N) and unit: [V] 8,155 prompts in total (our sum of the three sets) (p. 4); unit of analysis is the generated package string. Per-condition counts of generated Go package strings range from 0 (3B full/8-bit on MBPP) to 21,439 (1.5B full on SO), Table 1 (p. 6).
- Sampling / selection method: [V] Convenience/LLM-filtered: SO questions kept only if GPT-4o produced install commands (p. 4).
- Data availability (public? link?): [A] Datasets, results and replication package at https://anonymous.4open.science/r/phrGo-39EB (p. 2).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Qwen "LLMs4Code" family from the EvalPlus leaderboard, sizes 0.5B, 1.5B, 3B, 7B, 14B (p. 4); exact checkpoint names (e.g. Coder vs base, instruct vs base, version) not reported. bitsandbytes 8/4-bit; one NVIDIA A100 80GB (p. 5). Prompt wording, decoding parameters (temperature, max tokens), how package strings are extracted from responses, and the date of the reachability checks are not reported.
- Code availability: [A] Anonymous replication link (p. 2).

## 6. Evaluation metrics
- [V] PHR = |H| / |G|, hallucinated package strings over all generated package strings; answers RQ1 (p. 4, p. 5).
- [V] VPR = |V| / |E|, OSV-flagged packages over existing (reachable) packages; answers RQ2 (p. 5).
- Statistical testing: [V] none reported in the results — no confidence intervals, repeated runs or significance tests (p. 5, p. 6).

## 7. Key findings
1. [A] 8-bit quantization causes "a moderate and consistent increase" in PHR, e.g. 0.5B on SO 40.60% -> 43.04% (p. 5). [V] Table 1 does not show a consistent increase: PHR falls at 8-bit for 0.5B MBPP (53.58% -> 49.21%), 1.5B SO (46.17% -> 44.16%), 14B SO (30.52% -> 29.24%) and 3B Paraphrase (85.71% -> 78.89%), and rises sharply for 7B MBPP (48.39% -> 69.59%) (p. 6).
2. [V] 4-bit quantization raises PHR drastically for small models: 0.5B reaches 96.11% (SO), 98.78% (MBPP), 96.66% (Paraphrase); 3B 4-bit 92.09% / 97.60% / 87.74% (p. 6).
3. [V] Exception: 7B on SO falls from 34.00% to 10.21% at 4-bit, while its number of generated package strings drops from 4,185 to 1,655 (p. 5, p. 6).
4. [V] The discussion's summary numbers (8-bit "<2.5% PHR change"; 4-bit "0.5B: +55.5%, 3B: +58.8%", 7B "-23.8%", 14B "+6.6%") (p. 7) match percentage-point differences on the Stack Overflow dataset only (e.g. 96.11 - 40.60 = 55.51; 92.09 - 33.33 = 58.76; 34.00 - 10.21 = 23.79; 37.10 - 30.52 = 6.58), Table 1 (p. 6). The 3B full-precision SO baseline rests on only 3 generated package strings (p. 6).
5. [V] VPR among existing packages: 7B SO rises 12.89% -> 19.58% at 4-bit (p. 5); small models fluctuate (0.5B SO 12.49% -> 10.98%; 1.5B SO 13.70% -> 15.83%) (p. 5); some 4-bit VPRs fall (0.5B Paraphrase 15.57% -> 8.22%; 14B Paraphrase 12.30% -> 9.57%) (p. 6). [A] "Quantization correlates with an increased vulnerability presence rate" (p. 5) is therefore only partly supported.
6. [A] Generated package strings are mostly URLs, mainly github.com and golang.org; more than half of generated github.com URLs are hallucinated (p. 6). [V] In the only distribution table shown (1.5B 4-bit, SO; Table 2), 2,418 of 4,751 (51%) hallucinated strings are URLs (github.com 1,868; golang.org 42; other URLs 508) and 2,333 (49%) are file paths (1,372) or free-form strings (961) (p. 8). Existing strings in the same cell: github.com 1,794, golang.org 721 (p. 8).
7. [V] A placeholder string, `your.package.name`, resolved as an existing URL (p. 7).
8. [A] GitHub is "the largest attack vector" because anyone can create any username and repository; attackers may also compromise frequently recommended existing repositories or poison training data (p. 7).
9. [A] 8-bit quantization is recommended for resource-constrained deployment; 4-bit "requires extreme caution and robust validation layers" (p. 7).

## 8. Limitations stated by the authors
- [A] Package existence was checked by HTTP reachability "for simplicity" due to time constraints; an unreachable URL could still be downloadable as a Go package; future work should run `go get` instead (p. 7).
- [A] Prompts were not varied; future work should test different prompts (p. 7).

## 9. Limitations we identified
- [I] Tiny denominators are reported as rates without warning: 3B full/8-bit produced 3 and 1 package strings on SO and 0 on MBPP; 14B on MBPP produced 13/8/7, Table 1 (p. 6). The near-zero output of 3B at full precision is unexplained (possibly a generation or parsing failure).
- [I] The headline claim of a "consistent" increase (p. 5) contradicts the paper's own table (finding 1); the summary percentages in the discussion use only the SO dataset (finding 4). Conclusions overreach the data.
- [I] Oracle validity: HTTP reachability is neither necessary nor sufficient for a valid Go module (the authors acknowledge one direction, p. 7). File paths (1,372 on SO for 1.5B 4-bit) (p. 8) and "other" strings are counted as hallucinated packages, inflating PHR with strings that are not installable or squattable names.
- [I] About half of the "hallucinated packages" in the only distribution table (2,333 of 4,751 for 1.5B 4-bit on SO, Table 2 (p. 8)) are file paths or free-form strings, not installable module paths, so PHR overstates the number of squattable names.
- [I] Exploitability differs from PyPI/npm: Go modules are URL paths, so "squatting" means registering a free GitHub user/repo; whether hallucinated owners/repos were registrable was not checked. No persistence (repeat) analysis, so RQ2-style predictability is not measured.
- [I] Single model family (Qwen) and a single quantization library (bitsandbytes); laptop runtimes usually use other formats (e.g. GGUF k-quants), so effects may not transfer.
- [I] Prompts were created and filtered by GPT-4o (p. 4), which selects tasks GPT-4o itself answers with install commands — a selection bias toward install-heavy tasks.
- [I] The PDF still carries ACM template residue ("Do Not Use This Code", "Woodstock, NY", 2018 dates) (p. 1, p. 2), suggesting an early draft; preprint, not peer-reviewed.

## 10. Threats to validity
- Internal: no repeats or decoding settings reported; possible extraction failures (3B); GPT-4o-based prompt filtering — [I].
- External: Go only; one model family; one quantization method; open models up to 14B (p. 4, p. 5) — [I].
- Construct: "hallucinated" = unreachable URL string, including file paths and free-form strings (p. 4, p. 8) — [I].
- Statistical conclusion: no tests, no CIs, rates on n<=13 in several cells (p. 6) — [I].
- Reproducibility: anonymous link (may not persist), no prompts or decoding parameters in the paper — [I].

## 11. Future research directions
- Stated by authors [A]: verify packages by executing `go get`; vary prompts (p. 7); RQ3 insights could feed automated detection of suspicious recommendations and prompt strategies (p. 3).
- Suggested by us [I]: repeat the quantization comparison on PyPI/npm with GGUF quantization levels (as used by local runtimes), proper registry lookups, several samples per prompt and CIs; measure name repetition across runs and precisions.

# When LLMs Invent Rust Crates: An Empirical Study of Hallucination Patterns and Mitigation

- Authors: Zheng, Jieming; Guan, Hao; Liu, Yepang
- Year / venue: 2026, arXiv (preprint, not peer-reviewed)
- DOI: 10.48550/arxiv.2606.08444 · URL: https://arxiv.org/abs/2606.08444
- Source text: `fulltext.txt` (page refs = PDF page index); arXiv 2606.08444v2, 14 Aug 2026.

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
[A] First large-scale empirical study of crate (package) hallucination in LLM-generated Rust code: measure prevalence, characterise recurring patterns, compare with Python/JavaScript findings, and test prompt-level mitigation (p. 1, p. 2).

## 2. Research questions / hypotheses
- [A] RQ1 (Prevalence): How likely are LLMs to hallucinate when recommending Rust crates, and how do model family, size and decoding parameters affect this? (p. 2)
- [A] RQ2 (Patterns): What recurring patterns do Rust crate hallucinations show? (p. 2)
- [A] RQ3 (Mitigation): Can common prompt-engineering strategies mitigate crate hallucination? (p. 2)
- [A] Hypotheses stated: larger models have lower CHR (p. 5); higher temperature raises CHR (p. 5). Both were not supported (p. 5, p. 6).

## 3. Methodology
- Research design: [V] Cross-sectional measurement over a fixed task set, plus within-model size and temperature comparisons and a mitigation ablation with the same pipeline (p. 4, p. 5, p. 8).
- Approach / model / intervention: [V] Detection at the source-code reference level, not at Cargo.toml (p. 1). Ground-truth list = complete scraped crates.io name list + the five std crates (alloc, core, proc_macro, std, test) + rustc compiler crates + aliases mined from the collected crates' repositories (p. 4). Crate names are extracted with three patterns: `use` declarations, direct path prefixes (`crate_name::module::item`), and `extern crate` (p. 4). Any extracted name not on the list is a hallucinated crate (p. 5). RQ2 uses module vs non-module split, pairwise Jaccard across models, Levenshtein distance to nearest real crate, and a cross-domain check (p. 6, p. 7, p. 8). RQ3: (a) self-refinement — prompt tells the model to qualify std functionality via std::/core::, self-check each external crate name, and regenerate (up to 3 times) without a crate it judges hallucinated; (b) RAG — a database of the top 10,000 crates.io crates by recent downloads (name + description), top-5 retrieved per task, plus a fixed "STD list" seeded from the top-10 misused module names of RQ2 (p. 8).
- Baselines or comparison conditions: [V] No-mitigation condition for RQ3, Table 4 (p. 9); across-model and across-size comparisons for RQ1 (p. 5).

## 4. Dataset and sample
- Data source(s): [V] Stack Overflow: Rust-tagged questions ranked by votes, 1,001 unique questions, not further filtered (p. 3). GitHub: top-100 starred Rust repositories, 10 sampled after random sampling and manual inspection; functions with RustDoc comments turned into tasks (summary + signature): 1,011, minus 218 removed by four rules = 793 (p. 3). LLM-generated: top 250 crates from lib.rs plus 750 crates.io crates by recent downloads, each description rewritten by Qwen2.5:32B into one "Generate Rust code that ..." task = 1,000 (p. 4). Total 2,794 tasks (p. 2).
- Sample size (N) and unit: [V] RQ1 main run: 16,764 code snippets and 48,494 extracted crate references (p. 5); 16,764 = 6 models x 2,794 tasks, which implies one sample per task per model ([I], arithmetic). Models: 14 variants from six families (p. 2): GPT-5, Gemini 2.5 Pro, Claude 4 Opus; Qwen2.5-Coder 0.5/1.5/3/7/14/32B; DeepSeek-Coder-V2 16B/236B; OpenCoder 1.5B/8B, Table 1 (p. 4).
- Sampling / selection method: [V] Models chosen from SWE-bench Verified (commercial) and EvalPlus (open) leaderboards (p. 4); popularity-ranked sources for tasks (p. 3, p. 4).
- Data availability (public? link?): [A] Tasks, prompt templates, crate extraction, evaluation and mitigation scripts and result files at https://doi.org/10.6084/m9.figshare.32233767 (p. 10).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] All models run with default configurations; largest open-source size used for RQ1 (p. 4). Size variants are those "available on Ollama" (p. 5). Temperature study on four models (Gemini 2.5 Pro, GPT-5, DeepSeek-Coder-V2, Qwen2.5-Coder) at 0, 0.5, 1, 1.5, 2, and up to 5 for the open models, Fig. 3 (p. 7); (p. 6). Mitigation run on the three open-source models only (p. 8). Hardware: AMD EPYC 9654, 8 x NVIDIA RTX 6000 Ada, 768 GB RAM (p. 5). Not reported: quantization level of the Ollama models, crates.io snapshot date, exact prompt wording in the paper (templates are in the figshare package, p. 10), retriever type for RAG.
- [I] Normalisation between source identifiers and crates.io names is not reported: crates whose registry names contain hyphens (e.g. `tokio-util`) are referenced in Rust source with underscores (`tokio_util`). Without normalisation, every hyphenated crate used in code would count as a hallucination; with it, the hyphen-omission finding (32.96%, p. 7) needs re-checking, because names differing only in hyphen/underscore should then have matched.
- Code availability: [A] Yes, figshare package (p. 10).

## 6. Evaluation metrics
- [V] Crate Hallucination Rate (CHR) = hallucinated crates / total extracted crates — per-reference rate (p. 5).
- [V] Levenshtein distance to the nearest valid crate; prefix/suffix similarity; hyphen analysis (p. 7).
- [V] Pairwise Jaccard similarity of hallucination sets across models; share of names shared by >1 model (p. 7).
- Statistical testing: [V] ANOVA-style F-test for size within Qwen2.5-Coder, F(1,4) = 0.0138, p = 0.912, R^2 = 0.0034 (p. 5); ANOVA for temperature with model as blocking factor, temperature F(4,12) = 0.9159, p = 0.4859, model F(3,12) = 5.0425, p = 0.0173 (p. 6). No CIs; no tests for the mitigation differences.

## 7. Key findings
1. [V] 10,779 of 48,494 extracted crate references are hallucinated: overall CHR 22.23% (p. 5).
2. [V] Gemini 2.5 Pro has the lowest CHR (16.18%) and Claude 4 Opus the highest (26.90%), a 1.66x ratio; commercial mean 23.34% vs open-source 20.79% (25.23% for commercial without Gemini) (p. 5).
3. [V] Model size does not predict CHR: Table 2 values span 18.46%–21.92% across DeepSeek-Coder-V2, OpenCoder and Qwen2.5-Coder sizes; not significant within Qwen2.5-Coder (p. 5).
4. [V] Temperature has no significant effect; CHRs stay within 16.2%–26.1% (p. 6). [A] This contrasts with Python/JavaScript findings of prior work where higher temperature raised hallucination (p. 6).
5. [V] 45.47% of hallucinations are standard-library or internal modules treated as external crates; the top-10 list is led by `thread` (1,086) and `duration` (828) (p. 6). The text also says "over half" (p. 6), an internal inconsistency.
6. [V] Module hallucinations overlap strongly across models (average Jaccard ~0.44; 55.05% shared), non-module ones much less (average Jaccard ~0.16; 25.42% shared) (p. 7).
7. [V] Among 5,647 unique non-module hallucinated names (13,332 occurrences): weighted mean edit distance 3.42 to the nearest real crate; 40.78% within 1–2 edits; 86.48% within 5; 2.36% at 10+ (p. 7). 32.96% drop hyphens that the real crate has (e.g. httpresponse -> http-response) (p. 7). [A] This contrasts with prior Python/JS work where nearly half of hallucinations were 6+ edits away (p. 7, p. 8). [I] The figures are not directly comparable: Zheng et al.'s 40.78% and 86.48% are occurrence-weighted (p. 7), whereas Spracklen et al.'s 13.4% (1–2 edits) and 48.6% (6+ edits) are computed over 76,489 hallucinated Python package names [@spracklen2024we, p. 11].
8. [V] 38.9% of frequent (>10 occurrences) non-module hallucinations reuse names from other ecosystems or platforms, e.g. `queryparser` (Python), `winuser` (Windows API) (p. 8).
9. [V] Mitigation (Table 4): self-refinement lowers CHR by 2.22–3.26 points for all three open models; RAG by 1.92 and 0.96 points for DeepSeek-Coder-V2 and OpenCoder but raises Qwen2.5-Coder by 0.34 (p. 9). [A] About 10–15% relative reduction; prompt-level methods are insufficient (p. 9).
10. [A] Post-processing filters are "fragile in adversarial settings" because attackers can pre-register hallucinated names, so the authors focus on pre-generation methods (p. 8).
11. [A] A Rust-aware guardrail should (i) distinguish external crates from std/in-crate/rustc modules, (ii) do registry-aware near-miss checks (edit distance, naming conventions, aliases), and (iii) cross-check source references against Cargo.toml (p. 9).

## 8. Limitations stated by the authors
- [A] Models evolve quickly; results may not generalise to newer models or tool-integrated assistants (p. 9, p. 10).
- [A] Fixed model set and Rust-specific prompt dataset may not represent all Rust contexts (p. 10).
- [A] The synthetic task subset was generated by Qwen2.5-32B and may bias toward that family (no outlier observed) (p. 10).
- [A] False positives possible for aliases, outdated names, mis-parsed non-crate identifiers and private crates; alias coverage incomplete so the true rate is "likely slightly lower" (p. 4, p. 10).
- [A] Downstream consequences (build failures, repair effort, exploitability) are not measured; CHR is a source-level indicator, not evidence that a hallucinated crate would be installed (p. 10). In Rust a source reference alone does not trigger a download (p. 1).
- [A] Mitigation not evaluated on commercial models (p. 8, p. 9).

## 9. Limitations we identified
- [I] Extraction construct validity: pattern (2) "direct path prefixes" would also capture type paths such as `Duration::from_secs` or `VecDeque::new` when the type was imported with `use`. The top-10 "hallucinated crates" are mostly lowercased std type/module names (thread, duration, tokenstream, ordering, vecdeque) (p. 6). The paper does not report checking that the corresponding `use` line was missing, so part of the 22% may be parser artefacts rather than model errors.
- [I] The same top-10 list contains `trefcell`, `tu32`, `ttcplistener`, `thashset`, `tpoll` (p. 6) — std type names with a stray "t" prefix, which look like an extraction/normalisation bug; the paper does not discuss them although they are among the most frequent "hallucinations".
- [I] Counting inconsistency: RQ1 reports 10,779 hallucinated references (p. 5) but RQ2 analyses 13,332 non-module occurrences (p. 7) after excluding module confusions; how runs were pooled is not explained.
- [I] The abstract claims models show "surprisingly consistent hallucination rates" (p. 1), but the model factor is significant (p = 0.0173, p. 6) and the authors also call model choice "a very important factor" (p. 5).
- [I] The abstract frames mitigation "without sacrificing code quality" (p. 1), but RQ3 evaluates "solely by the change in CHR" (p. 8); code quality is not measured.
- [I] Open models were pulled from Ollama (p. 5), whose default model tags are usually quantized builds; the quantization level is not reported. This applies to all open models, including the RQ1 runs, which use the largest available sizes (p. 4) from the same Ollama variants (p. 5), not only to the size sweep; open-vs-commercial and size comparisons may therefore be confounded with precision (this rests on our understanding of Ollama defaults, to be checked).
- [I] The authors' argument against post-generation checking (p. 8) only shows that a pure existence check fails after squatting; registry metadata (age, downloads, near-miss to popular crate) could still flag squatted names. Their own guardrail proposal (p. 9) is a post-generation check.
- [I] No exploitability data: whether hallucinated crate names were free, later registered, or malicious on crates.io is not checked; snapshot date not reported.

## 10. Threats to validity
- Internal: parser artefacts (above); one sample per task; synthetic tasks from a Qwen model (p. 10) — [I].
- External: Rust only; models as of mid-2026; default configs (p. 4) — [I].
- Construct: CHR counts module mis-references and possibly type paths as "hallucinated crates"; source-level, not dependency-level (p. 1, p. 10) — [I].
- Statistical conclusion: size test on n = 6 points (p. 5); temperature ANOVA with 20 cells (p. 6); no CIs; mitigation deltas untested (p. 9) — [I].
- Reproducibility: good — data, prompts and scripts on figshare (p. 10); snapshot date and quantization not reported — [I].

## 11. Future research directions
- Stated by authors [A]: evaluate mitigation on commercial models (p. 8, p. 9); more sophisticated techniques beyond prompting (p. 2); a Rust-aware guardrail with namespace-, registry/near-miss- and Cargo-aware validation (p. 9); tighter toolchain-level verification (p. 9).
- Suggested by us [I]: measure at the Cargo.toml / `cargo add` level (what actually gets installed); implement and evaluate the proposed near-miss guardrail; check registrability and later registration of hallucinated crate names.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1, RQ2, RQ3, RQ4, RQ5.
- How it informs our work [I]:
  - RQ1: Adds the Rust/crates.io ecosystem; reports ~20% CHR insensitive to size and temperature (p. 5, p. 6), unlike Python/JS reports.
  - RQ2: Most non-module hallucinated names are near-misses of real crates (86.48% within 5 edits, p. 7) — this raises typosquatting-style collision risk and suggests attackers could predict names; cross-model sharing is moderate (p. 7).

The proposed but unevaluated near-miss guardrail (edit distance + naming convention + registry lookup + Cargo.toml cross-check, p. 9) is a natural lightweight client-side defence to implement and test.

# Refusing the Impossible: A Taxonomy and Benchmark for Code Hallucination in Large Language Models

- Authors: Dasu, Vishnu Asutosh; Kundu, Ashish; Tan, Gang
- Year / venue: 2026, arXiv (preprint, not peer-reviewed)
- DOI: 10.48550/arxiv.2609.03267 · URL: https://arxiv.org/abs/2609.03267
- Source text: `fulltext.txt` (page refs = PDF page index); arXiv 2609.03267v2, 31 Oct 2026.

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
[A] Test whether code LLMs recognise programming requests that cannot be satisfied (nonexistent packages, impossible algorithms) and refuse; define code hallucination as ungrounded generation, distinct from code errors; provide a taxonomy and benchmark (p. 1, p. 2).

## 2. Research questions / hypotheses
- [A] RQ1: How often do models comply with unsatisfiable requests rather than refuse, and is refusal a sign of over-caution? (p. 5)
- [A] RQ2: Does model scale reduce hallucination, equally for every kind? (p. 5)
- [A] RQ3: How do models hallucinate, and what failure modes do reasoning models add? (p. 5)
- [A] RQ4: What kinds of prompts exacerbate hallucination? (p. 5)

## 3. Methodology
- Research design: [V] Benchmark study with matched controls: unsatisfiable requests where any solution attempt is ungrounded by construction, plus minimal-edit solvable controls to detect over-refusal (p. 3, p. 4).
- Approach / model / intervention: [V] Taxonomy (Fig. 2): outcome CORRECT / HALLUCINATION / REFUSAL (ERROR on solvable tasks); D1 groundedness — absolute (A1–A4) vs relative (R1 nonexistent API or package, R2 header/flag, R3 protocol, R4 language feature, R5 fabricated version); D2 manifestation — syntactic / semantic / factual; D3 behaviour — B1 confident fabrication, B2 hedged compliance, B3 task substitution, B4 degenerate output (p. 3). Judge: Claude Opus 4.6 inside the Claude Code harness with a fixed rubric (six decision rules), shown prompt, response and ground-truth memo; responses that exhausted the token budget without an answer are labelled B4 by a deterministic rule (33 of 6,137) (p. 4). Hedged code counts as hallucination; fixing a typo and using the real package counts as correct (p. 4). An install/dependency line for a nonexistent name counts as using it (p. 4).
- Baselines or comparison conditions: [V] 91 solvable controls (p. 4); comparison across 17 models and size groups (p. 5, p. 6).

## 4. Dataset and sample
- Data source(s): [V] 270 hand-written adversarial templates, each with a memo naming the planted entity and why the request is unsatisfiable (e.g. crate `serde_ultra`) (p. 3, p. 4). Three families: theoretical impossibility (8 subcategories), plausible nonexistent entity (12, incl. nonexistent PyPI, npm, crates.io, Go, Java and C-header entities), typos/transplants/open tasks (4) (p. 4). Six languages: Python, C++, Rust, Go, Java, JavaScript (p. 4). Ten framing templates assigned by a hash of the seed, one frame per prompt (p. 4); Table VIII (p. 9).
- Sample size (N) and unit: [V] 17 models x 361 prompts = 6,137 judged responses (p. 1, p. 2); 1,547 control responses (p. 2). Package subsets are small: 12 nonexistent-npm and 10 nonexistent-crate prompts (p. 9); subcategories have 6–20 prompts per model (p. 10).
- Sampling / selection method: [V] Prompts hand-crafted; models chosen as open-weight, version-exact, with known parameter counts, covering small/older models still in production (p. 5).
- Data availability (public? link?): [A] Code artefacts and prompt suite open-sourced at a GitHub repository (rendered in the text layer as "https://github.com/vdasu/code hallucination") (p. 2).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Temperature 0, one completion per prompt, 16,384-token output budget; exception MiniMax-M2.7 at temperature 1.0, top-p 0.95 because it never left its reasoning phase under greedy decoding (p. 5). Models (Table III): DeepSeek-Coder 6.7B, CodeLlama 7B, CodeGemma 7B, Qwen2.5-Coder 7B, DeepCoder 14B, gpt-oss 20B, Devstral-Small-2 24B, Granite 4.1 30B, Qwen3-Coder 30B, Gemma 4 31B, Qwen2.5-Coder 32B, DeepSeek-R1-Distill 32B, Qwen3-Coder-Next 80B, gpt-oss 120B, MiniMax-M2.7 230B, MiniMax-M3 428B, DeepSeek-V3.2 671B (p. 5). The twelve models up to 32B ran with 4-bit weight quantization, the five larger at full precision (p. 10). Re-run of 28 exhausted MiniMax-M3 prompts with a 131,072-token budget (p. 8). Inference engine, quantization method and hardware are not reported. How and when nonexistence of planted names was checked against registries is not described beyond the memo and the statement that relative prompts depend on registry state at generation time (p. 10).
- Code availability: [A] Yes (p. 2).

## 6. Evaluation metrics
- [V] Hallucination rate (HR), refusal rate (RR), rate of correct non-refusals on adversarial prompts; over-refusal rate and HR on controls (p. 5).
- [V] 95% bootstrap intervals resampling prompts; Spearman correlation between log total parameters and HR (p. 5); Pearson correlation of adversarial vs control fabrication (p. 5); variance explained by prompt vs model identity (p. 8, p. 9).
- Judge validity: [V] on a 138-item gold set, outcome agreement 94%, Cohen's kappa 0.91; hallucination recall 0.93, precision 0.89; behaviour-label agreement 67%; manifestation 29/30, kappa 0.95; human labels replace judge labels for these 138 (p. 5).
- [V] No correction for multiple comparisons is reported in the metrics or results (p. 5, p. 6).

## 7. Key findings
1. [V] Across 17 models: 54% of responses to unsatisfiable prompts are ungrounded code, 31% refusals, 15% grounded non-refusals; only 1 of 1,547 control responses is a wrongful refusal; 5% of control responses hallucinate (p. 5).
2. [V] HR ranges from 0.23 (MiniMax-M3 428B) to 0.90 (CodeLlama 7B); small 4-bit models: CodeGemma 7B 0.84, Qwen2.5-Coder 7B 0.69, DeepSeek-Coder 6.7B 0.66, Table IV (p. 6).
3. [V] Scale helps on theoretical impossibilities (HR 0.84 / 0.49 / 0.32 for <=7B / 14–32B / >=80B; Spearman -0.71, p = 0.002) but much less on plausible nonexistent entities (0.88 / 0.71 / 0.61; -0.47, p = 0.059) and least on nonexistent npm packages + Rust crates (1.00 / 0.90 / 0.85; -0.43, p = 0.083); the size groups contain 4 small, 8 mid and 5 large models, Table V (p. 6). [I] The npm+crates subset has 22 prompts per model, so 1.00, 0.90 and 0.85 rest on 88, 176 and 110 responses respectively.
4. [V] DeepSeek-V3.2 (671B) and gpt-oss 120B fabricate on 100% of nonexistent npm/crate prompts; gpt-oss 20B and 120B have the same overall HR (0.46) (p. 6).
5. [V] By ecosystem (pooled): nonexistent npm packages fabricated on 94% of prompts, Rust crates 87%, C headers 76%, Go modules 63%, PyPI modules 63%, Java APIs 33%; largest models 87%, 84%, 68%, 50%, 50%, 15% (p. 8).
6. [V] A misspelled real package name is fabricated on only 14% of prompts, versus 94% for a correctly spelled fictional one (p. 8, p. 9); responses that fix the typo and use the real package count as correct (p. 4).
7. [V] Behaviour: 66% confident fabrication (B1), 19% hedged (B2), 13% task substitution (B3), 1.5% degenerate (B4) (p. 6, p. 7). Manifestation: 47% semantic (would fail at install/import/compile), 43% factual (runs; only claims are false); 18% of plausible-entity hallucinations are factual (p. 7); Table VII (p. 8). [A] "no registry check will notice" them (p. 7).
8. [V] Framing matters: "internal docs" frame HR 0.64 vs "learner" 0.43; the docs vs question-frames gap is 21 points (95% CI 8–34) (p. 8); Table VIII (p. 9).
9. [V] Prompt identity explains 34% of outcome variance vs 15% for model identity; 33 of 270 prompts fool at least 16 of 17 models and 11 fool all 17 (p. 8, p. 9).
10. [V] Collision example: MiniMax-M2.7 recommended `pip install pywfm`, a name that exists on PyPI as an unrelated 2015 package (p. 9).
11. [V] MiniMax-M3 exhausted the 16,384-token budget on 28 of 361 prompts; with 131,072 tokens 23 finished and 5 still produced no answer (p. 8).
12. [A] Recommended mitigations: ground generation in package registries at generation time; gate output on the model's own stated caveats; ask the feasibility question before the implementation question (p. 9, p. 11).

## 8. Limitations stated by the authors
- [A] Template-rendered prompts may differ from what developers type; absolute rates are benchmark-specific (p. 10).
- [A] Single sample per prompt; MiniMax-M2.7 run at temperature 1.0 (p. 10).
- [A] Relative prompts depend on the state of package registries at generation time; MiniMax-M2.7 has since been withdrawn (p. 10).
- [A] The LLM judge is the main internal threat; gold set labelled by one author; the judge sees the ground-truth memo, which could bias it (p. 10).
- [A] Models <=32B ran 4-bit, larger ones full precision: size is confounded with precision (p. 10).
- [A] Framing analysis is observational (one frame per prompt); subcategory counts are 6–20 per model, so the scale trend on plausible entities is treated as weak (p. 10).
- [A] Open-weight models only; may not generalise to closed frontier models (p. 10).

## 9. Limitations we identified
- [I] Construct differs from the slopsquatting threat model: the user supplies the fictional package name, so the benchmark measures *acceptance* of a planted name, not spontaneous invention of names. Rates such as 94% for npm (p. 8) are not comparable with spontaneous package hallucination rates from prompt-sampling studies.
- [I] Package-specific estimates rest on 22 prompts (12 npm + 10 crates, p. 9); per-model package rates have wide uncertainty (not reported per subcategory).
- [I] Publishing the planted fictional names creates a risk that someone registers them, silently changing ground truth for future replications (registry dependence acknowledged, p. 10).
- [I] Quantization method/engine and hardware not reported, which limits exact replication of the 4-bit small-model results.
- [I] Behaviour-level labels have only 67% judge-human agreement (p. 5); B1/B2 shares are indicative.
- [I] Very recent preprint (v2, 31 Oct 2026), not peer-reviewed.

- Internal: judge sees the memo; gold set from one author (p. 10); deterministic B4 rule affects 33 responses (p. 4) — [I].
- External: open-weight models only; template prompts (p. 10) — [I].
- Construct: "hallucination" includes hedged compliance (p. 4); planted-name acceptance vs spontaneous invention — [I].
- Statistical conclusion: bootstrap CIs given for model-level HR, Table IV (p. 6), and framing (p. 9); per-subcategory n = 6–20 (p. 10); size/precision confound (p. 10) — [I].
- Reproducibility: prompts, decoding and model identifiers reported; code released (p. 2, p. 5); engine/quantization method missing — [I].

## 11. Future research directions
- Stated by authors [A]: registry grounding at generation time and caveat-gating tools; asking feasibility first; treating an exhausted reasoning budget as an impossibility signal (p. 9, p. 10, p. 11).
- Suggested by us [I]: evaluate a registry-check tool as an intervention on the npm/crate/PyPI subsets; add closed models and agentic tools; combine planted-name prompts with spontaneous-invention prompts in one design.

- How it informs our work [I]:

  - Replication checklist: temperature 0, single completion, 16,384 output tokens; 10 framing templates; judge rubric with memo; HR/RR/over-refusal with bootstrap CIs over prompts; Spearman vs log parameters (p. 4, p. 5).
