# Methodology comparison: package hallucination and slopsquatting

- Project: `2026-11-12-package-hallucination-and-slopsquatting` · Date: 2026-11-12
- Inputs: 17 analyses with `status: complete`, `evidence-matrix.md` (172 rows, Contradictions, Agreements), `reports/critical-review-measurement.md`, `reports/critical-review-defences-tools.md`.
- Not used as evidence: the project also holds three agent-side attack papers (attacks that steer coding agents through rule files or agent "skills"). Their analyses are unfinished drafts, so this report does not rely on them. They have to be read before any claim about agent-side gaps is made.

**How to read this report.** Every substantive statement carries a label. **[V]** means we checked it against the paper's own tables or results. **[A]** means the authors say it and we cannot check it independently. **[I]** means it is our own interpretation, and we say what it rests on. Citations give the paper key and the PDF page number, in square brackets. Preprints are papers that have not been peer-reviewed, and they are flagged as such. Because the field is young, 10 of the 17 analysed papers are preprints or grey literature, and most findings come from a single study. (Project metadata counts 11, because it still lists spracklen2024we as an arXiv preprint.)

**Key terms.**
- *Package registry*: the public index that `pip` or `npm` downloads from (PyPI for Python, npm for JavaScript, crates.io for Rust).
- *Package hallucination*: a model recommends or imports a package name that does not exist in the registry.
- *Slopsquatting*: an attacker registers such a hallucinated name and fills it with malware.
- *Hallucination rate*: the share of something that is hallucinated. Papers divide by different things, and this matters a great deal (section 3.1):
  - *mention level*: per package name mentioned;
  - *generation* or *response level*: per answer that contains at least one hallucinated name;
  - *prompt level*: per prompt.
- *Import name* vs *distribution name*: in Python the name you `import` (e.g. `cv2`) can differ from the name you install (`opencv-python`). This difference turns out to be the largest source of measurement error in the field (section 5).
- *White-box*: a method that needs the model's weights or internal scores (*logits*, the scores a model gives every possible next token).
- *Black-box*: a method that only needs the model's text output, so it also works with closed APIs such as ChatGPT.

## 2. Approach families

### 2.1 Measurement studies: prompt a model, extract names, check the registry
Papers: [@spracklen2024we, p. 5]; [@churilov2026range, p. 4]; [@krishna2025importing, p. 3]; [@haque2025secure, p. 4]; [@zheng2026when, p. 4]; [@okwor2026hallucination, p. 3]. zhang2025llm is a related taxonomy study of repository-level code errors [@zhang2025llm, p. 3].

**How they work.** A prompt set (from Stack Overflow, LLM-written prompts built from package descriptions, or hand-made grids) goes to several models. Package names are extracted from the answers and checked against a registry list.

**Strengths.**
- [V] Large samples are possible: up to 2.23M mentions [@spracklen2024we, p. 7].
- [V] A replication on the same prompt corpus exists [@churilov2026range, p. 4].
- [V] The newest study re-checks names live, applies a time-of-generation rule, and preregisters its analysis [@churilov2026range, p. 5; @churilov2026range, p. 6].

**Weaknesses.** [I] Every design choice changes the rate, and the papers make different choices:
- *Extraction method* (section 3.1). One option is to ask the model for package lists [@spracklen2024we, p. 6]; the other is to parse imports [@krishna2025importing, p. 12].
- *Registry snapshot.* Static lists versus live checks. In churilov2026range the live re-check lowered every model's rate by about a fifth [@churilov2026range, p. 10].
- *Unit of the rate* (mention, generation, prompt, or package string).

None of the measurement studies observes an agent that installs packages on its own [@churilov2026range, p. 14].

### 2.2 Testing, fuzzing and benchmarks: search for prompts that trigger hallucination
Papers: [@zhao2025hfuzzer, p. 3]; [@dasu2026refusing, p. 3]; [@twist2026library, p. 3].

*Fuzzing* means generating many varied test inputs automatically to find failures.
- HFuzzer has one "tester" LLM write coding tasks from package descriptions, and keeps the tasks that make the "target" model hallucinate [@zhao2025hfuzzer, p. 4].
- dasu2026refusing hand-writes requests that cannot be satisfied (for example, naming a crate that does not exist) and pairs each with a solvable control [@dasu2026refusing, p. 3].
- twist2026library changes one slot of a fixed prompt. The slot holds a year, a typo, or a fake library name [@twist2026library, p. 3].

**Strengths.**
- [V] Good at *finding* hallucinations: 2.60× more unique names than the adapted baseline [@zhao2025hfuzzer, p. 6].
- Controlled single-factor designs [@twist2026library, p. 5].
- Matched controls that detect over-refusal [@dasu2026refusing, p. 6].

**Weaknesses.** [I] These designs do not estimate how often hallucination happens in normal use:
- Fuzzer rates are optimised for finding unique names, not for representing ordinary prompts.
- When the user supplies the fake name, the benchmark measures *compliance* (going along with a wrong name), not *spontaneous invention*. Both critical reviews make this point. It bears on slopsquatting because an attacker can only predict names that the model invents itself.

### 2.3 Model-side defences: change the model's weights
Papers:
- fine-tuning [@spracklen2024we, p. 13];
- localized model editing with LoRA, a small add-on weight matrix trained instead of the full model [@liu2026mitigating, p. 3];
- adaptive unlearning, training the model to make specific outputs less likely [@spracklen2026llm, p. 5].

**Strengths.**
- [V] Large reductions on the prompts tested: for example 21.23% → 2.56% [@spracklen2026llm, p. 10].
- [A] No extra cost at inference time [@spracklen2026llm, p. 12].

**Weaknesses.**
- [V] All three need white-box access and data-centre GPUs: 8 × A100 [@liu2026mitigating, p. 6]; MI210/MI300 for 12–24 h [@spracklen2026llm, p. 19].
- [V] Utility can suffer: HumanEval fell from 51.4% to 25.3% after fine-tuning [@spracklen2024we, p. 13].
- [I] Evaluation sets are small and close to the training distribution: paraphrases of 20 seed prompts [@spracklen2026llm, p. 8], or a "high-risk" pool from the same distribution [@liu2026mitigating, p. 5].

### 2.4 Decoding-time defences: change how the next token is chosen
Papers:
- PackMonitor [@liu2026packmonitor, p. 8];
- greedy, contrastive, DoLa, ALCD and Nudging decoding, plus RAG and Self-Refine as black-box comparators [@djire2026evaluating, p. 4];
- grammar-constrained decoding [@mirandapena2026empirical, p. 4].

PackMonitor compiles the PyPI name list into a *DFA* (a state machine that accepts exactly the listed names). After `pip install`, it sets the logit of any token that cannot continue a listed name to −∞ [@liu2026packmonitor, p. 9].

**Strengths.**
- [V] 0% PHR on five 7–8B models with ×1.07–×1.28 latency [@liu2026packmonitor, p. 13; @liu2026packmonitor, p. 14].
- [V] Greedy decoding (temperature 0) needs no special access and gave the best average trade-off between mitigation and utility in djire2026evaluating [@djire2026evaluating, p. 8].

**Weaknesses.**
- [V] Logit-level methods need a locally decoded model [@liu2026packmonitor, p. 9].
- [V] DoLa *raised* the average PHR to 38.0% [@djire2026evaluating, p. 6].
- [I] PackMonitor's 0% holds by construction against its own list, and any registered name passes the mask, including squatted ones [@liu2026packmonitor, p. 6].

### 2.5 Tool-side guards: check names outside the model
Papers:
- a PyPI 404 check plus a metadata classifier inside an agent loop [@raj2026names, p. 5];
- a PyPI-existence tool offered to the model [@twist2026library, p. 8];
- user-side measures from the pre-LLM era, such as version pinning and disabling install scripts [@ohm2020backstabbers, p. 16].

**Strengths.** [I] These work with closed API models and cost one registry lookup per name.

**Weaknesses.**
- [V] Evidence is thin: 300 hand-written prompts on one API model pair, with no manually checked ground truth for the run [@raj2026names, p. 7].
- [V] Models may not use the tool: GPT-5-mini called it on only 7.89% of responses [@twist2026library, p. 21].
- [A] Plain existence checks fail once an attacker has registered the name [@spracklen2024we, p. 12].

### 2.6 Static analysis
Paper: [@mirandapena2026empirical, p. 4]. Type checkers (Mypy, Pyright), a grammar built from library docstrings, and an LLM judge flag "imaginary" library features.

**Strengths.** [V] This is the only pipeline in the set that ran on a laptop-class machine (M2, 24 GB) [@mirandapena2026empirical, p. 17], at 1–4 s per sample [@mirandapena2026empirical, p. 19].

**Weaknesses.**
- [V] Existence is judged against the installed environment, not a registry [@mirandapena2026empirical, p. 4].
- [V] Detection for the right reason is only 4.0–37.6% [@mirandapena2026empirical, p. 8].
- [I] Package-level errors are a small, unseparated part of what it detects.

### 2.7 Background
ohm2020backstabbers supplies the pre-LLM attack model:
- [V] 56% of 174 real malicious packages ran at install time [@ohm2020backstabbers, p. 8];
- [V] 61% used typosquatting [@ohm2020backstabbers, p. 12];
- [A] a new package must be "discovered and referenced" by its victims [@ohm2020backstabbers, p. 7].

[I] Package hallucination is a new discovery channel of exactly this kind.

[V] Two papers quantify how much these choices matter:
- Counting stdlib modules as hallucinations raised Python PHR by 7.6 to 9.4 percentage points [@djire2026evaluating, p. 5].
- In churilov2026range's re-check, the largest false-positive class was import names of real packages: 144–207 mentions per model [@churilov2026range, p. 10].

[I] Both effects are of the same order as many of the differences between models that papers report.

### 3.2 The closest pair: Spracklen (2024) vs Churilov (2026)
**What they share.**
- [V] The same released prompt corpus [@churilov2026range, p. 4].
- [V] Nominally the same unit (per mention) [@churilov2026range, p. 6].

**What differs.**
- [V] Extraction: Churilov parses imports [@churilov2026range, p. 5], which Spracklen rejects [@spracklen2024we, p. 6].
- [V] Registry check: live vs static (section 3.1).
- [I] Aggregation: Churilov's per-model figures are pooled over Python and JavaScript. Spracklen's 5.2% and 21.7% are unweighted means of per-test rates, and the "best model 3.59%" is Python-only [@spracklen2024we, p. 20].

**The like-for-like check.** [V] Churilov's own Python-only rate for its best model, Haiku 4.5, is 4.38% [@churilov2026range, p. 7]. That is above Spracklen's Python-only 3.59%.

**Conclusion.** [I] The claim that 2026 frontier models are "level with" the best 2024 model is not established. The two studies support only a direction-level statement: commercial and frontier models hallucinate in the low single digits per mention, far below the 2023–24 open models (21.7% per-test mean [@spracklen2024we, p. 7]).

### 3.3 Same tool, same unit, different numbers: HFuzzer vs PackMonitor's vanilla runs
**What they share.** [V] PackMonitor evaluates on HFuzzer [@liu2026packmonitor, p. 12]. Its per-response rate (RHR) is the same unit as HFuzzer's PHR [@zhao2025hfuzzer, p. 5]. Two models appear in both papers.

**The numbers.**

| Model | HFuzzer (average over 9 testers) | PackMonitor vanilla (one round, DeepSeek-V3 tester) |
|---|---|---|
| Llama-3-8B | 7.10% [@zhao2025hfuzzer, p. 6] | 6.40% RHR [@liu2026packmonitor, p. 13] |
| DeepSeek-Coder-6.7B | 5.68% [@zhao2025hfuzzer, p. 6] | 11.60% RHR [@liu2026packmonitor, p. 13] |

[I] Even with the same tool and unit, the rates differ by up to about 2×. Each configuration gets a different, adaptively generated prompt stream, and each was run once. Fuzzer-based rates should therefore be read as properties of one run, not as base rates. PackMonitor also reuses HFuzzer as its benchmark, so its vanilla runs are not an independent replication of HFuzzer's numbers.

### 3.4 Defences: compare inside a paper, not across papers
[I] Within a paper, defences share the pipeline, so their rows can be ranked. Across papers, the baseline rate, unit, prompt selection and hardware all differ. The table below is meant to be read row by row. Absolute values are given where the paper reports them.

| Defence (access needed) | Paper | Reported effect [V] | Cost / hardware [V] |
|---|---|---|---|

- **Supported:** an ordering by *access needed*. The large reductions all come from white-box methods. The black-box methods give small or inconsistent reductions.
- **Not supported:** an ordering by *effectiveness* across papers. The reductions are measured on very different baselines: fuzzer streams, "high-risk" prompts selected for Sample-HR > 0.5 [@liu2026mitigating, p. 5], or 20 hallucination-heavy seeds [@spracklen2026llm, p. 8].
- **SFT numbers are not independent.** PackMonitor's SFT figures on Package4U equal Spracklen's (16.14% and 26.28% vanilla). Both critical reviews treat them as quoted, so this is one source, not a replication.

### 3.5 Other results that look comparable but are not
- **Compliance with user-supplied fake names.** [V] Three papers report high rates: 46.6–92.5% [@djire2026evaluating, p. 9]; up to 99.22% of tasks [@twist2026library, p. 6]; npm 94% [@dasu2026refusing, p. 8]. [I] The direction is consistent. The magnitudes are not comparable: they are per package, per task and judge-labelled per prompt, respectively, and the planted names differ.
- **Registration of hallucinated names.** [V] Both studies use the same metric, the share of names that become registered, with different time windows and sampling frames:
  - 25 of 2,282 within about six months [@churilov2026range, p. 12];
  - 0 of 1,641 after four days, and 22 of 149 public names [@okwor2026hallucination, p. 5].

  [I] The results are compatible: registration is rare, slow, and concentrated on publicised names.
- **Cross-model overlap and edit distance.** [V] The units differ:
  - share of unique names coming from one model: 81% [@spracklen2024we, p. 10];
  - mean pairwise Jaccard similarity (the overlap of two sets divided by their union): 0.219 [@churilov2026range, p. 8];
  - share of new names that are single-model: 450 of 455 [@okwor2026hallucination, p. 4];
  - unique-name edit distance: 13.4% within 1–2 edits [@spracklen2024we, p. 11];
  - occurrence-weighted edit distance: 86.48% within 5 edits [@zheng2026when, p. 7].

  Only the qualitative pattern is shared (section 4, item 6).
- **Utility checks.** [I] HumanEval pass@1 (the share of benchmark problems solved on the first try) appears in four defence papers, with different models, temperatures and quantization. Only the within-paper change is meaningful.

## 5. Methodological weaknesses across the field

These are recurring problems, ordered roughly by how much they threaten our RQs. Each one is [I], a synthesis of the analyses and the two critical reviews, with examples cited.

1. **No shared definition of "hallucinated package".**
   - Papers differ on all of these:
     - static vs live registry;
     - snapshot date (often not reported, e.g. [@liu2026packmonitor, p. 12]);
     - stdlib filtering (quantified only by [@djire2026evaluating, p. 5]);
     - name normalisation;
     - import → distribution mapping (section 3.1);
     - whether a name registered *after* the model's training cutoff counts as valid. Only [@liu2026mitigating, p. 5] and [@krishna2025importing, p. 3] treat such names as hallucinated, with [@zhao2025hfuzzer, p. 4] similar.
   - Every other paper scores attacker-registered squats as "valid". That undercounts exactly the names that matter for slopsquatting.
2. **Incompatible rate units.** Mention, generation, prompt, response, task, package string and source reference are all in use. Headline numbers are sometimes per-test means presented next to pooled rates [@spracklen2024we, p. 20]. Cross-paper rankings are therefore not meaningful (section 3).
3. **Little statistical testing and few repeated runs.**
   - Seven empirical papers report no tests (section 1).
   - Most defence papers report single runs ([@liu2026packmonitor, p. 12]; [@spracklen2026llm, p. 10]; [@liu2026mitigating, p. 6]).
   - Correlations are pseudo-replicated: the same model counted several times as if independent [@krishna2025importing, p. 6].
   - Small cells are reported as rates: some Haque conditions have fewer than 15 package strings [@haque2025secure, p. 6], and Raj's tiers have n = 5–30 [@raj2026names, p. 7].
   - Exception: churilov2026range has CIs, multiple-comparison correction and a power statement [@churilov2026range, p. 6; @churilov2026range, p. 12].
4. **Selected or near-in-distribution evaluation sets for defences.**
   - Defences are evaluated on high-risk prompts [@liu2026mitigating, p. 5], on paraphrases of the training seeds [@spracklen2026llm, p. 8], or possibly on fine-tuning data drawn from the evaluation pool (spracklen2024we analysis).
   - Relative reductions on such sets do not transfer to everyday rates.
   - Tuning and checkpoint selection were not matched across methods [@spracklen2026llm, p. 19].
5. **Hidden confounds: quantization and temperature.**
   - Open models were often quantized without the paper analysing it: GPTQ [@spracklen2024we, p. 6]; 4-bit up to 32B [@dasu2026refusing, p. 10]; Ollama builds [@zheng2026when, p. 5].
   - Temperatures differ between closed and open models [@mirandapena2026empirical, p. 5] and between providers [@twist2026library, p. 15].
   - Only haque2025secure varies precision on purpose, and it covers one model family and Go only [@haque2025secure, p. 4].
6. **Construct drift.**
   - Several high numbers measure *compliance with a planted name* ([@dasu2026refusing, p. 8]; [@twist2026library, p. 6]; [@djire2026evaluating, p. 9]), not invention.
   - Others measure environment errors [@mirandapena2026empirical, p. 4], or count file paths and free text as packages [@haque2025secure, p. 8].
   - Raj's "give-up" rate mixes non-code answers, true hallucinations and detector false positives [@raj2026names, p. 6].
7. **Weak utility and cost evidence for defences.**
   - HumanEval cannot reveal harm from a `pip install` mask, because it almost never triggers it [@liu2026packmonitor, p. 16].
   - Package Utility is an embedding proxy [@djire2026evaluating, p. 4].
   - No paper measures whether a forced substitute package is the *intended* one.
   - Latency is missing for djire2026evaluating's strategies [@djire2026evaluating, p. 4].
   - Overhead was measured only on A100-class hardware, with one laptop exception [@mirandapena2026empirical, p. 17].
8. **Existence ≠ safety.** [A] Registry-oracle defences can be "poisoned" by pre-registration [@spracklen2026llm, p. 12; @spracklen2024we, p. 12]. [V] A registry mask passes any listed name [@liu2026packmonitor, p. 6]. No analysed defence was tested against squatted names that come with realistic metadata [@raj2026names, p. 13].
9. **LLMs inside the measurement.**
   - Prompts were written by LLMs: Llama-2 [@spracklen2024we, p. 5], GPT-4o-mini [@djire2026evaluating, p. 3], GPT-4o [@haque2025secure, p. 4], Qwen [@zheng2026when, p. 4].
   - Imports were mapped by an LLM [@liu2026mitigating, p. 7].
   - Outcomes were judged by an LLM whose behaviour labels agree with humans only 67% of the time [@dasu2026refusing, p. 5].
10. **Internal inconsistencies and reliability.**
    - Mismatched counts or claims that contradict the paper's own tables appear in spracklen2024we, krishna2025importing, djire2026evaluating, spracklen2026llm, raj2026names, zheng2026when and haque2025secure (see their analyses, section 9).
    - Possible conflicts of interest:
      - NVIDIA authors evaluate NVIDIA models [@krishna2025importing, p. 1];
      - churilov2026range used Claude, one of the evaluated model families, to write its analysis code and draft the text, and used Google credits to run Gemini [@churilov2026range, p. 15].
11. **No agentic or install-time setting.**
    - Authors state that agentic or coding-agent workflows are untested in [@churilov2026range, p. 14], [@dasu2026refusing, p. 10] and [@liu2026packmonitor, p. 19].
    - okwor2026hallucination lists live agent traffic as future work [@okwor2026hallucination, p. 8].
    - Requirements files and Dockerfiles are outside PackMonitor's trigger [@liu2026packmonitor, p. 19].
12. **Reproducibility gaps.**
    - Code is not reported for krishna2025importing, liu2026mitigating and mirandapena2026empirical; okwor2026hallucination has only promised a deposit.
    - Hallucinated-name lists are withheld in [@spracklen2024we, p. 14] and [@okwor2026hallucination, p. 8], for understandable security reasons.
    - Closed-API results cannot be re-run exactly once endpoints change.

These weaknesses are inputs to the gap analysis (`gap-report.md`). They are not gaps in their own right until a novelty check has been run.

## 6. What this means for our research questions

Strength follows `docs/research-standards.md` §5. Strength is downgraded wherever the evidence comes from preprints or a single study.

### RQ1: How often, and what drives it?
**Current answer.**
- [V] Every study that measures it finds package hallucination in every model tested. This holds for 2023–24 open models ([@spracklen2024we, p. 7]), 2026 frontier models ([@churilov2026range, p. 6]), and Rust and Go as well as Python/JS ([@zheng2026when, p. 5]; [@haque2025secure, p. 6]).
- [V] Magnitude depends heavily on the unit and the model class:
  - 3.63–5.02% of mentions for five 2026 frontier models (preprint) [@churilov2026range, p. 6];
  - 16.1–47.9% of packages for small open 1–8B models [@djire2026evaluating, p. 5];
  - about 22% of Rust crate references (preprint; includes std-module confusions) [@zheng2026when, p. 5].
- [V] Drivers with consistent support:
  - the model itself;
  - prompt framing: year-based requests reach up to 84.74% of tasks for one model [@twist2026library, p. 5];
  - fake or misspelled names supplied by the user [@twist2026library, p. 6].
- [V]/[I] Drivers with contested or thin support:
  - language (contradiction #1);
  - model size (#3);
  - temperature (#4);
  - quantization: one Go study, inconsistent in its own table [@haque2025secure, p. 6].
- Agentic settings have not been measured.

**Evidence strength.**
- *Moderate* that hallucination is non-zero and model-dependent: consistent across many studies, but most are preprints.
- *Weak* for every individual driver except prompt framing and user-supplied fake names. Those two are *moderate*: twist2026library is a peer-reviewed controlled study, and fake-name compliance is corroborated by djire2026evaluating and dasu2026refusing.

### RQ2: What makes hallucinated names exploitable?
**Current answer.**
- [V] Names are predictable enough to matter:
  - 43% of hallucinated names recur in all 10 re-queries [@spracklen2024we, p. 9];
  - a shared core of 104 names is hallucinated by all five frontier models, 54 of them one edit from a registered package [@churilov2026range, p. 9].
- [V] Most names are still model-specific [@spracklen2024we, p. 10; @okwor2026hallucination, p. 4].
- [V] Real-world registration so far is rare: 25 of 2,282 names (1.1%) in about six months, one of them with malware [@churilov2026range, p. 12].
- [V] At least 23 suggested names had previously hosted malware [@churilov2026range, p. 12].
- [V] Publicly listed names are mostly claimed by defenders [@okwor2026hallucination, p. 5].
- [V] The payload mechanism is well established: install-time execution was used by 56% of real malicious packages [@ohm2020backstabbers, p. 8], and was reproduced offline for pip and npm [@okwor2026hallucination, p. 7].

**Evidence strength.**
- *Moderate* for persistence and the shared core: two large studies, but neither is a peer-reviewed replication of the other.
- *Weak* for real-world exploitation: two preprints, short windows, small counts.

### RQ3: Which defences work, at what cost, and where can they run?
**Current answer.**
- [V] White-box defences give the largest reductions:
  - DFA logit masking: 0% against its own list at ×1.07–×1.28 latency [@liu2026packmonitor, p. 13; @liu2026packmonitor, p. 14];
  - model editing [@liu2026mitigating, p. 7];
  - unlearning [@spracklen2026llm, p. 10].

  All of them need weights or logits and were run on data-centre GPUs.
- [V] Black-box options are cheap but inconsistent:
  - RAG helps in some ecosystems and hurts in others (contradiction #6);
  - self-refinement gives small gains [@zheng2026when, p. 9];
  - greedy decoding is the best simple trade-off for small models [@djire2026evaluating, p. 8];
  - self-check prompts and a PyPI tool reduce hallucination but do not remove it [@twist2026library, p. 18; @twist2026library, p. 21].
- [V]/[A] Tool-side registry checks are the only option for closed models. Their only evaluation is weak [@raj2026names, p. 7], and they cannot by themselves catch names that are already squatted [@spracklen2024we, p. 12].
- [I] No defence has been tested against squatted names, in agent workflows, or on CPU or laptop hardware, except static analysis [@mirandapena2026empirical, p. 17].

**Evidence strength.**
- *Weak to moderate.* Within-paper comparisons are sound, but single runs, selected prompt sets and the lack of independent replication limit them. Of the dedicated defence papers, only djire2026evaluating and liu2026packmonitor are peer-reviewed. twist2026library's prompting and tool studies are also peer-reviewed.

### RQ4: How is package hallucination measured, and what threatens validity?
**Current answer.**
- [V] Studies differ on five design choices:
  - prompt source: Stack Overflow, LLM-written, benchmarks, fuzzers or hand-written;
  - extraction: install commands, model-queried lists or import parsing;
  - existence rule: static vs live, with or without a release-date cutoff;
  - stdlib and import-name handling;
  - unit of the rate (section 3.1).
- [V] The two largest documented biases each shift rates by several points:
  - stdlib modules: +7.6 to +9.4 pp in Python [@djire2026evaluating, p. 5];
  - import names of real packages: the largest false-positive class, and the live re-check lowered rates by about a fifth [@churilov2026range, p. 10].
- [I] Further threats: pseudo-replicated statistics, quantization confounds, compliance being labelled as invention, and LLMs inside the measurement (section 5).

**Evidence strength.** *Moderate.* The biases are quantified in one peer-reviewed paper and one preregistered preprint, and the cross-paper pattern is consistent.

### RQ5: What has not been tested that a laptop-scale study could address?
**Current answer (candidates, not yet gaps).** [A]/[I] The analysed papers point to these untested areas:
- agentic tools that install dependencies on their own [@churilov2026range, p. 14; @dasu2026refusing, p. 10; @liu2026packmonitor, p. 19];
- local quantized models in PyPI/npm settings (churilov2026range excludes them [@churilov2026range, p. 14]; haque2025secure covers only Go);
- client-side guards that run on ordinary hardware and look beyond existence, for example vetted allowlists or registry metadata (not evaluated in [@liu2026packmonitor, p. 19] or [@raj2026names, p. 13]);
- a shared measurement protocol with live, dated, mapped and stdlib-aware checks (section 5).

The project also holds three agent-side attack papers that have not been analysed yet. They must be read before any agent-related gap is claimed.

**Evidence strength.** *Preliminary.* Under `docs/research-standards.md` §7, none of these counts as a gap until the novelty check in `gap-report.md` is complete.
