# Vulnerability Detection with Code Language Models: How Far are We?

- Authors: Ding, Yangruibo; Fu, Yanjun; Ibrahim, Omniyyah; Sitawarin, Chawin; Chen, Xinyun; Alomair, Basel; Wagner, David; Ray, Baishakhi; Chen, Yizheng
- Year / venue: 2025, 2025 IEEE/ACM 47th International Conference on Software Engineering (ICSE) (published)
- DOI: 10.1109/icse55347.2025.00038 · URL: https://doi.org/10.1109/icse55347.2025.00038
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
- [A] To evaluate whether code language models (code LMs) can detect security vulnerabilities in real code "in settings representative of that needed for real-world use", by scrutinising the datasets, benchmarks and metrics used to train and evaluate them (p. 1).
- [A] To provide a higher-quality benchmark (PrimeVul) and more realistic evaluation guidelines (temporal splits, VD-S, pair-wise evaluation) (p. 2).

## 2. Research questions / hypotheses
- [A] RQ1: How do open-source code LMs perform on PrimeVul? RQ2: Can more advanced training techniques improve them? RQ3: Can larger LLMs (GPT-3.5, GPT-4) improve detection? (p. 6–7).
- [A] Preceded by a dataset audit (Section II) of label accuracy, duplication and time-travel leakage in existing benchmarks (p. 3–5).

## 3. Methodology
- Research design: [V] (a) Manual label audit of 50 randomly sampled vulnerable functions per benchmark by three annotators with majority vote (p. 3); (b) exhaustive exact-copy leakage check between test and train after whitespace normalisation (p. 4); (c) construction of PrimeVul; (d) fine-tuning/prompting experiments on BigVul and PrimeVul (p. 7–9).
- Approach / model / intervention: [V] Seven code LMs: CodeT5 (60M), CodeBERT (125M), UnixCoder (125M), StarCoder2 (7B), CodeGen2.5 (7B) — all fine-tuned; GPT-3.5 (two-shot, chain-of-thought, fine-tuned) and GPT-4 (two-shot, chain-of-thought) (p. 7, Table IV). RQ2 adds class-weighted loss (weights 1–40) and contrastive learning (CLR, class-aware CA-CLR) to UnixCoder (p. 8–9).
- Baselines or comparison conditions: [V] Same models trained/tested on BigVul vs PrimeVul; cross-dataset (train BigVul → test PrimeVul) (p. 7, Table V); a random-guess baseline for pair-wise metrics (p. 9, Table VIII). [V] No static-analysis (SAST) tool is evaluated (p. 7).

## 4. Dataset and sample
- Data source(s): [V] PrimeVul merges security-related commits and changed functions from BigVul, CrossVul, CVEfixes and DiverseVul; Devign/CodeXGLUE excluded because many of its commits are unrelated to security (p. 5).
- Sample size (N) and unit: [V] Function. PrimeVul: 6,968 vulnerable and 228,800 benign functions across 755 projects and 6,827 commits, 140 CWEs (p. 6). Splits (Table III): train 5,574 vuln / 178,853 benign; dev 699 / 24,731; test 695 / 25,216; paired subset test 564 pairs (p. 6). Vulnerable:benign ratio roughly 1:32 (p. 8). Label audit: 50 vulnerable functions per benchmark (p. 3).
- Sampling / selection method: [V] Labels: PrimeVul-OneFunc (function is the only one changed by a security commit) and PrimeVul-NVDCheck (NVD description names the function, or names its file and it is the only function changed in that file) (p. 5–6). Pairs: vulnerable/patched functions sharing at least 80% of the string (p. 6). Temporal split: oldest 80% of commits train, middle 10% dev, newest 10% test; samples from one commit kept in one split (p. 6).
- Data availability (public? link?): [A] Artifact released at https://github.com/DLVulDet/PrimeVul (p. 3).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Learning rate 2×10⁻⁵ for all open-source fine-tuning; 10 epochs for models <7B, 4 epochs for 7B models; GPT-3.5 fine-tuned for 1 epoch (budget) on all train vulnerabilities plus 3× randomly sampled benign; A100 80 GB GPUs; OpenAI models via API with greedy decoding (p. 7, p. 9). [V] GPT models evaluated only on PrimeVul paired test functions because of cost (p. 9). Prompt templates in Supplementary Fig. 1–2 (p. 13–14). Random seeds / number of runs: not reported.
- Code availability: [A] https://github.com/DLVulDet/PrimeVul (p. 3).

## 6. Evaluation metrics
- Metric — what it measures — why chosen: [V] Accuracy and F1 reported for comparison but argued to be inappropriate (base-rate problem; F1 ignores false-alarm asymmetry) (p. 2, p. 5). [V] VD-S = false-negative rate at FPR ≤ r, with r = 0.5% (lower is better) — models practical alert-fatigue constraint (p. 6). [V] Pair-wise metrics on vulnerable/patched pairs: P-C (both correct), P-V (both predicted vulnerable), P-B (both predicted benign), P-R (both reversed) (p. 6).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): not reported (number of runs / seeds not reported; results are point estimates).

## 7. Key findings
1. Label accuracy of vulnerable functions, Ding's own manual audit (n=50 each; three annotators with majority vote except SVEN, p. 3): SVEN 94.0%, CodeXGLUE/Devign 24.0%, VulnPatchPairs 36.0%; PrimeVul-OneFunc 86.0%, PrimeVul-NVDCheck 92.0% — [V] (p. 4, Table I). BigVul 25.0%, CrossVul 47.8%, CVEFixes 51.7%, DiverseVul 60.0% are Chen et al.'s numbers reproduced by Ding (Table I footnote ∗) — [A] (p. 4).
2. Exact-copy test-to-train duplication: BigVul 12.7%, CVEFixes 18.9%, CodeXGLUE 0.6%, DiverseVul 3.3% (hash de-dup without whitespace normalisation), PrimeVul 0.0% — [V] (p. 4, Table II).
3. Benchmark inflation (Table V): StarCoder2 F1 68.26% train/test BigVul → 3.09% when the BigVul-trained model is tested on PrimeVul → 18.05% when trained and tested on PrimeVul. Same pattern for all five models: BigVul F1 62.88–68.26%; BigVul→PrimeVul F1 1.91–5.82%; PrimeVul→PrimeVul F1 18.05–21.43% — [V] (p. 7, Table V).
4. VD-S (FNR at FPR ≤ 0.5%): even on BigVul 61.73–81.77%; PrimeVul-trained models 88.78–91.51%, i.e. ~9 in 10 vulnerabilities missed at a tolerable false-alarm rate — [V] (p. 7, Table V; p. 8).
5. Pair-wise: PrimeVul-trained open-source models get both elements of a pair right in only 1.06–3.01% of pairs (P-C), and label both as benign in 84.22–88.30% (P-B) — [V] (p. 7, Table V).
6. Class weights (1–40) raise UnixCoder F1 from 21.43% to at most 26.28%, but VD-S stays 88.49–90.65%; contrastive learning CA-CLR gives F1 24.46%, VD-S 90.50% — [V] (p. 8–9, Tables VI–VII).
7. LLMs on 564 PrimeVul test pairs (P-C, higher is better): GPT-3.5 two-shot 5.67%, CoT 6.21%, fine-tuned 1.24%; GPT-4 two-shot 5.14%, CoT 12.94%; random guess 22.70%. GPT-4 two-shot labels both elements vulnerable in 71.63% of pairs (P-V) — [V] (p. 9, Table VIII).
8. GPT models beat fine-tuned open-source models on pair-wise correctness but are "no better than a random guess"; fine-tuned GPT-3.5 is biased by the 1:3 training ratio and does worse than prompting — [A] (p. 9).
9. Authors conclude code LMs, including GPT-4, are "a long way" from useful vulnerability detection and that fundamentally new approaches may be needed — [A] (p. 2, p. 10–11).

## 8. Limitations stated by the authors
- [A] PrimeVul label accuracy is below 100% (Table I), so some mislabelled data remain; authors believe results still hold (p. 10).
- [A] VD-S depends on the chosen FPR tolerance r; exact values change with r, conclusions expected to hold (p. 10).
- [A] OpenAI models were run only with default settings; hyper-parameter changes could vary results slightly (p. 10).
- [A] Function-level formulation without inter-procedural context may be "an impossible question" even for humans (p. 10).

## 9. Limitations we identified
- [I] The headline "68.26% → 3.09%" contrasts a model trained and tested on BigVul with the same model tested cross-dataset on PrimeVul; the fair within-dataset PrimeVul number is 18.05% (p. 7, Table V). The drop therefore mixes benchmark realism with distribution shift; both numbers should be cited together.
- [I] LLMs and fine-tuned models are not compared on the same metric: GPT models were evaluated only on paired functions (pair-wise metrics), never on the full imbalanced test set, so no F1 or VD-S exists for GPT-3.5/GPT-4 (p. 9). The paper therefore cannot answer whether GPT-4 has a better FNR at a fixed FPR than fine-tuned 7B models.
- [I] GPT-3.5 fine-tuning used one epoch and a 1:3 subsample (p. 9), which is a weak fine-tuning setup; its poor result says little about well-tuned LLMs.
- [I] De-duplication is exact-match after whitespace normalisation only (p. 5); near-clones (renamed identifiers, small edits) are not removed, so 0.0% leakage is a lower bound for "near-duplicate" leakage.
- [I] Label-accuracy figures for BigVul, CrossVul, CVEFixes and DiverseVul are copied from Chen et al., not re-measured (p. 4, Table I); audit samples are small (n=50, ~±14 pp at 95% binomial CI by our calculation) and annotators include the dataset's own authors.
- [I] Text/table inconsistency: the text says CodeBERT has "accuracy of 96.86%" on BigVul (p. 8), but Table V lists 95.57% for CodeBERT BigVul→BigVul (96.86% matches UnixCoder trained and tested on PrimeVul) (p. 7).
- [I] No SAST baseline, so the paper cannot place code LMs relative to static analysers on PrimeVul.

## 10. Threats to validity
- Internal (confounds, leakage, selection): [I] Strong leakage control (normalised hash de-dup + temporal, commit-grouped split) is the paper's main strength; residual near-duplicates possible. Cross-dataset BigVul→PrimeVul conflates label-noise effects with distribution shift.
- External (generalisability of sample/context): [I] C/C++ only; open-source projects from NVD-linked commits; function-level only; GPT results limited to 564 pairs and early-2024 model versions.
- Construct (do metrics measure the concept?): [I] VD-S and pair-wise metrics are better aligned with practice than F1, but r = 0.5% is a single chosen operating point; pair-wise evaluation measures discrimination between textually near-identical functions, which is harder than typical deployment.
- Statistical conclusion (power, multiple comparisons, variance): [I] No seeds, repeated runs, CIs or tests; small differences (e.g. CA-CLR +3 pp F1) cannot be distinguished from run-to-run noise.
- Reproducibility (data/code/setup reported?): [A] dataset, code and prompts released (p. 3, p. 13–14); [V] key hyper-parameters reported (p. 7).

## 11. Future research directions
- Stated by authors [A] (p. 10): give models broader (inter-procedural) context — PrimeVul keeps commit metadata to enable this; teach security concepts and build hybrid systems combining LMs with traditional security/program analysis tools; decompose detection into reasoning sub-steps (CoT showed slight promise).
- Suggested by us [I]: evaluate GPT-class LLMs and SAST tools on the full PrimeVul test set with VD-S so all families share one metric; add near-duplicate (clone) de-duplication; report variance over seeds/runs.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1, RQ2, RQ3, RQ5.
- How it informs our work [I]: Central evidence for RQ2 — quantifies label noise (24–36% accurate in Ding's own audit of manually labelled benchmarks; 25–60% for automatically labelled ones per Chen et al.) and duplication (up to 18.9%) in the benchmarks most LLM and DL papers use, and shows large F1 drops under realistic evaluation: 42–50 pp when models are trained and tested on PrimeVul instead of BigVul, and 58–65 pp when BigVul-trained models are tested on PrimeVul (Table V, p. 7). For RQ1 it gives the only LLM-vs-fine-tuned comparison in our set on a de-duplicated temporal benchmark: GPT-4 CoT beats fine-tuned models on pair-wise correctness (12.94% vs ≤3.01%) but stays below random (22.70%). It recommends hybrids with static analysis (RQ3) and context-aware formulations (RQ5). It contrasts with fu2023chatgpt, where fine-tuned models far outperform ChatGPT on random-split Big-Vul.

# Top Score on the Wrong Exam: On Benchmarking in Machine Learning for Vulnerability Detection

- Authors: Risse, Niklas; Liu, Jing; Böhme, Marcel
- Year / venue: 2025, Proceedings of the ACM on Software Engineering (published)
- DOI: 10.1145/3728887 · URL: https://doi.org/10.1145/3728887
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
- [A] To examine whether the dominant problem statement of machine learning for vulnerability detection (ML4VD) — "given a function, does it contain a security flaw?" — is well-defined, by measuring how often function vulnerability can be decided without external context in popular datasets, and to explain why ML4VD models nevertheless score highly (p. 1–2).

## 2. Research questions / hypotheses
- [A] Survey questions: what proportion of ML4VD papers use a function-level problem statement; which datasets they use (p. 3).
- [A] RQ.1 Can vulnerability detection be cast as function-level binary classification? (a) noisy labels, (b) context-dependent vulnerability, (c) context-dependent security of secure-labelled functions. RQ.2 Can high classification performance be achieved when the vulnerability's root cause is hidden (spurious features)? (p. 5).
- [A] Hypothesis: vulnerability of a function often cannot be decided without context (p. 1).

## 3. Methodology
- Research design: [V] (1) Literature survey of 2020–2024 ML4VD papers at ICSE, FSE, ASE, ISSTA, S&P, USENIX Security, NDSS, CCS, TSE, TOSEM, TIFS, TDSC, following Kitchenham/Petersen guidelines; >2,500 candidates → 109 by title → 81 by abstract/full text, filtered by one co-author (p. 3–4). (2) Manual labelling study by two security researchers with a 15-minute decision cap per function, plus a second round on context dependence (p. 6–7). (3) Constructing artificial vulnerable contexts for secure-labelled functions (p. 10). (4) Training a Gradient Boosting Classifier on word counts only (p. 7, p. 11).
- Approach / model / intervention: [V] Gradient Boosting Classifier on word-count features with no code structure, no pre-training; trained on each dataset's training subset and evaluated on its evaluation subset (p. 7, p. 11).
- Baselines or comparison conditions: [V] Published state-of-the-art scores: SNOPY 67.86% F1 and PDBERT 67.61% accuracy on Devign; DeepDFA 96.46% F1 on BigVul; CodeT5 Small 48.28% F1 on DiverseVul (Chen et al. benchmark) (p. 7). [V] SOTA values are taken from the literature, not re-run. [V] No LLM or static-analysis tool is evaluated experimentally (p. 7).

## 4. Dataset and sample
- Data source(s): [V] BigVul, Devign (most used in survey) and DiverseVul (recent, widely used in preprints); ReVeal excluded because it lacks patch-commit IDs/CVEs (p. 6).
- Sample size (N) and unit: [V] 100 randomly sampled vulnerable-labelled functions per dataset (300 total) from patch commits 2010–2022 covering 80 projects (BigVul 25, Devign 2, DiverseVul 60) (p. 6). 30 secure-labelled functions per dataset (90 total) for RQ.1-c (p. 10). Survey: 81 papers (p. 4). Class balance: Devign 47.9%, BigVul 4.5%, DiverseVul 5.4% vulnerable (p. 7).
- Sampling / selection method: [V] Random sampling; sample size "inspired by" Croft et al. (n=70) (p. 6). No power analysis.
- Data availability (public? link?): [A] Scripts, sampled functions, labels and explanations at https://github.com/niklasrisse/TopScoreWrongExam (p. 6–7, p. 13).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Annotators reviewed patch commit and, where available, CVE report; >150 hours total; labels Secure / Vulnerable / No decision; ambiguous callee-vs-caller fixes labelled callee only (p. 6). [V] Inter-rater agreement: 82% (Cohen's κ = 0.64) for vulnerable/secure; 98% (κ = 0.96) for context dependence; disagreements resolved by discussion (p. 6). [V] Annotators: 3 and 5 years security research experience; second annotator co-discovered three CVEs present in the datasets (p. 6–7). [V] Classifier training+evaluation took 30 minutes on a MacBook Pro (p. 11). GBC hyper-parameters and the exact train/evaluation splits: not reported in the paper text.
- Code availability: [A] GitHub repository above (p. 7).

## 6. Evaluation metrics
- Metric — what it measures — why chosen: [V] F1 as primary metric because it dominates the surveyed literature; accuracy only for balanced Devign, omitted for imbalanced BigVul/DiverseVul (p. 7). [V] Labelling outcomes reported as proportions; Cohen's kappa for agreement (p. 6).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): not reported beyond Cohen's kappa; no CIs on proportions.

## 7. Key findings
1. 88% of 81 surveyed ML4VD papers (2020–2024) define ML4VD as function-level binary classification (SE conferences 92%, security conferences 75%, journals 85%); 95% in 2024 — [V] (p. 5, Fig. 2a).
2. BigVul and Devign are each used by 36 papers and ReVeal by 22; 53 of 81 papers use at least one of the three — [V] (p. 5, Fig. 3).
3. Label accuracy of vulnerable-labelled functions: BigVul 39%, Devign 47%, DiverseVul 65% actually vulnerable (Devign 3% no decision) — [V] (p. 7–8, Fig. 6).
4. Reasons for wrong labels: patch-commit identification (BigVul 21%, Devign 54%, DiverseVul 3%), structural changes caused by the fix (48%, 38%, 66%), unrelated changes (31%, 8%, 31%) — [V] (p. 8, Table I).
5. All 151 truly vulnerable functions were context-dependent; none could be decided from the function alone — [V] (p. 9).
6. Types of context dependence: external functions 43–52%, function arguments 40–47%, globals 2–10%, type declarations 0–3%, execution environment 0–3% — [V] (p. 9, Table II).
7. For 82 of 90 secure-labelled functions the authors could construct a context in which the function is vulnerable — [V] (p. 10).
8. Word-count Gradient Boosting vs SOTA: BigVul F1 0.86 vs 0.96; Devign F1 0.62 vs 0.68 and accuracy 0.63 vs 0.68; DiverseVul F1 0.11 vs 0.48 — [V] (p. 11, Table III).
9. Authors conclude the function-level problem statement is ill-defined, "there is currently no evidence that ML4VD techniques are actually capable of identifying security vulnerabilities at the function-level", and high scores likely reflect spurious correlations — [A] (p. 2, p. 11–12).
10. Authors argue intra-procedural static analysis faces the same context-dependency problem and that combining static analysis with ML is promising — [A] (p. 2, p. 12–13).

## 8. Limitations stated by the authors
- [A] Selection bias from random sampling of 100 functions per dataset (p. 11).
- [A] Manual labelling is subjective; some human error may remain despite cross-labelling (p. 11–12).
- [A] Only three datasets; may not generalise to other datasets or real-world systems (p. 12).
- [A] Datasets are mainly C; may not generalise to other languages (p. 12).
- [A] Only the function-level problem statement studied; other granularities need similar study (p. 12).
- [A] Spurious correlation shown only with word counts; other spurious features need study (p. 12). The GBC result shows datasets can be exploited, not that SOTA models actually do so (p. 11).
- [A] Secure functions were not verified to be truly non-vulnerable (p. 10).

## 9. Limitations we identified
- [I] The context-dependence criterion is very permissive: almost any function that dereferences a pointer or uses an argument can be made vulnerable by an adversarial caller (e.g. passing NULL, Fig. 11, p. 10). The 100% / 82-of-90 results are partly a consequence of this definition and say more about the problem framing than about any detector.
- [I] Word-count GBC vs SOTA compares a model the authors trained with literature numbers produced under possibly different splits and preprocessing (p. 7, p. 11); no re-run of SOTA models on identical splits, no repeated runs, and GBC settings are not given.
- [V] On DiverseVul word counts reach only 0.11 F1 vs SOTA 0.48 (p. 11). [A] The authors say this "suggests that the dataset may contain fewer exploitable spurious features. However, this is not definitive proof" (p. 11). DiverseVul is the least noisy of the three by the authors' own audit (65% correct vs 39%/47%, p. 8); it is not the least leaky (exact-copy rate 3.3% vs 0.6% for CodeXGLUE/Devign [@ding2025vulnerability, p. 4]). [I] Our inference, resting on Table III (p. 11): the spurious-feature argument is strongest for BigVul/Devign and is not universal.
- [I] Label-accuracy samples are small (n=100; ~±10 pp at 95% binomial CI by our calculation) and κ = 0.64 for the first step is only "substantial"; the 15-minute cap may bias towards "secure" for complex cases.
- [I] Survey screening was done by a single author (p. 4), a risk for selection consistency.
- [I] No LLM or SAST experiment: relevance to LLM-vs-SAST is through benchmark validity, not head-to-head numbers.

## 10. Threats to validity
- Internal (confounds, leakage, selection): [I] Random sampling and released labels are strengths; single-screener survey and annotators' prior work on ML4VD critique (refs [19], [24]) could bias judgements towards the hypothesis.
- External (generalisability of sample/context): [I] Three C/C++ datasets; Devign sample spans only 2 projects (p. 6); results may differ for Java/Python or curated datasets such as PrimeVul.
- Construct (do metrics measure the concept?): [I] "Context-dependent" is not a measure of detector failure; a context-dependent vulnerability may still be statistically predictable from code patterns. The word-count probe tests exploitability of datasets, not model behaviour.
- Statistical conclusion (power, multiple comparisons, variance): [I] No CIs; per-dataset proportions from n=100 (vulnerable) and n=30 (secure).
- Reproducibility (data/code/setup reported?): [A] Full artifact (scripts, samples, labels, explanations) released (p. 13).

## 11. Future research directions
- Stated by authors [A] (p. 12–13): binary classification with abstention; other base units (lines, files, modules, inter-procedural slices); context-conditional classification with the full repository at the patch commit as context; replacing classification by generating a vulnerable context or an ML-assisted proof-of-vulnerability test case; combining static analysis and ML; methods to detect spurious correlations in benchmarks.
- Suggested by us [I]: test whether LLMs given repository-level context (or tool-augmented with static analysis) reduce the context-dependency problem on the released labelled subset; repeat the word-count probe on PrimeVul and Real-Vul.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ2, RQ3, RQ5.
- How it informs our work [I]: Key methodological critique for RQ2 — explains why high F1 on BigVul/Devign (used by most DL and many LLM papers) is weak evidence of detection ability: labels are 39–65% accurate, vulnerability is context-dependent, and word counts reach near-SOTA scores. Supports interpreting fu2023chatgpt's 94% F1 for fine-tuned models as benchmark-inflated. For RQ3/RQ5 it argues for context-aware formulations and static-analysis + ML combinations, but provides no experimental evidence on hybrids.

# Revisiting the Performance of Deep Learning-Based Vulnerability Detection on Realistic Datasets

- Authors: Chakraborty, Partha; Arumugam, Krishna Kanth; Alfadel, Mahmoud; Nagappan, Meiyappan; McIntosh, Shane
- Year / venue: 2024, IEEE Transactions on Software Engineering (published)
- DOI: 10.1109/tse.2024.3423712 · URL: https://doi.org/10.1109/tse.2024.3423712
- Source text: `fulltext.txt` (page refs = PDF page index)

Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.

## 1. Research objective
- [A] To test whether deep-learning vulnerability detectors that report up to 99% recall/F1 still perform in a realistic setting where the model scans entire codebases rather than only functions from fixing commits, and to provide a dataset (Real-Vul) for such evaluation (p. 1–2).

## 2. Research questions / hypotheses
- [A] RQ1: How do DeepWukong, LineVul, ReVeal and IVDetect perform in a realistic evaluation setting compared with the setting of the original studies? RQ2: How do they perform when also trained on a similar realistic training dataset? (p. 5).
- [A] Implicit hypothesis: prior datasets (synthetic SARD; commit-sampled Big-Vul/ReVeal with near-balanced ratio and label inconsistency) overestimate performance (p. 3).

## 3. Methodology
- Research design: [V] (1) Replication of four DL models on their original datasets with an 80/20 random split (p. 5–6); (2) evaluation of these models on the Real-Vul test set (RQ1, p. 6–7); (3) retraining on Real-Vul, imbalanced and balanced (RQ2, p. 8–9); (4) discussion analyses: project size vs FPR, cyclomatic complexity, LIME token analysis, dead-code augmentation, per-CWE-cluster and per-severity F1, and two fine-tuned LLMs (p. 9–12).
- Approach / model / intervention: [V] LineVul (CodeBERT, token-based), DeepWukong (GNN on XFG slices), ReVeal (GNN on code property graphs, uses SMOTE), IVDetect (graph-based with interpretation) (p. 4–5). [V] CodeLlama (7B) and Mixtral ("7B" per the paper) fine-tuned with parameter-efficient fine-tuning on Real-Vul (p. 12).
- Baselines or comparison conditions: [V] Each model's performance on its own original dataset (Table 2) is the baseline for the realistic setting (p. 6). [V] No static-analysis tool is evaluated; authors list this as future work (p. 13).

## 4. Dataset and sample
- Data source(s): [V] Real-Vul built from the 10 Big-Vul projects with the most vulnerabilities (Chromium, FFmpeg, ImageMagick, Jasper, Krb5, Linux, OpenSSL, php-src, QEMU, tcpdump), covering 73% of Big-Vul's vulnerable samples (p. 3–4, Table 1).
- Sample size (N) and unit: [V] Function. 5,528 vulnerable functions (4,418 train, 1,110 test) (p. 4); 1,682,713 uncertain functions (769,464 train, 913,249 test) (p. 4). Table 1 project sizes sum to 270,919 functions and p. 13 states "270,919 samples, of which 5,528 are vulnerable" (p. 4, p. 13).
- Sampling / selection method: [V] Vulnerable functions ordered by fix date; first 80% to train, last 20% to test. Uncertain functions = all functions in a repository snapshot taken after the last training fix date (train) and after the test period (test) whose MD5 hash matches no vulnerable function, avoiding label inconsistency (p. 4). [V] Authors found 15% of vulnerable samples in ReVeal also listed as uncertain (p. 3).
- Data availability (public? link?): [A] Real-Vul and scripts released at https://zenodo.org/record/8206635 (p. 2).

## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] DeepWukong 50 epochs, LineVul 10 epochs, ReVeal max 100, IVDetect max 50 epochs, early stopping after 5 epochs without F1 gain (p. 6). For RQ1, DeepWukong is retrained on Big-Vul (28,294 vulnerable / 639,047 uncertain XFGs) to be comparable (p. 7). Balanced training = random undersampling of uncertain samples to equal vulnerable count (p. 8). Augmentation: eleven dead-code insertion strategies (details in online appendix) (p. 10). LLM fine-tuning hyper-parameters: not reported beyond "parameter-efficient fine-tuning" (p. 12). Seeds/repeats: not reported; authors state repeated training was not feasible (p. 13).
- Code availability: [A] scripts released (p. 2).

## 6. Evaluation metrics
- Metric — what it measures — why chosen: [V] Accuracy, precision, recall, F1 and AUC, each defined in the paper (p. 5). Per-SFP-cluster (CWE group) and per-severity F1 (p. 10–11).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): [V] Mann-Whitney U tests for cyclomatic complexity (TP vs FP p = 0.043; TN vs FN p = 0.014) and for LIME positive-token ratio in FP vs TP (p = 0.13, α = 0.05) (p. 10). No CIs or tests for the main performance comparisons.

## 7. Key findings
1. Replication on original datasets: DeepWukong (SARD) P 87 / R 98 / F1 93 / AUC 88; LineVul (Big-Vul) P 96 / R 84 / F1 90 / AUC 85; ReVeal P 29 / R 59 / F1 38; IVDetect P 39 / R 63 / F1 24 (%) — [V] (p. 6, Table 2).
2. RQ1, original-trained models on Real-Vul test: DeepWukong P 1 / R 87 / F1 2 / AUC 62; LineVul P 1 / R 90 / F1 2 / AUC 58; ReVeal P 10 / R 80 / F1 17 / AUC 61; IVDetect P 2 / R 84 / F1 2 / AUC 59 (%) — [V] (p. 7, Table 3).
3. Drops vs original setting: precision −86 (DeepWukong), −95 (LineVul), −19 (ReVeal), −37 (IVDetect) pp; F1 −91, −88, −21, −22 pp — [V] (p. 7).
4. False positives on Real-Vul test: DeepWukong 439,494; LineVul 114,629; ReVeal 320,128; IVDetect 512,284 — [V] (p. 7).
5. RQ2, trained on imbalanced Real-Vul: DeepWukong and LineVul P/R/F1 0%, AUC 50% (predict everything uncertain); ReVeal F1 3%; IVDetect F1 0% — [V] (p. 8, Table 4).
6. RQ2, trained on balanced Real-Vul: F1 DeepWukong 2%, LineVul 20% (P 11, R 99), ReVeal 36% (P 31, R 45), IVDetect 6%; AUC 51.3–52.3% — [V] (p. 9, Table 5).
7. Dead-code augmentation: LineVul F1 20 → 46%, AUC 51.4 → 81.8%, precision 11 → 37%, recall 99 → 65%; smaller gains for graph models (DeepWukong F1 7%, ReVeal 38%, IVDetect 16%) — [V] (p. 10, Table 6).
8. Fine-tuned LLMs (with augmented training data): CodeLlama P 34 / R 54 / F1 42 / AUC 67; Mixtral P 38 / R 59 / F1 46 / AUC 71 (%). AUC lags LineVul by 14.8 and 10.8 pp; authors conclude "specialized tools (LineVul) outperform general large language models (LLMs)" — [V] numbers, [A] conclusion (p. 12, Table 8).
9. Per-CWE cluster: best F1 for information-leak (SFP 895, up to 33.6%) and tainted-input (896, 23.31%) clusters; worst for path resolution (893), predictability (905) and miscellaneous (907, no detections) — [V] (p. 10–11, Fig. 5). Cluster frequency strongly uneven (890 32%, 896 25%, 892 14%; 907 0.003%) — [V] (p. 11).
10. Per severity F1: high-severity vulnerabilities hardest (9.06–10.89%) vs medium (17.46–26.57%) and low (15.08–21.66%); only 5% of vulnerabilities are high severity — [V] (p. 10–11, Table 7).
11. Larger projects show lower false-positive rates (Fig. 4); higher cyclomatic complexity associated with FPs (p = 0.043) — [V] (p. 9–10).

## 8. Limitations stated by the authors
- [A] Some Big-Vul vulnerable samples may be mislabelled, though Big-Vul labels were manually verified by Fan et al. (p. 13).
- [A] Only ten open-source projects; may not represent all real-world scenarios (p. 13).
- [A] "Uncertain" functions may contain undiscovered vulnerabilities (p. 13).
- [A] Balanced datasets use one random undersample; multiple runs were not feasible due to compute (p. 13).
- [A] Hash-based label-consistency check may miss whitespace variants despite regex normalisation (p. 13).
- [A] Only DL techniques evaluated; static and dynamic analysis tools left for future work (p. 13).

## 9. Limitations we identified
- [I] Internal numerical inconsistencies: (a) IVDetect replication reports P 39 / R 63 but F1 24 (the harmonic mean of 39 and 63 is ~48) (p. 6, Table 2); (b) Table 1 project sizes total 270,919 functions while the text reports 1,682,713 uncertain functions (p. 4, p. 13); (c) balanced LineVul shows R 99% with AUC 51.4% (p. 9, Table 5), which is hard to reconcile with high recall at ~99% accuracy. These do not change the qualitative story but make exact numbers less reliable.
- [I] The LLM comparison is thin and partly contradicts its own conclusion: Mixtral's F1 (46%) equals augmented LineVul's F1 (46%) and its precision (38%) is higher than LineVul's (37%); only AUC favours LineVul (p. 10, p. 12). The LLM accuracy of 80–83% at 34–38% precision implies a test set far less imbalanced than the 1,110 / 913,249 Real-Vul test set, so the LLM test set appears to differ from the DL test set (inferred from Table 8 vs p. 4); test-set composition and hyper-parameters are not reported. Mixtral is described as "7 B parameter", which [I] understates its 8×7B mixture-of-experts size.
- [I] RQ1 conflates two shifts: from commit-sampled to whole-project negatives (realistic base rate) and from original training data to a different test distribution; RQ2 isolates the first, and still yields F1 ≤ 36%.
- [I] Big-Vul is the label source for Real-Vul vulnerable functions; only ~25% of Big-Vul vulnerable labels are correct according to Chen et al., as reported by [@ding2025vulnerability, p. 4] (Risse et al.'s own audit gives 39% [@risse2025top, p. 7]), so the authors' reliance on Fan et al.'s verification (p. 13) is optimistic.
- [I] Absolute false-positive counts are reported in different units (XFGs, chunks, CPGs, PDGs) per model (p. 7), so they are not directly comparable across models.

## 10. Threats to validity
- Internal (confounds, leakage, selection): [I] Temporal split and MD5-based label consistency reduce leakage; near-duplicates and inherited Big-Vul label noise remain. Single random undersample for balancing.
- External (generalisability of sample/context): [I] Ten large C/C++ projects dominated by Chromium and Linux; only function-level DL models plus two 7B-class LLMs; no SAST tools; no other languages.
- Construct (do metrics measure the concept?): [I] Precision at realistic base rate is the practically relevant metric and is the paper's key contribution; AUC values near 50% with high recall suggest threshold effects. "Uncertain" negatives may hide real vulnerabilities, depressing measured precision.
- Statistical conclusion (power, multiple comparisons, variance): [I] No CIs or repeated runs for performance; Mann-Whitney tests only in side analyses, no multiple-comparison correction.
- Reproducibility (data/code/setup reported?): [A] Dataset and scripts on Zenodo (p. 2); [I] augmentation strategies and LLM fine-tuning settings only in an online appendix / not reported.

## 11. Future research directions
- Stated by authors [A] (p. 10–13): augmentations inducing structural/data-flow changes for graph models; better data strategies and architectures for contextual and system-level vulnerabilities; improving detection of high-severity vulnerabilities; improving LLM specificity for vulnerability detection; evaluating static and dynamic analysis tools on Real-Vul.
- Suggested by us [I]: run SAST tools and prompted/fine-tuned LLMs on the identical Real-Vul test set and report precision at a fixed alert budget; combine Real-Vul's whole-project negatives with PrimeVul-style label verification.

## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1, RQ2, RQ4, RQ5.
- How it informs our work [I]: Strongest evidence in our set that base-rate realism (whole-project scanning) destroys precision of DL detectors (to 1–10%), complementing Ding et al.'s label/duplication findings. Gives per-CWE-cluster and severity breakdowns for RQ4, and a small fine-tuned-LLM vs LineVul comparison for RQ1 whose conclusion depends on the metric (AUC favours LineVul, F1 tied). Explicitly names SAST comparison on Real-Vul as missing (RQ5).
