## 9. Limitations we identified
- [I] There is no non-LLM baseline at all (no SAST tool, no fine-tuned DL/PLM model, no single-prompt LLM). So the paper cannot say whether the multi-agent design helps or hurts, or how LLMs compare with traditional tools. Based on §3/§5 above.
- [I] The statement-level recall in Table 3 appears not to follow the stated definition. We reconstructed integer counts from Table 3 and the flag counts on p. 13 (e.g. Claude: 215 flagged, 90 function-level TP, 119 positives, 33 statement-level TP). Every reported statement-level recall is reproduced exactly as TP_stat / (TP_stat + function-level FN). That means "right function, wrong reasoning" cases were not counted as FN, contrary to the definition on p. 7. Under the stated definition, Claude's statement-level recall would be about 27.7% (33/119), not 53.23%, and its F1 about 19.8%, not 23.83%. The same pattern holds for all five models (GPT-4.1: about 26.1% vs. 49.21%). This is our arithmetic on the paper's tables (p. 8, p. 13). It makes the headline numbers optimistic, not pessimistic.
- [I] The implied number of vulnerable functions differs by model (119-126), although the paper says 120 of 300 are vulnerable (p. 13). This suggests unreported per-model exclusions (e.g. failed outputs). Same reconstruction as above.
- [I] The detection evaluation uses only 300 functions (about 1.2% of the benchmark), drawn from Top-25 CWEs only, with no uncertainty reported. Gaps of a few points between models (e.g. Claude vs. GPT-4.1, 23.83% vs. 22.38%) are probably within sampling noise. Based on p. 8.
- [I] Experiment 2 is circular: the context "ground truth" was generated by GPT-4.1 (p. 6), and GPT-4.1 is also one of the evaluated models (p. 9). This makes the context accuracies hard to interpret.
- [I] The task differs from SAST use. The pipeline gets one function plus LLM-requested definitions, not the whole repository or build. The results describe LLM review of single functions, not project-scale scanning.
- [I] The 300-sample set is 40% vulnerable, far more than in real codebases, so precision would likely drop further in deployment. This rests on the 120/300 count (p. 13).
- [I] Data contamination is not discussed: CVEs up to 2024 and their public fixes may be in the training data of all five models, and there is no time-split analysis.

## 10. Threats to validity
- Internal (confounds, leakage, selection): the manual judging rules are lenient (sink-only counts as TP; up to two extra statements allowed) (p. 8). The number of raters and their agreement are not reported. There is also the recall inconsistency in §9. Heuristics reduce label noise, but noise in the vulnerability labels is never measured; only the context labels were validated (p. 5, p. 6). De-duplication removes exact duplicates only (p. 5).
- External (generalisability of sample/context): C/C++ only. Linux is a large share (2,793 of 10,998 vulnerable functions) (p. 5). The evaluation covers only Top-25 CWEs and 300 samples (p. 8), and five specific LLM versions at temperature 0.1 (p. 8).
- Construct (do metrics measure the concept?): "correct reasoning" is a human judgement with no stated protocol beyond the four rules (p. 8). Function-level detection is judged without checking whether the stated reason is right (p. 7, p. 8).
- Statistical conclusion (power, multiple comparisons, variance): only one run per model is reported, with no confidence intervals or tests on Table 3. The Mann-Whitney tests run across five models without multiple-comparison correction, but all p < 0.017, so they are likely robust (p. 13).
- Reproducibility (data/code/setup reported?): the dataset, code and full prompts are released (p. 3, p. 14-p. 16), and hardware and temperature are reported (p. 8, p. 17). Whether the manual judgements for the 300 samples are released is not stated.

## 11. Future research directions
- Stated by authors [A]: use the statement-level and context labels to train and evaluate detection models (p. 10); test smaller model sizes (p. 12); "advancing statement-level detection is essential" (p. 9).
- Suggested by us [I]: run SAST tools (e.g. CodeQL, Cppcheck) and fine-tuned DL detectors on the same 300-sample subset; report statement-level recall under the stated definition with confidence intervals; compare the multi-agent pipeline against a single prompt, with and without context; split by CVE date to check for contamination.

Counter-evidence: BM25 examples come from the "REEF training dataset" (p. 12), and the time-split run evaluates the model "trained on the original dataset" (p. 38). - [I] **Line-level accuracy/FPR are probably inflated by padding.** The DummyClf_vul precision on the line-level test set is 0.0267 (p. 23), i.e. 2.67% vulnerable lines. But Table 2 implies about 14.3% vulnerable lines (25,161 / 175,768) (p. 8). 810 test functions x 113 padded line slots ≈ 91,530 slots, and 2.67% of that ≈ 2,440 vulnerable lines, close to the ≈2,500 expected from the dataset average (3.1 per function). - Reproducibility (data/code/setup reported?): [I] Hyper-parameters reported (p. 5, p. 7); code/data claimed public without a link (p. 10); SAST configuration missing.

## 11. Future research directions
- Stated by authors [A]: shift from function-level to repo-level detection (p. 10); reduce LLM marked ratios via filtering untrustworthy predictions, adding repository structure context, better prompting or ensembles (p. 10); combine LLMs and SAST tools more effectively (p. 10–11).
- Suggested by us [I]: re-run with project-grouped splits, multiple seeds and larger test sets; measure precision on manually triaged samples; actually test SAST+LLM hybrids (e.g., LLM triage of SAST alerts). Based on the limitations in section 9.

## 8. Limitations stated by the authors
- [A] The only threat to validity discussed is missing relevant studies because of incomplete keywords or varied LLM terminology. It is mitigated by manual venue selection, automated search and snowballing (p. 24).
- [A] Scope: future versions will add vulnerability localisation and assessment (p. 24).

## 9. Limitations we identified
- [I] Dated corpus. The search ends in March 2024 (p. 5), before most agentic, repository-level and LLM + SAST hybrid work. Findings such as "encoder-only dominates" may not hold for 2025–2026: `kaniewski2026systematic` and `sheng2025llms` already report decoder-only dominance. Based on the time window and comparison with the other two surveys in this project.
- [I] Very thin evidence on LLM vs SAST. The single repo-level comparison is the authors' own study ([130], Zhou … Lo, 2024; ref list p. 29). The roadmap's statement about SAST-vs-LLM trade-offs is therefore effectively self-citation, not a synthesis.
- [I] No comparison with non-LLM DL detectors. GNN/RNN-only studies are excluded (p. 6), so the review cannot answer whether LLMs beat DL detectors.
- [I] The quality assessment uses "published in a prestigious venue" (QAC1) as a criterion (p. 6). This mixes venue prestige with methodological quality and structurally penalises preprints.
- [I] Gaps in process transparency: the number of screeners, their agreement and the per-study QA scores are not reported, and the search string is only in an external Google Doc (p. 5).
- [I] Minor internal inconsistencies:
  - The RQ3 answer says "three commonly used techniques" but lists two (p. 17).
  - Limitation 2 opens with "For vulnerability repair" while discussing detection label noise (p. 19).
  - By our count, Tables 2 and 3 contain 57 unique study references (Fu et al. [27] and [29] appear in both), versus 58 stated.

  None of these changes the main conclusions.
- [I] Repair is half of the scope, so detection-specific depth (metrics, benchmarks, CWE coverage) is limited.

## 10. Threats to validity
- Internal (confounds, leakage, selection): selection could be biased by the venue-first strategy and the prestige-weighted QA. Whether one or several people screened each paper is not reported. The review itself flags contamination of LLM pre-training corpora as a concern for primary studies (p. 20).
- External (generalisability of sample/context): the corpus covers Jan 2018–Mar 2024 and source code only, no binaries (p. 5–6). It is dominated by function-level studies (Table 2, p. 10).
- Construct (do metrics measure the concept?): the technique shares (≈73/17/10%) are given without a stated denominator (p. 9). The classification of studies into categories is not validated.
- Statistical conclusion: not applicable (no quantitative synthesis).
- Reproducibility: keywords are in an online appendix (p. 5). Extraction data and QA scores are not released (not reported).

## 11. Future research directions
- Stated by authors [A]:
  - Curate a smaller, manually verified, living high-quality test set for vulnerability detection, e.g. by combining manually checked samples from several studies (p. 22).
  - Repository-level detection and repair using long-context LLMs, extending the initial repo-level SAST-vs-LLM comparison (p. 22).
  - Open-source LLMs customised for vulnerability data (p. 22).
  - LLM usages not yet explored: agents, external tool use, advanced RAG (iterative, recursive, adaptive) (p. 22–23).
  - Deployment-ready features: developer interaction, explanations, IDE/VCS integration (p. 23).
  - Benchmarks with no overlap with LLM pre-training corpora, to avoid data contamination (p. 20).
  - Handling complex vulnerabilities: inter-procedural, rare CWE types, vulnerabilities spanning multiple code units (p. 20).
  - Vision for 2030: line- to repo-level detection and repair, evaluated on an expert-annotated benchmark (p. 23).
- Suggested by us [I]:
  - Check whether the agent, tool-use and repo-level directions proposed here have since been realised. Our corpus contains `guo2025repoaudit`, `li2024iris`, `yildiz2025benchmarking` and `li2026llm`.
  - Check whether the SAST-vs-LLM trade-off reported by `zhou2024comparison` (higher detection for LLMs, but more false positives) replicates in independent studies.
