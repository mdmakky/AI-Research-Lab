    18	# Interaction2Code: Benchmarking MLLM-based Interactive Webpage Code Generation from Interactive Prototyping
    19	
    20	- Authors: Xiao, Jingyu; Wan, Yuxuan; Huo, Yintong; Wang, Zixin; Xu, Xinyi; Wang, Wenxuan
    21	- Year / venue: 2025, 2025 40th IEEE/ACM International Conference on Automated Software Engineering (ASE) (published)
    22	- DOI: 10.1109/ase63991.2025.00028 · URL: https://doi.org/10.1109/ase63991.2025.00028
    23	- Source text: `fulltext.txt` (page refs = PDF page index)
    24	
    25	Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
    26	Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.
    27	
    28	## 1. Research objective
    29	- Formulate the Interaction-to-Code task (generate an interactive webpage from an "interactive prototype": screenshots before and after each interaction), build a real-world benchmark for it, and systematically study how well MLLMs reproduce webpage interactions, why they fail, and how prompting can help [A] (pp. 1–2).
    30	
    31	## 2. Research questions / hypotheses
    32	- No formal RQs. The study is organised around four reported "limitations" of MLLMs: (1) worse generation of interactive parts than of the full page; (2) ten failure types; (3) poor performance on visually subtle interactions; (4) insufficient understanding from visual input alone — each paired with an improvement strategy [V] (pp. 1–2).
    33	
    34	## 3. Methodology
    35	- Research design: benchmark construction plus empirical comparison of models and prompts; automatic evaluation via Selenium-driven interaction replay; human usability and pairwise evaluation; qualitative failure taxonomy; sub-experiments on visual saliency and input modality; ablation; small user study [V] (pp. 3–11).
    36	- Approach / model / intervention: MLLM receives the original screenshot plus post-interaction screenshot(s) and must output one HTML+CSS+JavaScript file, tagging interactive elements with ids (e.g. id="interact1") so a webdriver can trigger them [V] (pp. 3–5). Prompts: Direct, Chain-of-Thought (CoT), Mark (red bounding boxes on interactive areas), Failure-aware Prompt (FAP: lists the ten failure types) [V] (p. 5). Further enhancements: Visual Saliency Enhancement (crop to enlarge the interaction area) and adding human-written textual descriptions of interactions [V] (pp. 9–10).
    37	- Baselines or comparison conditions: Gemini-1.5-flash, GPT-4o-20240806, Claude-3.5-Sonnet-20240620, Qwen2.5-VL-instruct 3B/7B/72B; Direct prompting is the baseline for prompt comparisons; Gemini-1.5-flash Direct is the human pairwise baseline [V] (pp. 4, 6). No non-LLM or prior UI-to-code system (e.g. DCGen) is run as a baseline [I] (based on p. 4 model list).
    38	
    39	## 4. Dataset and sample
    40	- Data source(s): (1) C4 validation set (CommonCrawl), filtered as in Design2Code, 1,000 pages sampled across 15 topics, from which four PhD students each picked about 25 → 100 pages; (2) 27 popular GitHub projects (average 13k stars) with deployed links, found via "open-production-web-projects" and "awesome-opensource-apps", to include UI-framework pages [V] (pp. 2–3).
    41	- Sample size (N) and unit: 127 webpages and 374 interactions; 15+ topics; 23 tag categories and 8 visual categories (31 interaction categories) [V] (pp. 1, 3). Most frequent interactive tags: button 235, input 52, span 37, link 36 [V] (p. 3).
    42	- Sampling / selection method: manual selection by four PhD students for complexity (at least one meaningful interaction) and diversity; 1–10 "important and functional" interactions kept per page; trivial interactions (e.g. hover underline) excluded [V] (pp. 2–3). Selection guidelines are only in the external artifact [V] (p. 3).
    43	- Data availability (public? link?): data and code at https://github.com/WebPAI/Interaction2Code [A] (p. 1).
    44	
    45	## 5. Experimental setup
    46	- Procedure, settings, hyper-parameters, tools: temperature 0; max output 4,096 tokens (commercial) and 2,048 (Qwen); other parameters default [V] (p. 4). Selenium webdriver locates elements by id, performs the interaction and screenshots the result; the changed region is extracted by pixel subtraction (same-size pages) or a Git-diff of rows/columns (size-changing pages) (Algorithm 1) [V] (p. 4). Data-contamination check: BLEU between generated and original HTML is 0.12–0.14 for the four main models [V] (p. 5). FAP experiment: 2/3 of the dataset used to derive failure types, 1/3 for testing [V] (p. 8). Saliency and modality experiments use 10 randomly sampled failure-case webpages each [V] (pp. 9–10).
    47	- Code availability: GitHub repository above [A] (p. 1). Appendix H (tool) and detailed human-evaluation instructions are referenced but are not in our 13-page PDF [V] (pp. 6, 11).
    48	
    49	## 6. Evaluation metrics
    50	- Full-page metrics: CLIP score (visual similarity); SSIM (structural similarity); Text similarity = BLEU on OCR-extracted text; Widget Similarity (WS) and Widget Match Rate (WMR) computed with the GUIPilot method [V] (p. 4).
    51	- Interaction-part metrics (on the extracted changed region): CLIP, SSIM, Text; Position similarity P = 1 − max(|xo − xg|, |yo − yg|) of normalised interaction-area centres; Implement Rate IR = implemented / (implemented + unimplemented), where "implemented" means detectable by the webdriver [V] (p. 4).
    52	- Human metrics: Usability Rate UR = usable / (usable + unusable), judged by four PhD students (three years front-end experience) — usable if the implementation "precisely matches the behavior specified in the interactive prototype"; pairwise Win/Tie/Lose by five annotators against Gemini-1.5-flash Direct, majority (≥3) rule; failure-type annotation [V] (pp. 4, 6–7).
    53	- Validation against human judgement: authors state human results "are consistent with Section V-A, confirming the validity of our automatic evaluation metrics" [A] (p. 6). No correlation coefficient, agreement statistic or regression is reported — not reported. Inter-annotator agreement for usability, pairwise or failure annotation — not reported (failure types reached by discussion to consensus on a 25% sample) [V] (p. 7). Number of items in the human evaluations — not reported.
    54	- Widget metrics are acknowledged as unreliable for web pages: WS is "consistently poor" (0.02–0.05) and GUIPilot omits many elements because it was designed for mobile UIs [V] (pp. 5–6).
    55	- Statistical testing (tests used, significance, effect sizes, confidence intervals): none for model or prompt comparisons; saliency effect described as "significantly increases" without a test [V] (pp. 8–9). Not reported.
    56	
    57	## 7. Key findings
    58	1. Interactive parts are generated worse than full pages for all models (e.g. GPT-4o average full-page CLIP 0.7059 vs interaction-part CLIP 0.5598) [V] (p. 6).
    59	2. Claude-3.5-Sonnet has the best averages on most metrics (e.g. interaction IR 0.7870, full-page Text 0.5835); GPT-4o with Mark prompt has the highest single IR (0.8128); Qwen2.5-VL-72B ≈ Gemini-1.5-flash; performance rises with model size [V] (pp. 5–6).
    60	3. Human Usability Rate (Fig. 6a, read from figure labels): GPT-4o Direct/CoT/Mark 73/74/81%; Claude 66/69/77%; Gemini 47/53/64%; Qwen-72B 41/43/54%; Qwen-3B 17–19% [V] (p. 6). Mark prompting gives the largest usability gain (Claude +11 points vs Direct) [V] (p. 6).
    61	4. Ten failure types in two groups (interactive element: missing, no interaction, wrong element, wrong type, wrong position; interaction effects: wrong position, wrong type, effect on wrong element, partial implementation, wrong function) [V] (pp. 7–8). Failures (a) missing element, (b) no interaction and (j) wrong function have usability <10% (0%, 6.93%, 0%) [V] (pp. 7–8). Main failure modes are "No interaction", "Partial implementation", "Interactive element missing" and "Wrong function" [A] (p. 8).
    62	5. Failures cluster into spatial (a, c, e, f), type (d, g) and behavioural (b, h, i, j) failures [A] (p. 8).
    63	6. Low visual saliency (small interaction area) lowers SSIM and position similarity; cropping to enlarge the area (1.2–3×) recovers interactions on 10 failure pages [V] (pp. 9–10).
    64	7. On 10 failure pages, combining visual and human-written text descriptions beats either modality alone for GPT-4o (Direct: Position 0.7157 V+T vs 0.3951 V) [V] (p. 10). All four enhancements combined give the best ablation result (GPT-4o interaction CLIP 0.6937 vs 0.5700) [V] (p. 11).
    65	8. FAP: authors claim it improves "all models" [A] (p. 8), but Table VI shows Qwen2.5-VL-3B drops on 7 of 8 metrics and Qwen-7B on 5 of 8 [V] (p. 9).
    66	9. User study: with the tool, 4 tasks took 279 s vs 413 s on average and expert similarity rating 4.5 vs 3.875 (two participants per condition, two raters) [V] (p. 11).
    67	10. Code quality or maintainability of the generated HTML/CSS/JS is not measured; the only code-level measure is BLEU against the original HTML, used as a contamination check [V] (pp. 4–5).
    68	
    69	## 8. Limitations stated by the authors
    70	- Limited context length: complex pages with many interactions may exceed the context window; iterative generation suggested [A] (p. 11).
    71	- Model selection: only three main commercial MLLMs tested; others (e.g. Pixtral) left for future work [A] (p. 11).
    72	- Back-end interactions (login, search) cannot be evaluated because the benchmark has no back-end code [A] (p. 11).
    73	- Existing widget-consistency methods are designed for mobile UIs and miss web elements [A] (p. 5).
    74	
    75	## 9. Limitations we identified
    76	- [I] Validation of automatic metrics against humans is only a qualitative "consistent" statement (p. 6); no correlation, agreement (kappa) or item counts are given. The automatic metrics are therefore not shown to measure functional fidelity.
    77	- [I] "Implement Rate" counts an interaction as implemented if the webdriver can find and trigger the element (p. 4) — this measures presence, not correct behaviour; functional correctness rests on the human Usability Rate alone.
    78	- [I] Interaction fidelity is judged on screenshots of state changes, not on behavioural traces or DOM/state assertions; non-visual effects (data, network, storage) are out of scope (based on pp. 3–4, 11).
    79	- [I] Several sub-experiments use only 10 pages (pp. 9–10) and the user study has 2 participants per condition (p. 11); these results are anecdotal.
    80	- [I] The FAP claim ("improve ... on all models", p. 8) contradicts the paper's own Table VI (p. 9) for the two smaller Qwen models.
    81	- [I] The FAP test uses failure types derived from 2/3 of the same dataset (p. 8); split procedure and whether it is by page or by interaction is not stated.
    82	- [I] Fig. 9 "No failure" shares (about 36% for GPT-4o, about 40% for Claude, read from the figure, p. 9) look hard to reconcile with Usability Rates of 73–81% (p. 6); the denominators/definitions are not explained.
    83	- [I] The contamination argument (C4 has only text; BLEU 0.12–0.14, p. 5) is weak: C4 URLs' HTML is widely crawled elsewhere, and low BLEU does not rule out memorised layout.
    84	- [I] No code-quality, maintainability or code-structure measurement, despite generating JavaScript event logic.
    85	
    86	## 10. Threats to validity
    87	- Internal (confounds, leakage, selection): pages and interactions hand-picked by the authors' annotators (pp. 2–3); FAP failure types derived from the same benchmark (p. 8); Table VI direct baselines differ from Table IV (different subset), so improvements are relative to a subset [I].
    88	- External (generalisability of sample/context): 127 pages, front-end only, no back-end; mostly click-type interactions on buttons (235 of tagged elements) (p. 3); single-file output, not multi-file framework projects [I].
    89	- Construct (do metrics measure the concept?): visual metrics on changed regions approximate interaction fidelity; IR measures element presence; widget metrics admitted unreliable for web (p. 5) [I].
    90	- Statistical conclusion (power, multiple comparisons, variance): single deterministic run (temperature 0); no tests, CIs or agreement statistics; small N in sub-studies [I].
    91	- Reproducibility (data/code/setup reported?): data and code released (p. 1); prompts shown (p. 5); key guidelines and appendix only in the artifact; the PDF is arXiv v3 (1 Mar 2026), the ASE 2025 version may differ [I].
    92	
    93	## 11. Future research directions
    94	- Stated by authors [A]: iterative multi-round generation for many interactions; testing more MLLMs (e.g. Pixtral) (p. 11); handling interactions that require back-end code (p. 11); designing widget-level consistency detection suited to web pages (pp. 5–6).
    95	- Suggested by us [I]: validate interaction metrics against human usability with reported correlations; add behavioural assertions (DOM state, event sequences) and code-quality/maintainability analysis of generated JS; extend to multi-page apps with back-end.
    96	
    97	## 12. Relevance to our research
    98	- Research questions addressed (RQ ids): RQ1, RQ2, RQ4, RQ5 (RQ3 only by absence).
    99	- How it informs our work [I]: this is the closest web benchmark to reverse engineering from observable behaviour: input is before/after screenshots of interactions, and the target is a page that reproduces that behaviour. It supplies a usable failure taxonomy and the Usability Rate as a human functional-fidelity measure, but its automatic metrics are weakly validated and it ignores code quality.

    18	# ProgramBench: Can Language Models Rebuild Programs From Scratch?
    19	
    20	- Authors: Yang, John; Lieret, Kilian; Ma, Jeffrey; Thakkar, Parth; Pedchenko, Dmitrii; Sootla, Sten; McMilin, Emily; Yin, Pengcheng; Hou, Rui; Synnaeve, Gabriel; Yang, Diyi; Press, Ofir
    21	- Year / venue: 2026, arXiv (preprint, not peer-reviewed). Affiliations: Meta FAIR, Meta TBD, Stanford, Harvard (p. 1).
    22	- DOI: 10.48550/arxiv.2605.03546 · URL: https://arxiv.org/abs/2605.03546
    23	- Source text: `fulltext.txt` (page refs = PDF page index)

    28	## 1. Research objective
    29	- [A] Measure whether software-engineering (SWE) agents can develop whole programs "holistically", including the high-level architecture decisions that existing bug-fix or single-feature benchmarks do not test (p. 1; p. 2).
    30	- [A] Task: "given only a program and its documentation, agents must architect and implement a codebase that matches the reference executable's behavior" (p. 1).
    31	
    32	## 2. Research questions / hypotheses
    33	- Not stated as formal RQs. [I] Implicit questions: (1) can LMs rebuild real programs from an executable plus docs; (2) do generated behavioural tests capture the programs well enough to judge this; (3) how do model-written codebases and development trajectories differ from human ones; (4) how often do models cheat when allowed internet access.
    34	
    35	## 3. Methodology
    36	- Research design: [V] A benchmark built semi-automatically from open-source repositories, plus an evaluation of 9 LMs, two ablations (forced different language; internet access with cheating detection), test-suite validation (coverage, assertion strength) and descriptive analyses of codebases and trajectories (p. 3; p. 5; p. 7; p. 9).
    37	- Approach / model / intervention: [V] The agent receives the compiled gold executable (execute-only permissions, so it cannot be decompiled) and its usage documentation, inside a Docker container without internet. It must write source code in any language plus a build script that produces an executable with the same behaviour (p. 2; p. 4; p. 18). [V] The system prompt forbids obtaining source code, wrapping the binary, and decompiling or tracing it (strace/ltrace); only running the executable and reading the bundled docs is allowed (p. 19; p. 20).
    38	- Fidelity oracle: [V] Behavioural tests are generated by a SWE-agent (mini-SWE-agent with Claude Sonnet 4.5) that explores the program, its source code, existing tests and documentation. It harvests existing behavioural tests and iteratively adds tests that cover missing code paths, guided by line coverage (p. 3). Assertions target observable effects only: stdout/stderr content, exit codes and files produced (p. 2; p. 3). Weak tests are flagged by an assertion-quality linter and revised. Tests that do not pass the gold binary deterministically, or that pass a dummy binary, are discarded (p. 3; p. 27). The tests are never shown to the solving agent (p. 3).
    39	- Baselines or comparison conditions: [V] 9 LMs compared with each other; no human baseline ("we do not carry out any formal human studies") (p. 5; p. 20). For test quality, the generated suites are compared with the projects' native test suites (p. 7; p. 8).
    40	- [I] Relation to our topic: this is the closest design to black-box reverse engineering of an application. The agent observes the running program and its docs but not the source, and fidelity is judged by behavioural equivalence. The targets are CLI/TUI programs, not GUI or web apps.
    41	
    42	## 4. Dataset and sample
    43	- Data source(s): [V] 200 GitHub repositories in compiled languages that build a standalone executable: Rust 107, Go 46, C/C++ 45, other 2 (one Java, one Haskell). They range from small CLI tools to FFmpeg, SQLite, DuckDB, PHP and Lua (p. 2; p. 4).
    44	- Sample size (N) and unit: [V] 200 tasks; 248,853 test functions (median 770 per task, min 224, max 14,645) (p. 4). [V] 9 models x 200 tasks = 1,800 runs (p. 10); some analyses use 1,788 runs (p. 32). [V] Median codebase size 8,635 code lines (min 212, max 2,701,283) and 50 code files (p. 4). [V] Difficulty bins: Easy 28, Medium 143, Hard 29 (p. 31).
    45	- Sampling / selection method: [V] Filter for repositories that can produce a standalone executable, with compiled language as the heuristic. Repositories whose executable needs the internet are excluded; 18 networking tools are kept and tested over localhost (p. 3; p. 21). [I] How the 200 were chosen from the eligible pool (random, by stars, by build success) is not reported.
    46	- Data availability (public? link?): [A] Code at github.com/facebookresearch/ProgramBench, open-sourced (p. 1; p. 2).
    47	
    48	## 5. Experimental setup
    49	- Procedure, settings, hyper-parameters, tools: [V] mini-SWE-agent (bash-only minimal scaffold), vendor-default hyperparameters, 20 CPUs and 60 GB RAM per container, 1,000-step and 6-hour limits (p. 5), 3-minute per-action timeout, no cost limit, outputs truncated at 10,000 characters (p. 32). [V] Base image: Ubuntu 22.04 with Rust 1.92.0, Python 3.12, Go 1.21.0, a C/C++ toolchain and tmux for TUIs (p. 16). [V] Binary test assets that models cannot easily generate (images, audio, custom formats) are provided; standard text formats are not (p. 21; p. 22). [V] Before evaluation, all files matching the hash of the original executable are removed, and git history is wiped (p. 18; p. 19).
    50	- Number of runs: [V] One run per model-task (1,800 runs, p. 10). Repeats or seeds: not reported.
    51	- Code availability: [A] public (p. 1).
    52	
    53	## 6. Evaluation metrics
    54	- % Resolved: share of tasks where all tests pass and no cheating is flagged; the primary metric (p. 5).
    55	- % Almost: share of tasks with ≥95% of tests passing (p. 6).
    56	- % Tests Passed: per-task pass fraction. The authors say it is "only meaningful for relative comparisons" and "does not reliably correlate with percentage of working functionality" (p. 5).
    57	- Test-suite quality: line coverage of the original binary versus native suites; dummy pass rate (share of tests that a trivially wrong program passes) (p. 7; p. 8).
    58	- Code structure (descriptive): lines of code, number of files, maximum directory depth, function count and average function length, compared with the reference, for runs passing ≥75% of tests (p. 8; p. 9).
    59	- Trajectory metrics: action types (read/write/probe/execute/git) classified by keyword matching; edit counts; share of code written in the single largest edit (p. 9; p. 10).
    60	- Cheating rate: majority vote of 9 LM judges (p. 6; p. 17).
    61	- Statistical testing (tests used, significance, effect sizes, confidence intervals): [V] No significance tests or confidence intervals. The paper reports Pearson correlations of pass rate with API calls (r = 0.27) and cost (r = 0.21) (p. 33) and Fleiss' κ for judge agreement (p. 17). [I] The statement that "test pass rates are significantly different between models" (p. 2) is not backed by any reported test.
    62	
    63	## 7. Key findings
    64	1. [V] No model resolves any task (0% resolved for all 9). Claude Opus 4.7 reaches ≥95% of tests on 3.0% of tasks, Opus 4.6 on 2.5%, Sonnet 4.6 on 1.6%, and all others on 0% (p. 6).
    65	2. [V] Macro-averaged test pass rates: Opus 4.6 52.0%, Opus 4.7 51.2%, Sonnet 4.6 48.5%, GPT 5.4 38.3%, Gemini 3.1 Pro 36.6%, down to GPT 5 mini 15.9%. Rates fall from Easy to Hard for every model, e.g. Opus 4.6 from 73.9% to 24.7% (p. 31).
    66	3. [V] Across all runs, the median pass rate is 32%; about 18% of runs fall in the 0–5% bin, and fewer than 5% exceed 90% (p. 32). C/C++ tasks average 27.7%, against 38.5% for Rust and 38.4% for Go (p. 33).
    67	4. [V] Generated test suites average 79.7% line coverage (median 86.2%), against 56.8% (median 64.3%) for native suites, over 100 sampled repositories. Against 12 dedicated behavioural/integration suites, coverage is 62.16% versus 66.11% (p. 7; p. 8).
    68	5. [V] The assertion linter cut the mean dummy pass rate from 18.5% to 3.7%, and the stricter tests were 20–30 percentage points harder to pass without changing the model ranking (p. 8; p. 23).
    69	6. [V] Models chose the reference language in exactly 50% of runs. Python was the most common choice overall (36% of 1,800 runs) (p. 8).
    70	7. [V] Among 207 runs passing ≥75% of tests (88 tasks), model code had a median of 1,173 lines against 3,068 for the reference, 3 files against 15, and maximum directory depth 1 against 2. 60% of solutions had 1–3 code files, and 67% were shallower than the reference (p. 9).
    71	8. [V] Models write 10–29% as many functions as the reference, and their functions are longer (e.g. Gemini 3.1 Pro 1.62x, Sonnet 4.6 1.46x, GPT 5.4 1.08x average length) (p. 8; p. 9).
    72	9. [V] Development styles differ widely. Sonnet 4.6 issues a median of 868 commands per task, GPT 5.4 17 (p. 9). GPT 5.4 writes nearly all its code in one turn and makes 1.2 file modifications per trajectory on average, with 39.5% of trajectories making none (p. 10; p. 11). Probing the executable is the second-largest action category, at 22.6–34.1% of turns (p. 10).
    73	10. [V] More turns or money do not reliably help: per-run correlation with pass rate is r = 0.27 for API calls and r = 0.21 for cost, driven mostly by between-model differences (p. 33).
    74	11. [V] Forcing a different implementation language lowered Opus 4.7 (−8.0%) and Opus 4.6 (−3.5%) but raised each GPT model by 4.2%; the share of Python rose to 51% (p. 6; p. 7).
    75	12. [V] With internet access, 20–36% of tasks were flagged as cheating for the three stronger models tested (1% for GPT 5 mini), mostly source-code lookup (79–95% of flags). Judges disagreed on many tasks, with pooled Fleiss' κ = 0.57 over 786 tasks (p. 6; p. 7; p. 17).

    77	## 8. Limitations stated by the authors
    78	- [A] A finite test suite under-approximates the executable's full specification, so evaluation is a "lower bound" on correctness: passing solutions may still differ on untested inputs (p. 12; p. 3).
    79	- [A] Only input-output equivalence is tested. Non-functional properties (speed, memory, disk footprint) are not, so a passing solution could be far slower or more resource-hungry (p. 12).
    80	- [A] Only a single-agent baseline is evaluated; multi-agent and human-in-the-loop settings are left for future work (p. 12).
    81	- [A] Distinguishing meaningful behaviour from implementation artefacts is subjective. The gold executable is treated as the complete specification, and 5 tasks are at risk of implementation-dependent output (p. 26).
    82	- [A] No formal human study of feasibility; solvability is argued theoretically (Church–Turing) and from the observable, deterministic tests (p. 20).
    83	- [A] Cheating detection with LM judges is unreliable, so internet access is blocked by default (p. 6; p. 19).
    84	
    85	## 9. Limitations we identified
    86	- [I] Possible test-oracle bias. The test-writing agent had full access to the source code (p. 21) and used Claude Sonnet 4.5 (p. 3). The behaviours it chose to test may favour what a source reader finds salient, and same-family models (Claude) top the leaderboard (p. 31). The paper does not test for this.
    87	- [I] "Agent-driven fuzzing" (p. 1) overstates the method. The tests are LLM-written, coverage-guided pytest cases (p. 3; p. 23), not randomised input fuzzing. Coverage is high, but semantic coverage of edge cases is unknown.
    88	- [I] Contamination is only partly controlled. No-internet stops lookup, not memory. Many targets (FFmpeg, SQLite, jq, ripgrep) are famous and widely present in training data, and models can identify the program from `--help` output (p. 17). The different-language ablation (p. 5; p. 6) is the only memorisation probe, and its mixed results do not settle the question.
    89	- [I] Code-quality evidence is thin. Only size and structure statistics are reported (LoC, files, depth, function count and length) (p. 9), with no maintainability index, smells, duplication, tests, documentation or readability. These are computed only on runs passing ≥75% of tests, a selected subset, and are confounded by language changes: Python rewrites of C code are naturally shorter (p. 35). "Monolithic" is shown, but whether it is worse for maintenance is not measured.
    90	- [I] Single run per model-task (p. 10) with vendor-default sampling (p. 5), so run-to-run variance is unknown. Differences between closely ranked models (e.g. Opus 4.6 52.0% vs Opus 4.7 51.2%, p. 31) cannot be separated from noise.
    91	- [I] Small internal inconsistencies:
    92	  - 1,800 runs (p. 10) vs 1,788 runs (p. 32);
    93	  - median tests per task 770 (p. 4) vs 750 (p. 23);
    94	  - the Fig. 12 boxplot shows Sonnet 42% and Gemini 51%, the text says 44% and 53%, and the caption says GPT 5.4 writes "a median of 96%" while the text says 100% (p. 10);
    95	  - "best model" is Opus 4.7 by % almost (p. 6), but Opus 4.6 has the higher mean pass rate (p. 31).
    96	  
    97	  None changes the conclusions, but they lower confidence in exact figures.
    98	- [I] The main metric (% resolved) is all-or-nothing and saturates at 0% for every model (p. 6), so it cannot rank models; the paper relies on the softer metric that it itself says is only relative (p. 5).
    99	- [I] Tasks are CLI/TUI programs; GUI, web or mobile apps are not covered, so UI and visual fidelity are untested.
   100	
   101	## 10. Threats to validity
   102	- Internal (confounds, leakage, selection): [V] Leakage controls: separate build and inference containers, execute-only binary, wiped git history, no internet, hash-based removal of the original binary (p. 18; p. 19). [I] Remaining threats: pretraining memory of famous programs; test generation by a same-family model with source access; the provided test assets may hint at tested behaviours (p. 21).
   103	- External (generalisability of sample/context): [I] Compiled-language CLI/TUI programs; a minimal single-agent scaffold, unlike practitioners' vibe-coding tools with rich IDE context and human steering (p. 5; p. 12).
   104	- Construct (do metrics measure the concept?): [I] Behavioural equivalence on observable stdout/stderr/exit codes/files is a strong operational definition of functional fidelity for CLIs. The authors admit, however, that % tests passed does not track the share of working functionality (p. 5), and that untested inputs remain (p. 12). Code-structure metrics are size measures, not quality measures.
   105	- Statistical conclusion (power, multiple comparisons, variance): [I] One run per cell; no CIs or tests; large N (200 tasks) partly offsets this for model-level means, but not for per-task claims.
   106	- Reproducibility (data/code/setup reported?): [V] Harness configuration, prompts, linter rules and the full repository list are reported (p. 19; p. 27; p. 32; p. 36). [A] Benchmark open-sourced (p. 2).
   107	
   108	## 11. Future research directions
   109	- Stated by authors [A] (p. 12):
   110	  - richer test generation that improves coverage and adds system constraints (speed, memory);
   111	  - multi-agent approaches to long-horizon coding;
   112	  - human-centred agents, where a developer guides design decisions while the agent works from the executable;
   113	  - using the pipeline to generate training data (p. 5).
   114	- Suggested by us [I]:
   115	  1. Add maintainability measures (complexity, smells, duplication, modularity, ease of change) to the rebuilt codebases, and compare across languages.
   116	  2. Repeat runs to estimate variance.
   117	  3. Generate tests with several model families to check oracle bias.
   118	  4. Extend the same black-box protocol to GUI/web applications, where observable behaviour includes visuals and interaction.
   119	
   120	## 12. Relevance to our research
   121	- Research questions addressed (RQ ids): RQ1, RQ2, RQ3, RQ4, RQ5.
   122	- How it informs our work [I]: This is the most direct evidence on our core scenario: an agent rebuilding software only from the running artefact and its documentation, judged by behavioural equivalence. It gives (a) a concrete protocol for black-box reconstruction with leakage controls, (b) an oracle-construction method with measured coverage and assertion strength, and (c) evidence that rebuilds diverge structurally from human code (monolithic, few files, long functions). It does not measure maintainability as such, does not cover GUIs, and has no human-in-the-loop condition. These three gaps sit directly on RQ3 and RQ5.
