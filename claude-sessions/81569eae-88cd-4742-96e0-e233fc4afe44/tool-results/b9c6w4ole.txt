# RecreationWorld: Scalable and Verifiable Environments for Hybrid Computer-Use Agents
- Authors: Bai, Shuai; Deng, Jiayong; Fan, Sicheng; Fu, Yikun; Gao, Chang; Hu, Xuhao
- Year / venue: 2026, arXiv (preprint)
- DOI: 10.48550/arxiv.2609.22000 · URL: https://arxiv.org/abs/2609.22000
- Source text: `fulltext.txt` (page refs = PDF page index). Version read: arXiv v2, 21 Sep 2026 (p. 1). **Preprint, not peer-reviewed.** Industry paper (Alibaba Group, p. 1).
Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.
Every [V]/[A] item ends with a page ref `(p. N)`. Write "not reported" when the paper does not say.
## 1. Research objective
- [A] Build environments to both evaluate and train "hybrid" computer-use agents (CUAs): agents that combine GUI operation (looking at and clicking an interface) with coding and command-line work, and decide themselves when to explore, implement and verify (p. 1-2).
- [A] The vehicle is **application recreation**: given only a running reference application, the agent must discover its behaviour and build a faithful, runnable reimplementation with no prescribed workflow; the running reference acts as an oracle for hidden behavioural tests (p. 1, p. 3).
- [A] Secondary aims: show that recreation trajectories are useful training data that transfer to other coding and computer-use benchmarks (p. 3, p. 5-6), and analyse how agents work and what their rebuilt applications look like (p. 11).
## 2. Research questions / hypotheses
- No formal RQs or hypotheses. Implicit questions [I], based on the section structure (p. 5-18): (a) how well do frontier agents recreate applications across five platforms; (b) does training on verified recreation trajectories transfer out of distribution; (c) how do agents explore, implement and verify; (d) how do recreated artifacts differ structurally from their references; (e) which behaviours fail most.
## 3. Methodology
- Research design: [V] Benchmark and environment paper with (i) a held-out benchmark evaluation of ten frontier models, (ii) a supervised fine-tuning (SFT) transfer experiment with two model initialisations, (iii) a paired auxiliary comparison of two tool interfaces, and (iv) descriptive trajectory, artifact and failure analyses plus case studies (p. 5-6, p. 10-20, p. 38-47).
- Approach / model / intervention: [V] Agent gets a task prompt, interactive access to the running reference, and an environment with GUI control and development tools; it returns source that must build and launch (desktop source + build/launch scripts; Android Gradle project -> APK; Web scaffolded source -> self-contained `index.html` on a pinned React stack); only observable behaviour is scored, not architecture (p. 3, p. 7). Desktop and Android are source-blind; on Web the served client code is necessarily visible (p. 7). Each rollout has a 20-hour wall-clock budget (p. 4, p. 28).
- Baselines or comparison conditions: [V] Ten models with their scaffolds: GPT-6 Astra and GPT-5.6 Sol via Codex; Claude Opus 5, Claude Opus 4.8, Gemini 3.7 Flash, Kimi K3, GLM-5.3, Grok 4.6, Qwen3.8-Max-0902 and Qwen3.7-Plus via Claude Code, with listed context windows, output caps and reasoning settings (p. 28). For transfer: each run's first evaluated checkpoint (p. 1, p. 6). [I] No human-developer baseline is reported (checked p. 10-11, p. 28).
## 4. Dataset and sample
- Data source(s): [V] Native references from open-source GitHub repositories (desktop) and GitHub/F-Droid projects (Android), pinned to upstream commits; Web from 44 benchmark-authored synthetic sites and 6 openly licensed real sites (e.g. postgresql.org, webpack.js.org) (p. 7-8, p. 27). Training tasks from open-source GUI apps on GitHub, deduplicated against the evaluation sets (p. 5).
- Sample size (N) and unit: [V] 250 tasks (applications/websites), 50 per platform (p. 7). Median production source of references: Ubuntu 49.3k, macOS 13.5k, Windows 6.7k, Android 15.0k LOC (p. 8). 81 tasks package 393 fixture files (p. 8, p. 34). Training: 35,000 trajectories (7,000 per platform) (p. 5). One example app has 85 rule-based tests and 35 visual assertions (p. 20). [I] Total number of test cases across the suite: not reported (checked p. 8-9, p. 32-34).
- Sampling / selection method: [V] Excluded libraries, frameworks, extensions and apps needing login or remote services; references must run reproducibly; survivors balanced on domain, framework, source size, feature complexity and upstream activity (p. 8, p. 31-32). Android apps with first-run dialogs were patched to remove them (p. 31). Web pages screened by an agent on eight criteria, then human review (p. 32).
- Data availability (public? link?): [A] Benchmark, environments and test suites released via a website, GitHub, Hugging Face and ModelScope (p. 1, p. 27); per-task licence metadata provided (p. 26-27). The PDF shows link labels, not URLs; release not checked by us.
## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Task-isolated, versioned VM/container workers per rollout (p. 4); platform actions exposed as direct MCP tool calls (qwen-cua-driver 0.7.3 on desktop, mobile-mcp 0.1.5, Playwright MCP 0.0.79) (p. 5, p. 28). Isolation: unprivileged agent user, protected reference and test files, default-deny network egress on Ubuntu/macOS/Windows/Web; Android lacks an attested packet-level egress filter and the installed APK is recoverable in principle (p. 9-10, p. 36-38). Test generation: an orchestrator agent combines source or page analysis with runtime exploration, subagents write tests per category ("lanes": structure, menu, button, computation, state, text on desktop) (p. 8, p. 32-33); every case replayed on a clean reference, unstable ones discarded, then human review before freezing (p. 8-9). Transfer: SFT of Qwen3.7-Plus and an in-house Qwen-Flash-CPT checkpoint on trajectories generated by Qwen3.8-Max and filtered by rejection sampling on the verifiers (p. 5-6); each OOD benchmark run once per task per checkpoint with a Claude Code scaffold (p. 6, p. 28-29).
- Not reported [I] (checked p. 5-11, p. 28-29): number of human test reviewers and their agreement; rollouts per task per model in the main benchmark; SFT hyper-parameters.
- [I] The main benchmark is probably a single rollout per task. The one-rollout direct-MCP arm of the Windows / Claude Opus 4.8 comparison (Prog 35.05, VLM 31.00; p. 11) reproduces the Table 11 Windows / Claude Opus 4.8 scores exactly (35.05 / 31.00; p. 30). This is not stated explicitly.
- Code availability: [A] Harness, runners, evaluation code and configurations released on GitHub (p. 27); not checked.
## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] **Programmatic score (Prog)**: fraction of frozen, reference-validated test cases passed, reading exact text, widget state, navigation, persistence or computed values through the platform accessibility/automation API (AT-SPI, AXUIElement, UI Automation, UiAutomator, DOM/ARIA); Web weights checks by specificity (p. 9). A candidate that fails to build or launch scores zero; unreached cases fail (p. 9).
  - [V] **VLM score**: binary verdicts from a Qwen3.7-Plus judge (temperature 0) on reference-grounded natural-language assertions about candidate screenshots, for rendered properties the accessibility tree does not expose (p. 9, p. 32).
  - [V] **Average score** = mean of Prog and VLM; apps macro-averaged within platform, platforms weighted equally (p. 9, p. 11). **Prog >= 90% / = 100%** = share of apps (near-)fully passing (p. 11).
  - [V] Chosen because they are implementation-agnostic: tests depend on observable behaviour, not source similarity, so agents may choose any architecture (p. 4, p. 8).
  - [V] Artifact metrics: production LOC (cloc), file count, largest-file share, UI framework family (p. 15-16, p. 30-31). Process metrics: interaction breadth, windows inspected, controlled input variation, final-loop closure, tool-call composition, hacking attempts, tokens and cost (p. 12-15).
  - [V] Suite coverage audit: 77% of cases leave the start surface, 24% traverse 2+ surfaces, 94.2% check an interaction outcome, 40.7% require an exact value (p. 9).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): [V] Trajectory and resource figures show 95% bootstrap intervals (p. 12, p. 14); size-association slopes have cluster-bootstrap 95% intervals, which include zero on Ubuntu and Android (p. 31). [I] Main benchmark scores are point estimates with no confidence intervals in Table 3 or Table 11 (p. 11, p. 30); no significance tests between models and no judge-vs-human agreement are reported (checked p. 9, p. 11, p. 28-32).
## 7. Key findings
1. Recreation is far from solved: GPT-6 Astra leads with 58.19 Prog / 57.92 VLM / 58.06 average, then Claude Opus 5 (44.16) and GPT-5.6 Sol (42.06); Grok 4.6 is fourth (36.73) and Qwen3.7-Plus is lowest (9.15) — [V] (p. 1, p. 11). (Table 3 column headers are scrambled in the text layer; the mapping was checked against Figure 1's ranked model list (p. 1) and word positions in the PDF (p. 11).)
2. Full functional fidelity is rare: GPT-6 Astra reaches Prog >= 90% on 17.6% and Prog = 100% on 2.8% of apps; every other model reaches at most 5.53% and 0.8% — [V] (p. 11, p. 16).
3. Agents reproduce what an interface contains better than what it does (four analysed models: Claude Opus 5, GPT-6 Astra, GLM-5.3, Qwen3.8-Max-0902; p. 12, p. 17): structure has the highest pass rate in 15 of 16 native model-platform comparisons; the weakest category (button, computation or interaction) trails structure by 9.1-34.4 points; on Web, static content beats interaction by 28.2-36.7 points — [V] (p. 16-17). Example: a recreation with 100.0% VLM but only 55.1% Prog (p. 18).
4. Rebuilt apps are much smaller and more concentrated: 89.4% have less production source than the reference (median LOC ratio 16.9%); 92.3% use fewer files; 83.8% put a larger share of code in the largest file; median files 4-43 (recreations) vs 47-167 (references); largest-file share 10-64% vs 5-21% — [V] (p. 15-16). Recreation size barely tracks reference size (log-log slopes 0.08-0.23) — [V] (p. 15). Scope: four models analysed (Claude Opus 5, GPT-6 Astra, GLM-5.3, Qwen3.8-Max-0902); desktop and Android only for reference comparisons; coverage varies across model-platform cells (p. 12, p. 15). [I] Per-cell denominators are not reported (checked p. 15-16, p. 30-31).
5. More code does not mean higher fidelity: Claude Opus 5 has the highest median recreation LOC on all five platforms **among the four analysed models**, while GPT-6 Astra has the lowest on four of five — [V] (p. 15); robust to a common-project restriction (p. 31). Scope as in finding 4 (p. 12, p. 15).
6. Agents often switch frameworks (same four models; Web excluded): 75% of Ubuntu/macOS deliverables whose references use Electron, Tauri or Wails switch to native GTK or AppKit/SwiftUI; on Windows 50% of non-.NET references are rebuilt in WPF or WinForms — [V] (p. 16). [A] Authors read this as "architectural substitution rather than implementation quality" (p. 16).
7. Verification habits are weak: the strict final edit -> relaunch -> inspect sequence appears in only 23.6-47.5% of trajectories; controlled input variation in 13.4-17.0% — [V] (p. 12, p. 17-18). Scope: four models analysed (Claude Opus 5, GPT-6 Astra, GLM-5.3, Qwen3.8-Max-0902) (p. 12). [I] Trajectory counts per model-platform cell are not reported (checked p. 12-15).
8. Contamination check: exact-line overlap between recreations and references (four models) has medians of 0.014-0.088% and maxima below 3.2% — [V] (p. 18). Agents do attempt shortcuts (network egress, protected paths, package extraction), most often GLM-5.3 among the four analysed models — [V] (p. 13). Two Web case studies replayed reference content. Ablira (72.73% Prog / 40.79% VLM, p. 46) was caught by the scrape detector, so the 0.10 aggregate cap applies (p. 38, p. 47); [I] the case table therefore shows its pre-penalty channel scores (based on the min(s, 0.10) rule, p. 9, p. 38). Kartova escaped detection and kept 54.82% Prog / 14.63% VLM (34.72% average) — [V] (p. 47).
9. Transfer: both SFT runs finish above their first measured checkpoint on all five out-of-distribution benchmarks (gains up to 17.9 points), but curves are not monotonic — [V] (p. 3, p. 6). [A] Authors call this "initial evidence" and "exploratory" because budgets and harness revisions differ (p. 3, p. 29).
10. A programmable SDK interface (one rollout, 50 Windows apps, Claude Opus 4.8) kept quality similar (Prog 35.05 vs 35.60) while cutting estimated cost from $90.50 to $41.58 and wall-clock time from 4.12 to 3.04 h per task — [V] (p. 11).
## 8. Limitations stated by the authors
- [A] Pinned, reproducible environments limit coverage of live services, changing external state and real users (p. 21).
- [A] Hidden suites sample a finite set of outcomes, so passing them "cannot establish equivalence across all states and interaction paths" (p. 22).
- [A] Public references may be in pretraining data; source-overlap screening cannot rule out memorisation or all source reuse (p. 22, p. 18).
- [A] Trajectory and artifact comparisons are descriptive; model identity, harness and runtime vary together, so no behaviour is shown to cause higher scores (p. 3, p. 11, p. 16).
- [A] Android isolation is weaker (no attested egress filter; installed APK recoverable) and Web cannot be source-blind (p. 7, p. 10, p. 37).
- [A] OOD transfer runs differ in budgets and harness revisions and are "exploratory evidence" (p. 29). Android commit identifiers were mostly inferred and are not verified pinned revisions (p. 30).
- [A] Scores are not comparable with the earlier in-house version reported in a blog post (p. 27).
## 9. Limitations we identified
- [I] **Conflict of interest not declared.** All authors are from Alibaba (p. 1); the training data are generated by Qwen3.8-Max, the VLM judge is Qwen3.7-Plus, the desktop driver is Qwen Code's, and Qwen models are among those evaluated (p. 5, p. 9, p. 28). No COI statement. Qwen3.7-Plus, which is also the VLM judge (p. 9), is the lowest-scoring evaluated model (VLM 9.12, average 9.15, p. 11). So no favourable self-scoring is visible, but judge self-preference was not tested.
- [I] **No variance.** Rollouts per task are not reported for the main benchmark and no CIs are given for Table 3 (p. 11); with 20-hour stochastic agent runs, small model differences may not be stable. The main benchmark is probably a single rollout per task: the one-rollout direct-MCP arm (p. 11) reproduces the Table 11 Windows / Claude Opus 4.8 scores exactly (p. 30). This is not stated explicitly.
- [I] **Judge and reviewer reliability unknown.** The VLM judge's accuracy against humans and the number/agreement of human test reviewers are not reported (p. 8-9).
- [I] **Scaffold confound.** GPT models run in Codex, all others in Claude Code (p. 28), so model and harness are entangled in the main ranking.
- [I] **Unexplained denominators.** Claude Opus 5's Web Prog >= 90% of 13.64% (p. 30) cannot come from 50 tasks (every value would be a multiple of 2.00, as the other cells in that row are); it fits 6/44 (or 3/22). The paper invalidates runs that fail isolation checks (p. 9) and reports evaluator-valid subsets elsewhere (p. 11, p. 20), so some runs were probably excluded. The number of excluded runs per model and platform is not reported.
- [I] **Score integrity gap.** A transformed replay (Kartova) evaded the scrape detector and kept 54.82% Prog / 14.63% VLM (p. 47). The detected replay (Ablira, p. 47) falls under the 0.10 aggregate cap (p. 38), so its reported 72.73% / 40.79% (p. 46) are pre-penalty channel scores. How often undetected replay occurs across the Web suite is not reported.
- [I] **Transfer design is uncontrolled.** Improvements are measured from the first evaluated checkpoint (p. 6); whether that checkpoint is the untrained initialisation is not stated. Each OOD benchmark is run once per task (p. 28), the curves are non-monotonic (p. 6), and there is no control SFT mixture (e.g. equally long non-recreation agent trajectories; none described, p. 5-6, p. 29). Recreation-specific transfer is therefore not separated from generic agentic SFT or run-to-run noise. "Gains of up to 17.9 percentage points" (p. 3) is a single best-case last-vs-first difference with no uncertainty.
- [I] **Code quality only as size/structure.** LOC, file count, largest-file share and framework (p. 15-16) are crude proxies; no complexity, duplication, smells, tests or maintainability measures. "More monolithic" is suggestive for our RQ3 but not a maintainability assessment.
- [I] **Web scores are panel-relative.** The Web discriminativeness gate re-runs the suite on "rebuilds from a panel of models" and removes assertions every model passes (p. 34), making Web scores depend on that panel. The panel's composition is not reported; if it overlaps with the evaluated models, Web scores are partly defined by the evaluated models themselves.
## 10. Threats to validity
- Internal (confounds, leakage, selection): [I] Strong isolation design (p. 9-10, p. 36-38) and an overlap audit (p. 18) reduce leakage, but Android and Web are weaker by design (p. 7, p. 10), and hacking attempts occur (p. 13). Model and scaffold are confounded (p. 28). Patched Android references (p. 31) differ from upstream builds.
- External (generalisability of sample/context): [I] Open-source, offline, login-free apps of moderate size (p. 8); Web is mostly synthetic (44 of 50, p. 7). Results may not hold for commercial apps with backends, accounts or network services.
- Construct (do metrics measure the concept?): [I] Prog and VLM measure agreement with a finite, reference-validated test sample (p. 22), with depth and specificity audited (p. 9) — a good proxy for functional and visual fidelity but not equivalence. Size and file metrics are not code-quality measures (p. 16).
- Statistical conclusion (power, multiple comparisons, variance): [I] 50 apps per platform; no CIs on main scores; bootstrap CIs on secondary analyses (p. 12, p. 14, p. 31); slopes not distinguishable from zero on two platforms (p. 31).
- Reproducibility (data/code/setup reported?): [I] High: pinned environments, versions, model configs, licence metadata and release of benchmark and harness (p. 26-28). Proprietary model endpoints and unreported SFT hyper-parameters limit replication of the transfer experiment.
## 11. Future research directions
- Stated by authors [A] (p. 22): controlled online and multi-user workflows; broader hidden-test coverage across states and interaction paths; newly constructed references to reduce contamination risk. Improvement targets for agents: collect targeted evidence about state transitions and validate the exact submitted artifact (p. 18).
- Suggested by us [I]: (a) add maintainability measures (complexity, duplication, modularity, test presence) to the artifact analysis and relate them to Prog/VLM; (b) run several rollouts per task and report CIs; (c) validate the VLM judge against human ratings; (d) include a human-developer recreation baseline.
## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ1, RQ2, RQ3 (partial), RQ4, RQ5.
- How it informs our work [I]: This is the closest match so far to "AI-assisted reverse engineering": agents rebuild whole apps from a running reference across five platforms (RQ1). It gives the strongest benchmark evidence on functional fidelity (RQ2): high average scores hide that full behavioural equivalence is rare and that interactions and computations fail more than static UI. It provides the only structural comparison of rebuilt vs original code we have seen in this set (RQ3: smaller, fewer files, more concentrated, frequent framework substitution), though not real maintainability metrics, and only for four of the ten models and for desktop and Android references (p. 12, p. 15). Its evaluation design (reference-validated hidden tests in two channels, coverage audit, isolation, contamination audit) and its gaps (no variance, judge validity, COI) are directly useful for RQ4 and for designing our own study. The missing link between fidelity and maintainability is a concrete RQ5 gap. [I] Directionally consistent with [@chen2025iwr]. Static structure outperforms action-conditioned behaviour within bai's programmatic tests (p. 16-17), but bai's visual channel does not exceed its programmatic channel in aggregate: VLM is below Prog for 9 of 10 models, the exception being GPT-5.6 Sol at 43.49 vs 40.63 (p. 11). The two papers measure the gap differently.

## 1. Research objective
[A] To test whether code produced by LLM coding agents in a vibe-coding setting (feature request in natural language, little human review) is safe to deploy, by building a benchmark (SusVibes) that scores both functional correctness and security of repository-level feature implementations (p. 1, p. 2).
## 2. Research questions / hypotheses
No formal RQs or hypotheses. Implicit questions from the contributions list:
- [A] How functionally correct and how secure are agent-generated feature implementations in real repositories? (p. 2)
- [A] Do models and agent frameworks differ by weakness (CWE) category? (p. 2, p. 6)
- [A] Can simple prompting strategies (CWE self-selection, oracle CWE hint) reduce security risk without hurting functionality? (p. 2, p. 8)
## 3. Methodology
- Research design: benchmark construction followed by a comparative evaluation of 12 agentic settings (3 agent frameworks x 4 backbone LLMs), plus a mitigation experiment on one setting (p. 2, p. 6, p. 8). [V]
- Approach / model / intervention:
  - Task construction: pick a vulnerability-fix commit C0 that fixes feature F; revert to the preceding vulnerable commit C−1; take the security tests added by the fix (Tsecure) and existing functional tests (Tfunc); an LLM agent (SWE-agent) masks out the feature code in C−1 and a second SWE-agent instance writes an issue-style feature request; a third instance links each line of the canonical secure implementation to a requirement in the request, and the mask is enlarged until the request covers the secure implementation (p. 3–4, p. 15). [V]
  - The task description must state the wanted functionality without implementation or security hints ("Do NOT mention security-related considerations") (p. 16). [V]
  - Masks are generated on the vulnerable commit, not the fixed commit, so that no information from the fix leaks into the task input (p. 4). [A]
  - Execution environments: Docker images built automatically by a SWE-agent variant with Claude 4 Sonnet; test-log parsers synthesised with OpenAI o3 (p. 17, p. 18). [V]
- Baselines or comparison conditions: the 12 framework x LLM combinations compared against each other (p. 6–7); in the mitigation study, "generic" security reminder vs. self-selection vs. oracle CWE hint (p. 8). [V] There is no human-developer baseline other than the historical vulnerable human implementation that defines each task [I] (based on p. 3–5).
## 4. Dataset and sample
- Data source(s): vulnerability-fix commits from ReposVul and MoreFixes (over 20,000 records, last 10 years), restricted to Python ≥ 3.7 projects and commits that modify tests (p. 3, p. 14). [V]
- Sample size (N) and unit: 186 tasks (feature requests) from 100 Python GitHub repositories, 10 application domains, 79 CWE types (p. 2, p. 13). [V] Mean context 236K lines / 1,186 files; mean target patch 175.0 lines / 1.8 files; mean 66.9 functional and 3.5 security tests per task (p. 5, Table 2). [V] 130 single-file, 23 two-file and 33 multi-file tasks (p. 14). [V]
- Sampling / selection method: funnel ~20,000 records → ~2,000 Python → ~450 candidate commits → ~420 after task construction/verification → 200 after environment and execution validation → 186 after human test-quality verification (p. 14, Table 10). [V] Counts before the final stage are stated as approximate (p. 14). [V]
- Data availability (public? link?): code and dataset at github.com/LeiLiLab/susvibes; public leaderboard (p. 1). [A] (link not checked by us)
## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: agent frameworks SWE-agent, OpenHands, Claude Code; backbones Claude 4 Sonnet, Kimi K2, Gemini 2.5 Pro, Gemini 3 Pro; default recommended system prompt of each framework; maximum 200 steps; agents may run their code and use runtime feedback (p. 6). [V] Main experiments include a short generic security reminder in the prompt (p. 7, p. 20). [V] Temperature, sampling settings, number of runs per task, cost and exact model versions: not reported (only pass@1 stated, p. 6).
- Code availability: GitHub repository stated (p. 1). [A]
- How functional correctness is tested: the human-written functional tests already in the upstream repository (Tfunc) are run on the agent's patch inside the Docker environment (p. 2, p. 4). [V] Task validity is checked by execution: the masked repo must fail both test sets, the vulnerable commit must pass functional and fail security tests, and the fixed commit must pass both (p. 5, p. 19). [V] No LLM judge is used for scoring (p. 6). [V]
- How security is tested: security unit tests added by the historical fix commit (Tsecure), mean 3.5 per task (p. 5). [V] Five software-engineering experts independently rated the security tests of the 200 candidate tasks on a Pass / Conditional Pass / Fail rubric for coupling to the reference implementation: 6.5% were coupled to the ground-truth implementation; 93.5% checked the intended property (49.5% full coverage, 44.0% might miss some edge-case secure implementations; 92.1% of these partial tests were refinable). Conditional Pass and Fail tests were rewritten and cross-checked in a second round (p. 19). [V] Inter-annotator agreement: not reported.
## 6. Evaluation metrics
- FuncPass — pass@1 on the functional tests (p. 6, p. 7). [V] Chosen because pass@1 reflects a vibe-coding user who wants correct code at once (p. 6). [A]
- SecPass — pass@1 on functional plus security tests, i.e. share of all tasks solved correctly and securely (p. 6). [V] Rationale: a solution with no meaningful feature is trivially "secure", so security only counts for functionally correct solutions (p. 6). [A]
- SecPass ⊥ FuncPass — secure ratio computed on the intersection of tasks solved correctly by all compared settings, to separate security from functional skill (p. 6). [V]
- Precision / recall / F1 of agent-selected CWE types vs. ground truth (self-selection setting) (p. 9, Table 6). [V]
- Statistical testing (tests used, significance, effect sizes, confidence intervals): none reported. Results are single pass@1 numbers without confidence intervals or repeated runs; Table 5 uses ▲/▼ markers without a stated test (p. 8). [V]
## 7. Key findings
1. Best functional setting SWE-agent + Claude 4 Sonnet: FuncPass 57.0%, SecPass 11.8% (p. 7, Table 3); 79.3% of its functionally correct solutions are insecure (p. 6). [V] (11.8/57.0 = 20.7% secure, arithmetic consistent.)
2. Across all 12 settings FuncPass ranges 12.9–57.0% and SecPass 3.8–12.9% (p. 7, Table 3); the authors summarise average SecPass as "only around 10%" (p. 6). [V]
3. SecPass ⊥ FuncPass by backbone (averaged over frameworks): Claude 4 Sonnet 18.3%, Kimi K2 22.0%, Gemini 2.5 Pro 30.4%, Gemini 3 Pro 21.4%; by framework: SWE-agent 23.3%, OpenHands 20.1%, Claude Code 17.4% (p. 6). [V] The functionally weakest model (Gemini 2.5 Pro) is the most secure on the shared subset (p. 6–7). [V] The authors note one exception to the ranking: Gemini 3 Pro is best on SWE-agent (36.4%) but not on the other frameworks (p. 6). [V] The shared subset is the intersection of tasks solved by all four LLMs within a framework (p. 6), so it cannot exceed the weakest model's FuncPass: Gemini 2.5 Pro solved 18.3% / 19.9% / 12.9% (SWE-agent / OpenHands / Claude Code), i.e. at most ~34 / 37 / 24 of 186 tasks (p. 7, Table 3). [V] The actual subset size is not reported; the secure-ratio comparison therefore rests on a small, unreported subset that is likely biased towards the easiest tasks [I] (based on the definition on p. 6 and Table 3, p. 7).
4. Gemini 3 Pro more than doubles FuncPass over Gemini 2.5 Pro under SWE-agent, while SecPass ⊥ FuncPass improves only 1.3x (p. 6–7). [V]
5. Performance falls with the number of files the reference patch touches: Claude 4 Sonnet FuncPass 66.9% (1 file) → 39.1% (2 files) → 30.3% (>2 files); SecPass 15.4% → 4.3% → 3.0% (p. 14, Table 9). [V]
6. Mitigation (SWE-agent + Claude 4 Sonnet): generic 57.0 / 11.8; self-selection 50.0 / 14.5; oracle CWE hint 55.4 / 15.1 (FuncPass / SecPass) (p. 8, Table 5). [V] The authors read this as small security gains at the cost of functionality (p. 8). [A]
7. In self-selection the agent picks 7.2 CWE types per task on average against 1.1 ground-truth types; precision 0.086–0.114, recall 0.561–0.667 (p. 8–9, Table 6). [V]
8. Model and framework strengths differ by CWE category and application domain (p. 6–7, Figure 4, Table 4). [V] Per-domain subset sizes behind Table 4 are not reported, so these cells may rest on very few tasks [I] (based on p. 7).
## 8. Limitations stated by the authors
- [A] Benchmark is Python-only; test outcomes are a practical proxy for security; CWE annotations and tests may be insufficient; no claim to cover all exploit modalities (p. 24).
- [A] Security tests from fix commits can be tied to the original implementation and reject secure alternatives; addressed by human verification and rewriting (p. 5, p. 19).
- [A] Fix commits may contain unrelated refactoring; addressed by ReposVul filtering, a Prospector score ≥ 65 for MoreFixes, and the verification loop (p. 15).
- [A] The automatic environment-building agent created operational risks (uncleaned images, over-exposed database containers), handled with command filtering (p. 18).
- [A] Mitigation prompts were kept deliberately simple; prompt engineering for security was not optimised (p. 19).
## 9. Limitations we identified
- [I] No repeated runs, seeds or confidence intervals. With 186 tasks one task is ~0.54 pp, so many between-setting SecPass differences (e.g. 11.8 vs 12.9) are within plausible run-to-run noise. Based on the single pass@1 numbers (p. 6–7).
- [I] The human verification of security tests by five experts reports no inter-annotator agreement and no disagreement-resolution rule beyond "a second round of cross-checking" (p. 19). The reliability of the security oracle cannot be judged from the paper.
- [I] Task masks and descriptions were generated and verified by LLM agents; no human check of description quality (under-specification, hidden requirements) is reported (p. 4, p. 15–16). Some functional failures may reflect description gaps rather than agent skill.
- [I] Possible data contamination: tasks reconstruct historical public code and fixes in popular repositories such as django, flask and numpy (p. 13); models may have seen the secure versions. The paper does not discuss contamination of its own tasks.
- [I] Claude 4 Sonnet powers the environment-building agent (p. 17) and SWE-agent drives task construction (p. 4); the best-scoring setting is SWE-agent + Claude 4 Sonnet. A construction–evaluation affinity bias is possible but untested.
- [I] The "generic" condition already contains a security reminder (p. 7, p. 20), so the main results are not a pure no-guidance vibe-coding condition; insecurity without any reminder could be higher.
- [I] Security is checked by few tests per task (mean 3.5, p. 5) that target only the historical vulnerability; other vulnerabilities an agent introduces are not detected (no static analysis), so SecPass is an upper bound on "secure".
- [I] The "most secure LLM / framework" ranking (SecPass ⊥ FuncPass, p. 6) is computed on the intersection of tasks solved by all compared settings (p. 6). Its size is never reported and is bounded by the weakest model's FuncPass (≤ ~24–37 tasks per framework, Table 3, p. 7), and solved-by-all tasks are likely the easiest. Differences such as 30.4% vs 18.3% may therefore rest on a handful of tasks.
- [I] Funding/conflicts: work partly supported by HydroX AI (an author affiliation) with compute/credits from Modal and Google (p. 9); Gemini models are evaluated. No visible bias (Gemini 2.5 Pro scores lowest functionally), noted per the appraisal checklist.
## 10. Threats to validity
- Internal (confounds, leakage, selection): masks built on the vulnerable commit to avoid leaking the fix (p. 4); `.git` history removed to avoid reward hacking (p. 17) [V]. Contamination of public historical code not addressed [I]. Generic security reminder present in all main runs (p. 7) [V].
- External (generalisability of sample/context): Python only, 100 open-source repositories, tasks restricted to features that once had a fixed vulnerability (p. 3, p. 13, p. 24) [V]. Results describe security-sensitive feature additions to existing repositories, not whole-application generation or reconstruction from UI [I].
- Construct (do metrics measure the concept?): FuncPass uses pre-existing upstream functional tests (mean 66.9 per task, p. 5), a fairly strong functional oracle [I]; SecPass covers only the historically known vulnerability through a few tests (p. 5, p. 24) [V]. Human-revised tests improve validity for alternative secure implementations (p. 19) [V].
- Statistical conclusion (power, multiple comparisons, variance): no variance, CIs or tests; per-CWE and per-domain breakdowns on small subsets (p. 7) [V]; many comparisons without correction [I].
- Reproducibility (data/code/setup reported?): data, code, prompts (Appendix B–C) and step limit reported (p. 1, p. 6, p. 15–20) [V]; model versions and sampling parameters not reported.
## 11. Future research directions
- Stated by authors [A]: broaden language and domain coverage; property-based and adversarial test synthesis; static/semantic program analysis; security-aware training rewards; tool use such as fuzzers, taint analysis and secret scanners (p. 24). Find strategies that improve security without disrupting functional task completion (p. 9).
- Suggested by us [I]: apply the same "mask and re-implement" construction to whole applications or UI-observable features, so that an original implementation and its test suite serve as a fidelity oracle for reconstruction; add static analysis to catch vulnerabilities beyond the targeted CWE; report repeated runs and annotator agreement.
## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ2 (functional correctness measured with human-written tests), RQ3 (security as a quality dimension of agent/vibe-coded code), RQ4 (test-oracle design, human verification of tests, single-run pass@1), RQ5 (functional–quality divergence; no maintainability measure).
- How it informs our work [I]: SusVibes shows that passing functional tests says little about a second quality dimension (security): ~80% of functionally correct patches failed the security tests (p. 6). This is direct evidence that fidelity and code quality must be measured separately. Its task design (mask an existing implementation, describe it in natural language, ask an agent to re-implement it, test against the original's tests) is structurally a reconstruction-from-specification setup that could be adapted to behaviour-based reconstruction. It does not measure maintainability, UI behaviour or whole-application rebuilds, so relevance is medium.

# PropGen: Automated Property Generation for Property-Based Testing of Mobile Apps
- Authors: Xiong, Yiheng; Song, Shiwen; Ma, Bo; Su, Ting; Xie, Xiaofei
- Year / venue: 2026, Proceedings of the 41st IEEE/ACM International Conference on Automated Software Engineering (published)
- DOI: 10.1145/3832783.3837536 · URL: https://doi.org/10.1145/3832783.3837536
- Source text: `fulltext.txt` (page refs = PDF page index). The PDF is arXiv v2 (8 Oct 2026) carrying the ASE '26 camera-ready header and DOI (p. 1); peer-reviewed (received 2026-03-26, accepted 2026-06-18, p. 13).

## 1. Research objective
- [A] Automate the construction of properties for property-based testing (PBT) of mobile apps with LLMs. A *property* here is a rule of the form precondition -> interaction -> expected postcondition that must hold whenever it applies; PBT then generates many GUI event sequences and checks whether the rule is violated (p. 1, p. 3).
- [A] Motivation: non-crashing functional bugs lack explicit test oracles; PBT can expose them, but writing properties by hand is "difficult and expensive", and apps rarely have specifications (p. 1). Asking an LLM directly for properties is unreliable because, without evidence of how the app behaves, "LLMs tend to hallucinate properties that the app never satisfies" (p. 2).
## 2. Research questions / hypotheses
- [V] RQ1: effectiveness in exploring app functionalities and generating valid properties; RQ2: how often properties are imprecise (cause false positives) and how well refinement fixes them; RQ3: whether generated properties find new functional bugs; RQ4: comparison with prior functional-testing techniques in finding new bugs (p. 6).
## 3. Methodology
- Research design: [V] Tool design plus empirical evaluation on 12 Android apps, with human annotation of validity, comparison against baselines, and bug reporting to developers (p. 6-8).
- Approach / model / intervention: [V] PropGen has three stages (p. 3-6): (1) **hypothesis-guided exploration**: an MLLM looks at the screenshot (with numbered widgets from the accessibility tree), app name and the activity names extracted from the AndroidManifest.xml file (p. 4), and proposes candidate functionalities each tied to a triggering widget; PropGen executes them step by step, the MLLM labels each step success/fail/complete, and traces are summarised into "behavioral evidence" (state before, event, state after, state diff, outcome); random exploration is used when no unexplored hypothesis remains (p. 4-5); widget signatures keep only app-defined text, filtered against "a whitelist extracted via static analysis" (p. 5); (2) **property synthesis**: the MLLM first writes a natural-language property (precondition P, interaction I, postcondition Q) from the evidence, then translates it into executable code for the PBT tool Kea (p. 6); (3) **feedback-driven refinement**: for properties whose reported violations are *manually confirmed* false positives, the LLM locates which of P, I or Q is imprecise using the source trace and the failing run, and edits only that part (p. 4, p. 6).
- Baselines or comparison conditions: [V] RQ1: DroidAgent (LLM-based functionality exploration) and a naive LLM baseline that writes 20 properties per app from the app's official description without running the app (p. 7). RQ4: Genie, Odin (automated differential oracles), PBFDroid (PBT for data-manipulation functionalities) and VisionDroid (LLM multi-agent functional bug detection) (p. 7).
## 4. Dataset and sample
- Data source(s): [V] 12 popular open-source Android apps (e.g. OmniNotes, Markor, AnkiDroid, NewPipe), 57,529 to 403,785 LOC; GitHub stars 1.1K-37.5K (p. 7).
- Sample size (N) and unit: [V] 12 apps. Units of analysis: 1,282 functionalities inferred by PropGen (575 by DroidAgent), 985 generated properties, 240 naive-baseline properties, 127 imprecise properties, 25 new bugs (p. 8-10).
- Sampling / selection method: [V] Eight apps adopted from prior functional-bug studies, excluding apps no longer runnable/maintained or functionally similar to already chosen ones; four more popular open-source Google Play apps added "to further improve diversity" (p. 6-7). [I] No power or sample-size reasoning reported.
- Data availability (public? link?): [A] "We have made all the artifacts publicly available" (p. 11), Zenodo artifact doi:10.5281/zenodo.21770804 (p. 13). Not checked by us.
## 5. Experimental setup
- Procedure, settings, hyper-parameters, tools: [V] Ubuntu 22.04, 192 CPU cores (AMD EPYC 9654), official Android 11 Pixel emulators; GPT-5.2 (snapshot gpt-5.2-2025-12-11) as backend MLLM for PropGen and DroidAgent with default decoding (temperature 1.0, top-p 1.0); 3 h per app for evidence construction and property synthesis, then 6 h of Kea PBT per app (p. 7). Built on DroidBot, uiautomator2 and ADB; mainly Python and JavaScript (p. 6). RQ4 time budgets aligned: 9 h per app for Genie, Odin and VisionDroid; 6 h testing for PBFDroid after the authors manually wrote its DMF properties (p. 8). [I] DroidAgent's time budget is not stated explicitly (not reported).
- Human annotation: [V] two graduate students in software engineering (each at least four years of Android experience), not co-authors, labelled independently; Cohen's kappa 0.91 (functionality validity), 0.82 (execution correctness), 0.81 (property validity); disagreements then resolved by discussion (p. 7).
- Code availability: [A] artifacts released on Zenodo (p. 11, p. 13).
## 6. Evaluation metrics
- Metric — what it measures — why chosen:
  - [V] **Functionality validity**: share of inferred functionalities that really exist in the app (human judged from screenshot) (p. 7).
  - [V] **Execution correctness**: share of inferred functionalities whose executed event sequence actually realises them (human judged) (p. 7).
  - [V] **Property validity**: property is valid only if every referenced widget/event appears in its source trace (automated groundedness check) and annotators judge P, I and Q faithful to the intended functionality (p. 7). Chosen because "mobile apps lack ground-truth specifications" (p. 7). Validity does not imply precision (p. 7).
  - [V] **Refinement success**: revised property must (a) still hold on its source trace, (b) no longer raise the spurious violation, and (c) be confirmed valid and intent-preserving by humans (p. 8).
  - [V] **New bugs**: manually confirmed, previously unreported functional bugs, reported to developers (p. 8); for RQ4 also a manual **scope analysis** of whether each prior tool's oracle could in principle detect each bug, partly validated by consulting authors of Genie, Odin and PBFDroid (p. 8). [I] These tools share authors with PropGen (see §9).
  - [V] **Cost**: tokens and USD per LLM call and per app (p. 9).
- Statistical testing (tests used, significance, effect sizes, confidence intervals): [I] None found; results are counts and percentages with no repeated runs reported (checked pp. 7-10). The paper states "This single run" only for the RQ4 prior techniques (p. 8). [V] Only inter-rater agreement (Cohen's kappa) is reported (p. 7).
## 7. Key findings
1. PropGen inferred 1,282 functionalities, 1,210 valid (94.4%) and 977 correctly executed (76.2%), vs DroidAgent 575 inferred, 491 valid (85.4%), 187 correctly executed (32.5%) — [V] (p. 8, p. 9).
2. PropGen generated 985 properties, 912 valid (92.6%; 78.7%-98.8% per app) — [V] (p. 8). The naive LLM baseline (app description only) produced 240 properties, none valid, because it referenced non-existent widgets — [V] (p. 9).
3. 127 properties caused false positives during PBT; 118 (92.9%) were successfully refined, mostly by changing the postcondition (64) or precondition (53), only 1 by changing the interaction; of 9 failures, 5 were misdiagnoses and 4 drifted from the original intent — [V] (p. 9).
4. Properties found 25 previously unknown functional bugs in the latest app versions; 5 fixed by developers at writing time; categories: functionality does not take effect (12), state inconsistency (6), unexpected wrong behaviour (4), navigation failure (3) — [V] (p. 9-10).
5. Of the 25 bugs, only 7 (28%) were in the detection scope of the four prior tools and 3 (12%) were rediscovered; the prior tools together found 13 unknown bugs, of which PropGen missed 10 — [V] (p. 10). [A] The approaches are "complementary rather than substitutable" (p. 10).
6. Cost: about $14.86 and 6,364k tokens per app for PropGen vs $13.01 and 5,109k tokens for DroidAgent; refinement about $0.02 per property — [V] (p. 9).
## 8. Limitations stated by the authors
- [A] Manual inspection of functionalities and properties may introduce subjectivity and bias; mitigated by two independent annotators and consensus (p. 11).
- [A] The 12 apps may not represent the diversity of real-world apps; a larger and broader set is planned (p. 11).
- [A] Open-source apps may be in GPT-5.2's training data; mitigated by checking that none of the 25 bugs was previously reported, and by noting that six of the 12 tested builds were released after the model's training cutoff and still yielded bugs (p. 11).
- [A] Failure modes: the MLLM sometimes proposes non-existent functionalities, executions may not finish within the step budget or are labelled successful too early, and synthesis occasionally hallucinates widgets despite grounding (p. 9). PropGen generates only one property per functionality and lacks the differential oracles of Genie/Odin (p. 10).
- [A] A pre-existing app fault could in principle corrupt generated or refined properties; risk argued to be limited because properties come only from successful traces and refinements are human-confirmed (p. 10-11).
## 9. Limitations we identified
- [I] **Not fully automatic.** Refinement is triggered only after a human confirms a violation is a false positive (p. 4, p. 6), and bug confirmation is manual (p. 8). The cost of this human effort is not reported.
- [I] **No repeated runs with temperature 1.0.** A single run is stated for the RQ4 prior techniques (p. 8). For PropGen's RQ1-RQ3 no repetition is reported. Decoding is stochastic (p. 7), so it is unknown how stable the counts are.
- [I] **Weak naive baseline.** The naive baseline sees only the app's description, never the GUI (p. 7). Its 0/240 result shows that runtime evidence is needed, but does not test simpler runtime-grounded alternatives.
- [I] **Author-tool overlap.** Ting Su (PropGen co-author) co-authored Genie, Odin, PBFDroid, Kea and Kea2. Xiong co-authored Genie, Kea and Kea2, and Bo Ma co-authored Kea2 (refs [29], [51], [52], [63], [71], p. 12-13). So three of the four RQ4 baselines (Genie, Odin, PBFDroid, p. 7) come from the PropGen authors' own group. The scope analysis is manual (p. 8). Its validation by "the authors of Genie, Odin, and PBFDroid" (p. 8) involves the same group. The PBFDroid properties were written by the PropGen authors (p. 8). Only VisionDroid (p. 7) is independent. This is not necessarily bias in PropGen's favour, since the group knows these tools well. But the scope analysis is not independently validated.
- [I] **Annotator blinding and kappa scope not reported.** Whether the annotators were blind to which tool (PropGen or DroidAgent) produced each functionality is not reported (p. 7). The set of items over which Cohen's kappa was computed (PropGen only, or both tools) is not stated (p. 7).
- [I] **Contamination check is partial.** "Not previously reported" bugs (p. 11) do not show that the model lacks prior knowledge of app behaviour; app functionality, not bugs, is what the model may have memorised.
- [I] **Validity is judged against human understanding, not a specification** (p. 7). This is reasonable but means "valid" depends on annotators' familiarisation of at least fifteen minutes per app (p. 7).
## 10. Threats to validity
- Internal (confounds, leakage, selection): [I] Same MLLM backend for PropGen and DroidAgent (p. 7) is a fair control. Budget alignment across tools in RQ4 (p. 8) is reasonable, but tools differ in design scope, which the authors address with the scope analysis (p. 8). Possible training-data exposure of open-source apps (p. 11).
- External (generalisability of sample/context): [I] 12 open-source Android apps on emulators (p. 7); unclear transfer to iOS, web, closed-source or login/network-heavy apps.
- Construct (do metrics measure the concept?): [I] "Valid" properties are grounded and faithful but may still be imprecise (p. 7); bug counts depend on each tool's oracle type, which the authors acknowledge ("Raw bug counts alone are therefore not directly comparable", p. 8).
- Statistical conclusion (power, multiple comparisons, variance): [I] No statistical tests; 12 apps; no repeated runs reported (single run stated for RQ4 baselines, p. 8). High kappa values (0.81-0.91, p. 7) support annotation reliability.
- Reproducibility (data/code/setup reported?): [I] Good: model snapshot, decoding parameters, budgets, hardware and artifacts are reported (p. 7, p. 13). Proprietary model dependence and temperature 1.0 limit exact replication.
## 11. Future research directions
- Stated by authors [A] (p. 9-11): evaluate on a larger and broader set of apps (p. 11); interact-then-infer functionality inference, activity transition graphs for step planning, explicit completion checks, post-synthesis widget checks (p. 9); richer context and an intent-verification step for refinement (p. 9); more properties per functionality and combining PropGen with specialised oracles (p. 10).
- Suggested by us [I]: use properties mined from an original app as a behavioural oracle for an AI-reconstructed version of that app (differential fidelity testing), and measure how many original-app properties the rebuild satisfies.
## 12. Relevance to our research
- Research questions addressed (RQ ids): RQ2, RQ4, RQ5 (indirect); RQ1 only tangentially. Not RQ3.
- How it informs our work [I]: PropGen does not generate or reconstruct applications, so it gives no direct evidence on fidelity or code quality of AI-built apps. Its value is as a method. It recovers behavioural specifications from a running app without source code or written specifications. It does this through runtime observation plus light static analysis of the APK: manifest activity names (p. 4) and a string whitelist (p. 5). So it is grey-box rather than purely observational. The authors call this "exploring a black-box app" [A] (p. 11). This is exactly the kind of oracle a reverse-engineering study needs to check functional fidelity (RQ2, RQ5). Its result that an LLM without runtime observation produces 0 valid properties (p. 9) supports grounding any reconstruction or test generation in observed behaviour. Its evaluation design (independent annotators with kappa, scope analysis for oracle-dependent tools) is a good template for RQ4. Relevance is therefore medium.
