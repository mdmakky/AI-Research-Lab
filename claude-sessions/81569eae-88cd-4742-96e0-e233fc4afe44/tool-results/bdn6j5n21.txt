    18	# Is Vibe Coding Safe? Benchmarking Vulnerability of Agent-Generated Code in Real-World Tasks
    19	
    20	- Authors: Zhao, Songwen; Wang, Danqing; Zhang, Kexun; Luo, Jiaxuan; Li, Zhuo; Li, Lei
    21	- Year / venue: 2025, arXiv (preprint)
    22	- DOI: 10.48550/arxiv.2512.03262 · URL: https://arxiv.org/abs/2512.03262
    23	- Source text: `fulltext.txt` (page refs = PDF page index)

PMLR 306, 2026" (p. 1). Per the project decision in RESEARCH.md, treat as peer-reviewed (ICML 2026, PMLR 306, no DOI). Page refs refer to this arXiv v4 PDF, not PMLR pagination.

    29	## 1. Research objective
    30	[A] To test whether code produced by LLM coding agents in a vibe-coding setting (feature request in natural language, little human review) is safe to deploy, by building a benchmark (SusVibes) that scores both functional correctness and security of repository-level feature implementations (p. 1, p. 2).
    31	
    32	## 2. Research questions / hypotheses
    33	No formal RQs or hypotheses. Implicit questions from the contributions list:
    34	- [A] How functionally correct and how secure are agent-generated feature implementations in real repositories? (p. 2)
    35	- [A] Do models and agent frameworks differ by weakness (CWE) category? (p. 2, p. 6)
    36	- [A] Can simple prompting strategies (CWE self-selection, oracle CWE hint) reduce security risk without hurting functionality? (p. 2, p. 8)
    37	
    38	## 3. Methodology
    39	- Research design: benchmark construction followed by a comparative evaluation of 12 agentic settings (3 agent frameworks x 4 backbone LLMs), plus a mitigation experiment on one setting (p. 2, p. 6, p. 8). [V]
    40	- Approach / model / intervention:
    41	  - Task construction: pick a vulnerability-fix commit C0 that fixes feature F; revert to the preceding vulnerable commit C−1; take the security tests added by the fix (Tsecure) and existing functional tests (Tfunc); an LLM agent (SWE-agent) masks out the feature code in C−1 and a second SWE-agent instance writes an issue-style feature request; a third instance links each line of the canonical secure implementation to a requirement in the request, and the mask is enlarged until the request covers the secure implementation (p. 3–4, p. 15). [V]
    42	  - The task description must state the wanted functionality without implementation or security hints ("Do NOT mention security-related considerations") (p. 16). [V]
    43	  - Masks are generated on the vulnerable commit, not the fixed commit, so that no information from the fix leaks into the task input (p. 4). [A]
    44	  - Execution environments: Docker images built automatically by a SWE-agent variant with Claude 4 Sonnet; test-log parsers synthesised with OpenAI o3 (p. 17, p. 18). [V]
    45	- Baselines or comparison conditions: the 12 framework x LLM combinations compared against each other (p. 6–7); in the mitigation study, "generic" security reminder vs. self-selection vs. oracle CWE hint (p. 8). [V] There is no human-developer baseline other than the historical vulnerable human implementation that defines each task [I] (based on p. 3–5).
    46	
    47	## 4. Dataset and sample
    48	- Data source(s): vulnerability-fix commits from ReposVul and MoreFixes (over 20,000 records, last 10 years), restricted to Python ≥ 3.7 projects and commits that modify tests (p. 3, p. 14). [V]
    49	- Sample size (N) and unit: 186 tasks (feature requests) from 100 Python GitHub repositories, 10 application domains, 79 CWE types (p. 2, p. 13). [V] Mean context 236K lines / 1,186 files; mean target patch 175.0 lines / 1.8 files; mean 66.9 functional and 3.5 security tests per task (p. 5, Table 2). [V] 130 single-file, 23 two-file and 33 multi-file tasks (p. 14). [V]
    50	- Sampling / selection method: funnel ~20,000 records → ~2,000 Python → ~450 candidate commits → ~420 after task construction/verification → 200 after environment and execution validation → 186 after human test-quality verification (p. 14, Table 10). [V] Counts before the final stage are stated as approximate (p. 14). [V]
    51	- Data availability (public? link?): code and dataset at github.com/LeiLiLab/susvibes; public leaderboard (p. 1). [A] (link not checked by us)
    52	
    53	## 5. Experimental setup
    54	- Procedure, settings, hyper-parameters, tools: agent frameworks SWE-agent, OpenHands, Claude Code; backbones Claude 4 Sonnet, Kimi K2, Gemini 2.5 Pro, Gemini 3 Pro; default recommended system prompt of each framework; maximum 200 steps; agents may run their code and use runtime feedback (p. 6). [V] Main experiments include a short generic security reminder in the prompt (p. 7, p. 20). [V] Temperature, sampling settings, number of runs per task, cost and exact model versions: not reported (only pass@1 stated, p. 6).
    55	- Code availability: GitHub repository stated (p. 1). [A]
    56	- How functional correctness is tested: the human-written functional tests already in the upstream repository (Tfunc) are run on the agent's patch inside the Docker environment (p. 2, p. 4). [V] Task validity is checked by execution: the masked repo must fail both test sets, the vulnerable commit must pass functional and fail security tests, and the fixed commit must pass both (p. 5, p. 19). [V] No LLM judge is used for scoring (p. 6). [V]
    57	- How security is tested: security unit tests added by the historical fix commit (Tsecure), mean 3.5 per task (p. 5). [V] Five software-engineering experts independently rated the security tests of the 200 candidate tasks on a Pass / Conditional Pass / Fail rubric for coupling to the reference implementation: 6.5% were coupled to the ground-truth implementation; 93.5% checked the intended property (49.5% full coverage, 44.0% might miss some edge-case secure implementations; 92.1% of these partial tests were refinable). Conditional Pass and Fail tests were rewritten and cross-checked in a second round (p. 19). [V] Inter-annotator agreement: not reported.
    58	
    59	## 6. Evaluation metrics
    60	- FuncPass — pass@1 on the functional tests (p. 6, p. 7). [V] Chosen because pass@1 reflects a vibe-coding user who wants correct code at once (p. 6). [A]
    61	- SecPass — pass@1 on functional plus security tests, i.e. share of all tasks solved correctly and securely (p. 6). [V] Rationale: a solution with no meaningful feature is trivially "secure", so security only counts for functionally correct solutions (p. 6). [A]
    62	- SecPass ⊥ FuncPass — secure ratio computed on the intersection of tasks solved correctly by all compared settings, to separate security from functional skill (p. 6). [V]
    63	- Precision / recall / F1 of agent-selected CWE types vs. ground truth (self-selection setting) (p. 9, Table 6). [V]
    64	- Statistical testing (tests used, significance, effect sizes, confidence intervals): none reported. Results are single pass@1 numbers without confidence intervals or repeated runs; Table 5 uses ▲/▼ markers without a stated test (p. 8). [V]
    65	
    66	## 7. Key findings
    67	1. Best functional setting SWE-agent + Claude 4 Sonnet: FuncPass 57.0%, SecPass 11.8% (p. 7, Table 3); 79.3% of its functionally correct solutions are insecure (p. 6). [V] (11.8/57.0 = 20.7% secure, arithmetic consistent.)
    68	2. Across all 12 settings FuncPass ranges 12.9–57.0% and SecPass 3.8–12.9% (p. 7, Table 3); the authors summarise average SecPass as "only around 10%" (p. 6). [V]
    69	3. SecPass ⊥ FuncPass by backbone (averaged over frameworks): Claude 4 Sonnet 18.3%, Kimi K2 22.0%, Gemini 2.5 Pro 30.4%, Gemini 3 Pro 21.4%; by framework: SWE-agent 23.3%, OpenHands 20.1%, Claude Code 17.4% (p. 6). [V] The functionally weakest model (Gemini 2.5 Pro) is the most secure on the shared subset (p. 6–7). [V]
    70	4. Gemini 3 Pro more than doubles FuncPass over Gemini 2.5 Pro under SWE-agent, while SecPass ⊥ FuncPass improves only 1.3x (p. 6–7). [V]
    71	5. Performance falls with the number of files the reference patch touches: Claude 4 Sonnet FuncPass 66.9% (1 file) → 39.1% (2 files) → 30.3% (>2 files); SecPass 15.4% → 4.3% → 3.0% (p. 14, Table 9). [V]
    72	6. Mitigation (SWE-agent + Claude 4 Sonnet): generic 57.0 / 11.8; self-selection 50.0 / 14.5; oracle CWE hint 55.4 / 15.1 (FuncPass / SecPass) (p. 8, Table 5). [V] The authors read this as small security gains at the cost of functionality (p. 8). [A]
    73	7. In self-selection the agent picks 7.2 CWE types per task on average against 1.1 ground-truth types; precision 0.086–0.114, recall 0.561–0.667 (p. 8–9, Table 6). [V]
    74	8. Model and framework strengths differ by CWE category and application domain (p. 6–7, Figure 4, Table 4). [V] Per-domain subset sizes behind Table 4 are not reported, so these cells may rest on very few tasks [I] (based on p. 7).
    75	
    76	## 8. Limitations stated by the authors
    77	- [A] Benchmark is Python-only; test outcomes are a practical proxy for security; CWE annotations and tests may be insufficient; no claim to cover all exploit modalities (p. 24).
    78	- [A] Security tests from fix commits can be tied to the original implementation and reject secure alternatives; addressed by human verification and rewriting (p. 5, p. 19).
    79	- [A] Fix commits may contain unrelated refactoring; addressed by ReposVul filtering, a Prospector score ≥ 65 for MoreFixes, and the verification loop (p. 15).
    80	- [A] The automatic environment-building agent created operational risks (uncleaned images, over-exposed database containers), handled with command filtering (p. 18).
    81	- [A] Mitigation prompts were kept deliberately simple; prompt engineering for security was not optimised (p. 19).
    82	
    83	## 9. Limitations we identified
    84	- [I] No repeated runs, seeds or confidence intervals. With 186 tasks one task is ~0.54 pp, so many between-setting SecPass differences (e.g. 11.8 vs 12.9) are within plausible run-to-run noise. Based on the single pass@1 numbers (p. 6–7).
    85	- [I] The human verification of security tests by five experts reports no inter-annotator agreement and no disagreement-resolution rule beyond "a second round of cross-checking" (p. 19). The reliability of the security oracle cannot be judged from the paper.
    86	- [I] Task masks and descriptions were generated and verified by LLM agents; no human check of description quality (under-specification, hidden requirements) is reported (p. 4, p. 15–16). Some functional failures may reflect description gaps rather than agent skill.
    87	- [I] Possible data contamination: tasks reconstruct historical public code and fixes in popular repositories such as django, flask and numpy (p. 13); models may have seen the secure versions. The paper does not discuss contamination of its own tasks.
    88	- [I] Claude 4 Sonnet powers the environment-building agent (p. 17) and SWE-agent drives task construction (p. 4); the best-scoring setting is SWE-agent + Claude 4 Sonnet. A construction–evaluation affinity bias is possible but untested.
    89	- [I] The "generic" condition already contains a security reminder (p. 7, p. 20), so the main results are not a pure no-guidance vibe-coding condition; insecurity without any reminder could be higher.
    90	- [I] Security is checked by few tests per task (mean 3.5, p. 5) that target only the historical vulnerability; other vulnerabilities an agent introduces are not detected (no static analysis), so SecPass is an upper bound on "secure".
    91	- [I] Funding/conflicts: work partly supported by HydroX AI (an author affiliation) with compute/credits from Modal and Google (p. 9); Gemini models are evaluated. No visible bias (Gemini 2.5 Pro scores lowest functionally), noted per the appraisal checklist.
    92	
    93	## 10. Threats to validity
    94	- Internal (confounds, leakage, selection): masks built on the vulnerable commit to avoid leaking the fix (p. 4); `.git` history removed to avoid reward hacking (p. 17) [V]. Contamination of public historical code not addressed [I]. Generic security reminder present in all main runs (p. 7) [V].
    95	- External (generalisability of sample/context): Python only, 100 open-source repositories, tasks restricted to features that once had a fixed vulnerability (p. 3, p. 13, p. 24) [V]. Results describe security-sensitive feature additions to existing repositories, not whole-application generation or reconstruction from UI [I].
    96	- Construct (do metrics measure the concept?): FuncPass uses pre-existing upstream functional tests (mean 66.9 per task, p. 5), a fairly strong functional oracle [I]; SecPass covers only the historically known vulnerability through a few tests (p. 5, p. 24) [V]. Human-revised tests improve validity for alternative secure implementations (p. 19) [V].
    97	- Statistical conclusion (power, multiple comparisons, variance): no variance, CIs or tests; per-CWE and per-domain breakdowns on small subsets (p. 7) [V]; many comparisons without correction [I].
    98	- Reproducibility (data/code/setup reported?): data, code, prompts (Appendix B–C) and step limit reported (p. 1, p. 6, p. 15–20) [V]; model versions and sampling parameters not reported.
    99	
   100	## 11. Future research directions
   101	- Stated by authors [A]: broaden language and domain coverage; property-based and adversarial test synthesis; static/semantic program analysis; security-aware training rewards; tool use such as fuzzers, taint analysis and secret scanners (p. 24). Find strategies that improve security without disrupting functional task completion (p. 9).
   102	- Suggested by us [I]: apply the same "mask and re-implement" construction to whole applications or UI-observable features, so that an original implementation and its test suite serve as a fidelity oracle for reconstruction; add static analysis to catch vulnerabilities beyond the targeted CWE; report repeated runs and annotator agreement.
   103	
   104	## 12. Relevance to our research
   105	- Research questions addressed (RQ ids): RQ2 (functional correctness measured with human-written tests), RQ3 (security as a quality dimension of agent/vibe-coded code), RQ4 (test-oracle design, human verification of tests, single-run pass@1), RQ5 (functional–quality divergence; no maintainability measure).
   106	- How it informs our work [I]: SusVibes shows that passing functional tests says little about a second quality dimension (security): ~80% of functionally correct patches failed the security tests (p. 6). This is direct evidence that fidelity and code quality must be measured separately. Its task design (mask an existing implementation, describe it in natural language, ask an agent to re-implement it, test against the original's tests) is structurally a reconstruction-from-specification setup that could be adapted to behaviour-based reconstruction. It does not measure maintainability, UI behaviour or whole-application rebuilds, so relevance is medium.

    18	# DeclarUI: Bridging Design and Development with Automated Declarative UI Code Generation
    19	
    20	- Authors: Zhou, Ting; Zhao, Yanjie; Hou, Xinyi; Sun, Xiaoyu; Chen, Kai; Wang, Haoyu
    21	- Year / venue: 2025, Proceedings of the ACM on Software Engineering (published)
    22	- DOI: 10.1145/3715726 · URL: https://doi.org/10.1145/3715726
    23	- Source text: `fulltext.txt` (page refs = PDF page index)

    28	## 1. Research objective
    29	- Propose DeclarUI, an automated approach that combines computer vision (CV), MLLMs and compiler-driven iterative refinement to generate multi-page declarative mobile UI code (React Native, Flutter, ArkUI) from UI design mockups or app screenshots, improving visual fidelity, navigation completeness and code quality [A] (pp. 1–2).
    30	
    31	## 2. Research questions / hypotheses
    32	- RQ1 Effectiveness: how does DeclarUI perform vs. baselines "when operating autonomously without human intervention"? [V] (p. 6)
    33	- RQ2 Ablation: contribution of individual modules [V] (p. 6)
    34	- RQ3 User study and manual repair: how do professional developers rate DeclarUI code vs. the baseline, and how much manual effort repairs compilation failures? [V] (p. 6)
    35	
    36	## 3. Methodology
    37	- Research design: technique proposal evaluated by a controlled comparison with two raw-MLLM baselines on a curated dataset, an ablation on a subset, a within-subject developer study, and a manual-repair timing study [V] (pp. 6–11).
    38	- Approach / model / intervention: (1) Page Transition Graph (PTG) construction — Claude-3.5 infers nodes (pages) and edges (transitions with conditions/actions) from the design set as JSON; "designers or developers review the generated PTG, making necessary corrections or additions" [V] (pp. 3–4); (2) UI component extraction — Grounding DINO detection + Segment Anything segmentation + Claude-3.5 classification and functional description of each component [V] (p. 4); (3) prompt synthesis combining PTG, component analysis and the full screenshot [V] (p. 5); (4) iterative refinement — static-analysis check of implemented navigation vs. PTG (up to 3 iterations per page) and compile-error feedback (up to 3 iterations per project) [V] (pp. 5–6).
    39	- Baselines or comparison conditions: GPT-4o and Claude-3.5-Sonnet-20240620 given unprocessed design images with "meticulously designed" prompts following prior image-to-code work, in React Native only [V] (p. 7). DeclarUI is run with GPT-4o and Claude-3.5 as base models; Flutter and ArkUI are run with DeclarUI (Claude-3.5) only, with no baseline [V] (pp. 8–9). No prior UI-to-code tool is used as a baseline [I] (based on p. 7).
    40	
    41	## 4. Dataset and sample
    42	- Data source(s): Figma community mockups (selected from 194 designs with >300 followers, ≥5 pages, mobile-specific) and Google Play apps (top 10 by downloads per category, excluding paid apps and complex registration; APKs installed on an emulator and screenshots captured manually) [V] (pp. 6–7).
    43	- Sample size (N) and unit: 50 apps (25 Figma, 25 Google Play), 5 logically connected pages each = 250 pages, 10 functional categories × 5 apps [V] (pp. 6–7). Ablation: 13 apps chosen by CLIP-score distribution across categories [V] (p. 9). User study: 12 apps stratified by CLIP score (3 > 0.85, 6 in 0.8–0.85, 3 < 0.8) [V] (p. 9). RAG experiment: 20 apps (100 pages) [V] (p. 11).
    44	- Sampling / selection method: 3–5 per category per source, random selection of five when more available, "to control experimental costs while ensuring research quality and statistical significance" [A] (p. 7). Sample size limited "due to MLLMs' token cost constraints" [A] (p. 12).
    45	- Data availability (public? link?): not reported in our PDF (no repository link found).
    46	
    47	## 5. Experimental setup
    48	- Procedure, settings, hyper-parameters, tools: generated code inserted into an initial project in Android Studio (React Native, Flutter) or DevEco Studio (ArkUI) without manual intervention, built into an APK and run on the built-in emulator [V] (p. 8). Hardware: 2× RTX 3090, 64-core AMD EPYC, 512 GB RAM; custom Python scripts of 2,935 lines [V] (p. 8). UTG for evaluation obtained with DroidBot [V] (p. 7). Temperature, sampling settings and GPT-4o version: not reported. Image assets are excluded from evaluation [V] (p. 2).
    49	- Code availability: not reported in our PDF.
    50	
    51	## 6. Evaluation metrics
    52	- CLIP score — semantic visual similarity of generated vs original UI [V] (p. 7).
    53	- SSIM — layout/structural similarity [V] (p. 7).
    54	- PTG Coverage Rate PCR = |PTG edges ∩ UTG edges| / |PTG edges| × 100%, "manually calculated by human evaluators", comparing the predefined PTG with the DroidBot-explored UI Transition Graph of the built app — a navigation/functional-fidelity measure [V] (p. 7).
    55	- Compilation Success Rate (CSR) — share of apps compiling after up to three automated refinement iterations [V] (p. 7).
    56	- Average Compilation Iteration Count (ACIC) — compilation attempts per successfully compiled app (max 3) [V] (p. 7).
    57	- Average Manual Correction Time (AMCT) — human repair time per compilation-failed app [V] (p. 7).
    58	- Developer-rated code quality (user study, following Chen et al. [11]): Code Availability (proportion of generated code kept after modification to meet basic business requirements, tracked with git, mapped from 0.8 in 5% intervals to levels 1–5); Modification Time (5 points ≤5 min down to 1 point >20 min; 20-min cap per app); Readability and Maintainability (five-point Likert ratings) [V] (pp. 7, 9).
    59	- Validation against human judgement: none for CLIP/SSIM; authors acknowledge they "may not fully capture human-perceived UI similarity" and state the user study "confirmed the validity of our evaluations" [A] (p. 12). No correlation between automatic metrics and human ratings is reported.
    60	- Statistical testing (tests used, significance, effect sizes, confidence intervals): Mann-Whitney U test for user-study ratings (p from 9.23E-08 to 2.57E-13) [V] (p. 10). No tests, CIs or run-to-run variance for CLIP/SSIM/PCR/CSR comparisons; no effect sizes — not reported.
    61	
    62	## 7. Key findings
    63	1. React Native: DeclarUI (Claude-3.5) CLIP 0.88, SSIM 0.68, PCR 96.8%, CSR 98%; DeclarUI (GPT-4o) 0.87 / 0.58 / 88.6% / 88%; baselines GPT-4o 0.66 / 0.44 / 1.4% / 76% and Claude-3.5 0.65 / 0.41 / 43.3% / 74% [V] (p. 9).
    64	2. Raw MLLMs largely fail to implement multi-page navigation (GPT-4o PCR 1.4%) [V] (p. 9). Baseline compilation failures came from non-existent packages/components, special-character handling and missing imports [A] (p. 8).
    65	3. Generalisation: Flutter PCR 99.4%, CSR 92%; ArkUI PCR 95.9%, CSR 86% (DeclarUI Claude-3.5 only) [V] (p. 9). Knowledge-graph RAG for ArkUI on 20 apps: CSR 86% → 90%, AMCT 183 s → 43.5 s [V] (p. 11).
    66	4. Ablation (13 apps): removing CV extraction drops SSIM 0.72 → 0.57; removing PTG + refinement drops PCR to 23.1% and CSR to 80% [V] (pp. 9–10).
    67	5. User study (5 developers × 12 apps): DeclarUI vs Baseline (Claude-3.5) — availability 4.97 vs 4.15, modification time 4.03 vs 2.45, readability 4.62 vs 3.75, maintainability 4.55 vs 3.37, all p < 0.05 (Mann-Whitney U) [V] (p. 10). 73.3% of DeclarUI code modified within 10 min; 80% of baseline code needed >10 min [V] (p. 10).
    68	6. Manual repair: AMCT 48 s (React Native, Claude-3.5), 43.2 s (GPT-4o), 62 s (Flutter), 183 s (ArkUI) [V] (p. 11).
    69	7. Authors conclude generated code "meets industrial-grade standards" in availability, modification time, readability and maintainability [A] (pp. 1–2) — this rests on Likert ratings from five developers.

    71	## 8. Limitations stated by the authors
    72	- CLIP and SSIM may not capture human-perceived UI similarity; PCR does not reflect navigation fluidity or intuitiveness [A] (p. 12).
    73	- Results depend on prompt design; user-study participant experience may bias results [A] (p. 12).
    74	- Sample of 50 design sets may not represent all mobile UI types; limited by token cost [A] (p. 12).
    75	- Uneven framework performance; ArkUI weaker, attributed to limited MLLM knowledge; RAG implementation limited by time [A] (p. 11).
    76	- PTG construction could not be ablated alone because refinement depends on it [A] (p. 9).

    78	## 9. Limitations we identified
    79	- [I] Human in the loop vs "autonomous" claim: the PTG is reviewed and corrected by designers/developers (p. 4), while RQ1 is framed as operating "without human intervention" (p. 6). How often and how much the PTG was corrected is not reported.
    80	- [I] PCR is partly circular: DeclarUI receives the PTG as input and is checked against it during refinement, then scored against the same PTG (pp. 5–7); baselines never see the PTG. PCR also counts only edges, not correct behaviour on each screen, and is computed manually without reported agreement (p. 7).
    81	- [I] Ablation numbers are internally implausible: on 13 apps, CSR values of 98.0% and 80.0% (p. 10) cannot arise (possible values are k/13, e.g. 76.9%, 84.6%, 92.3%), and the "Full" PCR/CSR equal the 50-app values (pp. 9–10). The Table 2 "Full" row may mix 50-app and 13-app results.
    82	- [I] User-study statistics treat 60 ratings per condition (5 developers × 12 apps) as independent; the tiny p-values (down to 2.57E-13, p. 10) overstate certainty (pseudo-replication). Blinding of participants to condition is not reported. Five participants is a small sample.
    83	- [I] Code quality and maintainability are measured only subjectively (Likert) and by modification time; no static analysis, complexity, duplication or code-smell metrics.
    84	- [I] Minor inconsistencies: Baseline Claude PCR 43.4% (p. 8) vs 43.3% (p. 9); ACIC defined as "number of compilation attempts" (max 3) yet reported as 0.22 (pp. 7, 9), implying it counts only repair iterations.
    85	- [I] Single run per configuration; no variance across runs, though MLLM outputs are stochastic (sampling settings not reported).
    86	- [I] Our PDF is arXiv v1 (18 Sep 2024); the FSE 2025 version may report different numbers.
    87	
    88	## 10. Threats to validity
    89	- Internal (confounds, leakage, selection): human PTG correction; PCR scored against the method's own input; ablation subset chosen by CLIP score; possible training-data exposure of popular Google Play apps' UIs not discussed [I].
    90	- External (generalisability of sample/context): 50 apps × 5 pages; only UI and navigation (no back-end, data, business logic); image assets ignored (p. 2) [I].
    91	- Construct (do metrics measure the concept?): CLIP/SSIM unvalidated proxies for visual fidelity (p. 12); PCR measures presence of transitions, not their correctness of state; compilation success is a weak proxy for functional correctness; maintainability is self-reported [I].
    92	- Statistical conclusion (power, multiple comparisons, variance): Mann-Whitney on non-independent ratings; four tests without correction (not critical given p values); no CIs or effect sizes [I].
    93	- Reproducibility (data/code/setup reported?): no code or data link in our PDF; model sampling settings missing; tools (Grounding DINO, SAM, DroidBot) named (pp. 4, 7) [I].
    94	
    95	## 11. Future research directions
    96	- Stated by authors [A]: richer knowledge-graph RAG for less common frameworks such as ArkUI, dynamic KG updates, extension to other frameworks (p. 11); larger and more diverse UI samples (p. 12).
    97	- Suggested by us [I]: report PTG correction effort; measure navigation and in-screen behaviour with automated GUI tests rather than manual edge counts; add objective maintainability metrics (static analysis, code smells) alongside developer ratings; use mixed-effects models for user-study ratings.

   100	- Research questions addressed (RQ ids): RQ1, RQ2, RQ3, RQ4, RQ5.

It shows that structuring the observable behaviour (page transition graph) and compiler feedback matter, but its maintainability evidence is subjective and its fidelity metrics have design weaknesses.

    19	
    20	- Authors: Zhu, Yuecai; Tsantalis, Nikolaos; Rigby, Peter C.
    21	- Year / venue: 2026, Proceedings of the 41st IEEE/ACM International Conference on Automated Software Engineering (published)
    22	- DOI: 10.1145/3832783.3834413 · URL: https://doi.org/10.1145/3832783.3834413
    23	- Source text: `fulltext.txt` (page refs = PDF page index). Our PDF is arXiv 2605.02741v1 (4 May 2026), titled "AI-Generated Smells: An Analysis of Code and Architecture in LLM- and Agent-Driven Development" (p. 1). The title differs from metadata.json, but authors and abstract match, so we treat it as the preprint of the ASE paper. The published version may differ.

    25	Labels: **[V]** verified in the paper's own data/tables/results · **[A]** author claim · **[I]** our interpretation.

    28	## 1. Research objective
    29	Audit the code smells (technical debt) in code produced by single LLMs and by a multi-agent system, and analyse how moving from single-file algorithmic tasks to multi-file applications changes the density and kinds of smells [A] (p. 1).
    30	
    31	## 2. Research questions / hypotheses
    32	- RQ1: To what extent do code-generating agents introduce code smells in standard coding tasks? RQ2: What taxonomy of code smells do code-generating agents most often show? RQ3: How does the complexity of the target architecture affect smell prevalence, and can prompt strategies mitigate it? [V] (p. 1). These are the paper's own RQs, not our project RQs.
    33	- No formal hypotheses. Note: the results section maps RQ2 and RQ3 differently from the introduction (RQ2 = complex-system smells, RQ3 = drivers of decay) (p. 6, p. 8, p. 9).
    34	
    35	## 3. Methodology
    36	- Research design: exploratory, two-experiment static-analysis study [V] (p. 3). Experiment I: five LLMs generate Python solutions for algorithmic problems under zero-shot and few-shot prompts; smells compared with human solutions [V] (p. 3, p. 4). Experiment II: MetaGPT multi-agent framework (Qwen-Coder 480B backend) generates full Python applications for 5 scenarios, each at 4 increasingly detailed requirement stages; smells related to size, scenario and stage [V] (p. 5, p. 8).
    37	- Approach / model / intervention: Exp I models: Gemini 2.5 Pro, Llama 3.3 70B, deepseek-coder-v2 16B, qwen3-coder 30B and 480B [V] (p. 3). Zero-shot prompt replicates Santa et al.; few-shot prompt adds role, output rules and a boilerplate `solution` method [V] (p. 4). Exp II prompts require OOP and modular files because preliminary trials produced monolithic "God Class" scripts [V] (p. 5). Scenarios: Crossy Road game, Flashcard app, Pacman, Personal Finance (CLI + web dashboard), Online Bookstore backend [V] (p. 5).
    38	- Baselines or comparison conditions: Exp I — one randomly sampled verified human Python submission per problem; zero-shot as prompt baseline [V] (p. 4). Exp II — no human or alternative-agent baseline; comparison only across scenarios and stages [V] (p. 5, p. 9).
    39	
    40	## 4. Dataset and sample
    41	- Data source(s): CodeContests dataset (AlphaCode) for Exp I; author-written product requirements for Exp II [V] (p. 1, p. 3, p. 5).
    42	- Sample size (N) and unit: Exp I — 90 problems, 5 LLMs × 2 prompt conditions, plus 90 human solutions; unit = one generated .py file per problem [V] (p. 4). Exp II — 5 scenarios × 4 stages [V] (p. 5); the resulting number of repositories (20 implied) and the number of generation runs per prompt are not reported explicitly.
    43	- Sampling / selection method: 90 problems "randomly sampled" (p. 4), later described as a "stratified sample" balanced across Easy/Medium/Hard (p. 9) [V]. Model selection to span dense vs MoE, proprietary vs open, and parameter scale [V] (p. 3).
    44	- Data availability (public? link?): replication package at https://doi.org/10.5281/zenodo.19245562 with sampling scripts, Exp I scripts, Exp II prompts and analysis scripts [V] (p. 10). Generated repositories announced as a benchmark dataset "released alongside this paper" [A] (p. 5).
    45	
    46	## 5. Experimental setup
    47	- Procedure, settings, hyper-parameters, tools: each solution saved as a .py file and analysed with PyExamine; counts per smell type aggregated [V] (p. 4). Exp II repositories also measured with cloc (TLoC), total number of files (ToF) and Agent Action Count (AAC) [V] (p. 5). No iterative "validate and correct" loop in Exp I (budget) [V] (p. 9). Temperature, sampling settings, model quantisation/hosting, PyExamine version and thresholds: not reported. Results for AAC: not reported. The factor "ALpF" in Table 3 is not defined in the text (p. 9).
    48	- Code availability: scripts in the Zenodo package (p. 10).
    49	
    50	## 6. Evaluation metrics
    51	- Metric — what it measures — why chosen:
    52	  - PyExamine smell counts at three levels: code-level (e.g. Long Method, Long File, High Cyclomatic Complexity), structural (class/object level, e.g. Too Many Branches, High Response for a Class, Temporal Field) and architectural (e.g. Unstable Dependency, Scattered Functionality, Potential Improper API Usage) [V] (p. 3, p. 7, p. 8). Chosen as a comprehensive, "un-opinionated", static and repeatable Python smell detector, and to separate structural smells from superficial linting issues counted by SonarQube [A] (p. 2, p. 4).
    53	  - TLoC and ToF as project size/complexity [V] (p. 5).
    54	  - Feature Envy and Potential Shotgun Surgery were excluded from Exp I interpretation after a manual audit found systematic false positives; Long Method and Long File were judged high precision [V] (p. 6). The size of this audit and precision values are not reported.
    55	- Statistical testing (tests used, significance, effect sizes, confidence intervals): Exp I — raw counts only, no statistical test, no normalisation by code size [V] (p. 7). Exp II — Spearman's ρ (continuous factors) and Kruskal-Wallis H (Scenario, Stage), p < 0.05; no multiple-comparison correction, no confidence intervals [V] (p. 8, p. 9). Functional correctness of generated code: not measured or reported.
    56	
    57	## 7. Key findings
    58	1. Exp I: Long Method counts were higher for larger LLMs than for humans — zero-shot Qwen Coder 480B 11, Qwen Coder 30B 7, Gemini 2.5 Pro 5, deepseek 2, Llama 3 70B 0, human 1 (across 90 problems) — [V] (p. 7, Table 1).
    59	2. Exp I: Temporal Field appeared only in human solutions (4 instances), never in LLM output — [V] (p. 6, p. 7).
    60	3. Exp I: few-shot prompting did not reduce Long Method (Qwen 480B 11 → 13; Gemini 5 → 8) — [V] (p. 6, p. 7, Table 2).
    61	4. Exp I interpretation: a "Reasoning-Complexity Trade-off" — more capable models produce more procedural bloat; larger models' failed solutions had more Long Methods — [A] (p. 6, p. 7). The failed/passing split is not shown in any table.
    62	5. Exp II: most prevalent smells were Too Many Branches, High Response for a Class, Potential Improper API Usage, Scattered Functionality and Unstable Dependency, across all stages and scenarios — [V] (p. 7, p. 8, Figure 1).
    63	6. Exp II: TLoC correlated with code-level (ρ = 0.53, p = 0.017), structural (ρ = 0.59, p = 0.007) and architectural smell counts (ρ = 0.94, p < 0.001); ToF with architectural smells ρ = 0.72 (p < 0.001) — [V] (p. 8, p. 9, Table 3).
    64	7. Exp II: scenario affected architectural smells (H = 9.86, p = 0.043); requirement stage had no significant effect on any smell level (p > 0.8) — [V] (p. 8, p. 9, Table 3).
    65	8. Authors' framing: a "Volume-Quality Inverse Law" and a "Modular Mirage" (files are separated but behaviour is fragmented); agents act like "junior developers" lacking architectural foresight — [A] (p. 8, p. 9).
    66	9. Abstract/introduction claim that functional correctness is decoupled from quality ("running code is just as likely to be structurally flawed as failed code") — [A] (p. 1, p. 2). No supporting data is reported in the results.

    68	## 8. Limitations stated by the authors
    69	- [A] No iterative debug/repair loop in Exp I; first-pass code only (p. 9, p. 10).
    70	- [A] Exp I uses 90 problems, not the full dataset; may miss long-tail problem types; authors plan to scale up "to verify the statistical significance of these findings" (p. 9).
    71	- [A] Exp II uses only MetaGPT; findings may be specific to its SOP-based paradigm; other tools (SpecKit, Cursor Composer) may differ (p. 9, p. 10).
    72	- [A] Small sample, so non-parametric tests were used (p. 8).

    74	## 9. Limitations we identified
    75	- [I] Central claims rest on very small counts. Exp I differences are a handful of smell instances over 90 files (e.g. 11 vs 1 Long Method), with no test, no per-LoC normalisation and no variance across runs (p. 7). Treat as descriptive.
    76	- [I] The "Volume-Quality Inverse Law" correlates smell *counts* with code size (p. 8, p. 9). More code mechanically yields more smell instances, so ρ = 0.94 does not show that larger code is worse per line. The paper says size metrics allow density normalisation (p. 5) but reports no density analysis.
    77	- [I] The claims that functional correctness does not mitigate decay (p. 1, p. 2) are not backed by any reported correctness measure; Exp II apps were not executed or tested at all as far as the paper reports.
    78	- [I] The "longitudinal"/"architectural rot" framing (p. 2, p. 5) is questionable: the four stage prompts are self-contained (p. 5), and the paper does not say that each stage evolves the previous codebase. It may be four independent generations.
    79	- [I] Exp II has n ≈ 20, one LLM backend, one framework, no human or single-agent baseline, and 15 significance tests without correction (p. 9); the "near-perfect predictor" wording overstates a single small sample.
    80	- [I] Internal inconsistencies: RQ numbering differs between introduction and results; "random" vs "stratified" sampling; "ALpF" undefined; smell abbreviations in Exp I (EC, HFI) are not expanded (p. 1, p. 4, p. 6, p. 7, p. 9).
    81	- [I] PyExamine validity: two smell types were dropped as false positives after an unquantified audit (p. 6); no precision figures for the architectural smells that drive the main conclusion.
    82	- [I] Model inference settings (temperature, quantisation; model names suggest local deployment) are not reported, which limits reproducibility.
    83	
    84	## 10. Threats to validity
    85	- Internal (confounds, leakage, selection): size confounds smell counts (Exp II); CodeContests problems may be in model training data (not discussed); prompts for Exp II were engineered to force modularity after preliminary trials (p. 5).
    86	- External (generalisability of sample/context): Python only; competitive programming tasks (Exp I); five small app scenarios with a single agent framework and one LLM (Exp II) (p. 5, p. 9, p. 10).
    87	- Construct (do metrics measure the concept?): maintainability is equated with PyExamine smell counts; no human assessment of maintainability; FE and PSS judged unreliable (p. 6).
    88	- Statistical conclusion (power, multiple comparisons, variance): no tests in Exp I; small n and no correction in Exp II; no repeated generations, so model randomness is not estimated (p. 7, p. 8, p. 9).
    89	- Reproducibility (data/code/setup reported?): Zenodo package with scripts and prompts (p. 10); generation hyper-parameters not reported. Authors note Gemini 3.1 was used for editorial purposes (p. 10).

    91	## 11. Future research directions
    92	- Stated by authors [A]: architecturally-aware agents (explicit "Architect" role, constitutional design principles); refactoring agents that detect and fix AI-specific smells such as the "Modular Mirage"; longitudinal benchmarks of continuous software evolution; metrics for semantic cohesion (p. 10); extend the benchmark to other agent platforms (p. 9); scale Exp I to the full dataset (p. 9).
    93	- Suggested by us [I]: repeat Exp II with smell density per KLoC, multiple runs per prompt, a human-written reference implementation of the same apps, and functional tests, so that "correctness vs quality" is actually measured.

    96	- Research questions addressed (RQ ids): RQ3 (main), RQ1, RQ4.
    97	- How it informs our work [I]: Exp II is close to our setting: complete small applications (games, GUI tools, web backend) generated by an agent from natural-language requirements.
